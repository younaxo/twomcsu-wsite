# TwoMC — MASTER ROADMAP 2026

**Версия:** 3.0 · **Дата:** 2026-11-15 · **Статус:** УТВЕРЖДЁН ВЛАДЕЛЬЦЕМ
**Источник:** задание владельца «TWOMC — MASTER ROADMAP & DEVELOPMENT KICKOFF» v3.0.
**Действует вместо очерёдности** `docs/product-audit/ROADMAP.md` (волны 1–8) и `docs/implementation/ROADMAP.md` (PHASE 00–37). Номера волн и срезов сохраняются для трассировки требований (раздел 4). Исторические ADR не переписываются.

## 1. Решение владельца

1. Крупные повторные аудиты вместо разработки больше не проводятся — идёт фактическое завершение проекта.
2. Сначала пользовательские системы, обращения, наказания, Minecraft-интеграции, инвентари и донат-привилегии.
3. Реальные платежи и платёжные провайдеры — ближе к концу (этап 14).
4. Производственная безопасность обязательна, даже если оплата отложена.
5. Git-коммиты, push, Pull Requests и CI — ответственность Claude Code (Chief), а не владельца; доступ — ограниченный, без постоянного admin-токена.
6. После стабилизации основных систем API выносится в отдельный репозиторий (этап 16).
7. Активные проекты — только два сайта: `younaxo/twomcsu-website` (старый, референс) и `younaxo/twomcsu-wsite` (новый, основной). Перечень активных проектов по историческим репозиториям не расширяется.
8. Новая очерёдность имеет приоритет над волнами 1–8, если не противоречит требованиям безопасности.

## 3. Содержание этапов

### Часть I. Подготовка

**Этап 00 — GitHub, агенты и техническая основа (P0).**

- GitHub: интеграция PR #139; Phase 02 и план Phase 03 — отдельными PR (#140, #141, стеком); защита `main` (rulesets: PR, обязательные CI, CodeQL и gitleaks, запрет force-push и удаления веток); secret scanning; самостоятельные push и PR Chief через машинный аккаунт или GitHub App с минимальными правами; без постоянного admin-доступа агента и без Bypass; модельная политика (Chief — Opus, директора и разработчики — Sonnet, простая документация — Haiku); безопасная архивация 13 legacy-агентов.
- Технические исправления (план `docs/phase-03/PHASE-03-SECURITY-STABILITY-PLAN.md`): P3-04 ключ Turnstile в Docker-сборке; P3-02 доверенные прокси и корректный IP; обязательная административная 2FA (P3-A1); безопасные production-cookie (P3-A2); закрытие или жёсткая блокировка небезопасного платёжного webhook до полноценной реализации (P3-01 — устранение уязвимости, не запуск платежей); устранение наиболее критичных уязвимостей зависимостей без массового обновления (P3-06a); защита от повторного выполнения фоновых задач; проверка server-side RBAC; начальная стратегия бэкапов и восстановления (P3-03).
- Новые реальные платежи не подключаются.

### Часть II. Обращения и модерация

**Этап 01 — Полноценная система обращений (P0, первый пользовательский этап).** Референс — старый `/report`, `/moderation/reports`, API `/reports/*`.

- Игрок: `/support` со списком своих обращений; создание; типы — жалоба на игрока, жалоба на администратора, обжалование наказания (привязка к конкретному наказанию), техническая проблема, проблема с донатом, другое; уникальный номер; статусы, история и timeline; отправка и редактирование сообщений; вложения и доказательства через RU-S3 (ссылки, изображения, файлы допустимых форматов); уведомления о сообщениях и статусе.
- Персонал: полная очередь; фильтры по статусу, типу, приоритету, ответственному; назначение и передача; внутренние заметки, невидимые игроку; статус и вердикт; архив и поиск; ограничение злоупотреблений; история действий персонала; RBAC.
- Реальное API, без моков. Модель приоритетов совместима с будущими Donation Entitlements (приоритетная поддержка Heracles, Poseidon, Zeus).

**Этап 02 — Наказания в реальном времени (P0).**

- Сайт: публичная страница наказаний (`/bans` или согласованный маршрут), поиск по нику, тип (ban, mute, warn и др.), причина, дата выдачи, срок, окончание, активность, выдавший — по политике публичности; история наказаний пользователя; «Мои наказания»; обжалование из карточки наказания; административное управление в пределах полномочий.
- Minecraft: проверить фактический плагин наказаний; интеграционный адаптер (не предполагать LiteBans); передача выдачи, снятия, изменения срока и причины; идемпотентность и порядок событий; восстановление после разрыва; первоначальная синхронизация; WebSocket-обновления страниц; периодическая reconciliation.
- Результат: выданное или снятое на сервере наказание обновляется на сайте без перезагрузки страницы.

### Часть III. Minecraft и инвентарь

**Этап 03 — TwoMC Minecraft Bridge (P0).** Проверить версии серверов, прокси, API и плагинов. Плагин или адаптер с контрактом к NestJS API: `/site-connect` и привязка UUID; подпись и защита от повторов; привязка и отвязка; статистика игрока; онлайн и статус сервера; события наказаний; состояние инвентаря и Ender Chest; задания на выдачу игровых товаров; повторы и идемпотентность; восстановление после отключения; версии контрактов; audit и наблюдаемость. Плагин не блокирует игровой поток долгими HTTP-запросами; доступ сайта к игровым данным — только после серверной проверки прав.

**Этап 04 — Полноценный игровой инвентарь (P0).** Два разных инвентаря:

1. Minecraft Inventory — просмотр своего инвентаря, броня и вторая рука, предметы с количеством, зачарованиями и метаданными, Ender Chest, время обновления, offline-состояние, публичный и приватный режим, чужой инвентарь только при праве (с защитой от прямых API-запросов), изображения предметов включая ItemsAdder, оптимизация снимков.
2. Site Cosmetics Inventory — каталог украшений, выдача и отзыв, история, экипировка, предпросмотр на аватаре, витрина профиля, админка, совместимость с Donation Entitlements.

Права на игровой инвентарь: Apollo+ — просмотр по правилам; Ares+ — Ender Chest; Poseidon+ — дополнительная приватность; Zeus — максимум по требованиям. Проверка на backend, не только в UI.

### Часть IV. Донат-привилегии

**Этап 05 — Donation Tier и Entitlements (P0).** Источник — `docs/donations/REQUIREMENTS.md`. Отдельная система, не равная staff RBAC и Level System. Порядок: Dionysus -> Hermes -> Heracles -> Apollo -> Ares -> Poseidon -> Zeus. Старшая наследует младшие; одно центральное определение capabilities; сроки действия; назначение и отзыв сотрудниками с правами; автоматическая потеря возможностей после истечения; без административных прав; числовые лимиты — override, не сумма; проверка на сервере; независимый audit; unit и e2e на всю цепочку наследования. До покупок — тестовое административное назначение в безопасной локальной среде.

**Этап 06 — Все возможности донатов (P0–P1).** Все утверждённые возможности из `docs/donations/REQUIREMENTS.md`:

- Dionysus — оформление профиля, баннеры, скрытие соцсетей, дополнительная приватность, статус и badge.
- Hermes — шрифты ника, закреплённые комментарии, управление заявками в друзья, расширенные настройки профиля и общения.
- Heracles — закрытие ЛС и комментариев, дополнительная приватность, приоритетная поддержка, связанные лимиты.
- Apollo — цвета и шрифты ника, закрытие профиля, приватность статистики, просмотр игрового инвентаря по правилам.
- Ares — Ender Chest, кастомный адрес профиля, скрытие привилегии, скидка 5%, дополнительные возможности событий и переводов рубинов.
- Poseidon — карта, приватность инвентаря и Ender Chest, скидка 7%, расширенное оформление, события раз в сутки, установленные лимиты переводов.
- Zeus — карта с игроками, скрытие своего местоположения, максимальное оформление, скидка 10%, эксклюзивные возможности, до трёх событий в сутки, увеличенные лимиты переводов.
- Minecraft-команды (CMI): сопоставить семь уровней с ранее утверждённой матрицей; не выдумывать команды, права и лимиты — проверить ТЗ, уточнить недостающее, согласовать фактическую матрицу с плагином.
- Результат: привилегии действуют на сайте и в игре; администратор назначает, игрок видит доступное, backend запрещает недоступное. Реальная покупка не включается.

### Часть V. Остальная функциональность

**Этап 07 — Профили и социальные возможности.** Профиль и настройки, приватность, друзья и блокировки, ЛС и группы, комментарии и реакции, закрепление комментариев, уведомления, поиск игроков, упоминания, достижения и витрины, внешние аккаунты, оформление профиля, мобильная навигация. Сверка со старым сайтом по современным требованиям.

**Этап 08 — Полная административная панель.** Пользователи, роли и RBAC, наказания, очереди обращений, модерация комментариев и профилей, медиа-заявки, украшения, донаты, игровые серверы, уведомления и массовые рассылки, журнал аудита, статистика, настройки сайта, контент, недостающие интерфейсы backend-функций. Отдельно — конструктор форм (срез 7.4).

**Этап 09 — Новости, формы, события и контент.** Редактор новостей, категории, теги, закрепление; формы и конструктор, черновики, приглашения, статистика ответов; события и участие; голосования; правила, документация, FAQ; Wiki — при подтверждённой необходимости; управление публикациями; загрузки и вложения; серверные проверки прав.

**Этап 10 — Игровая статистика, рейтинги и карта.** Статистика Minecraft (убийства, смерти, игровое время и др.), история онлайна, карточки и страницы серверов с графиками, рейтинги, достижения, корректное отсутствие данных, карта сервера при наличии источника, игроки на карте по правам, приватность местоположения.

**Этап 11 — Уровни, бонусы и геймификация.** Источник — `docs/levels/REQUIREMENTS.md`: уровни 1–70, финальный badge, без Level 71+, официальные ассеты, XP и прогресс на backend, достижения, ежедневные бонусы, серии дней, рефералы, история начислений, админ-инструменты, совместимость с Minecraft Bridge. **До реализации** — зафиксировать вариант перехода 70 -> финальный badge (ADR).

**Этап 12 — Мини-игры.** Апгрейдер, рулетка, краш, внутренний кошелёк, журнал транзакций, проверяемая честность, ограничения использования, история ставок, WebSocket, админка и аудит. До включения для игроков — юридическая и продуктовая проверка. Без обмена на реальные деньги, вывода средств и связи с реальными платежами без отдельного правового решения; донаты не меняют вероятность выигрыша.

### Часть VI. Магазин и платежи

**Этап 13 — Магазин без реальной оплаты** (после основных пользовательских, игровых и донат-систем). Карточки товаров, категории, поиск и фильтры, корзина, промокоды, наборы, подарки, wishlist, валюта отображения, админка магазина, заказы и история, статусы выдачи, выдача привилегий, украшений и игровых товаров, Delivery Queue, идемпотентность, отзыв и повторная выдача, тестовые сценарии без списания денег. Связь с Minecraft и Donation Entitlements готова до запуска продаж.

**Этап 14 — Реальная платёжная система** (только после этапа 13 и отдельного согласования владельца). Выбор провайдера, российские карты и СБП, иностранные платежи в допустимых юрисдикциях, договорные условия, оферта, возвраты, чеки, защита webhook, проверка суммы и валюты, идемпотентность, защита от двойной выдачи, история операций, мониторинг ошибок, тестовая и боевая среды. До этого этапа настоящая оплата отключена.

### Часть VII. Запуск и архитектура

**Этап 15 — Production Infrastructure.** Целевая схема: RU-01 (Next.js, NestJS, Redis), RU-DB-01 (PostgreSQL), RU-S3 (файлы и бэкапы), EU-01 (только разрешённые публичные ресурсы). Бюджет около 5 000 ₽/месяц без Minecraft-серверов. Требования: правомерная обработка ПДн граждан РФ, проверка трансграничной передачи, доступность из РФ и Украины, TLS, firewall, приватные соединения, бэкапы и тестовое восстановление, мониторинг, защита от DDoS, безопасный CI/CD, секреты вне репозитория, проверки миграций, smoke и нагрузочные тесты. Развёртывание — только с разрешения владельца.

**Этап 16 — Выделение API в отдельный репозиторий** (после основной разработки и стабилизации). Предварительное имя `twomcsu-api` (утверждает владелец). Перед переносом: shared-контракты, OpenAPI и версии, раздельный CI, проверка миграций Prisma, публикация общих типов, границы ответственности, WebSocket и авторизация, совместимость Minecraft Bridge, поэтапный перенос без потери истории и данных, возможность отката. Сейчас не переносить и репозиторий не создавать.

## 5. Правила исполнения

### Старый сайт — только референс

Для каждой функции сопоставлять: что было в старом UI; какие API существовали; что реально работало; что было заглушкой; что реализовано в новом проекте; какие сценарии потеряны; что реализовать современным способом. Не переносить glassmorphism, устаревшие роли, старые CAPTCHA и устаревшую авторизацию. ### Git и выполнение

Для каждой задачи: отдельная ветка от `main` -> разработка правильными агентами -> независимая проверка -> тесты -> небольшие коммиты на русском -> push через разрешённые средства -> Pull Request -> GitHub Actions -> исправления -> результат владельцу.

- Owner-admin-токен не используется для автономной работы. Пока ограниченный доступ (машинный аккаунт или GitHub App) не подключён — Chief готовит его и сообщает владельцу точный объём однократного подключения; ручной push владельцем не становится постоянным процессом.
- Не удалять feature-ветки, не делать force push, не выполнять merge в `main` и deploy без установленных разрешений и успешных проверок; без Bypass.
- Ветки от `main` готовятся в отдельных git worktree, чтобы не трогать незакоммиченную работу владельца в основном каталоге.

### Definition of Done

Функция завершена, только если: backend реализован (если нужен); frontend работает; права и приватность работают; данные реальные; проверены пустые, ошибочные и загрузочные состояния; релевантные тесты пройдены; проверены адаптивность и доступность; нет новых подтверждённых критических уязвимостей; документы обновлены; CI успешен; PR готов или слит по политике; есть итоговый отчёт.

### Ограничения, которые остаются в силе

- Реальные платежи — только этап 14 и отдельное согласование.
- Level System — до реализации ADR о переходе 70 -> финальный badge.
- Мини-игры — после юридической проверки, без вывода средств и связи с реальными деньгами.
- Миграции БД применяются только по разрешённому процессу (CI на одноразовой БД; production — этап 15).
- Перенос API и новые репозитории — только этап 16.
