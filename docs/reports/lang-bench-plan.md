# План бенчмарка lang-bench (B1) и требования к раннеру VDS

Статус: ГОТОВО К ЗАПУСКУ, не запускалось. Дата: 2026-11-23. Источники: промпт 19 (задача 2), промпт 22 (фаза B), `docs/architecture/POLYGLOT-ANALYSIS.md` (разделы «Правило решения по приросту», «B1 — подробный критерий», «Требования безопасности»). Код: `experiments/lang-bench/` (см. README там).

## 1. Что умеет раннер сейчас

Раннер описан в `docs/runbooks/vds-runner.md`, скрипты `infrastructure/vds-runner/` (на момент плана — в ветке `feature/vds-runner-cdn`, в `main` не слит; в ветке `docs/polyglot-analysis` каталога нет). Поддерживаются только задания `unit`, `api-e2e`, `web-build`, `docker-build` (список зашит в `run-remote.sh` и в `server/remote/enqueue.sh`). Задания бенчмарка нет, тайм-аут задания по умолчанию 2700 с (`RUNNER_JOB_TIMEOUT_SEC`), в `done/<id>/` сохраняются только `result.env`, `summary.txt`, `job.log`.

Решение по заданию: раннер в этой ветке НЕ расширялся (вне области записи и вне поддерживаемых заданий). Ниже — спецификация нужного задания `bench`; её реализует владелец раннера отдельным PR после слияния `feature/vds-runner-cdn`.

## 2. Нужное задание `bench`

| Параметр | Значение |
|---|---|
| Вход | снимок кода (`--ref` или `--worktree`), нужен каталог `experiments/lang-bench/`; параметры окружения: `OHA_IMAGE` (закреплённый тег), `PROFILE`, `DB_LATENCY_MS`, `DATASET_FILE`, `RULES` |
| Образы вариантов | `langbench-ts-current`, `langbench-ts-batch` (node:24-alpine), `langbench-rust` (rust:1-alpine -> scratch), `langbench-java` (maven:3.9-eclipse-temurin-21 -> eclipse-temurin:21-jre-alpine); сборка `docker build -f impl/<имя>/Dockerfile experiments/lang-bench` |
| Нагрузчик | oha (`OHA_IMAGE`, тег закрепить заранее), `--network host`, ядра нагрузчика отдельно от серверных |
| Лимиты варианта | одинаковые: `--cpus 2 --cpuset-cpus 0-1 --memory 512m --memory-swap 512m --pids-limit 512`; Java дополнительно `-Xms256m -Xmx256m` |
| Ядра нагрузчика | `--cpuset-cpus 2-3` (VDS 6 vCPU: ядра 4–5 остаются стенду) |
| Порядок | сначала эквивалентность всех четырёх (остановка при расхождении), затем по очереди ts-current, ts-batch, rust, java: холодный старт, прогрев 60 с при 50 соединениях, затем 1 / 50 / 500 соединений x 3 повтора x 60 с, пауза 5 с между повторами |
| Запуск | `experiments/lang-bench/bench/run-bench.sh` на хосте (как `docker-build`; сам запускает docker) с `nice -n 15 ionice -c3`; `BENCH_LABEL=twomc-runner-job=<id>`, чтобы контейнеры чистились штатной очисткой |
| Длительность | прогрев и замеры около 11 минут на вариант, 4 варианта около 45 минут + сборка (Rust и Maven ориентировочно 10–20 минут) + эквивалентность: ориентир 70–80 минут. Нужен `RUNNER_JOB_TIMEOUT_SEC` не менее 6000 для задания `bench` |
| Условие запуска | стенд не под нагрузкой (проверка нагрузки перед стартом; окно согласуется владельцем); один SSH-сеанс, блокировка `with-vds-lock.sh` |
| Артефакты (в `done/<id>/`, забирать в `--out`) | `summary.md`, `summary.json`, `meta.json`, `equivalence.log`, `<вариант>-static.json` (холодный старт, размер образа), `<вариант>-c<N>-r<K>.json` (вывод oha), `*.stats.csv` (docker stats раз в секунду), `build-<вариант>.json`, `job.log`. Потребуется расширить копирование артефактов (сейчас копируются три файла) |
| Сеть | исходящий доступ для `docker build`/pull (crates.io, Maven Central, Docker Hub/GHCR); входящих портов нет (только `127.0.0.1`) |
| Секреты | не используются; на раннер не передаются; ключи и `.env*` не монтируются |
| Очистка | образы `langbench-*` и `results/` удаляются очисткой раннера (старше 3 суток) |

Изменения раннера (для владельца раннера): (1) добавить `bench` в регулярные выражения `run-remote.sh` и `enqueue.sh`; (2) `server/ops/jobs/bench.sh` — вызов `run-bench.sh` с переменными; (3) повышенный тайм-аут для `bench`; (4) копирование каталога результатов в `done/<id>/`. `.github/workflows` не затрагивается.

## 3. Прогоны (после готовности задания)

1. Чистая логика: `DB_LATENCY_MS=0`, `PROFILE=medium`, затем `small` и `large`. Базовая линия — `ts-current`.
2. Модель обращений к БД: `DB_LATENCY_MS=2` (допущение: сетевая задержка до БД на VDS около 1–3 мс); показывает вклад N+1 (в `ts-current` задержка умножается на число товарных позиций, в остальных — одно обращение).
3. Большой набор данных: `RULES=5000`, `DATASET_FILE=generated/dataset-large.json` (одинаков у всех).
4. Сквозной замер с реальной БД (одинаковый пул соединений и одинаковый объём данных у всех вариантов, одноразовая копия БД) — отдельный этап, НЕ входит в текущие прототипы (нужны реализации с драйвером PostgreSQL и общий пул); решается после результатов шагов 1–3 и только при выигрыше в серой зоне и выше.

## 4. Метрики и отчёт

RPS, p50/p95/p99, доля ошибок, CPU (среднее по `docker stats`, 200 % = два ядра), пик RSS, холодный старт (до первого 200 на расчёте), размер образа (измеренный; оценки в анализе помечены как оценка), время сборки. Медиана по трём повторам. Java — отдельно прогрев JIT (>= 60 с) и фиксированный heap. Отчёт — `docs/reports/lang-bench-report.md`: таблицы, выводы по «Правилу решения по приросту» (менее 30 % / 30 %–2x / 2x и более — относительно `ts-batch`, не относительно `ts-current`), оговорки: источник данных в памяти, сеть loopback, `node:http` вместо NestJS, дополнительно размеры оценок.

## 5. Риски

- Rust и Java не собирались ни разу: первый запуск на VDS может упасть на сборке; правки — отдельными коммитами в `experiments/lang-bench/`.
- `Cargo.lock` не зафиксирован (создаётся при первой сборке): версии crate «плавают»; зафиксировать после первой успешной сборки.
- Версия образа oha не закреплена в репозитории; без тега скрипт не стартует (`OHA_IMAGE` обязателен).
- Нагрузка на общую VDS: ядра 0–3 заняты на 70–80 минут; стенд и розыгрыш работают на оставшихся ядрах и могут деградировать.
- Выводы чистой логики нельзя переносить на сквозную задержку (БД доминирует); решение о внедрении принимается только по сквозному замеру.
