# План бенчмарка lang-bench (B1) и требования к раннеру VDS

Статус: ГОТОВО К ЗАПУСКУ, не запускалось. Дата: 2026-11-23. Источники: промпт 19 (задача 2), промпт 22 (фаза B), `docs/architecture/POLYGLOT-ANALYSIS.md` (разделы «Правило решения по приросту», «B1 — подробный критерий», «Требования безопасности»). Код: `experiments/lang-bench/` (см. README там).

## 1. Что умеет раннер сейчас

Раннер описан в `docs/runbooks/vds-runner.md`, скрипты `infrastructure/vds-runner/` (на момент плана — в ветке `feature/vds-runner-cdn`, в `main` не слит; в ветке `docs/polyglot-analysis` каталога нет). Поддерживаются только задания `unit`, `api-e2e`, `web-build`, `docker-build` (список зашит в `run-remote.sh` и в `server/remote/enqueue.sh`). Задания бенчмарка нет, тайм-аут задания по умолчанию 2700 с (`RUNNER_JOB_TIMEOUT_SEC`), в `done/<id>/` сохраняются только `result.env`, `summary.txt`, `job.log`.

Решение по заданию: раннер в этой ветке НЕ расширялся (вне области записи и вне поддерживаемых заданий). Ниже — спецификация нужного задания `bench`; её реализует владелец раннера отдельным PR после слияния `feature/vds-runner-cdn`.

## 2. Нужное задание `bench`

| Параметр | Значение |
|---|---|
| Вход | снимок кода (`--ref` или `--worktree`), нужен каталог `experiments/lang-bench/`; параметры окружения: `OHA_IMAGE` (закреплённый тег), `PROFILE`, `DB_LATENCY_MS`, `DATASET_FILE`, `RULES` |
| Образы вариантов | `langbench-ts-current`, `langbench-ts-batch` (node:24-alpine), `langbench-rust` (rust:1.90-slim-bookworm -> debian:bookworm-slim, glibc, не musl), `langbench-java` (maven:3.9.9-eclipse-temurin-21 -> eclipse-temurin:21.0.5_11-jre-alpine); образы закреплены тегами версий, digest получить на VDS (`docker buildx imagetools inspect`) и передать через `DOCKER_BUILD_ARGS` (README, «Воспроизводимость»); сборка `docker build -f impl/<имя>/Dockerfile experiments/lang-bench` |
| Нагрузчик | oha (`OHA_IMAGE`, тег закрепить заранее), `--network host`, ядра нагрузчика отдельно от серверных |
| Лимиты варианта | одинаковые: `--cpus 2 --cpuset-cpus 0-1 --memory 512m --memory-swap 512m --pids-limit 512`; Java дополнительно `-Xms256m -Xmx256m -XX:+UseG1GC` (GC явный, пишется в `meta.json`) |
| Ядра нагрузчика | `--cpuset-cpus 2-3` (VDS 6 vCPU: ядра 4–5 остаются стенду) |
| Порядок | сначала эквивалентность всех четырёх (остановка при расхождении): golden и сгенерированные корзины на `fixtures/dataset.json`; при `DATASET_FILE` дополнительно сравнение вариантов между собой на большом наборе БЕЗ golden (`--no-golden`). Затем замеры ПО КРУГУ: для каждого из 3 повторов все варианты по очереди (порядок сдвигается на 1: повтор 1 — ts-current, ts-batch, rust, java; повтор 2 — ts-batch, rust, java, ts-current; и т. д.): холодный старт, прогрев 60 с при 50 соединениях, затем 1 / 50 / 500 соединений x 60 с, пауза 5 с между замерами |
| Запуск | `experiments/lang-bench/bench/run-bench.sh` на хосте (как `docker-build`; сам запускает docker) с `nice -n 15 ionice -c3`; `BENCH_LABEL=twomc-runner-job=<id>`, чтобы контейнеры чистились штатной очисткой |
| Длительность | на один повтор варианта: холодный старт + прогрев 60 с + 3 уровня x (60 с + 5 с) около 4,5–5 минут; 4 варианта x 3 повтора около 55–60 минут + сборка (Rust и Maven ориентировочно 10–20 минут) + эквивалентность (две серии при `DATASET_FILE`): ориентир 80–95 минут. Нужен `RUNNER_JOB_TIMEOUT_SEC` не менее 7200 для задания `bench` |
| Условие запуска | стенд не под нагрузкой (проверка нагрузки перед стартом; окно согласуется владельцем); один SSH-сеанс, блокировка `with-vds-lock.sh` |
| Артефакты (в `done/<id>/`, забирать в `--out`) | `summary.md`, `summary.json`, `meta.json`, `equivalence.log`, `equivalence-large.log` (при `DATASET_FILE`), `<вариант>-static.json` (размер образа), `<вариант>-cold-r<K>.json` (холодный старт каждого повтора), `<вариант>-c<N>-r<K>.json` (вывод oha), `*.stats.csv` (docker stats сервера раз в секунду), `*.loadgen.csv` (то же для нагрузчика oha), `build-<вариант>.json`, `job.log`. Потребуется расширить копирование артефактов (сейчас копируются три файла) |
| Сеть | исходящий доступ для `docker build`/pull (crates.io, Maven Central, Docker Hub/GHCR); входящих портов нет (только `127.0.0.1`) |
| Секреты | не используются; на раннер не передаются; ключи и `.env*` не монтируются |
| Очистка | образы `langbench-*` и `results/` удаляются очисткой раннера (старше 3 суток) |

Изменения раннера (для владельца раннера): (1) добавить `bench` в регулярные выражения `run-remote.sh` и `enqueue.sh`; (2) `server/ops/jobs/bench.sh` — вызов `run-bench.sh` с переменными; (3) повышенный тайм-аут для `bench`; (4) копирование каталога результатов в `done/<id>/`. `.github/workflows` не затрагивается.

## 3. Прогоны (после готовности задания)

1. Чистая логика: `DB_LATENCY_MS=0`, `PROFILE=medium`, затем `small` и `large`. Базовая линия — `ts-current`.
2. Модель обращений к БД: `DB_LATENCY_MS=2` (допущение: сетевая задержка до БД на VDS около 1–3 мс); показывает вклад N+1 (в `ts-current` задержка умножается на число товарных позиций, в остальных — одно обращение).
3. Большой набор данных: `RULES=5000`, `DATASET_FILE=generated/dataset-large.json` (одинаков у всех).
4. Сквозной замер с реальной БД (одинаковый пул соединений и одинаковый объём данных у всех вариантов, одноразовая копия БД) — отдельный этап, НЕ входит в текущие прототипы (нужны реализации с драйвером PostgreSQL и общий пул); решается после результатов шагов 1–3 и только при выигрыше в серой зоне и выше.

## 4. Метрики и отчёт

RPS, p50/p95/p99, доля ошибок и `errorDistribution` oha, CPU (среднее по `docker stats`, 200 % = два ядра), пик RSS, холодный старт (до первого 200 на расчёте, медиана по повторам), размер образа (измеренный; оценки в анализе помечены как оценка), время сборки, CPU и память самого нагрузчика (признак насыщения: средний CPU >= 80 % его ядер). Медиана по трём повторам. Java — отдельно прогрев JIT (>= 60 с), фиксированный heap и явный GC (G1). Отчёт — `docs/reports/lang-bench-report.md`: таблицы, выводы по «Правилу решения по приросту». ЕДИНОЕ ПРАВИЛО СРАВНЕНИЯ (одинаково в B1 `POLYGLOT-ANALYSIS.md`, здесь и в `tools/summarize.mjs`): каждый вариант сравнивается И с (a) `ts-current`, И с (b) `ts-batch`; прирост p95 = база / вариант - 1, прирост RPS = вариант / база - 1; классы по приросту p95: менее 30 % / от 30 % до 2x (серая зона) / 2x и более; РЕШЕНИЕ принимается по сравнению с (b) `ts-batch` (иначе выигрыш от исправления N+1 припишется языку), сравнение с (a) справочное. `summarize.mjs` выводит обе таблицы. Оговорки: источник данных в памяти, сеть loopback, `node:http` вместо NestJS, размеры образов — измеренные (не оценки), а также оговорки ниже.

Обязательные оговорки отчёта:
- Node однопоточный против двух ядер контейнера: потолок ts-вариантов около 100 % CPU; прирост Rust и Java на высоком параллелизме частично даёт многопоточность, а не язык.
- Rust собран под glibc, чтобы не занижать результат медленным аллокатором musl (размер образа больше, чем у musl+scratch); `mimalloc`/`jemalloc` не пробовались.
- Java на `com.sun.net.httpserver` (простой серверный стек JDK) показывает заниженные цифры относительно Netty/Undertow/Helidon; GC явно G1 (иначе на 2 vCPU / 512 МиБ JVM выбрала бы SerialGC).
- Нагрузчик oha делит стенд: его CPU и память снимаются; строки с насыщением нагрузчика (CPU >= 80 % ядер) помечаются и не годятся для выводов.
- Строки с ошибками (`errorDistribution`, доля не 200) помечаются в сводке: цифры RPS/p95 при ошибках недостоверны.
- Порядок по кругу (повтор -> варианты) снижает влияние дрейфа стенда, но не устраняет шум соседей по VDS; при разбросе повторов более 10 % прогон повторить в другое окно.

## 5. Риски

- Rust и Java не собирались ни разу: первый запуск на VDS может упасть на сборке; правки — отдельными коммитами в `experiments/lang-bench/`.
- `Cargo.lock` не зафиксирован (создаётся при первой сборке): версии crate «плавают»; после первой успешной сборки на VDS зафиксировать `Cargo.lock` в `impl/rust/` и собирать с `--build-arg CARGO_FLAGS=--locked` (README). Digest базовых образов не закреплены (только теги версий): получить на VDS (`docker buildx imagetools inspect`) и записать в отчёт; теги, выбранные без сети (особенно `rust:1.90-slim-bookworm`), могут потребовать замены.
- Версия образа oha не закреплена в репозитории; без тега скрипт не стартует (`OHA_IMAGE` обязателен).
- Нагрузка на общую VDS: ядра 0–3 заняты на 70–80 минут; стенд и розыгрыш работают на оставшихся ядрах и могут деградировать.
- Выводы чистой логики нельзя переносить на сквозную задержку (БД доминирует); решение о внедрении принимается только по сквозному замеру.
