# Подэтап 0.7. Веб выдачи купленного (2026-11-18)

Ветка `feature/l0-07-delivery` (worktree web), основание: ADR-0184, `docs/plan/PRIORITY-PLAN-DRAFT.md` «### 0.7», контракт API из отчёта `2026-11-18-l0-07-delivery-api.md` (ветка `feature/l0-07-delivery-api`).

## Результат

- Админка `/admin/store/delivery`: очередь заданий, фильтры (статус, исполнитель, номер заказа, ник получателя), пагинация, переход в карточку.
- Карточка `/admin/store/delivery/[id]`: сводка задания, «Отметить выданным» (причина ОБЯЗАТЕЛЬНА, до 1000 символов) и «Повторить» (чекбокс-подтверждение «команда могла уже выполниться», причина необязательна). Диалоги на Radix Dialog: role="dialog", aria-modal, фокус-ловушка, Esc, возврат фокуса на кнопку-открыватель, подписи через FormField; пока идёт запрос, закрытие заблокировано. 409 и 2FA разбираются в понятный текст без сырых статусов.
- Навигация: пункт «Выдача» в разделе «Магазин» по `store.delivery.view` (группа тоже открывается этим правом); действия по `store.delivery.manage` и допустимому статусу (зеркало MANUAL_DONE_FROM и RETRY_FROM на API).
- Карточка заказа админки: блок «Выдача» со статусом заданий по позициям и ссылкой на задание; показывается и запрашивается только при `store.delivery.view`.
- Покупатель: страница заказа (общий статус в карточке + статус у каждой позиции) и «Мои заказы» (бейдж в строке): «Ожидает выдачи» / «Выдано» / «Ошибка выдачи». Показываются только три значения `deliveryStatus`; неизвестное и `null` (заказ не завершён) не рендерятся. Ошибки транспорта, id заданий и исполнитель не выводятся.
- Права `store.delivery.view` и `store.delivery.manage` добавлены в общий каталог `packages/shared/src/permissions.ts` (тот же текст, что в ветке API, чтобы слияние не конфликтовало).
- Стиль: семантические токены, Lucide, solid-поверхности, без blur и glass; статус всегда текстом и иконкой, не только цветом.

## Допущения

1. Контракт взят из DTO и сервиса API-ветки: фильтр ника называется `nick`; тело повтора `{ confirmed: true, reason? }`; ручная отметка `{ reason }`.
2. API-карточка заказа админки не содержит заданий выдачи, поэтому блок «Выдача» запрашивает очередь `GET /admin/delivery/tasks?orderNumber=…&limit=100` и сужает до точного номера на клиенте (API ищет номер подстрокой). Заказ с более чем 100 заданиями показал бы неполный список (маловероятно для 0.7).
3. Админ-статус заданий показан подробно (9 статусов), покупателю только 3 значения, как отдаёт API.
4. Чекбокс подтверждения повтора добавлен сверх требования «подтверждение»: повтор команды может выдать покупку дважды.
5. Текст «Ожидает выдачи» показывается и при выключенном флаге доставки (API отдаёт `pending`): отдельной подсказки про флаг для покупателя нет.
6. Для старых ответов API без `deliveryStatus` бейдж не показывается (поля опциональны).

## Риски

- Контракт опирается на ветку `feature/l0-07-delivery-api`, ещё не слитую: при расхождении имён полей (например `nick`) потребуется правка `store-delivery.ts`.
- Права в каталоге продублированы между ветками (идентичный текст); при слиянии возможен тривиальный конфликт в `permissions.ts`.
- Права `store.delivery.*` попадут в роли только после seed/синхронизации каталога на API (вне scope веба): без этого пункт навигации не появится ни у кого, кроме ролей с полным доступом.
- Админский `lastError` и `renderedCommand` показываются персоналу как есть (очищены на сервере); веб дополнительной маскировки не делает.
- Кнопки действий проверяют только право и статус; окончательное решение за сервером (409/403 обрабатываются).

## К переносу

- R174. Блок «Выдача» в карточке заказа админки зависит от отдельного запроса очереди и права `store.delivery.view`; для больших заказов (>100 заданий) список усечён.
- R175. Права `store.delivery.view/manage` нужно выдать ролям персонала отдельно (синхронизация каталога прав на API, делает владелец/агент API).
- Обновить `docs/product-audit` и CHANGELOG: веб 0.7 готов, ожидает слияния API-ветки.
