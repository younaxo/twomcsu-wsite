# Отчёт: снятие мута и бана в чате по иерархии (Q25, 2026-11-17)

## 1. Итог

Статус: COMPLETE (unit-проверки зелёные; e2e не запускались; review и security не проводились). Решение владельца Q25: снять мут или бан может только выдавший либо равный/старший по приоритету. Реализовано в `ModerationService`, ADR-0171.

## 2. Что сделано

- `apps/api/src/modules/chat/moderation.service.ts`: `unmute(actorId, id)` и `unban(actorId, id)`; после проверки существования (404 сохранён) вызывается `assertCanRevoke`. 403 с общим текстом «Недостаточно прав для снятия этого ограничения».
- `apps/api/src/modules/roles/permission.service.ts`: новый метод `canRevokeSanction(actorId, issuerId)`: выдавший == снимающий, либо приоритет снимающего >= приоритета выдавшего (`getMaxPriority`, superuser бесконечный).
- `apps/api/src/modules/chat/admin-chat.controller.ts`: передаёт `user.id` (`@CurrentUser`); URL, права и ответы не менялись.
- Самоснятие: если снимающий и цель совпадают и он не выдавший, отказ.
- `canActOn` при снятии не применяется (обоснование в ADR-0171).
- Неизвестный выдавший: `mutedBy`/`bannedBy` пуст, пользователь не найден, либо `accountType=SYSTEM`. Допущение: нужен приоритет >= максимального приоритета среди всех ролей (фактически владелец; без ролей только superuser).
- Схема, миграции, seed не трогались.
- Пути в чате: WS-путей снятия нет (`chat.gateway.ts` содержит только `mute_user`/`ban_user`); единственные вызовы `unmute`/`unban` чата: `admin-chat.controller.ts`.

## 3. Тесты

- `moderation.service.spec.ts`: для mute и ban: выдавший (с меньшим приоритетом) снимает, равный снимает, старший снимает, младший 403 с точным текстом, неизвестный выдавший (null и id не найден) по допущению, самоснятие только выдавшим, несуществующий id даёт NotFound без проверки прав.
- `permission.service.spec.ts`: `canRevokeSanction` с реальной логикой (выдавший, равный/старший/младший, неизвестный: null, undefined, пустая строка, удалённый, SYSTEM; нет ролей).
- e2e `apps/api/test/chat.e2e-spec.ts` (строки ~544 и ~590): модератор снимает собственные мут и бан, это разрешено правилом, правка не нужна. e2e на 403 не добавлялся (e2e не запускаются).

## 6. Риски и data risks

- Данных и схемы изменения не затрагивают. Существующие санкции с `mutedBy`, которого нет в `users`, снимает только владелец.
- Равный приоритет разрешён (в отличие от строгого `canActOn` при выдаче).
- R38 записан в `docs/implementation/RISKS.md`.

## 7. Вопросы владельцу

1. Неизвестный выдавший (удалён, SYSTEM, пусто): допущение «только владелец». Варианты: а) оставить; б) любой с приоритетом выше `moderator`; в) любой с правом на снятие. Рекомендация а). Блокирует: ничего.
2. Применять ли Q25 к account-level бану (`quick-moderation`, bulk) и `ReportBan`? Для account-level нужно поле «кто выдал» (миграция). Рекомендация: да, отдельной задачей. Блокирует: правку этих путей.
3. Самоснятие: запрещено, кроме выдавшего. Устраивает ли? Рекомендация: да.

## 8. Исправления по ревью

- M2: e2e в `apps/api/test/chat.e2e-spec.ts` (блок «Q25»): мут и бан старшего, младший снимает: 403, запись остаётся активной; мут и бан младшего, старший и равный по приоритету снимают: 200. Сотрудникам выставляется 2FA через `markStaffTwoFactorEnabled` (внутри `grantRole`). e2e по запрету владельца не запускались; проверка статическая (tsc с `test/`).
- L7, L8: в ADR-0171 добавлены пункты: владелец не снимает с себя санкцию, выданную другим; приоритеты сравниваются на момент снятия.
- L9: реальная ошибка. Кеш сериализует `-Infinity` как `null`; `null >= 0` и `null > -Infinity` дают true. Тест на кеш-пути до исправления падал (3 из 3 новых), после исправления проходит. Минимальное исправление в `getEffectivePermissions` (чтение кеша). Риск R39.
- M1 (`admin-users-bulk`, `quick-moderation`, `ReportBan`) не исправлялся, остаётся R38.
