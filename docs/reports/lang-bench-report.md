# Отчёт по замеру языков, фаза B1: расчёт корзины `POST /store/cart/calculate`

Дата замера: 2026-11-27. Задание раннера `20261127T024428Z-bench-6053ab`, код `origin/main@fdd957d8`. Сырые итоги: `experiments/lang-bench/results/b1-2026-11-27/` (`summary.md`, `summary.json`, `equivalence.log`, `meta.json`).

## 1. Сводка для владельца

- Замерили чистую логику расчёта корзины на четырёх вариантах: текущий TypeScript, TypeScript с исправленным N+1 (контроль), Rust и Java 21. Базы данных в замере нет (задержка БД 0 мс).
- Ответы всех вариантов совпали с эталоном: 58 из 58 golden-фикстур у каждого, 2072 сгенерированные корзины, 0 расхождений.
- На чистом расчёте Rust быстрее TS примерно в 3,5 раза по RPS при 50 и 500 соединениях (22,4 тыс. против 6,4 тыс.), Java в 2,9 раза. Но TS уже даёт около 6000 RPS, а нагрузка сайта — единицы RPS.
- В реальном запросе время почти целиком уйдёт на запросы Prisma к БД и сеть, поэтому выигрыш на проде будет заметно меньше этих цифр. Замера с БД пока нет.
- Исправление N+1 в TS на чистой логике почти ничего не даёт (+2…+5 % RPS, +3…+14 % по p95); его эффект виден только с БД.
- Рекомендация: расчёт корзины на другой язык сейчас не переписывать. Исправление N+1 внедрять в TS только после замера с БД. Rust держать как вариант на случай CPU-тяжёлого расчёта при сотнях RPS. Java не даёт преимущества над Rust при памяти в разы больше.
- Строку Java при 500 соединениях нельзя использовать для выводов без разбора: есть реальные обрывы соединений (раздел 5).

## 5. ОГОВОРКИ (обязательно читать вместе с цифрами)

1. **Нет базы данных.** `db_latency_ms = 0`: это замер чистой логики. В реальном `POST /store/cart/calculate` узкое место — запросы Prisma и сеть до PostgreSQL; доля CPU на расчёт мала, поэтому выигрыш от смены языка на проде будет существенно меньше цифр выше. Решение о внедрении по критерию принимается только по сквозному замеру с БД; его нет.
2. **Потолок в 2 ядра и нагрузчик.** Rust (203–205 %) и Java (171–196 %) на c=50/500 выбирают 2 ядра сервера почти полностью: это предел при выбранных лимитах, а не «скорость языка вообще». Нагрузчик oha на этих строках потребляет 91–97 % CPU (Java c=50/500: 92,6 / 97,0; Rust c=50/500: 91,0 / 93,8) при бюджете 200 % (2 ядра). По формальному порогу раннера (160 % = 80 % ядер нагрузчика) насыщения нет, и `summary.md` помечает все строки «насыщение: нет». Тем не менее нагрузчик и сервер делят одну машину, и влияние нагрузчика на абсолютные цифры Rust/Java исключить нельзя. Поэтому абсолютные RPS Rust/Java считать нижней границей, а относительные приросты на c=50/500 — осторожной оценкой. Для TS нагрузчик не ограничивает (34–36 % из 200 %), сервер упирается примерно в одно ядро Node (109 %).
   - Расхождение с постановкой: формулировка «нагрузчик близок к насыщению» по данным формально не подтверждается: 91–97 % — это около 46–49 % от 200 %. Числа верны, вывод записан по данным.
3. **Java c=500: реальные обрывы соединений.** Сумма по 3 повторам: `connection closed before message completed` 1641 (539 / 914 / 188 по повторам), `operation was canceled` 190 (53 / 109 / 28); сходится с `summary.md`. Это 1831 запрос из примерно 3 431 150 успешных (около 0,05 %); в таблице доля округляется до 0,00 %, фактическая успешность по повторам 99,90–99,98 %. Ещё 1455 записей `aborted due to deadline` — штатное обрезание запросов в конце окна замера (порядка числа соединений на повтор; такие записи есть и у остальных вариантов). Причину обрывов (keep-alive, лимиты Java-сервера, heap/GC) не разбирали; строку Java c=500 нельзя использовать для выводов без разбора. У Rust и TS обрывов соединений нет.
4. **`ts-current` — не боевой код.** Это минимальный `node:http`-сервис без NestJS и Prisma, с BigInt вместо `Prisma.Decimal`. Реальный стек добавит накладные расходы (DI, guards, сериализация, Decimal), так что абсолютные цифры TS в проде будут ниже.
5. **Один заход.** Одно задание раннера, 3 повтора внутри; в таблицах медианы, разброс не приведён. Для Java c=500 он заметен: 17 751 – 20 191 RPS между повторами.
6. **Общая VDS.** У раннера 6 vCPU; `loadavg` до замера 1,09 / 1,10 / 1,16, после 2,95 / 3,44 / 4,02. Посторонняя нагрузка на свободных ядрах возможна.
7. **Профиль корзины.** Использован `medium`; `small` и `large` не запускались. Точное число позиций в `medium` здесь не проверялось (по плану профили соответствуют 3/10/50 позициям).
8. **Холодный старт** — время до первого ответа 200 (медиана по 3 запускам); размер образа — измеренный.

## 6. Выводы по критерию (`POLYGLOT-ANALYSIS.md`, раздел 5)

Критерий: переписывание допустимо, только если выполнены все условия (сквозной p95 лучше в 2 раза при реальной БД либо память меньше в 3 раза на тот же RPS; прирост нужен реальной нагрузке; не более +1 контейнера и +256 МБ; контрактные тесты и флаг; одобрение владельца). Прирост менее 30 % — оставить TS; 30 %–2x — серая зона; 2x и более при остальных условиях — кандидат фазы C.

- **ts-batch (N+1) к ts-current:** +3…+14 % по p95, менее 30 %: на чистой логике эффекта нет, как и ожидалось (N+1 бьёт по БД). Исправление имеет смысл внедрить в TS, но только с замером с БД.
- **Rust:** c=1 серая зона (+65 % по p95); c=50 и 500 класс 2x и более (+164 % и +227 %), память в 3–35 раз меньше TS. Но условие «при реальной БД» не проверено, а реальной потребности нет: нагрузка сайта — единицы RPS, TS уже даёт около 6000 RPS на чистом расчёте (ts-current 6038 / 5981, ts-batch 6358 / 6168 при c=50 / 500). Цена: второй источник правды для денег и +1 контейнер (образ 110 МиБ, RSS 3–18 МиБ — в бюджет +256 МБ укладывается). Решение: не переписывать сейчас; вернуться, если понадобится CPU-тяжёлый расчёт при сотнях RPS.
- **Java 21:** класс тот же (c=1 серая зона +42 %; c=50 +117 %; c=500 +181 % с оговоркой об обрывах), но RSS 200–240 МиБ (в 2–5 раз больше TS), холодный старт 613 мс, образ 273 МиБ. По сравнению с Rust: RPS ниже на 19 % (c=50) и 13 % (c=500), p95 хуже на 22 % и 16 %. Преимущества над Rust нет; не рекомендуется.
- **Итог:** переписывать расчёт корзины сейчас не рекомендуется. Узкое место в проде — БД. Условия «реальная БД» и «реальная нагрузка» не выполнены, поэтому ни один вариант не переходит в фазу C.
