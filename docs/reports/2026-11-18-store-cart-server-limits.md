# Отчёт: серверные лимиты корзины, коды ошибок промокода (шаг 2)

1. Итог: API корзины и заказа проверяет isUnique/maxPerPurchase на сервере, сливает одинаковые строки, отдаёт машинные коды ошибок и promoError, публичные поля промокода — по белому списку. Статус: DONE.

## 2. Что сделано

- S1 (Medium). Новый модуль `apps/api/src/modules/store/cart-limits.ts` (`assertCartLimits`) — единая проверка итогового состояния корзины. Лимиты считаются на товар целиком: количество суммируется по всем строкам, вариантам и получателям подарка. Уникальный товар — не более 1 шт. и 1 строки.
  - `CartService.addItem`: проверка суммарно с уже лежащим количеством; тот же вариант (или набор) с тем же получателем подарка сливается в одну строку (quantity += n), а не создаёт новую.
  - `CartService.updateItem` (PATCH): проверка нового количества; если смена получателя подарка делает строку такой же, как другая, строки сливаются.
  - `OrdersService.createFromCart`: проверка лимитов по всем строкам корзины (защита от дублей, появившихся в обход API); `quickBuy`: те же лимиты (прежняя ручная проверка заменена общей, добавлена проверка уникальных).
  - Параллельность: add/patch выполняются в транзакции с `SELECT ... FOR UPDATE` по строке корзины — без миграции и уникального индекса.
  - Коды: `CART_MAX_PER_PURCHASE` (400), `CART_UNIQUE_DUPLICATE` (409), `CART_UNIQUE_ALREADY_OWNED` (400, уже было сообщение при заказе, добавлен код).
- A2 (Medium). `PricingService.requireValidPromoCode` бросает ошибки с телом `{code, message}`: `PROMO_NOT_FOUND` (404), `PROMO_NOT_STARTED`, `PROMO_EXPIRED`, `PROMO_EXHAUSTED`, `PROMO_NOT_APPLICABLE`, `PROMO_MIN_AMOUNT`, `PROMO_FIRST_PURCHASE_ONLY` (все 400). `POST /store/promocodes/validate` дополнительно возвращает `code`. `computeTotals(..., { softPromo })`: в мягком режиме отказ промокода превращается в `promoError {code, message}` без скидки.
- A1 (Low). `lines[].cartItemId` в расчёте (для `quick-buy` строка условная, наружу не отдаётся).
- A3 (Low). `giftToUsername` в DTO: 3–16 символов, `[A-Za-z0-9_]` (как ник при регистрации); пустая строка = снять подарок. Единый ответ 404 `CART_GIFT_UNAVAILABLE` и одинаковое тело для «нет такого игрока» и «подарок самому себе». Отказ по товару (не подарочный / только для себя) — 400 `CART_GIFT_NOT_ALLOWED`, он не зависит от получателя и проверяется до поиска игрока.
- N2 (Low). `promoCode` в ответах корзины — только `code`, `description`, `discountType`, `discountValue`.
- Типы в `packages/shared/src/api/store-cart.ts` (добавочно, экспорт из index).

## 7. Риски и допущения

- Допущение A2: корзина с недействительным сохранённым промокодом возвращается со статусом 200, без скидки, с `promoError`; код остаётся привязанным (не снимается), потому что причина может исчезнуть (добавили товары до минимальной суммы). Создание заказа с таким промокодом — 400 с кодом `PROMO_*`, а не тихое повышение суммы. `calculate` с явным кодом — 4xx с кодом.
- Допущение: лимит `maxPerPurchase` считается на товар суммарно по всем вариантам, строкам и получателям подарка. Уникальный товар в подарок другому игроку тоже ограничен 1 шт. в корзине.
- Допущение: добавление в корзину уже купленного уникального товара не блокируется (как и раньше, проверка владения — при создании заказа, `CART_UNIQUE_ALREADY_OWNED`); существующий e2e это ожидает.
- Поведение: подарок самому себе теперь отклоняется (`CART_GIFT_UNAVAILABLE`) — раньше проходил. Возможна несовместимость с UI, где такой сценарий считался допустимым.
- Поведение: `applyPromo` теперь проверяет минимальную сумму от суммы после скидки лояльности — как `computeTotals`; раньше мог применить код, который расчёт тут же отклонял бы.
- Поведение: ответы 400 -> 409 для уникальных товаров при повторном добавлении (раньше 201 с дублем строки).
- В `items[].product` ответа корзины теперь есть `maxPerPurchase` (публичное поле товара, уже отдаётся каталогом).
- Наборы (bundle) лимитами не ограничиваются: состав набора с уникальными товарами и maxPerPurchase не раскрывается и не проверяется. Отдельное решение.
- Данные: существующие корзины с дублями строк уникальных товаров не мигрируются; при заказе пользователь получит 409 и должен убрать дубль.
- Из-за блокировки строки корзины (`FOR UPDATE`) параллельные запросы одной корзины выполняются по очереди; для других корзин влияния нет.
- В ветке S1 (c13aaa6) были нарушения prettier (3 ошибки lint в `products.service.ts`, `public-product.spec.ts`): исправлены отдельным коммитом c05fdfc; при слиянии с веткой S1 возможно совпадение изменений.
- Миграции и seed не создавались; e2e применял существующие миграции только на одноразовую БД.

- Ревью (M2, исправлено): поиск получателя подарка заменён с `findFirst {equals, mode: insensitive}` (Prisma транслирует в ILIKE, где `_` — подстановка) на `$queryRaw` `lower(username) = lower($1)` с параметром, точное совпадение регистра первым. e2e: игроки `u_xxxx` и `uXxxxx`, подарок уходит именно адресату. Что именно генерировал Prisma, по SQL-логу не проверялось: замена сделана превентивно.
- Ревью (L1, исправлено): `assertCartLimits(lines, onlyProductId?)`; add/patch проверяют только затронутый товар (набор — не проверяют), создание заказа — полная проверка. Тесты: unit и e2e.
- Ревью (L2, исправлено): быстрая покупка отдаёт `cartItemId: null` в lines.
- Остаточный риск M1 (не менять, вопрос владельцу): на подарочные операции нет отдельного лимита. Глобальный `ThrottlerGuard` есть (`app.module.ts`, APP_GUARD, 100 запросов/60 с по умолчанию); отдельных `@Throttle` на корзине нет. Оракул существования ника: существующий получатель — 201, несуществующий или сам отправитель — 404, то есть перебором ников можно выяснить, кто существует (ограничено глобальным лимитом). Решить: отдельный строгий лимит на подарочные add/patch или единый ответ.
- Остаточный риск L3: `requireCart` использует `upsert`; при параллельном первом обращении возможна гонка с P2002 на уникальном `userId` (500 вместо повтора). Не исправлено.

### M1 (Medium): лимит операций с подарком — исправлено

- Реализация: `apps/api/src/modules/store/cart-gift-rate.guard.ts` (`CartGiftRateGuard`), подключён `@UseGuards` на `POST store/cart/items` и `PATCH store/cart/items/:id` в `cart.controller.ts`. Класс-уровневый `JwtAuthGuard` выполняется раньше, `req.user` доступен.
- Срабатывает только при непустой строке `giftToUsername` в теле. Запросы без подарка, снятие подарка (`""`), `DELETE`, `GET`, `apply-promo`, `calculate` счётчик не трогают и остаются под глобальным `ThrottlerGuard` (100/60 с).
- Ключи (Redis, фиксированное окно, `SET NX EX` + `INCR` + `TTL` в одном `MULTI`, ключ без TTL не остаётся): по userId — 10/мин и 60/час (строго, как в Q81); по IP через `rateLimitKey` (IPv6 /64, ADR-0177) — 30/мин и 200/час. Выбрано оба ключа: userId защищает от перебора одним аккаунтом, IP — от обхода через много аккаунтов; IP мягче, чтобы общий NAT не блокировал честных игроков. Это отклонение от буквы «10/60 на пользователя» только для IP-ключа; значения в `CART_GIFT_LIMITS`, меняются одной строкой.
- Счётчик растёт и у отклонённых запросов; запросы с невалидным форматом ника тоже считаются (guard выполняется до валидации DTO) — это строже, не слабее.
- Redis недоступен: 503 (fail closed), только для подарочных операций.
- Комментарий в `cart.service.ts` (`resolveGiftTarget`) исправлен: единый 404 убирает лишь различие между «нет игрока» и «сам себе»; перебор ников НЕ исключён (успех 201 отличим от 404), защита — этот лимит.
- Код `CART_GIFT_RATE_LIMITED` добавлен в `store-errors.ts` и `packages/shared/src/api/store-cart.ts` (`STORE_CART_ERROR_CODES`).
