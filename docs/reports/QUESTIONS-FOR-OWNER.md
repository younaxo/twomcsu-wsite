# Вопросы владельцу (накопительный файл)

Ведёт `twomc-chief` по промпту 06 (п. 1.2). Владельца не спрашиваем до сообщения «я пришёл»; по каждому вопросу принято консервативное обратимое допущение. Статусы: ОТКРЫТ / ОТВЕЧЕН / СНЯТ.

## Q1. Подключить машинный аккаунт для Git (нужно действие владельца)

- Этап: B (Git), влияет на все этапы.
- Суть: twomc-chief-bot не подключён (нет remote `agent`, нет `%USERPROFILE%\.twomc\gh-bot`). Без него агент не может публиковать ветки, открывать PR и сливать их: admin-токен по решению владельца больше не используется.
- Варианты: (а) выполнить шаги 1–2 из `docs/runbooks/agent-github-access.md` (аккаунт с 2FA + collaborator Write; classic PAT `public_repo` без `workflow` + 4 команды PowerShell); (б) GitHub App с правами contents/pull-requests write, без workflows.
- Рекомендация: (а) — быстрее, уже описано.
- Заблокировано: push, PR, CI, merge всех локальных веток (список — в CHECKPOINT и итоговом отчёте).
- Допущение пока: работа идёт локально стеком веток (каждая следующая от вершины предыдущей), коммиты локальные.
- Статус: ОТКРЫТ.

## Q2. Локальный запрет `gh pr merge *` в `.claude/settings.json`

- Этап: B.
- Суть: даже под ботом слияние командой `gh pr merge` заблокировано deny-правилом в `.claude/settings.json` (deny сильнее allow в `settings.local.json`). Промпт 04 (раздел 1, п. 2) разрешает `gh pr merge` под ботом, но правку deny в `settings.json` явно не называет; кроме того, в этом файле лежит ваша незакоммиченная правка.
- Варианты: (а) разрешить заменить `Bash(gh pr merge *)` / `PowerShell(gh pr merge *)` на узкое правило «только под ботом» при подключении бота; (б) оставить deny, сливать PR через `gh api .../merge` под ботом; (в) сливать вручную.
- Рекомендация: (а) — прозрачнее, чем обход через `gh api`.
- Заблокировано: самостоятельное слияние PR после подключения бота.
- Допущение пока: при подключении бота читаю п. 1.2 промпта 04 как разрешение сузить deny `gh pr merge` до формы «только под ботом»; остальные deny не трогаю. Слияния #139–#141 2026-11-16 выполнены admin-токеном через `gh api` (разовое исключение п. 0.4).
- Статус: ОТКРЫТ.

## Q4. P3-02: топология прокси и Cloudflare

- Этап: A (P3-02).
- Суть: от топологии зависит значение `TRUST_PROXY` и настройка nginx.
- Варианты: (а) клиент → nginx → api; (б) клиент → Cloudflare → nginx → api (nginx `real_ip` по диапазонам Cloudflare).
- Рекомендация: в обоих случаях `TRUST_PROXY=1`; для (б) включить блок Cloudflare в nginx и закрыть origin файрволом для диапазонов Cloudflare.
- Заблокировано: ничего в коде; влияет на production-настройку.
- Допущение пока: `TRUST_PROXY=1` по умолчанию в compose, блок Cloudflare в примере nginx — закомментирован с инструкцией.
- Статус: ОТКРЫТ.

## Q7. Свободное место на диске C:

- Этап: общий (раздел 4 промпта 06).
- Суть: свободно было 11 ГБ (< 20 ГБ). По п. 4.1 очищены свои артефакты: кэш сборки Docker (2,5 ГБ), `.next` в своём worktree, `pnpm store prune` → 14 ГБ. Docker Desktop хранит данные в образе диска WSL, который сам не сжимается после prune.
- Варианты для владельца: удалить `apps/web/.next` в основном дереве (2,2 ГБ, пересобирается); сжать образ диска Docker Desktop (Troubleshoot → Clean / Purge data или Optimize-VHD); почистить другие папки по своему усмотрению.
- Допущение пока: основное дерево не чищу (папка владельца); при < 10 ГБ — действую по п. 4.2, при < 5 ГБ — п. 4.3.
- Статус: ОТКРЫТ.

## Q8. `TRUST_PROXY=true` в серверном `.env` и в `.env.example`

- Этап: A (P3-02).
- Суть: после P3-02 API отвергает `TRUST_PROXY=true` при старте (доверие всем hop-ам позволяло подделать IP). Старый документ PHASE-35 рекомендовал `true`; серверный `.env` и `.env.example` агент не читает (запрет).
- Действие владельца: перед следующим деплоем заменить в серверном `.env` `TRUST_PROXY=true` на `TRUST_PROXY=1` (или удалить строку — compose подставит `1`); проверить `.env.example` и при необходимости разрешить агенту его правку.
- Заблокировано: ничего в разработке; без правки `.env` API на сервере не стартует после выката P3-02.
- Допущение пока: значение по умолчанию в compose — `1`; предупреждение записано в ADR-0155 и CHANGELOG.
- Статус: ОТКРЫТ.

## Q9. IPv6 /64 и лимиты входа

- Этап: A (P3-02), остаточный риск.
- Суть: brute-force и throttle считают по полному IPv6-адресу; клиент с подсетью /64 может обойти лимиты, меняя адреса.
- Варианты: (а) агрегировать IPv6 по /64 для ключей лимитов (отдельная задача S); (б) оставить.
- Рекомендация: (а) отдельной задачей после этапа 00.
- Допущение пока: не делается в P3-02, записано в ADR-0155 как остаточный риск.
- Статус: ОТКРЫТ.
