# Отчёт: лимиты входа по подсети /64 для IPv6 (2026-11-17)

## 1. Итог

Счётчик и блокировка brute-force (логин и 2FA) теперь считаются по /64 для IPv6. Статус: PARTIAL (unit-проверки зелёные, e2e отложен: диск; review и security не проводились).

## 2. Что сделано

- `apps/api/src/config/trust-proxy.ts`: чистая функция `rateLimitKey(ip)`. IPv4 и `::ffff:a.b.c.d` дают IPv4; IPv6 даёт `v6:<h1>:<h2>:<h3>:<h4>` (первые 4 хекстета после разворота `::`, нижний регистр, без zone id, обрабатывается встроенный IPv4-хвост); пусто/undefined дают `unknown` (как `normalizeIp`); непустой мусор даёт `raw:` + 16 hex sha256 от строки в нижнем регистре.
- Применено: `apps/api/src/modules/auth/brute-force.service.ts` (`counterKey`, `blockedKey`). Это единая точка для логина (`auth.service.ts` ~245-296) и 2FA (~322-337): оба вызывают `bruteForce.isBlocked/registerFailure/reset`.
- Не применено (намеренно): `req.ip`/`context.ip` для журналов, аудита, `lastLoginIp`, согласий, `captcha.verify` (полный адрес через `normalizeIp`); `forms.controller.ts` (req.ip идёт в данные формы, не в ключ лимита); `registration.service.ts`, `social-auth` (ключей лимитов из IP нет, только per-route `@Throttle`).
- Глобальный `ThrottlerGuard` (`app.module.ts:99`) и per-route `@Throttle` не менялись. Допущение: вход покрыт отдельным brute-force счётчиком, а подкласс guard с tracker=`rateLimitKey` затронул бы весь API (в т.ч. ~25 маршрутов вне auth); при сомнении выбрано консервативно не менять. Остаточный эффект: throttler (10/мин на вход, 5-20/мин на регистрацию/OTP) по-прежнему считает полный адрес.
- Фолбэк для мусора: sha256-хеш выбран вместо `raw:<строка>`, чтобы ключ имел ограниченную длину и не содержал управляющих символов от клиента; не бросает и не делит общий `unknown`. Допущение: пустой/undefined остаётся `unknown`, согласованно с `normalizeIp`.
- Тесты: `trust-proxy.spec.ts` (+8 тестов `rateLimitKey`), новый `brute-force.service.spec.ts` (3 теста, in-memory Redis-мок: общая /64 делит счётчик, капчу и блокировку, разные /64 и IPv4 нет, mapped = IPv4).
- Документы: ADR-0163 в `docs/implementation/DECISIONS.md`, строка в `docs/implementation/CHANGELOG.md`, этот отчёт.

## 7. Риски

- Подсеть /64 (типичный клиент) делит лимит, как клиенты за NAT; соседи в одной /64 у хостингов могут получить ложную блокировку (10 неудач за 15 мин на всю /64).
- Админка «подозрительная активность» (`admin-tools.service.ts`) показывает ключ как есть: для IPv6 это `v6:2001:db8:0:1`, для мусора `raw:<хеш>`; код не менялся (вне scope), UI может требовать пояснения.
- Старые ключи с полным IPv6 истекают по TTL 900 с; сброс блокировки старым адресом не снимет новый ключ (после деплоя на 15 мин).
- Требует e2e: реальный `req.ip` за доверенным прокси (ADR-0155) для IPv6.

Фолбэк: нет `rateLimitIp` — используется `ip`; пустое значение и литерал `unknown` — общий ключ `unknown` (без IP нечем различать; зафиксировано в ADR-0163).
