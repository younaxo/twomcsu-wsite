## 2. API (срез 2)

Все маршруты: `JwtAuthGuard` + `InventoryEnabledGuard` (без `BRIDGE_ENABLED=true` ответ `503 inventory_unavailable`). Заголовки `Cache-Control: private, no-cache`, `Vary: Authorization, Cookie` (по коду `inventory.controller.ts` и ADR-0179 п. 13; прежнее значение `Vary: Cookie` в первой редакции отчёта и дизайна было ошибкой).

- `GET /inventory/me?server=<slug>` (60/мин): `InventoryMeResponseDto`; ETag по телу, `If-None-Match` даёт 304. Неверный `server` даёт `422 invalid_param`.
- `GET /inventory/me/privacy` (60/мин): `InventoryPrivacyDto { inventoryPublic, enderPublic }`.
- `PATCH /inventory/me/privacy` (10/мин): тело `{ inventoryPublic?, enderPublic? }`; пустое тело или `enderPublic=true` при непубличном основном даёт `422 invalid_param`; скрытие основного скрывает Ender.

Чужой инвентарь, админ-маршруты, приёмник Bridge: не входят в срез.

## 3. Миграции для обязательного ревью (Q28)

## 6. К переносу в общие файлы (я их не менял)

### ADR-0179: ядро инвентаря на сайте (срез 2)

Статус: Accepted (в рамках допущений Q34-Q38, ожидают подтверждения владельцем). Дата: 2026-11-17.

Контекст: ADR-0168 описывает инвентарь игрока на сайте; срез 2 реализует хранилище, чтение своего инвентаря и приватность без приёмника Bridge.

Решение:
1. Хранится только последнее состояние на `(userId, serverSlug, grp)`, без истории (Q36 а). Очистка рядов без обновлений 90 суток реализована, но не запланирована.
2. Предмет не больше 600 байт канонического JSON (Q35 а); лор отбрасывается с конца, если не помещается; иначе `invalid_data`.
3. Имена и лор хранятся как есть, при выдаче экранируются как текст, не HTML (Q38 а).
4. Приватность по умолчанию «приватно»; Ender Chest публичен только при публичном основном (Q34 а).
5. UUID игрока в БД не хранится; в ответ не попадают userId, epoch, rev, contentHash.
6. Раздел fail-closed: без `BRIDGE_ENABLED=true` 503 `inventory_unavailable`.
7. Донат-правила не реализуются: точка расширения возвращает `default` (hard gate).
8. apps/api держит локальное зеркало контракта shared; тест `inventory-contract.sync.spec.ts` сверяет оба файла (L5).
9. Сборка частей снимка не зависит от транспорта (`InventoryAssemblerService`): проверки формата, диапазонов, `slotGroup`, границ epoch/rev выполняются до обращения к Redis; буфер в Redis с TTL; полнота и захват применения атомарны (Lua, дизайн 4.4); применяется только полный комплект со сверкой набора `slotGroup`; повтор части не даёт дубля; повтор завершающей части после сбоя применения не теряет снимок; таймаут (120 с) отбрасывает неполную сборку; разное `parts` даёт `snapshot_mismatch` и отметку poison.
10. Свежесть: сначала `epoch`, затем `rev`; `capturedAt` в сравнении не участвует (L1). Ряд 32 КБ (Q35).
11. Лимиты (допущения до Q61/Q62, всё в `inventory-assembly.config.ts`): 6 сборок/мин на игрока, 2 сборки на игрока и группу, 256 сборок и 8 МБ буфера на сервер, доля сервера `min(20 МБ, 64 МБ / N)`, глобально 64 МБ, не более 64 серверов, TTL служебных меток выводится из T (не меньше T + 90 с).
12. Fail-closed: при `maxmemory-policy` не `noeviction` или невозможности проверить политику приём частей блокируется (`resync_required`); снять блокировку может только явное подтверждение владельца (`redisPolicyAcknowledged`).
13. `Vary: Authorization, Cookie` на ответах `/inventory/me` (L2).

Последствия: чужой инвентарь, админ-доступ и приёмник Bridge остаются следующими срезами; миграция требует ревью (Q28).

### Риски R70-R79

- R70: миграция написана вручную и не применена на БД; возможен дрейф со схемой при первом применении. Митигация: тест сверки, ревью (Q28), применение только на одноразовой БД.
- R71: e2e-спека не запускалась; возможны ошибки окружения. Митигация: запуск владельцем или отдельным заданием.
- R72: очистка 90 суток выключена; без неё таблица растёт. Митигация: срез с планировщиком и блокировкой лидера.
- R73: без приёмника Bridge раздел пуст; ложное ощущение готовности. Митигация: guard `BRIDGE_ENABLED`, срез приёмника.
- R74: имена как есть (Q38 а) могут содержать вводящий в заблуждение текст; экранирование защищает от XSS, не от обмана. Митигация: решение по Q38 при публичном показе.
- R75: лимит 600 байт отбрасывает лор; предметы с большим NBT дают `invalid_data`. Митигация: метрика отказов после запуска.
- R76: ETag меняется при `isFresh`, поэтому 304 реже; нагрузка выше расчётной. Митигация: лимит 60/мин.
- R77: дубль контракта (shared и api) может разойтись. Митигация: правка обоих файлов, проверка в ревью.
- R78: политика донат-прав пуста; при включении этапа 05 нужен пересмотр `canViewInventory`. Митигация: hard gate.
- R79: приватность по умолчанию «приватно» снижает видимость функции для игроков; продуктовое решение Q34.

## 7. Доработка по ревью (часть 1: M-1, L-2, L-1, M-2)

- M-1: выбрана перепроверка потолков на каждой части, а не резерв 32 КБ. Причина: резерв занижает полезную долю сервера для всех сборок и не защищает от сокращения доли L(N) при подключении других серверов; перепроверка в одном Lua-вызове атомарна и ничего не резервирует. Функция `ceilings()` в `redis-inventory-assembly.store.ts` вызывается при создании и на каждой новой части; при превышении сборка сбрасывается, ответ `resync_required` с причиной потолка. Та же логика в `apps/api/test/support/in-memory-assembly.ts`.
- L-2: `inventory-redis-policy.service.ts`. NOPERM/unknown command на `CONFIG GET` ведёт к запасной проверке `INFO memory` (`maxmemory_policy`, `maxmemory`); прочие ошибки дают fail-closed без учёта флага; `maxmemory` 0 ведёт к `maxmemory_unset`; `onReconnect()` сбрасывает состояние и выполняет реальную проверку (результат устаревшей проверки не перезаписывает новый); флаг `INVENTORY_REDIS_POLICY_ACKNOWLEDGED=true` только из окружения, по умолчанию false, действует лишь когда проверить нечем; использование пишется warn и счётчиком `owner_acknowledged_used`.
- L-1: `parseEpoch` (`inventory-normalize.ts`) принимает только JSON number (безопасное целое, от 1 до now + 10 мин); строки отклоняются как `invalid_data`; выше границы - `epoch_out_of_range`. `epochAlarmAheadMs` (120 с) подключён в `inventory-assembler.service.ts`: счётчик `alarm:epoch_ahead` и warn для зоны 120 с - 10 мин.
- M-2: по дизайну 3.5 применяется только строго более свежий (epoch, rev). Равные (epoch, rev): тот же `contentHash` - `applied` без изменений и без записи; иной состав - `stale`. Одиночный (`applySnapshot`) и собранный (`applyAssembled`) путь идут через одно правило; `capturedAt` не участвует. Старая развязка по `capturedAt` удалена. Это ужесточение: если плагин шлёт разное содержимое с тем же rev, снимок отбрасывается (плагин обязан увеличивать rev).

### Часть 2: пп. 5-9 и новые риски

- M-3: тест «после истечения сборки пришли все 4 части заново -> снимок применён» (`inventory-assembler.service.spec.ts`).
- L-3: `recompute()` не вызывается при отказе `ceiling_servers` (Lua и in-memory); тест.
- L-4: расчёт памяти не менялся; обоснование в комментарии `inventory-assembly.config.ts` (`rl:`/`own:` ~300 Б на снимок входят в служебные 2 КБ; `p:`/`h:`/`g:` входят в 1 КБ; `g` около 6 КБ на Redis). Это оценка, не измерение.
- L-5: `m:uh` считается HMAC-SHA256 с ключом `INVENTORY_UUID_HASH_KEY`; без ключа прежний SHA-256 без соли. Ключ должен быть одинаков на всех экземплярах; значение задаёт владелец.
- L-6: у `g`/`gts` нет хэш-тега; в коде зафиксировано «только Redis без кластера».
- Пустая часть с другим `slotGroup` -> `snapshot_mismatch` (`slot_group_differs`); `rejects` проверяет причину; граница 600 Б на срезе лора; sync-тест игнорирует комментарии; тест окна «БД применила, `finish('applied')` упал»; `afterEach` e2e сбрасывает `app`/`prisma` (e2e не запускалась).
- П.9: `redis-inventory-assembly.store.redis.spec.ts`, 6 тестов, требует Redis, без `INVENTORY_REDIS_TEST_URL` пропускается; не запускался.

Новые риски:
- R84-сб: плагин обязан увеличивать `rev` при изменении состава; тот же (epoch, rev) с другим составом даёт `stale` (M-2).
- R85-сб: без `INVENTORY_UUID_HASH_KEY` в production `m:uh` без соли; разные ключи на экземплярах дают `snapshot_mismatch`.
- R86-сб: сборщик не поддерживает Redis Cluster (CROSSSLOT на `g`/`gts`).
- R87-сб: тест Lua на реальном Redis написан, но не запускался; Lua не проверен на настоящем Redis (см. R70-сб).
- R87-сб (обновление 2026-11-17, Q35): тест Lua на реальном Redis 7 запущен, 6/6. Первые 3 падения были дефектом хелпера теста (`capturedAtMs: nowMs` менялся между частями снимка), не Lua и не стора: в проде `capturedAtMs` берётся из `part.capturedAt` и одинаков во всех частях. Добавлен юнит-регресс `redis-inventory-assembly.store.spec.ts` (заголовочные ARGV 17..23 не зависят от части и nowMs; порядок ARGV сверен с индексами в Lua). Условие для плагина (допущение): `capturedAt` обязан быть одинаковым во всех частях одного снимка, иначе `snapshot_mismatch/header`.
