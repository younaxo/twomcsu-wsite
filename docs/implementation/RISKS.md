# RISKS — внешние блокеры и ограничения

Формат: статус (`OPEN`/`MITIGATED`), описание, что сделано в обход блокера,
что требуется от владельца проекта, чтобы снять блокер полностью.

## R1 — Подпись коммитов (GPG) — MITIGATED (частично)

`git config commit.gpgsign` не настроен в рабочем окружении, `gpg --list-secret-keys`
не возвращает секретных ключей. Коммиты создаются без подписи. Чтобы включить
подпись: сгенерировать GPG-ключ (`gpg --full-generate-key`), привязать его к
`menidan78.offical@gmail.com`, выполнить `git config user.signingkey <KEYID>` и
`git config commit.gpgsign true` в этом репозитории, добавить публичный ключ в
GitHub (Settings → SSH and GPG keys).

## R2 — Платёжный провайдер — OPEN

Нет выбранного провайдера и нет production-credentials (см. ADR-0009). Реализован
интерфейс `PaymentProvider` + `TestPaymentProvider` для dev/test (безопасен: не
позволяет завершить заказ без внутреннего вызова, отключается в production).
**Нужно от владельца:** выбрать провайдера (ЮKassa/CloudPayments/Stripe/другой),
получить `PAYMENT_PROVIDER`, `PAYMENT_API_KEY`, `PAYMENT_WEBHOOK_SECRET`.
P3-01 / ADR-0157: вебхук проверяется HMAC над сырым телом, дефолта секрета нет; секрет в production
станет обязательным вместе с подключением реального провайдера (формат подписи реального провайдера —
своя реализация `verifyWebhook`). Порядок событий и требования к реальному провайдеру — R29.

PHASE 17 (Store): реализовано полностью по плану выше —
`modules/store/payment/{payment-provider.interface,payment-provider.registry,
test-payment-provider.service}.ts`, вебхук `POST /webhooks/payments/:provider`
(ADR-0034). `PaymentProviderRegistry` не регистрирует `TestPaymentProvider` при
`NODE_ENV=production` — до выбора реального провайдера `createFromCart()`/
`quickBuy()` в production вернут 503 (ADR-0039), не тихий фейк-успех.

## R3 — Объектное хранилище (S3-совместимое) для CDN — OPEN

`StorageService` с `local`-драйвером реализуется полностью рабочим для dev. Для
production нужен S3-совместимый бакет и домен `cdn-files.twomc.su`.
**Нужно от владельца:** `STORAGE_BUCKET`, `STORAGE_ENDPOINT`, `STORAGE_ACCESS_KEY`,
`STORAGE_SECRET_KEY`, настройка DNS/реверс-прокси для `cdn-files.twomc.su`.
Затронуто также PHASE 15 (Forms): `POST /forms/:slug/responses/upload` (загрузка
файлов для `FILE_UPLOAD`/`IMAGE_GALLERY`) не реализован в PHASE 15 — поля этих
типов принимают уже готовые URL в `fileUrls` (см. `FormsService.buildAnswerData`),
сам upload-эндпоинт появится вместе с `StorageService` (PHASE 23).
Затронуто также PHASE 16 (Reports): `POST /reports/:reportNumber/attachments`,
`.../messages/:messageId/attachments` (вложения к обращениям) и
`POST /admin/reports/:reportNumber/export` (экспорт ответов) не реализованы —
та же зависимость от `StorageService`, ADR-0033.

## R4 — SMTP (доставка писем) — OPEN (блокер DNS)

`EmailService` реализуется с рабочим интерфейсом; без `SMTP_HOST/USER/PASSWORD`
отправка писем выключается (логируется, не падает). Влияет на: email verification,
password reset, email-дайджесты.

2026-10-09: владелец передал SMTP Beget для `noreply@twomc.su` (хранится только
в локальном ignored `.env`). Авторизация проходит, но отправка отклоняется:
`550 You can send from only domains with BeGet MX records in DNS` — MX домена
`twomc.su` указывают на Cloudflare Email Routing. Регистрация (ADR-0070) без
доставки кода в production отвечает 503 `mail_failed`; в development код
пишется в лог разработки.
**Нужно от владельца:** решение по почте — MX/SPF/DKIM для Beget или другой
провайдер отправки (SendGrid/Mailgun/Postmark/Resend), совместимый с текущими MX.

## R5 — hCaptcha — OPEN

Заменено Turnstile (ADR-0059): нужны `TURNSTILE_SECRET_KEY` и
`NEXT_PUBLIC_TURNSTILE_SITE_KEY` для production (см. R17).
PHASE 21: hCaptcha-виджет на странице входа не подключён (без site key его
нечем проверить) — ответ backend `{ requiresCaptcha: true }` показывается как
явная ошибка «требуется проверка captcha» (ADR-0052), не как «неверный пароль»;
виджет добавляется вместе с ключами.
**Нужно от владельца:** регистрация сайта в hCaptcha, получение ключей.

## R6 — Внешние интеграции стриминга (Twitch/YouTube) — OPEN

статуса каналов (PHASE 14, Streaming — см. ADR-0026). CRUD каналов и
публичный список полностью рабочие уже сейчас; `POST /admin/streams/refresh`
честно отвечает `{refreshed: false, reason: 'no_platform_credentials_configured'}`

периодический cron для автообновления — когда появятся ключи (реализация
API-клиента) и PHASE 29 (cron-инфраструктура для автообновления).
**Нужно от владельца:** зарегистрировать приложение в Twitch Developer
Console и получить API key в Google Cloud Console (YouTube Data API v3).

## R11 — Обнаружены старые Docker volumes от предыдущего проекта (не удалены)

При первом `pnpm db:up` (PHASE 03) docker compose с project-именем `twomcsu`
(как в `docs/technical/33-DEPLOYMENT.md`) обнаружил уже существующие volumes
`twomcsu_postgres-data` и `twomcsu_redis-data`, созданные **2026-07-27** — то есть
до начала этой сессии, предположительно локальные данные предыдущей версии
проекта. Контейнеры были пересозданы поверх этих volumes (данные не удалялись —
`docker compose down` без `-v` не трогает volumes), после чего это было замечено
и **исправлено**: `infrastructure/docker-compose.yml` переименован в project
`twomc-su` (контейнеры `twomc-su-postgres`/`twomc-su-redis`), что создаёт отдельные
volumes `twomc-su_postgres-data`/`twomc-su_redis-data` и не трогает старые.

**Статус:** старые volumes `twomcsu_postgres-data`/`twomcsu_redis-data` по-прежнему
существуют на машине и не удалены — автоматическое удаление чужих/непроверенных
данных не выполнялось намеренно. **Нужно от владельца:** решить, нужны ли эти
данные (похоже на дев-дамп предыдущей версии проекта) — если нет, удалить вручную:

```bash
docker volume rm twomcsu_postgres-data twomcsu_redis-data
```

## R12 — Границы historical branches для PHASE 04/05 неоднозначны — MITIGATED

**Контекст.** PHASE 00–07 изначально велись в одной ветке
(`feature/project-bootstrap`) вместо отдельной ветки на каждый этап — задним
числом созданы historical branches (`feature/infrastructure`,
`feature/database-foundation`, `feature/authentication`,
`feature/rbac-permissions`, `feature/users`), указывающие на последний commit
соответствующего этапа (см. таблицу в `STATUS.md`).

Три commit'а (`344f9b1` fix(docs) — убрать шаблонный README, `9911306`
docs(status) — зафиксировать находку gitleaks, `2346864` fix(ci) — добавить
`.gitleaksignore`) оказались между завершением PHASE 04 (`33996ef`) и началом
PHASE 05 (`c8c3f65`). Это не фичи PHASE 04 и не PHASE 05 — это исправления
CI/repo hygiene (ложные срабатывания gitleaks) для PR, который на тот момент
покрывал фазы 0–4 целиком.

**Решение.** Не переписывать историю ради идеальной границы. `344f9b1`/
`9911306`/`2346864` включены в хвост `feature/database-foundation` (ветка
указывает на `2346864`) — это честнее, чем прикреплять их к PHASE 05
(`feature/authentication`), так как они фиксируют состояние CI именно после
PHASE 04, до появления кода PHASE 05. `feature/project-bootstrap` сохранена
как есть (указывает на актуальный HEAD, т.к. это действующая ветка открытого
PR #5) — согласно прямому указанию не удалять и не менять её при
нормализации.

## R13 — e2e: `beforeAll` под полным сьютом может превысить дефолтный таймаут Jest — MITIGATED

**Контекст.** `apps/api/test/*.e2e-spec.ts` поднимают полный `AppModule` через
`Test.createTestingModule(...).compile()` и создают 1–3 реальных пользователей
(`bcrypt`, 12 раундов) в `beforeAll`. По отдельности каждый файл укладывается в
дефолтный таймаут Jest (5000 мс на хук). PHASE 10 добавил восьмой параллельный
e2e-файл (`direct-messages.e2e-spec.ts`, с `app.listen(0)` для реального
Socket.IO-сервера) — под полным `pnpm test:e2e` (CI: `.github/workflows/ci.yml`,
без `--runInBand`, т.е. параллельные Jest-воркеры делят один Postgres+Redis)
`social.e2e-spec.ts` однократно упал с `Exceeded timeout of 5000 ms for a hook`
(при изолированном запуске — проходит за ~28 с). Это конкуренция за ресурсы
между воркерами, а не логическая регрессия (подтверждено повторным изолированным
запуском).

**Решение.** `jest.setTimeout(20_000)` добавлен на уровне файла в
`auth.e2e-spec.ts`, `roles.e2e-spec.ts`, `profiles.e2e-spec.ts`,
`social.e2e-spec.ts`, `users-domain.e2e-spec.ts`, `direct-messages.e2e-spec.ts`
(и явные таймауты `beforeAll(..., 30_000)`/`afterAll(..., 15_000)` в двух
последних, плюс защита `afterAll` от `undefined` при упавшем `beforeAll`).
`app.e2e-spec.ts`/`health.e2e-spec.ts` не трогались — не создают пользователей,
риск не подтверждён. Если флуктуации продолжатся на реальном CI (другое
железо/нагрузка), следующий шаг — `--runInBand` для job `test` в CI (ценой
последовательного, более медленного прогона) вместо дальнейшего роста таймаутов.

## R28 — Фавиконки внешних сайтов: живая проверка с настоящим DNS — MANUAL QA

Резолвер `GET /link-preview/favicon` (ADR-0102) покрыт тестами (SSRF, redirect, размер,
формат, живой HTTP на локальном сервере). На машине разработки внешние хосты резолвятся в
fake-IP прокси (198.18/15, см. R24), и резолвер их правильно блокирует — локально в окне
перехода видна Globe. **Проверить на staging/production:** ссылка на произвольный сайт
(например, reallyworld.ru) показывает его иконку, повторный переход — из кэша Redis.

## R27 — Web Push: production-ключи VAPID и учёт вкладок — OPEN

Код готов (ADR-0097). **Нужно от владельца при деплое:** сгенерировать
production-пару VAPID и задать `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` /

Переход из push прямо в диалог — вместе с разделом «Сообщения».

## R24 — CDN `cdn-files.twomc.su` недоступен с машины разработки — OPEN (сеть)

## R23 — Cleanup e2e с `undefined` удаляет всё — MITIGATED (инцидент 2026-10-10)

Для Prisma `{ id: undefined }` — пустой фильтр. В `users-domain.e2e-spec.ts`
`afterAll` удалял по `let`-переменным из `beforeAll`; когда `beforeAll` упал
(в dev-БД включены техработы → 503), cleanup удалил **все** роли, назначения
ролей, права ролей и журнал аудита **dev-БД** (production не затронут).
Исправлено: cleanup только по реально созданным id. Восстановлены три
superuser-роли из сида и назначения `younaxo_` → chief-curator, `qaadmin` →
chief-developer; роли, созданные вручную через админку, и журнал аудита
восстановить не из чего. Дальше: e2e — только на отдельной тестовой БД (CI
так и делает), локально — `DATABASE_URL` тестовой базы; рассмотреть
`strictUndefinedChecks` Prisma.

## R22 — Скины игроков без лицензии — OPEN

3D-скин берётся из API Mojang (ADR-0089). Для ников без лицензионного профиля
скина нет — показывается пустое состояние. Если сервер в offline-режиме, это
большинство игроков. **Решение владельца:** источник скинов с серверов через
плагин (R20, SkinsRestorer и т.п.) или сторонняя система скинов — только
после выбора владельцем (надёжность и правила).

## R21 — Брендированные страницы ошибок Cloudflare 502/503/504 — DEFERRED

Офлайн-режим внутри сайта готов (ADR-0086): страница `/offline` через Service
Worker, плашка «нет связи», состояния «сервер не отвечает». Если недоступен
сам origin (web-сервер), посетитель без установленного SW видит стандартную
страницу Cloudflare. Брендированные страницы ошибок Cloudflare отложены по
решению владельца: настраиваются в Cloudflare Dashboard (Custom Pages), это
production-настройка, а не код. **Нужно от владельца:** доступ к Cloudflare
(или настроить самостоятельно) — шаблон страницы можно собрать из `/offline`.

## R29 — failed раньше succeeded оставляет оплаченный заказ в FAILED — OPEN

`OrdersService.handleWebhook` переводит только заказы в `PENDING` (ADR-0157). Если провайдер прислал
`failed`, а затем `succeeded` по тому же заказу (повторная попытка оплаты, перестановка событий), заказ уже

(`orders.service.spec.ts`), чтобы любое изменение было осознанным. Для тестового провайдера риск
не актуален; он станет реальным с подключением платёжного провайдера (hard gate, реализация только по
команде владельца).

**Требования к будущему реальному провайдеру (только документ, без реализации):**

- собственный `verifyWebhook` под формат подписи провайдера;
- минимальная длина секрета и процедура его ротации;
- переход `FAILED` -> `COMPLETED` при позднем `succeeded` с обязательной проверкой суммы, валюты и
  `paymentId`;
- отдельный лимит для ретраев провайдера (сейчас на вебхуке действует только глобальный `ThrottlerGuard`, своего лимита нет);
- лимит 10 запросов в минуту на `quick-buy` остаётся (ответ владельца на Q13).

## R37 — Права при редактировании роли: wildcard и момент проверки (Q23, ADR-0170) — OPEN

`roles.controller.ts:185` и `role-bulk.service.ts:90` сравнивают добавляемые права со списком редактора через `includes`, без учёта права `*` (WILDCARD), в отличие от выдачи роли (ADR-0170). Сейчас `*` нигде не выдаётся, поэтому практического эффекта нет; при появлении wildcard-прав редактор с `*` получит отказ при добавлении конкретного права. Это ошибка в безопасную сторону, не эскалация. Вторая особенность: проверка подмножества при выдаче роли делается в момент выдачи; если у выдающего позже отняли право, ранее выданные роли остаются. Рекомендация: при введении wildcard вынести сравнение в общий хелпер `PermissionService`; пересмотр ранее выданных ролей не делать без решения владельца.

## R39 — Кеш прав: maxPriority = -Infinity превращался в null (L9, ревью Q25, ADR-0171) — MITIGATED

`getEffectivePermissions` кладёт результат в Redis через `JSON.stringify`; `-Infinity` («нет ролей») становится `null`, а в сравнениях `null` равен 0. До исправления при чтении из кеша пользователь без ролей проходил `canActOn` над другим пользователем без ролей (`null > -Infinity`) и `canRevokeSanction` для санкции выдавшего с ролью приоритета 0 (`null >= 0`). Практический эффект ограничен: действие всё равно требует права по PermissionsGuard, у пользователя без ролей прав нет, а роли с приоритетом 0 и `chat.*` не заведены. Исправлено восстановлением `-Infinity` при чтении кеша; кеш уже записанных значений (`null`) обрабатывается тем же кодом, сброс не нужен. Тесты: `permission.service.spec.ts` (кеш-путь). Остаточный риск: другие потребители сырого кеша `perm:user:*` вне `PermissionService` (не найдено).

## R46 — Соседи по одной /64 делят лимит throttler (Q21, ADR-0177) — OPEN (принято владельцем)

Глобальный throttler и per-route `@Throttle` считают по `rateLimitKey`: все адреса одной IPv6 /64 делят один лимит. Клиент-нарушитель может исчерпать лимит соседей по подсети (у хостингов и провайдеров, раздающих /64 нескольким клиентам); обратная сторона: ротация адресов внутри /64 больше не обходит лимит. ## R47 — Общий ключ `unknown` при неопределимом IP (Q21, ADR-0177) — OPEN (при верном TRUST_PROXY не ожидается)

Если `req.ip` и `socket.remoteAddress` пусты (или равны литералу `unknown`), все такие запросы делят один ключ `unknown` в throttler и в brute-force. При корректном `TRUST_PROXY` и реальном клиентском IP ситуация не ожидается; при неверном `TRUST_PROXY` (например, все запросы приходят с адреса прокси) все клиенты делят один ключ этого прокси. Непустой мусор получает отдельный ключ `raw:<hash>`. Проверять `TRUST_PROXY` перед выкладкой (см. `docs/runbooks/production-env-checklist.md`).

Правовое основание обработки полного IP и запись в реестре обработки персональных данных — решение владельца (L5 ревью), не принято.

Ожидания 400 (пустое тело) и 429 (шестой запрос) основаны на предположении, что глобальный guard срабатывает до pipes валидации; не подтверждено прогоном.

## R50 — /64 объединяет NAT64 и 6to4 (Q21, ADR-0177) — OPEN (принято)

`rateLimitKey` сворачивает IPv6 до /64 без учёта типа адреса: клиенты за одним NAT64-шлюзом (`64:ff9b::/96` и локальные префиксы операторов) и адреса 6to4 (`2002::/16`) могут попадать в общую корзину throttler и brute-force и делить лимит (см. `apps/api/src/config/trust-proxy.ts`, `rateLimitKey`). Для мобильных сетей с NAT64 возможны ложные 429. Следить за жалобами; исключения по префиксам — только по решению владельца.

## R51 — Успешный вход сбрасывает счётчик и lastip всей /64 (Q21, ADR-0177) — OPEN (принято)

`BruteForceService.reset()` удаляет счётчик, блокировку и `bruteforce:lastip:<ключ>` по ключу подсети. Успешный вход любого клиента из /64 сбрасывает неудачные попытки и «Последний IP» для всех соседей по подсети; для IPv6 охват шире, чем для IPv4 (один адрес). Злоумышленник с доступом к своей учётной записи в той же /64 может сбрасывать счётчик, перебирая чужой пароль с чередованием успешных входов (счётчик по IP, не по учётной записи). Смягчение (сброс только счётчика входа по логину или отдельные ключи) — решение владельца.

## R52 — Миграция зеркала наказаний не применялась (ADR-0178) — OPEN (перед merge)

`20261117020000_punishments_mirror` написана вручную и не прогонялась ни на какой БД, `PrismaPunishmentMirrorStore` (сырой SQL: `ON CONFLICT`, `xmax = 0`, приведения к ENUM и `timestamp(3)`) и тесты на PostgreSQL не запускались; сервис проверен только на хранилище в памяти. Перед merge: обязательный ревью (Q28), применить на одноразовой локальной БД и прогнать интеграционную проверку upsert. После раунда исправлений (F4) к этому добавлены не проверенные на PostgreSQL лимиты интерактивной транзакции (`APPLY_TX_MAX_WAIT_MS`, `APPLY_TX_TIMEOUT_MS`): реальная работа таймаутов Prisma проверяется только на живой БД. Миграцию нужно применить до включения `LITEBANS_ENABLED` (ADR-0178).

## R53 — Откат или восстановление БД источника (ADR-0178) — OPEN (принято, скорректировано)

При откате `maxId` ниже курсора сервис выставляет `NEEDS_RECONCILE` и ждёт полной сверки (F1). Курсор опускается до `maxId` только после успешной сверки (мягкой: без массовой пометки `DELETED_AT_SOURCE`), поэтому откат не повторяется на каждом тике, а новые строки с низкими id снова читаются (F2). До сверки новые строки с id не выше курсора минус перекрытие (100) не видны; полная сверка раз в 60 минут. Пустой источник не приводит к массовой пометке (`SOURCE_EMPTY`). Массовая пометка блокируется порогом: более `MASS_DELETE_MAX_RATIO` = 0.5 от зеркала при не менее `MASS_DELETE_MIN_ROWS` = 10 строк даёт тревогу `MASS_DELETE_SUSPECTED`. Порог 0.5 эвристический: реальное массовое удаление ниже порога пометится, а легитимная чистка выше порога потребует решения человека.

## R54 — Двойной лидер при паузе процесса (ADR-0178) — OPEN (принято, скорректировано)

Redis-блокировка не исключает паузу процесса (GC, остановка ВМ) между проверкой токена лидера и записью. По ревью (F6) токен проверяется непосредственно перед каждой записью зеркала, а транзакция записи ограничена по времени (F4), так что обычная запись укладывается в TTL (`LEADER_LOCK_TTL_MS` = 10 с). Раунд 2 (M1/M2): токен проверяется и между группами пометки, и перед каждой записью состояния (`patchState`), устаревший лидер тревоги не ставит и не снимает; события `deleted` по группам, записанным до утраты токена, теряются. Остаточный риск: пауза процесса между проверкой токена и записью дольше TTL; закрывается только лимитами транзакции (F4), полностью не исключается. Запись идемпотентна (upsert по `rowHash`, `GREATEST` для курсора), порча данных не ожидается; возможны лишние события `updated` с повышением `rev`.

## R55 — Срез 1 без публичной поверхности (ADR-0178) — OPEN (ожидаемо)

Нет адаптера источника, HTTP API, страницы `/bans`, «Мои наказания» и WebSocket: данные в зеркало не попадают, пока владелец не даст доступ к БД LiteBans и ресурсы (срез 2). `getStatus()` отдаёт «не настроено».

## R56 — Очистка текстов наказаний эвристическая (ADR-0178, ревью среза 1) — OPEN (принято, скорректировано)

`text-sanitizer.ts` скрывает IP и контакты по шаблонам, гарантии нет; `sanitizeReasonDetailed` возвращает признак маскировки, `isReasonMasked` позволяет скрыть причину целиком (Q59 по умолчанию, см. отчёт среза 1). Принятые обходы и остатки: контакты словами (`user at example dot com`), платформы без разделителя (`foo #1234`), IPv4 в нестандартной записи (`0x7f.0.0.1`, `2130706433`), телефоны из 7-9 цифр без `+`, гомоглифы, контакты вне списка платформ. Fail-closed ложные срабатывания (известный список, принят): `ig: foo`, `snap: foo`, `ds user` (любое слово после метки соцсети), `vk 123 times` -> `[скрыто] times`, `user@gmail`, `версия 1.2.3.4`, `8 999 123 45 67 кг`, `ok.museum`, `пример.онлайн` (любой домен с новой зоной), `это не discord. gg ok`; также имена файлов `x.py`, слова с точкой без пробела перед двухбуквенной или расширенной зоной (`end.Today`), числа `192 168 1 1`. Закрыто по ревью: IPv6 со встроенным IPv4 и портом, зоны ccTLD/gTLD/punycode, IPv4 с разделителями. Вывод только как plain text.

Раунд 2 (N1/N5): добавлены склонения и описательные формы платформ (`в дискорде: vasya`, `my discord is vasya`, `discord→vasya`, `в телеге vasya`) и маскировка секретов (`password:`, `пароль`, `Bearer`, `ghp_`, `sk-`, длинные base64/hex). Новые ложные срабатывания (fail-closed, приняты): слово после «в телеге/в дискорде/на дискорду/in discord» скрывается всегда (`в дискорде отвечает`, `spam on discord server`); `discord is down`, `дискорд это зло` (после «is/это/будет»); `в вк тоже` ; `секретно: да`, `токен-бот`, `token - 5 min`; `пароль vasya123` и любой токен с цифрой после слова «пароль/password/token/secret»; `pin=1`, `pass: ok`; любая цепочка из 32+ знаков `A-Za-z0-9+/_-` с цифрой (хеши коммитов, идентификаторы, длинные имена файлов с цифрой) и 48+ знаков со смесью регистров. Остаток (не закрыто): `мой дискорд vasya`, `discord vasya` без предлога и разделителя, `дискорд у меня vasya`, пароль/ключ словами, секреты короче порога без метки, разбитые пробелами или переносами секреты.

## R57 — Heartbeat и сбои блокировки лидерства (ADR-0178, ревью среза 1) — OPEN (принято, скорректировано)

Heartbeat выдаётся между пачками и непосредственно перед записью (F4/F6); сама транзакция ограничена по времени. Закрыто: heartbeat после `release()` не захватывает блокировку (F7); сбой `eval` Redis трактуется как потеря лидерства, своя блокировка возвращается без ожидания TTL (F8). Остаток: пауза процесса дольше TTL (см. R54).

## R58 — Контракт адаптера: невалидные строки (ADR-0178, ревью среза 1) — OPEN (требование к срезу 2, скорректировано)

`fullReconcile` и `poll` учитывают `PunishmentSource.drainSkippedIds?()` (F5): невалидные строки (SourceDataInvalid) не получают `DELETED_AT_SOURCE`, пачка считается полной по сырому числу строк, непродвигающаяся сверка даёт `RECONCILE_STALLED`. Адаптер среза 2 обязан реализовать `drainSkippedIds`, а `fetchByIds` не должен включать невалидные строки в `missing` (иначе слой 2 пометит их удалёнными).

## R80 — Расхождение копий типов api и shared (ADR-0180, срез 2) — OPEN (требование к срезу реализации)

`eslint` запрещает `apps/api` импортировать `@twomc/shared`, поэтому типы наказаний (`PublicPunishment`, `MyPunishment`, `StaffPunishment`, виды, статусы, коды ошибок) живут в двух копиях: `apps/api/src/modules/punishments/api/punishments-api.types.ts` и `packages/shared/src/api/punishments.ts`. Без защиты копии разойдутся, и web получит форму ответа, которой API не отдаёт (или наоборот). Мера: контрактный тест `punishments-contract-sync.spec.ts` (текстовый разбор компилятором TypeScript, нормализация, равенство множеств экспортов без API-only экспортов, кроме `IsoDateString`; сверка видов и статусов с `punishment.types.ts` и enum Prisma из `schema.prisma`). Также `export * from './api/punishments';` в `packages/shared/src/index.ts` - часть реализации. Диапазон рисков среза 2: R80-R89.

## R81 — Публичное имя выдавшего: персональные данные и давление на персонал (ADR-0180, Q63 п.3) — OPEN (принято владельцем)

Мера, выбранная владельцем: персонал куратор и выше принудительно скрывает выдавшего у конкретного наказания (4.2 контракта); скрытие реактивное, по умолчанию имя открыто. ## R83 — Флаг скрытия выдавшего живёт только в зеркале сайта (ADR-0180, Q63 п.3) — OPEN (требование к реализации)

## R84 — Имя выдавшего из LiteBans публикуется (ADR-0180, Q63 п.3) — OPEN (принято, скорректировано)

`banned_by_name` в LiteBans может быть display name с цветовыми кодами и произвольным текстом (дизайн, таблица столбцов). Срез 1 очищает метку эвристически (R56). Мера контракта: публичный слой показывает имя только при формате `^[A-Za-z0-9_.]{1,16}$` и без маркера `[скрыто]`, иначе `executor = null` (fail-closed); `uuid` выдавшего не отдаётся никогда. Остаток: ник реального игрока-модератора совпадает с валидным форматом, но не с его сайтовой личностью; консоль отдаётся как `{ console: true }`.

## R85 — Публичное название сервера (область наказания) (ADR-0180, Q63 п.4) — OPEN (принято владельцем)

Область показывается публично везде с названием сервера. Значение `server_scope` задаётся конфигом LiteBans и может быть внутренним именем (тестовый, закрытый, будущий сервер). ## R87 — «Куратор и выше» зависит от данных ролей, а не от кода (ADR-0180, Q63 п.3) — OPEN (требование к настройке)

В seed заданы только superuser-роли (Owner 1000, Chief Curator 900, Chief Developer 900); роль Curator и ниже создаёт владелец, приоритет в коде не задан. ## R88 — Блокировка записи при CREATE INDEX на production (ADR-0180, миграция среза 2) — OPEN (требование к применению)

Миграция `20261117040000_punishments_public_indexes` создаёт три индекса без `CONCURRENTLY` (в миграции Prisma он невозможен): Prisma выполняет файл одной транзакцией, блокировки держатся до её конца. По ревью Q28 (M1) три `CREATE INDEX` стоят ПЕРЕД четырьмя `ADD COLUMN`: на время построения индексов таблица `minecraft_punishments` закрыта для записи (`SHARE`), чтение идёт; затем четыре `ADD COLUMN` берут `ACCESS EXCLUSIVE` (закрыто и чтение, но только метаданные, мгновенно, до фиксации). Итог по факту: запись зеркала закрыта на всю транзакцию (индексы плюс ADD COLUMN), чтение закрыто лишь на момент ADD COLUMN; формулировка «блокируется только запись» неточна. Повышение блокировки с `SHARE` до `ACCESS EXCLUSIVE` ждёт завершения идущих чтений; перед применением выставить `lock_timeout`. Для таблицы порядка десятков тысяч строк построение занимает доли секунды или секунды; `ADD COLUMN ... NOT NULL DEFAULT false` на PostgreSQL 11 и новее не перезаписывает таблицу. Откат (L1): `DROP COLUMN issuerHidden*` допустим только до первого использования скрытия выдавшего; после него колонки несут данные, и возврат возможен только восстановлением из резервной копии. Меры: перед применением зафиксировать размер таблицы и версию PostgreSQL; применять при `LITEBANS_ENABLED=false` или в малонагруженное время; применение к production - только владелец. Побочное: индексы-выражения и частичный индекс Prisma не знает, поэтому автогенерация следующей миграции может включить `DROP INDEX`; защита - ручные миграции (Q43 а), юнит-тест `punishments-public-indexes-migration.spec.ts`, ревью.

## R89 — Несопоставленный выдавший: скрытие только для вершины персонала (ADR-0180, N3) — OPEN (принято, обратимо)

Выдавший сопоставляется с пользователем сайта только по подтверждённой привязке `MinecraftAccount`. Игрок-сотрудник без привязки, бывший сотрудник и uuid версии 3 не сопоставляются; скрыть их имя может только superuser или действующий с приоритетом не ниже максимального среди не superuser-ролей с правом скрытия или `users.punishments`. Следствие: у куратора рангом ниже вершины не получится скрыть имя несопоставленного выдавшего (403 `punishments_issuer_hide_forbidden`), пока сотрудник не привяжет аккаунт; владелец может заменить правило числом приоритета. Право `punishments.issuer.hide` до seed в БД отсутствует (N1): скрывать может только superuser. Откат миграции (L1): после первого скрытия выдавшего колонки `issuerHidden*` содержат данные и аудит ссылается на них; `DROP COLUMN` допустим только до первого использования, дальше только восстановление из резервной копии.

## R90 — Право punishments.issuer.hide не выдано ролям, кроме superuser (ADR-0180, N1) — OPEN (действие владельца)

Ключ `punishments.issuer.hide` добавлен только в каталог `packages/shared/src/permissions.ts`; в БД он появляется после seed, который выполняет владелец (hard gate). До seed и до назначения права ролям в админке скрывать выдавшего может только superuser (wildcard), остальные получают обычный 403; роль с `users.punishments` скрытие не получает. «Куратор и выше» достигается только данными ролей (R87). Мера: после seed владелец назначает право нужным ролям; проверить на одноразовой БД e2e `bans.e2e-spec.ts` (он сам создаёт ключ права, если seed не выполнялся).

## R91 — Юнит-тесты на моках не доказывают откат транзакции и поведение под гонкой (ADR-0180, срез 2) — OPEN (до запуска e2e)

Атомарность скрытия выдавшего (UPDATE и аудит в одной `$transaction`, N2), идемпотентность и гонки POST/POST и POST/DELETE проверены в unit-тестах на подставных Prisma и AuditService: они подтверждают порядок вызовов, но не реальный откат и не блокировки строк. Реальную проверку делает статический e2e `bans.e2e-spec.ts` (сбой `AuditService.logInTx` через spy, параллельные запросы), который агентом НЕ запускался. Не проверено e2e: сброс серверного кэша именно после фиксации (при откате), заголовки 429 (`Cache-Control: no-store` на ответе троттлера зависит от фильтра контроллера), порядок проверок на реальном стеке. До прогона на одноразовой БД эти свойства считаются непроверенными.

## R100 — Повторная проверка иерархии в транзакции читает права вне её снимка (ADR-0180, раунд исправлений 1) — OPEN (принято)

## R126 — Токен агента на GitHub обходит rulesets (роль Admin); защита только на стороне агента (Q76, промпт 10 v1.1) — ACCEPTED (владелец, 2026-11-17)

Агент публикует fine-grained токеном владельца (только репозиторий `twomcsu-wsite`; Contents RW, Pull requests RW, Actions/Checks/Statuses read; без Administration и Workflows) через отдельный `GH_CONFIG_DIR`. Токен действует от учётной записи с ролью Admin, поэтому rulesets для него обходятся: `all-branches-integrity` и `tags-protection` (bypass «always» — сервер не запрещает force-push и удаление веток и тегов), `main-protection` (bypass «pull_requests_only» — прямой push в `main` запрещён, но PR можно слить без обязательных проверок). Решение владельца: машинный аккаунт не создавать, риск принят. Меры: deny-правила `.claude/settings.json` (force-push, удаление, `--mirror`/`--all`, refspec с `:` и `+`, push в `main`, `gh pr merge` под учётной записью по умолчанию и с `--admin`, `gh api` DELETE); обёртка push (одна ветка, не `main`, без флагов, только fast-forward); обёртка слияния (PR CLEAN, три обязательные проверки `success` на текущем коммите, `--match-head-commit`, без `--admin`). Запрещено этим токеном всегда: force-push, удаление веток и тегов, слияние без трёх зелёных проверок и CLEAN, изменение rulesets, настроек и `.github/workflows`. Описание — `docs/runbooks/agent-github-access.md`.

## R127 — Окно повторного применения между publish и applied (раунд безопасности, контракт 5.2) — ACCEPTED

Сбой между publish и отметкой `applied` оставляет `received`; повтор применяется заново. Безопасно, пока источник наказаний идемпотентен по `(sourceScope, sourceId)` и порядку `occurredAt`; при нарушении идемпотентности источника возможно двойное применение. Покрыто юнит-тестом и e2e.

## R128 — Счётчик неверных подписей по паре (ip, key-id) (M1) — OPEN

Счётчик считает пару (ip, key-id), верная подпись не блокируется. Атакующий с множеством IP обходит счётчик; общий NAT игрового хоста может делить счётчик между серверами. Порог и окно — настраиваемые значения, подбор после первых боевых серверов.

## R129 — Ограничение M3: 503 до разбора тела глобально не реализован — OPEN

Парсер тела `/bridge/v1` ограничивает размер (413) и формат (400 invalid_body). Уточнение: 503 при выключенном или ненастроенном Bridge отдаётся ДО чтения тела. Остаётся неаутентифицированный разбор тела до 256 КБ (до проверки подписи), ограниченный throttler; ответ 503 при недоступности Redis возникает уже после чтения тела. Глобальная реализация «503 до парсинга» потребовала бы правки глобального конвейера и не делалась. Парсер реализован на node-потоке (без `express` в зависимостях): превышение лимита прерывает буферизацию, остаток отбрасывается.

## R133 — Потеря stale-маркера в Redis может вернуть старое событие в зеркало (M2) — OPEN

Приёмник защищается от устаревших событий маркером в Redis; upsert зеркала сам не сверяет `occurredAt`. При потере маркера (flush, eviction, рестарт Redis без персистентности) старое событие перезапишет более новое в зеркале. Условие в WHERE upsert потребует миграции - отдельный срез с ревью по Q28. Мера: Redis с персистентностью и политикой `noeviction` для ключей `bridge:*`.

## R134 — Поиск ключа до проверки блокировки и ключи authfail под произвольный key-id (N2) — OPEN

`findUnique` по key-id выполняется до проверки блокировки, а счётчики `bridge:authfail` создаются под произвольный key-id из заголовка (неаутентифицированный ввод): лишняя нагрузка на БД и рост числа ключей Redis (есть TTL). Ограничено throttler; доработка - проверка блокировки до поиска и ограничение формата/числа key-id.

## R135 — Маркер продвигается до publish (N3) — OPEN

Маркер последнего события продвигается до публикации (publish). Сбой publish без повторной отправки оставляет зеркало stale: повтор того же события будет отброшен как устаревшее. Мера: повтор publish/реконсиляция либо продвижение маркера после publish.

## R136 — TTL блокировки записи короче publish (N4) — OPEN

TTL блокировки записи 15 с может быть меньше длительности publish при деградации Redis/БД: блокировка истечёт, и параллельная запись пройдёт. Мера: продление блокировки или TTL с запасом, привязанный к `applyLatencyLimitMs`.

## R130 — Строгий мастер-секрет (L3) может остановить старт — OPEN

Проверка энтропии мастер-секрета отклоняет слабые значения; сообщение об ошибке не содержит значения. Владелец обязан задать достаточно случайный секрет перед включением `BRIDGE_ENABLED` в production.

## R131 — Боевая регистрация сервера только владельцем (L5) — OPEN

Флаги `--production --confirm-owner` защищают от случайного запуска, но не являются технической границей: любой с доступом к БД и мастер-секрету может зарегистрировать сервер. Агент скрипт не запускает; ключ выводится только владельцу.

## R132 — Допущение об авторитетном источнике Bridge и LiteBans (L2, L6) — OPEN

Bridge пишет в зеркало со своим `sourceScope`; опрос LiteBans не отключён. Для одной записи возможны два источника с разным scope (дубль наказания в зеркале), пока владелец не решит, какой источник авторитетен для каждого сервера (`punishments-authoritative`). Формат `pluginVersion`/`platform` в `bridge.hello` ограничен (L4); неподходящие значения - `invalid_data`.

## R137 — Серверные таймауты Node и прокси не заданы под slow-body (F1 остаточный) — OPEN

Парсер `/bridge/v1` ограничивает чтение тела дедлайном `BRIDGE_BODY_READ_TIMEOUT_MS` (10 с, 408), но глобальные `requestTimeout`/`headersTimeout` Node и таймауты прокси не менялись. Медленные заголовки (slowloris до парсера) и медленное чтение ответа остаются на значениях по умолчанию. Рекомендация владельцу/инфраструктуре: в nginx `client_header_timeout 10s`, `client_body_timeout 10s`, `send_timeout 15s`, `limit_conn` на `/bridge/v1`; в Node оставить `headersTimeout` не больше 15 с и `requestTimeout` не больше 30 с. Без этого защита от slow-body неполная; решение за владельцем.
