# ТЗ на дизайн — twomc.su

> Этот документ — функциональное задание на дизайн, НЕ визуальная
> спецификация. Здесь нет цветов, градиентов, radius, теней, конкретных
> анимаций и т.п. — выбор визуального стиля полностью на усмотрение
> Claude Design. Задача документа: описать, что на сайте есть, кто это
> видит, какие данные/действия/состояния у каждого экрана, чтобы дизайн
> был спроектирован под реальный, уже работающий функционал, а не
> придуман заново.

## 0. Контекст проекта

twomc.su — сайт Minecraft-сообщества (сервер/сеть серверов): новости,
форум-подобные топики/документы/правила, магазин доната, статус
игровых серверов, достижения/рейтинги, личные сообщения и публичный
чат, система обращений/жалоб с модерацией, формы (опросы/заявки),
голосование за сервер на мониторингах, стримы участников, полноценная
админ-панель.

Backend (NestJS + PostgreSQL + Redis) реализован полностью по фазам
00–20 из `docs/implementation/ROADMAP.md` — 20 из 37 фаз, все API,
которые ниже описаны как "готово", реально работают и покрыты e2e-
тестами против настоящей БД (не моки). Frontend (`apps/web`, Next.js 14
+ Tailwind) пока существует только как пустой boilerplate — ни одной
реальной страницы ещё нет. Этот документ — функциональная спецификация
для дизайна ПЕРЕД тем, как страницы начнут строиться (PHASE 21 и
дальше).

Важно: это НЕ копия старого проекта. Там, где новая архитектура
отличается от старой (см. §1), документ описывает НОВОЕ поведение —
многие страницы/механизмы старого проекта сознательно не переносятся
(см. §1.3 "Чего не будет").

## 1. Архитектурные отличия от старого проекта (важно для дизайна)

### 1.1 Роли → Permissions (RBAC)

Старая модель — один `RoleGroup` enum (PLAYER < HELPER < MODERATOR <
ADMIN < OWNER), линейная иерархия "выше/ниже". Новая модель — Discord-
подобная: у пользователя может быть **несколько ролей**, у каждой роли —
набор точечных **permissions** (`"achievements.view"`, `"store.products.edit"`
и т.п., ~280 ключей на сегодня). Доступ к разделу/действию = наличие
нужного permission (через объединение permissions всех ролей
пользователя), а не "роль ≥ X". Три специальные superuser-роли (`Owner`,
`Chief Curator`, `Chief Developer`) имеют wildcard-доступ ко всему.

Отдельно — **priority** (число у роли): определяет не ЧТО можно делать, а
**НАД КЕМ** можно действовать (забанить/отредактировать/назначить роль) —
действие разрешено, только если максимальный priority актёра строго
больше максимального priority цели. Это как в Discord: высокая роль не
даёт доступа к функциям сама по себе, но не даёт младшим модерировать
старших.

**Что это значит для дизайна:**
- Навигация (особенно админка) должна быть **динамической**, собранной из
  фактических permissions текущего пользователя, а не захардкоженным
  списком пунктов меню "для роли ADMIN". Один и тот же `/admin` может
  показывать разным сотрудникам разные наборы разделов.
- Нужен полноценный UI управления ролями: список ролей, редактирование
  набора permissions роли (матрица/дерево по модулям), назначение/снятие
  роли пользователю, отображение "эффективных" permissions пользователя
  (сумма по всем его ролям), визуализация priority ("эта роль не может
  редактировать того, кто выше").
- Там, где у страницы "нет доступа" — это ВСЕГДА про permission, не про
  "твоя роль недостаточно высокая" в абстрактном смысле.

### 1.2 Audit log

Каждое значимое административное действие должно быть видно в едином
журнале аудита (кто, что, над чем, когда, IP). Раздел audit log —
постоянный источник доверия для дизайна: админ должен видеть "кто это
сделал" из каждого места, где это уместно (история заказа, история
банов пользователя, история изменений настроек).

### 1.3 Чего не будет (сознательно не переносится из старого проекта)

- **Мок-оплата** (`/store/mock-payment`, кнопка "подтвердить оплату
  вручную") — в новом проекте оплата подтверждается только настоящим
  вебхуком платёжного провайдера (сейчас — тестовый провайдер без UI
  вообще; реальный провайдер появится по `RISKS.md R2`). В интерфейсе
  магазина НЕ должно быть кнопки "я оплатил" — после оформления заказа
  пользователь видит статус ожидания оплаты и дожидается реального
  обновления статуса.
- **Кастомные emoji** — не входит в scope.
- **Wiki, FAQ, игровые (in-game) репорты через внешний анти-чит** — в
  старом проекте это были незаконченные заглушки (TODO); в новый проект
  не переносятся как отдельные страницы. Раздел "Правила"/"Документы"
  полностью покрывает текстовый контент; обращения (жалобы/баг-репорты/
  апелляции) идут через раздел "Обращения" (§3.10), не через отдельный
  "wiki".
- **Захардкоженный список из 33 пунктов меню админки** — заменяется
  динамическим меню из permissions (см. §1.1).
- **Единая `/dashboard` зона "только для OWNER" с отдельными chart-
  эндпоинтами** — в новой архитектуре это просто ещё один раздел `/admin`,
  доступный по permission (`dashboard.view`), без отдельного маршрута и
  без выделенных под каждый график отдельных эндпоинтов — все графики
  одного дашборда приходят одним агрегированным ответом.

## 2. Информационная архитектура / навигация

### 2.1 Global nav (публичная, видна всем)

Главная · Новости · Правила/Документы · Сервера · Магазин · События ·
Топ (leaderboards) · Достижения · Стримы · Голосование за сервер ·
Поддержка/Обращения

### 2.2 User nav (после входа, иконка аккаунта)

Профиль · Друзья · Сообщения (ЛС) · Уведомления (колокольчик с
счётчиком непрочитанных) · Избранное (wishlist) · Мои заказы ·
Настройки аккаунта · Выход

### 2.3 Admin nav (permission-driven, см. §1.1)

Группы разделов (каждая группа видна, если есть хотя бы один permission
`*.view` внутри неё — см. §1.1):

- **Дашборд** — общая сводка
- **Пользователи** — список/карточка/bulk-действия/роли и permissions
- **Модерация** — обращения, жалобы на комментарии/профили, быстрые
  санкции, история наказаний
- **Контент** — новости, топики/документы/правила, формы, события,
  стримы, голосование
- **Геймификация** — достижения, награды, бейджи, заявки на медиа-бейдж
- **Магазин** — каталог, категории, наборы, скидки, промокоды, валюты,
  заказы, возвраты, статистика
- **Minecraft-сервера** — категории, сервера, логи статуса
- **Чат** — каналы, баны/муты, настройки
- **Безопасность** — сессии, подозрительная активность, история входов,
  IP-whitelist
- **Система** — настройки сайта, audit log, рассылки (broadcast),
  закладки/сохранённые фильтры/запланированные экспорты (личные
  инструменты самого админа)

### 2.4 Moderation nav (для ролей с модераторскими permissions, но не
полным доступом в `/admin`)

Подмножество "Модерация" из §2.3 — отдельная упрощённая зона для ролей
уровня "хелпер"/"модератор": обращения, жалобы, быстрые санкции (мут/
варн/кик/бан), поиск по чату.

### 2.5 Mobile nav

Та же глобальная навигация в виде нижнего таб-бара или бургер-меню;
админка на мобильном — отдельная тема ниже (§6).

### 2.6 Contextual-навигация

- Профиль пользователя — вкладки (Обзор / Достижения / Награды /
  Комментарии / Активность)
- Магазин — сайдбар категорий + хлебные крошки
- Конструктор форм — пошаговый wizard (поля → логика → настройки →
  публикация)
- Обращение (тикет) — переписка в виде треда с боковой панелью
  метаданных (статус, исполнитель, заметки)

основные экраны, ключевые данные/действия. Состояния — см. §4 (общий

### 3.4 Социальные функции

Комментарии на профиле (с реакциями), система жалоб на комментарий/
профиль (кнопка "пожаловаться" с выбором причины) — встроены в
профиль/ленту, отдельных страниц не требуют, кроме как в модерации
(§3.11).

### 3.5 Личные сообщения

| Экран | Route | Содержимое |
|---|---|---|
| Сообщения | `/messages` | Список бесед (личных и групповых), создание новой беседы, групповые беседы по инвайт-ссылке (`/g/:code`), real-time (печатает…, прочитано, онлайн) |

Realtime: сообщение приходит мгновенно всем участникам открытой
беседы; есть индикатор "печатает"; soft-delete сообщения видно как
"сообщение удалено".

### 3.6 Публичный чат

Общий чат сайта (каналы: общий/трейд/помощь/объявления/игровой/флуд),
с модерацией (мут/бан прямо из интерфейса для staff), закреплённые
сообщения, онлайн-список. Полноценный realtime (как Discord-виджет),
встраивается как отдельная секция (не обязательно отдельная
полноэкранная страница — скорее постоянно доступный виджет/панель).

|---|---|---|

### 3.9 Уведомления (система)

Типы: заявка в друзья/принята, комментарий/упоминание/ответ, подарок
получен, статус заказа изменился, упоминание в чате, новость
опубликована, достижение разблокировано, выдана награда/бейдж/ранг,
жалоба назначена/есть вердикт, новое сообщение, объявление (broadcast),
режим техработ. Каналы доставки (настраиваются пользователем): сайт
(всегда), email, push, Discord-вебхук. Экран настроек — тумблеры по
каждому типу + "тихие часы".

## 4. Общий контракт состояний (применяется ко всем data-driven экранам)

Для каждого списка/детальной страницы/формы — подразумевать (если не
указано иное для конкретного экрана выше):

- **default** — данные загружены и есть
- **loading** — первичная загрузка
- **skeleton** — предпочтительно вместо спиннера для списков/карточек
- **empty** — данных нет ("пока нет заказов", "список пуст" + осмысленный CTA, где уместно)
- **error** — сетевая/серверная ошибка, с повтором
- **403** — нет нужного permission (не "страница не найдена", а явное "недостаточно прав", желательно с указанием какого раздела/permission не хватает)
- **404** — сущность не найдена (например заказ/достижение по несуществующему slug)
- **offline** — потеря соединения (особенно важно для чата/ЛС/уведомлений — реконнект Socket.IO, баннер "соединение потеряно/восстановлено")
- **maintenance** — сайт в режиме техработ (см. §3.1, полноэкранная замена для ВСЕХ страниц кроме самой maintenance-страницы и админки)
- **success** — успешное действие (toast/inline-подтверждение)
- **validation error** — построчная ошибка в форме (с текстом из API)
- **disabled** — действие временно недоступно (например "уже проголосовали сегодня", "форма закрыта для приёма ответов")
- **locked** — сущность заблокирована для изменений (например тикет в статусе `CLOSED`, топик заблокирован)

Специфичные отличия:
- Чат/ЛС: дополнительно "печатает…", "онлайн/оффлайн", read-receipt.
- Магазин/checkout: отдельное промежуточное состояние "ожидание
  подтверждения оплаты" (не success и не error — см. §1.3).
- Таблицы в админке: доп. состояние "выбрано N строк" (bulk-режим) с
  панелью доступных массовых действий.
- Формы (конструктор, §3.13): "черновик сохранён", "лимит ответов
  достигнут", "ответы закрыты".

## 5. Основные user flows (сквозные сценарии)

1. **Регистрация → профиль.** `/register` → автоматический вход →
   `/profile/settings` (предложение заполнить профиль) → публичный
   профиль `/users/:username` уже доступен.
2. **Друзья → ЛС.** Публичный профиль → "добавить в друзья" → уведомление
   получателю → принятие → кнопка "написать" на профиле становится
   активной → `/messages` новая беседа.
3. **Магазин → заказ.** `/store` → товар → в корзину → `/store/cart`
   (промокод) → `/store/checkout` → создание заказа (PENDING) →
   редирект к провайдеру/ожидание → вебхук провайдера подтверждает →
   статус COMPLETED → уведомление пользователю → `/profile/orders`.
4. **Жалоба → модерация → наказание.** `/report/new` → выбор типа →
   форма → тикет создан (PENDING) → модератор в `/moderation/reports`
   берёт в работу (IN_REVIEW) → переписка → вердикт → (опционально)
   наказание пользователю, видно в его истории наказаний → уведомление
   автору обращения.
5. **Admin-действие → audit log.** Любое действие из §3.16/3.17 (бан,
   изменение настроек, выдача роли) → мгновенно появляется запись в
   `/admin/audit-log` с указанием actor/action/target/diff.
6. **Достижение → уведомление → витрина.** Пользователь выполняет
   условие (например добавляет друга) → администратор (или в будущем —
   фоновый job) запускает пересчёт → достижение разблокируется →
   уведомление "Достижение разблокировано" → пользователь добавляет его
   в витрину на своём профиле (до 10 достижений).
7. **Форма по инвайт-ссылке.** Админ создаёт форму → генерирует инвайт →
   `/forms/invite/:code` → пользователь заполняет (возможно,
   многошагово) → админ видит ответ в `/admin/forms/:id/responses`.
8. **Broadcast → баннер + уведомление.** `/admin/broadcast` → форма →
   создаётся объявление → все пользователи целевой роли получают
   уведомление + видят баннер объявления на сайте до истечения срока
   показа.
9. **Назначение роли.** `/admin/roles` → выбор пользователя → назначение
   роли (разрешено, только если приоритет роли меньше приоритета
   актёра) → эффективные permissions пользователя обновляются
   мгновенно (без ожидания переlogin'а).

## 6. Responsive

- **Публичные и пользовательские разделы** (главная, новости, профиль,
  магазин, чат, ЛС, уведомления, достижения, обращения) — полноценный
  mobile-first: не просто сжатый desktop-layout, а отдельно продуманные
  mobile-паттерны (нижний таб-бар, свайпы по карточкам, модалки вместо
  боковых панелей, корзина как bottom-sheet).
- **Модерация** — используется преимущественно с desktop/планшета, но
  должна оставаться пригодной на планшете (переписка по тикету, быстрые
  санкции).
- **Админ-панель** — приоритет desktop/laptop; на планшете — рабочий
  layout с адаптированными таблицами (меньше колонок по умолчанию,
  остальное — в развороте строки); на мобильном — "best effort":
  таблицы превращаются в карточки, сложные формы (конструктор форм,
  матрица permissions) могут требовать десктоп с явным предупреждением.

## 10. Явное ограничение

Этот документ описывает UI/UX на основе УЖЕ РЕАЛИЗОВАННОЙ бизнес-
логики backend. Claude Design может предлагать улучшения UX
(расположение, группировку, названия разделов, дополнительные
состояния интерфейса), но **не должен самовольно менять бизнес-правила**
(например: кто кого может банить, как считаются скидки, какие статусы
у заказа/тикета существуют). Если в процессе дизайна обнаруживается
место, где напрашивается новая бизнес-функция — это нужно вынести
ОТДЕЛЬНОЙ пометкой "Предложение для бизнес-логики" в своём выводе, а не
закладывать в дизайн как факт.
