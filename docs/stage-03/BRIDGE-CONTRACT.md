# Этап 03: контракт TwoMC Bridge (плагин и сайт)

Статус: проект, решения владельца по Q32 приняты (ADR-0167, Accepted-by-owner для платформы, ключей, миграций и данных игроков; прокси и число серверов открыты, Q42). Дата: 2026-11-17. Только документ: плагина, кода сайта, миграций и ключей нет. Плагин пишется позже, после ответов владельца (раздел 12).

Платформа (решение владельца, Q32): ядро игрового сервера — UniverseSpigot 1.21.4 (Spigot API `1.21.4-R0.1-SNAPSHOT`, Minecraft 1.21.4), Java не ниже 21 (точную версию Java на хосте владелец уточнит). UniverseSpigot — форк: плагин TwoMC Bridge пишется под стандартный Spigot API 1.21.4, а поведение (потоки, события, совместимость с LiteBans) обязательно проверяется на реальном сервере владельца. Плагин пишет агент позже, после ответов владельца на открытые вопросы (раздел 12). Прокси сети (Velocity или BungeeCord) и количество серверов НЕ указаны: открытый вопрос Q42; пока контракт не предполагает прокси, а на каждый игровой сервер приходится свой `serverId` и ключ. Сам контракт описывает только HTTP-границу, поле `platform` — произвольная строка (для текущего ядра ожидается `spigot`).

Связанные документы: `docs/stage-02/LITEBANS-INTEGRATION-DESIGN.md` (адаптер `PunishmentSource`, нормализованная модель), `docs/implementation/MINECRAFT-PLUGIN-CONTRACT.md` (существующая привязка `/site-connect`, ADR-0072), ADR-0157 (HMAC-вебхук платежей).

## 1. Транспорт

Решение: плагин сам отправляет пачки событий на сайт по HTTPS (`POST`, JSON) с HMAC-подписью. Соединения от сайта к игровому серверу нет.

| Критерий                          | HTTPS-вебхуки плагин→сайт                 | WebSocket плагин↔сайт                                             |
| --------------------------------- | ----------------------------------------- | ----------------------------------------------------------------- |
| Входящие порты на игровом сервере | не нужны                                  | не нужны (клиент — плагин)                                        |
| Идемпотентность и повтор          | естественны: `eventId`, повтор пачки      | нужно строить подтверждения поверх канала                         |
| Устойчивость к обрывам            | без состояния, исходящая очередь на диске | реконнект, возобновление, липкие сессии                           |
| Backpressure                      | `429` и `Retry-After`                     | кастомный протокол                                                |
| Команды сайт→сервер               | нет                                       | возможны                                                          |
| Совпадение с существующим кодом   | ADR-0072 и ADR-0157 уже на HMAC-HTTP      | нужна новая инфраструктура (у Socket.IO сайта нет Redis-адаптера) |

Выбор: HTTPS для v1. Команды сайт→сервер (выдача и снятие наказаний, выдача предметов) в v1 ЗАПРЕЩЕНЫ: это отдельное решение владельца и отдельный протокол (WebSocket или опрос команд), он не входит в этот контракт. Все события v1 — только «сервер сообщает сайту».

Эндпоинты (префикс `/bridge/v1`):

| Метод и путь                 | Назначение                                                     |
| ---------------------------- | -------------------------------------------------------------- |
| `GET /handshake`             | версия протокола, лимиты, серверное время; подпись обязательна |
| `POST /events`               | пачка событий (до 100 штук, до 256 КБ)                         |
| `POST /punishments/snapshot` | страница полного среза наказаний для сверки (раздел 6)         |

Только HTTPS; редирект с HTTP не выполняется. `Content-Type: application/json; charset=utf-8`.

## 2. Аутентификация сервера и версия протокола

### 2.1 Заголовки

| Заголовок           | Значение                                                                                  |
| ------------------- | ----------------------------------------------------------------------------------------- |
| `x-twomc-key-id`    | идентификатор ключа: `<serverId>.<поколение>`, например `survival.1` (`serverId` в протоколе = `BridgeServer.slug`, см. 2.4) |
| `x-twomc-timestamp` | Unix-время в секундах                                                                     |
| `x-twomc-nonce`     | 16–32 случайных байта в base64url (22–43 символа), новое на КАЖДЫЙ запрос, включая повтор |
| `x-twomc-protocol`  | целое, `1`                                                                                |
| `x-twomc-signature` | hex от HMAC-SHA256                                                                        |

### 2.2 Подпись

```
canonical = "twomc-bridge-v1" LF key-id LF timestamp LF nonce LF METHOD LF path LF sha256hex(сырое тело)
signature = hex(HMAC-SHA256(ключ_сервера, canonical))
```

`path` — путь без домена и query, `LF` — символ `\n`, для запросов без тела хэш считается от пустой строки. Версия протокола и `key-id` входят в подписываемую строку (префикс `twomc-bridge-v1` фиксирует версию схемы подписи). Подпись считается над СЫРЫМ телом (как в ADR-0157), а не над разобранным JSON. Эталонный вектор для проверки реализации плагина (ключ тестовый, в production не использовать):

```
ключ:       example-secret-not-for-production-use-0123456789
key-id:     survival.1
timestamp:  1794916800
nonce:      AAAAAAAAAAAAAAAAAAAAAA
METHOD:     POST
path:       /bridge/v1/events
тело:       {"schema":"twomc.bridge.v1","sentAt":"2026-11-17T12:00:00.000Z","events":[{"eventId":"0193f0a2-7c1e-7000-8000-000000000001","type":"bridge.hello","serverId":"survival","streamId":"boot-0001","seq":1,"occurredAt":"2026-11-17T12:00:00.000Z","data":{"pluginVersion":"0.0.0-example","platform":"example"}}]}
sha256(тело): 948f3c8711ceacb9257f84d3f4037387f1a7008fd2f5239cf72c2bb4d4fd9ad5
signature:  9cbc99b98b00133f034fd5d058bdaff1818f54fa3003c074d14823f2dd80c2fc
```

Вектор получен командой `openssl dgst -sha256 -hmac` над `canonical`; тело в вычислении — одна строка без перевода строки в конце.

### 2.3 Проверка на сайте (порядок важен)

0. Формат до любых обращений к Redis и БД: `x-twomc-key-id` соответствует `^[a-z0-9][a-z0-9-]{1,31}\.[0-9]{1,6}$` (часть до точки — формат `slug`, 2.4); `x-twomc-timestamp` — ровно 10 цифр; `x-twomc-signature` — ровно 64 hex-символа (иначе `401`, чтобы `timingSafeEqual` не получил буферы разной длины); `x-twomc-nonce` — base64url 22–43 символа; любой query-параметр в URL и путь, отличный от списка эндпоинтов (без нормализации и редиректов), — `401`/`400`. Заголовок `Content-Encoding` (кроме `identity`) отклоняется раньше, на уровне парсера тела `/bridge/v1`, до аутентификации: `415 unsupported_encoding`. Префикс `/bridge/v1` парсер сопоставляет без учёта регистра и по пути до `?`.
1. Протокол: незнакомая мажорная версия — `426`.
2. Размер тела не больше лимита (`413`), `Content-Type` JSON. Лимит применяет собственный парсер тела `/bridge/v1` (`BRIDGE_MAX_BODY_BYTES`, по умолчанию 262144): превышение - `413`, неверный JSON или невалидный UTF-8 - `400 invalid_body`, `Content-Encoding` - `415 unsupported_encoding`, чтение тела дольше `BRIDGE_BODY_READ_TIMEOUT_MS` (по умолчанию 10000, 1000-30000) - `408 request_timeout` с `Connection: close`; до проверки подписи тело сырым не сохраняется сверх лимита.
3. `key-id` разбирается; ключ выводится (2.4); неизвестный `serverId`, отозванное или истёкшее поколение — `401`.
4. Время: `abs(now - timestamp) <= 60 с` (окно уже, чем ±5 минут в ADR-0157: серверы синхронизированы по NTP, а нонс всё равно ограничивает повтор). Иначе `401`. При отказе по времени ответ содержит стандартный заголовок `Date`, чтобы плагин мог записать в лог расхождение часов (диагностика без раскрытия деталей проверки).
5. Подпись: `timingSafeEqual` над сырым телом. Пустой или отсутствующий ключ — всегда отказ. Иначе `401`.
6. Нонс: только после успешной подписи `SET bridge:nonce:<key-id>:<nonce> NX EX 180` в Redis; уже есть — `401`. (Подпись проверяется до записи нонса, чтобы неаутентифицированные запросы не засоряли Redis.)
7. Все отказы 1–6 имеют одинаковое тело `{"error":"unauthorized"}` без деталей, причина только в серверном логе без подписи, тела и ключа.
8. Redis недоступен: fail-closed `503` (запрос не принимается), а не пропуск проверки нонса. Окно повтора после сброса Redis без персистентности — до 60 с; поэтому Redis с AOF или явное принятие риска (открытые пункты, раздел 13).
9. Лимиты запросов по `key-id` применяются только ПОСЛЕ успешной подписи (иначе аноним, зная несекретный `key-id`, выбьет лимит чужого ключа). До подписи действуют грубый лимит по IP и счётчик неудачных аутентификаций по IP; guard подписи стоит раньше throttler по `key-id`.

### 2.4 Ключи, ротация

Решение владельца (Q32): ключи серверов — HKDF от мастер-секрета, с ротацией. Ключ на сервер выводится, а не хранится: `ключ_сервера = HKDF-SHA256(BRIDGE_MASTER_SECRET, соль = serverId, info = "twomc-bridge" 0x00 "v1" 0x00 u32be(поколение))`. На сайте в БД хранится только номер поколения. Плюсы: нет секретов в БД. Минус: компрометация мастер-секрета затрагивает все серверы; смягчение — ротация мастера и хранение в хранилище секретов. `BRIDGE_MASTER_SECRET` — 32 байта от криптостойкого генератора в base64url. Для ротации самого мастера в `key-id` допустим необязательный третий компонент (идентификатор мастера), чтобы серверы переезжали по одному. Альтернатива — случайный ключ на сервер, зашифрованный в БД (envelope); требует шифрования-ключа и больше кода.

Выдача ключа (решение владельца, Q32: ключи для серверов создаёт владелец): владелец генерирует `BRIDGE_MASTER_SECRET` (не агент) и сам получает ключ сервера админ-командой/скриптом, затем кладёт его в конфиг плагина (права файла 600). Агент ключи НЕ создаёт и не видит.

Ротация: поколение увеличивается; сайт принимает текущее и предыдущее поколение в течение окна перекрытия (по умолчанию 7 суток), затем предыдущее отклоняется. Плагин переходит на новый ключ без простоя: два ключа в конфиге. Экстренная ротация при подозрении на компрометацию: `previousGenValidTill = now` (старое поколение отклоняется сразу), поколения выше текущего отклоняются всегда. Экстренный отзыв: статус сервера `REVOKED` — все его ключи отклоняются немедленно.

**Уточнения среза 1 (ADR-0182; соль, возможности, регистрация и вывод ключа).** Действуют вместе с текстом выше; при расхождении формулировок побеждает этот абзац.

Единая соль и slug. Соль HKDF везде одна: `BridgeServer.slug`. Термин `serverId` в протоколе (`key-id`, поле конверта, пара `(serverId, eventId)`) всегда означает этот `slug`; отдельного идентификатора нет. Формат slug: `^[a-z0-9][a-z0-9-]{1,31}$` (2-32 символа, начинается с буквы или цифры, точка запрещена, чтобы не ломать разбор `key-id`). Смена slug запрещена: новый slug = новый сервер (новая строка `BridgeServer`, новые ключи, новая дедупликация); старая строка переводится в `REVOKED`. Внешнего ключа на таблицы с `serverSlug` нет (дрейф slug - R116), поэтому смена slug «на месте» недопустима и в БД, и в коде.

Возможности сервера (`capabilities`). `capabilities` равно `NULL`, пустому объекту или пустому массиву - то же, что `{punishments}` (минимум по умолчанию). Неизвестные ключи игнорируются и никогда не расширяют права: действуют только ключи из закрытого списка контракта (`punishments`, `punishments-authoritative`, `player-events`), каждый - только при значении `true`. `punishments-authoritative` и `player-events` включает владелец.

Регистрация и выдача ключа (две отдельные операции).
1. Регистрация строки `BridgeServer` (CLI-скрипт): создаёт строку (slug, `displayName`, поколение 1, `status = ACTIVE`). Мастер-секрет НЕ требуется и не читается. Fail closed: если `NODE_ENV` пустой или не задан, он считается production (как `isProductionLike` в `apps/api/src/config/node-env.ts`), и скрипт отказывает; в production регистрацию запускает только владелец. Скрипт проверяет формат slug и отказывает при существующем slug.
2. Вывод ключа сервера (решение владельца, Q32: ключи для серверов создаёт владелец) - отдельная команда, её запускает ТОЛЬКО владелец; агент её не запускает никогда. Владелец сам генерирует `BRIDGE_MASTER_SECRET`. Ключ выводится только в stdout, только при явном флаге (например `--print-key`), с предупреждением «ключ показан один раз, кладите в конфиг плагина с правами 600»; в логи (Nest Logger, файлы, CI) ключ не попадает никогда. В автотестах используется только синтетическая константа мастер-секрета (заведомо тестовая, не из `.env*` и не из хранилища секретов); боевой мастер-секрет в тестах не используется.

Агент ключи НЕ создаёт и не видит.

### 2.5 Версия протокола и совместимость

- `x-twomc-protocol` и поле `schema: "twomc.bridge.v1"`. `GET /handshake` отвечает `{minProtocol, maxProtocol, serverTime, limits, features}`.
- Совместимые изменения (новые необязательные поля, новые типы событий) версию не повышают. Получатель игнорирует неизвестные необязательные поля в `data` (конверт строгий: новое поле конверта означает v2); неизвестный тип события отклоняет по событию с кодом `unsupported_type` (не повторять).
- Несовместимые изменения — `v2`, новые пути `/bridge/v2`; v1 поддерживается минимум 6 месяцев после выхода v2.

## 3. События

### 3.1 Конверт

Пачка (тело `POST /events`):

```json
{
  "schema": "twomc.bridge.v1",
  "sentAt": "2026-11-17T12:00:00.000Z",
  "events": [
    {
      "eventId": "...",
      "type": "...",
      "serverId": "...",
      "streamId": "...",
      "seq": 1,
      "occurredAt": "...",
      "data": {}
    }
  ]
}
```

| Поле события | Тип                      | Описание                                                                                                         |
| ------------ | ------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `eventId`    | строка 26–64 символа     | глобально уникальный (UUIDv7 или ULID); ключ идемпотентности; повтор того же события использует тот же `eventId` |
| `type`       | строка                   | тип из таблицы ниже                                                                                              |
| `serverId`   | строка `^[a-z0-9][a-z0-9-]{1,31}$` (= `slug`) | обязан совпадать с `serverId` из `x-twomc-key-id`, иначе событие отклоняется `server_mismatch`                   |
| `streamId`   | строка до 64             | идентификатор запуска плагина; меняется при каждом старте                                                        |
| `seq`        | целое > 0                | монотонно растёт внутри `streamId` без пропусков (для обнаружения потерь)                                        |
| `occurredAt` | ISO 8601 UTC с мс        | время факта на сервере                                                                                           |
| `data`       | объект                   | зависит от `type`; объём не более 16 КБ на событие                                                               |

### 3.2 Типы событий v1

| Тип                                     | Когда                                                                                   | Статус                                                                                                                     |
| --------------------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `bridge.hello`                          | старт плагина и после каждой смены ключа                                                | v1                                                                                                                         |
| `punishment.created`                    | выдано наказание                                                                        | v1                                                                                                                         |
| `punishment.updated`                    | изменены причина или срок                                                               | v1                                                                                                                         |
| `punishment.removed`                    | снято                                                                                   | v1                                                                                                                         |
| `punishment.deleted`                    | запись удалена в источнике                                                              | v1                                                                                                                         |
| `player.join`                           | игрок зашёл                                                                             | v1; вход и выход разрешены владельцем (Q32); IP не передаётся никогда; включается конфигурацией (`features.player_events`) |
| `player.quit`                           | игрок вышел                                                                             | так же, как `player.join`                                                                                                  |
| `chat.*`                                | сообщения чата                                                                          | НЕ входит в v1: отдельное решение владельца позже (Q32); тип не резервируется, получатель отвечает `unsupported_type`      |
| `queue.overflow`                        | плагин отбросил события из-за переполнения очереди: `{ "fromSeq", "toSeq", "dropped" }` | v1                                                                                                                         |
| `player.stats.snapshot`                 | периодический срез статистики                                                           | БУДУЩЕЕ (этап 04): получатель отвечает `unsupported_type`                                                                  |
| `inventory.snapshot`, `inventory.delta` | состояние и изменения инвентаря                                                         | БУДУЩЕЕ (этап 10): тот же ответ                                                                                            |

События экономики, донатной валюты, рубинов и их передачи в контракт НЕ входят: это hard gate (решение владельца), типы не резервируются.

`inventory.snapshot` передаётся частями (чанками) по группам слотов: ответ владельца на Q35, правила в разделе 6.1; лимит одного события 16 КБ не повышается. Тип остаётся будущим, номер этапа инвентаря (Q33) не менялся.

Допущение (до ответа владельца, вопрос Q58): значение по умолчанию `features.player_events = false`; включается администратором для сервера. Владелец разрешил передачу входа и выхода (Q32), но включение остаётся явным действием.

### 3.3 Данные событий v1

`punishment.*`: `data` — нормализованное наказание из `docs/stage-02/LITEBANS-INTEGRATION-DESIGN.md`, 3.1, в виде полного состояния (не диффа):

```json
{
  "kind": "BAN",
  "sourceId": "123",
  "subjectUuid": "069a79f4-44e9-4726-a5be-fca90e38aaf5",
  "subjectName": "TestPlayer001",
  "ipBan": false,
  "reason": "Причина без цветовых кодов",
  "executor": { "uuid": null, "name": null, "console": true },
  "startedAt": "2026-11-17T10:00:00.000Z",
  "until": null,
  "status": "ACTIVE",
  "removal": null,
  "scope": "*",
  "origin": "survival",
  "silent": false,
  "template": null
}
```

Для `punishment.deleted` достаточно `kind` и `sourceId`. IP в событиях не передаётся.

`player.join`: `{ "uuid", "name", "sessionId", "onlineMode": true, "proxy": "строка или null" }`. `player.quit`: `{ "uuid", "sessionId", "reason": "disconnect|kick|ban|timeout|unknown", "playedSeconds": 0 }`. IP-адреса и координаты не передаются (решение владельца Q32: вход и выход да, IP нет; расширение — отдельное решение владельца). Чат в контракт не входит.

`bridge.hello`: `{ "pluginVersion", "platform", "platformVersion", "protocol": 1, "punishmentSource": "litebans|none|строка", "punishmentSourceVersion" }`. Поля `platform*` — информационные, сайт их не интерпретирует.

## 4. JSON Schema (draft 2020-12, сокращённо)

Полные файлы схем появятся вместе с реализацией приёмника (`packages/shared`, после разрешения). Обязательные ограничения:

```json
{
  "$id": "twomc.bridge.v1/envelope",
  "type": "object",
  "required": ["schema", "sentAt", "events"],
  "additionalProperties": false,
  "properties": {
    "schema": { "const": "twomc.bridge.v1" },
    "sentAt": { "type": "string", "format": "date-time" },
    "events": {
      "type": "array",
      "minItems": 1,
      "maxItems": 100,
      "items": {
        "type": "object",
        "required": ["eventId", "type", "serverId", "streamId", "seq", "occurredAt", "data"],
        "additionalProperties": false,
        "properties": {
          "eventId": { "type": "string", "minLength": 26, "maxLength": 64 },
          "type": { "type": "string", "maxLength": 48 },
          "serverId": { "type": "string", "pattern": "^[a-z0-9][a-z0-9-]{1,31}$" },
          "streamId": { "type": "string", "maxLength": 64 },
          "seq": { "type": "integer", "minimum": 1 },
          "occurredAt": { "type": "string", "format": "date-time" },
          "data": { "type": "object" }
        }
      }
    }
  }
}
```

Схема `punishment.*`: `kind` — enum `BAN|MUTE|WARN|KICK`; `sourceId` — строка `^[0-9]{1,20}$`; `subjectUuid` — null или UUID с дефисами; `subjectName` — null или строка до 32 без жёсткого набора символов (ники Floodgate/Bedrock содержат точку и пробелы); `reason` — null или строка до 2048; `status` из `data` приёмник ИГНОРИРУЕТ и вычисляет сам по типу события, `removal` и `until` (как в 3.3 дизайна этапа 02); `startedAt` и `until` — `date-time` или null (`until`); `scope`, `origin` — null или строка до 32. Схема `player.*`: `uuid` — UUID; `name` — 1–32 символа (ники Java Edition до 16; для Bedrock требует сверки); `sessionId` — строка до 64.

Получатель отклоняет пачку целиком (`422`) при ошибке конверта и отклоняет отдельное событие (`rejected`, `invalid_data`) при ошибке `data`. Неизвестные поля в `data` игнорируются и считаются в метрике.

## 5. Доставка: идемпотентность, порядок, повторы, лимиты

### 5.1 Ответы

`POST /events` при аутентифицированном запросе и валидном конверте отвечает `200`:

```json
{
  "results": [{ "eventId": "...", "status": "accepted|duplicate|stale|rejected", "code": "..." }],
  "serverTime": "2026-11-17T12:00:01.000Z"
}
```

| status                                                                                                     | Смысл                                                 | Действие плагина                                                                                                                                                  |
| ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `accepted`                                                                                                 | применено                                             | удалить из очереди                                                                                                                                                |
| `duplicate`                                                                                                | `eventId` уже был принят                              | удалить из очереди                                                                                                                                                |
| `stale`                                                                                                    | событие старше уже применённого состояния этой записи | удалить из очереди                                                                                                                                                |
| `rejected` с кодами `invalid_data`, `unsupported_type`, `server_mismatch`, `conflict`, `snapshot_mismatch` | событие неисправимо                                   | удалить, записать в локальный лог и счётчик; для `punishment.*` с `invalid_data` дополнительно предупреждение администратору (наказание не должно теряться молча) |

Код `resync_required` (части снимка инвентаря, 6.1) тоже не повторяется той же частью: плагин удаляет её и строит новый снимок. Код `epoch_out_of_range` (6.1: эпоха вне верхней границы) неисправим и переводит плагин в безопасный режим инвентаря (правило плагина в 6.1), а не в повтор. Код `inventory_unavailable` (6.1, «Построчный отказ по инвентарю») — построчный отказ, когда сборка или применение снимка сейчас невозможны; он НЕ превращается в `503` на всю пачку.

Коды уровня запроса: `401` подпись/время/нонс; `413` слишком большое; `422` невалидный конверт; `426` версия протокола; `429` лимит (заголовок `Retry-After`, секунды); `503` приёмник выключен, перегружен или недоступен Redis. Для `429`, `503`, `5xx` и сетевых ошибок плагин повторяет ТУ ЖЕ пачку (те же `eventId`) с новыми `timestamp` и `nonce`. `401`: повтор не более 3 раз, затем пауза 5 минут и предупреждение администратору.

### 5.2 Идемпотентность

Пара `(serverId, eventId)` уникальна. Для `punishment.*` применение события и запись в журнал дедупликации выполняются в одной транзакции БД; конфликт уникальности — `duplicate`. Для `player.*` (применяются в Redis) дедупликация идёт в Redis с TTL 24 часа, в БД они не пишутся (иначе до 30 млн строк журнала за 7 суток). Повтор того же `eventId` с другим содержимым — `rejected` с кодом `conflict` (хэш содержимого хранится вместе с записью журнала). Журнал `punishment.*` хранится 7 суток; очередь плагина отбрасывает события старше 6 суток, чтобы повтор не пережил журнал.

Исключение для частей снимка инвентаря (`inventory.snapshot`, раздел 6.1): ключи дедупликации `eventId`, метка применённого снимка `done` и метки `mark` (служебные ключи, `svc`) живут `TTLsvc` секунд, а не 24 часа (единое значение для всех трёх; `TTLsvc` ВЫВОДИТСЯ из таймаута сборки `T`, а не фиксировано: `TTLsvc = max(300, ceil10(1,4 × (T + 90)))`, где `T + 90` = отсечка `T + 30` плюс расхождение часов 60 с, а 1,4 — запас около 40%; при `T = 120 с` получается 300 с, при `T = 30 с` — 300 с, при `T = 600 с` — 970 с; приёмник при запуске отказывается стартовать сборку, если `TTLsvc < T + 90`; значения до подтверждения владельцем (Q61, Q62)). Фиксированные 300 с при `T = 600 с` были бы короче самой сборки: окно повтора вернулось бы, поэтому дальше в тексте «300 с» означает значение по умолчанию при `T = 120 с`. Обоснование: повтор части ПОСЛЕ окна `TTLsvc` не создаёт дубль и не портит состояние. Часть, которая создала бы новую сборку, при `capturedAt` старше 150 с получает `resync_required`; более молодая (до 210 с по часам с учётом расхождения до 60 с) на первой части получает `stale` по правилу 6а (сборка не создаётся), потому что дедупликация применённых снимков идёт по `(epoch, rev)` и `snapshotId` в транзакции БД, а не по `eventId`. 24 часа держали бы миллионы ключей вне лимитов памяти (дизайн этапа 04, 4.4). Для значения по умолчанию окно 300 с = отсечка 150 с + расхождение часов 60 с = 210 с, плюс запас около 40%. Учёт `svc` в лимитах сервера ведётся С ЗАПАСОМ, а не по фактическому размеру: каждый служебный ключ засчитывается по верхней оценке 256 байт (с накладными расходами Redis), потому что `MEMORY USAGE` недоступен в атомарном скрипте и в части managed Redis; верхний предел числа ключей `svc` сервера = события в минуту × `TTLsvc` / 60 (при 3000 в минуту и 300 с это 15 000 ключей, около 3,8 МБ; при 970 с — около 12 МБ), предел пересчитывается вместе с `TTLsvc` (допущение до подтверждения владельцем (Q61)).

### 5.3 Порядок

- Плагин отправляет пачки строго по возрастанию `seq` внутри `streamId`, следующая пачка — после ответа на предыдущую.
- Получатель не полагается на строгий порядок (повторы и параллельные пачки возможны). Наказания — полным состоянием. Порядок определяет приёмник, а не часы плагина: `occurredAt` обязан лежать в границах `[сейчас - 7 суток, сейчас + 60 с]` (иначе `rejected invalid_data`, чтобы событие «из далёкого будущего» не сделало все следующие события записи устаревшими). Событие старше уже применённого состояния той же записи по `occurredAt` получает `stale`; при равенстве `occurredAt` побеждает событие, принятое позже (порядок приёма). `eventId` для упорядочивания не используется (его подделка не должна давать преимущество).
- Пропуск `seq` внутри `streamId` допустим только после события `queue.overflow` с соответствующим диапазоном; иначе он фиксируется (метрика, статус сервера) и закрывается ближайшей сверкой (раздел 6).
- Часы сервера: расхождение с сайтом больше 5 с даёт предупреждение в статусе сервера (по `sentAt` и `serverTime`).

### 5.3.1 Исходящая очередь плагина

Диск, ограничение 50 000 событий или 50 МБ; при переполнении первыми отбрасываются `player.*`, затем самые старые `punishment.*` (с записью в лог и счётчиком потерь; потеря закрывается сверкой). Очередь переживает перезапуск; после перезапуска новый `streamId`, `seq` с единицы.

### 5.4 Backpressure и лимиты

| Лимит                          | Значение по умолчанию    | Ответ при превышении    |
| ------------------------------ | ------------------------ | ----------------------- |
| Размер тела                    | 256 КБ                   | `413`                   |
| События в пачке                | 100                      | `422`                   |
| Размер события                 | 16 КБ                    | `rejected invalid_data` |
| Запросы на ключ                | 10 в секунду, всплеск 30 | `429` и `Retry-After`   |
| События на сервер              | 3000 в минуту            | `429`                   |
| Параллельные запросы на сервер | 2                        | `429`                   |

Лимит считается по `key-id` и применяется только после успешной подписи (2.3, п. 9), а не по IP (игровой хост может быть за общим адресом). До подписи действует грубый лимит по IP и счётчик неудачных аутентификаций. Приёмник при задержке применения выше порога (по умолчанию 2 с на пачку) отвечает `429` с `Retry-After`, плагин замедляется; плагин объединяет события в пачки с интервалом не менее 500 мс и сам не превышает лимиты.

### 5.5 Уточнения среза 1 (ADR-0182; имеют приоритет над разделами 5.1, 5.2 и 5.4)

Эти абзацы описывают реализацию среза 1 и при расхождении формулировок побеждают текст выше.

Коды уровня запроса на уровне парсера тела, до аутентификации. Помимо кодов из 5.1: `408` (`request_timeout`) - тело не получено за дедлайн чтения; `415` (`unsupported_encoding`) - заголовок `Content-Encoding` не пуст и не `identity`. Оба кода выдаёт парсер тела ДО проверки подписи; для них действует тот же повтор плагина, что и для `5xx` (та же пачка, новые `timestamp` и `nonce`).

Порядок применения `punishment.*` (уточнение 5.2: запись в журнал и применение НЕ в одной транзакции). (1) `received` - короткая транзакция БД с записью в журнал дедупликации (маркер порядка ставится атомарно); (2) publish источнику наказаний вне транзакции; (3) `applied` - отметка в журнале. Сбой между шагами оставляет `received`; повтор того же события применяется заново (идемпотентно), а не отвечает `duplicate`; конфликт уникальности на завершённой записи (`applied`) - `duplicate`. Для `player.*` порядок и срок дедупликации без изменений (Redis, TTL 24 часа).

Канонизация `payloadHash`. Хешируется только поле `data` события (не весь конверт, не `occurredAt`, не `seq`); сериализация - JSON без пробелов, ключи объектов на всех уровнях в лексикографическом порядке (по кодовым точкам UTF-16/юникода), порядок элементов массивов сохраняется, строки в UTF-8; хэш - SHA-256, результат в hex нижнего регистра (64 символа). Отдельная защита от смены строкового представления чисел (`1` и `1.0`) вне среза; плагин обязан слать стабильные типы. В журнал пишутся только принятые события (`applied`, `duplicate`-ссылка на первую запись); `rejected` не пишутся (R117): повтор невалидного события каждый раз проходит проверки заново и считается в лимит по `key-id` (5.4).

Лимит тела (уточнение 5.4). Размер тела 256 КБ задаётся `BRIDGE_MAX_BODY_BYTES` и проверяется собственным парсером тела `/bridge/v1`: превышение - `413`; нечитаемое, не JSON или невалидное UTF-8 тело - `400 invalid_body`; тело не получено за дедлайн чтения - `408` (`request_timeout`).

## 6. Сверка наказаний (snapshot)

Назначение: закрыть потери, переполнение очереди, удаления и правки задним числом (как слои 2 и 3 из дизайна этапа 02). `POST /punishments/snapshot`: тело `{ "schema", "snapshotId", "kind", "page", "totalPages", "totalItems", "last", "items": [нормализованные наказания, до 500] }`. Плагин при старте и затем раз в 6 часов (настраивается) отправляет все записи типа страницами. Защита от массового «удаления» зеркала: (1) срез принимается только от сервера с возможностью `punishments-authoritative` (в `bridge.hello` `punishmentSource` не `none`); (2) проверяются непрерывность `page` и совпадение числа элементов с `totalItems`; (3) `snapshotId` привязан к `serverId`, одновременно активен один срез на сервер; страницы идемпотентны по `(snapshotId, page)`; (4) если срез пометил бы удалёнными больше 20% активных записей, он НЕ применяется и админ получает предупреждение; (5) незавершённый срез (нет `last` за 10 минут) отбрасывается без изменений. По завершении отсутствующие в срезе записи этого сервера помечаются `DELETED_AT_SOURCE`, отличающиеся обновляются.

### 6.1 Части снимка инвентаря (ответ владельца на Q35)

Решение владельца (Q35, 2026-11-17): делить снимок инвентаря на части (чанки) по группам слотов с общим идентификатором снимка, номером части и числом частей; сайт собирает снимок из частей, применяет только полный комплект и по таймауту отбрасывает неполный; лимит одного события Bridge НЕ поднимается (16 КБ, раздел 5.4); тесты на потерю и повтор частей обязательны. Тип `inventory.snapshot` по-прежнему БУДУЩИЙ (получатель отвечает `unsupported_type`, пока владелец не решит Q33 и не включит возможность `inventory-sync`); номер этапа инвентаря («этап 10», раздел 3.2) этим изменением не менялся: Q33 открыт. Полная схема предмета и слотов — `docs/stage-04/INVENTORY-SITE-DESIGN.md`, раздел 3.2; здесь только транспортные правила частей.

Числовые значения ниже (таймаут 120 с, отсечка 150 с, TTL `done`, `evt` и `mark` `TTLsvc` (по умолчанию 300 с, выводится из таймаута, см. 5.2), верхняя граница `epoch` now + 10 минут и порог тревоги now + 120 с, снимок 32 КБ, 256 сборок и 8 МБ на сервер, 6 снимков в минуту, захват 30 с) — «Допущение до подтверждения владельцем (Q61, Q62)»: это параметры сборки, владелец их не называл; значения настраиваются, реализация не должна считать их окончательными. Везде ниже «300 с» у меток и дедупликации снимков — значение `TTLsvc` по умолчанию (таймаут 120 с); при другом таймауте оно пересчитывается по формуле 5.2, а не остаётся 300 с.

**Что такое снимок и часть.** Снимок — полное состояние одного контейнера игрока (`group`: `main` или `ender`) на момент `capturedAt`. Он ВСЕГДА передаётся как комплект из `parts` событий `inventory.snapshot` (при одном событии `parts = 1`). Каждая часть — самостоятельное событие в пределах обычного лимита 16 КБ; лимиты события, пачки (100) и тела (256 КБ) не меняются. Комплект из 4 частей по 16 КБ помещается в одну пачку, но плагин вправе слать части разными пачками.

**Поля части (в `data`, помимо общих полей схемы 3.2).**

| Поле            | Тип и правила                                                                                                                                                                                                   |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `snapshotId`    | строка, регулярка `^[0-9A-Za-z-]{26,64}$` (UUIDv7 или ULID); проверяется ДО обращения к Redis (иначе `rejected invalid_data`); один на комплект, новый при каждом новом снимке; повтор частей использует тот же |
| `part`          | целое от 1 до `parts`; НУМЕРАЦИЯ С 1 (как `seq`), чтобы 0 не означал «поле не заполнено»                                                                                                                        |
| `parts`         | целое: число частей комплекта, допустимо только значение из закрытого перечня ниже; одинаково во всех частях                                                                                                    |
| `slotGroup`     | метка группы слотов части из закрытого перечня ниже; допустимость для `group` проверяется ДО Redis; в комплекте уникальна                                                                                       |
| `slots`         | слоты только этой группы (схема 3.2); пустая группа — `slots: []`, часть всё равно отправляется (полнота определяется набором частей, а не содержимым)                                                          |
| общие заголовки | `uuid`, `group`, `epoch`, `rev`, `capturedAt`, `playerOnline`, `schemaVersion` повторяются в КАЖДОЙ части и обязаны совпадать (это ядро проверки согласованности)                                               |

**Закрытый перечень раскладок (v1).** Допустимы только такие пары `(group, parts)` и наборы `slotGroup`; любое другое сочетание — `rejected invalid_data` до Redis:

| `group` | `parts` | Набор `slotGroup` (ровно он, по одному на часть)                                                                                            |
| ------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `main`  | 4       | `hotbar` (area `hotbar`, 9 слотов), `storage_a` (area `main`, 0–13), `storage_b` (area `main`, 14–26), `equipment` (`armor` 4, `offhand` 1) |
| `main`  | 1       | `all` (все 41 слот; только если событие помещается в 16 КБ)                                                                                 |
| `ender` | 2       | `ender_a` (0–13), `ender_b` (14–26)                                                                                                         |
| `ender` | 1       | `all` (все 27 слотов; только если событие помещается в 16 КБ)                                                                               |

Число частей не больше числа групп слотов контейнера (для `main` 4, для `ender` 2), поэтому прежний предел 8 частей снижен до 4: при закрытом перечне больше частей быть не может, а свободное деление группы дальше убрано, чтобы набор `slotGroup` был проверяем. Каждый слот обязан лежать в диапазоне своей `slotGroup` (иначе `invalid_data`) и встречается ровно в одной части. Ориентир размера предмета — не более 600 байт JSON (обрезка лора на стороне плагина), группа не более 14 слотов, поэтому часть около 8,4 КБ плюс служебные поля, с запасом до 16 КБ. Плагин ОБЯЗАН проверить размер части перед отправкой; если часть превышает 16 КБ, он усиливает обрезку содержимого предметов (деление группы дальше в v1 запрещено) и не шлёт событие больше лимита.

**Свежесть снимков: единый порядок.** Один порядок во всём разделе: сначала `epoch`, затем `rev`; `capturedAt` в сравнении свежести НЕ участвует и служит только для отсечки просрочки (правило 5).

- Снимок A свежее B, если `A.epoch > B.epoch`, либо эпохи равны и `A.rev > B.rev`. Равные `(epoch, rev)` при разных `snapshotId` у исправного плагина не бывают; побеждает уже применённый (новый получает `stale`), случай считается в метрике.
- Обоснование. `epoch` растёт при каждом перезапуске плагина (после перезапуска `rev` начинается заново), поэтому снимок после перезапуска ВСЕГДА новее, даже если часы хоста ушли назад и его `capturedAt` меньше прежнего; сравнение по `capturedAt` в первую очередь отбросило бы такой снимок как `stale` и потеряло бы актуальное состояние. `capturedAt` берётся с часов плагина и пригоден только для грубой оценки возраста, но не для порядка (как 5.3: порядок определяет приёмник по надёжной величине).
- Формат `epoch` (допущение до уточнения дизайном этапа 04 и Q33): целое, строго растущее между перезапусками; плагин хранит его на диске и берёт максимум из «сохранённый плюс 1» и «время старта в миллисекундах». Если `epoch` потерян (стёрт диск), плагин берёт время старта. Повторные `stale` на снимок новой эпохи фиксируются счётчиком и дают предупреждение администратору (признак отката часов или потери диска); такой снимок не применяется.
- Верхние границы (до Redis и до БД, шаг П0 правила 9; значения до подтверждения владельцем (Q61, Q62)). `epoch` не больше «сейчас по часам приёмника + 10 минут», единицы по формату эпохи (для принятого допущения «миллисекунды» это `now_ms + 600 000`); 10 минут = расхождение часов 60 с (окно подписи, 2.3) плюс запас на хосты без NTP: легитимный `epoch` — это время старта плагина, то есть не позже «сейчас» по часам плагина. `rev` не больше 2 147 483 647 (2^31 - 1, предел `Int` в БД). Нарушение `epoch` — `rejected epoch_out_of_range` (новый неисправимый код, раздел 5.1), нарушение `rev` — `rejected invalid_data`; в обоих случаях без записи в буфер, в БД и в дедупликацию. Причина: без границы одно событие с огромным `epoch` (ошибка плагина, компрометация ключа сервера) навсегда сделало бы все нормальные снимки игрока `stale` (порядок «`epoch`, затем `rev`»), а `rev` выше предела `Int` ломал бы запись. Прежние 7 суток (раунд 2) заменены: окно «отравления» ряда эпохой из будущего было неделей, а исправный плагин, запущенный раньше отравленного значения, оставался бы `stale` до перезапуска. Если формат эпохи изменится (дизайн этапа 04, Q33), границы пересчитываются в её единицах.
- Тревога о скачке эпохи (допущение до подтверждения владельцем (Q61, Q62)). Сайт хранит на каждый сервер `maxSeenEpoch` — наибольшую ПРИНЯТУЮ эпоху (место хранения — Redis с персистентностью либо поле в `bridge_servers`, решается в срезе 1; потеря значения не опасна, оно восстанавливается по приходящим снимкам). Тревога (метрика и статус сервера, предупреждение администратору) поднимается, если принятая эпоха опережает часы приёмника больше чем на 120 с: `epoch - now > 120 с`, либо `maxSeenEpoch` вырос на такое значение вперёд относительно часов. Обоснование порога: исправный плагин ставит эпоху равной времени старта (не позже «сейчас» по его часам), поэтому опережение не превышает расхождение часов, которое подпись уже ограничивает 60 с (2.3, п. 4); 120 с = 60 с плюс запас в 60 с, чтобы дрожание NTP не давало ложных тревог. Сравнение с «приростом относительно прежнего `maxSeenEpoch`» непригодно: между двумя законными эпохами проходит время работы плагина (дни), порог пришлось бы ставить в недели. Зона 120 с … 10 минут принимается с тревогой, выше 10 минут — отказ `epoch_out_of_range` (тоже с тревогой); три тревоги по серверу за час переводят его статус в «ключ под подозрением» и предлагают владельцу ротацию (2.4). Тревога также поднимается, если `stale` повторяется на эпохе, меньшей `maxSeenEpoch`, при том что `maxSeenEpoch` опережает часы больше чем на 120 с (признак отравления ряда).
- Остаточный риск: значение внутри окна 10 минут всё же «забегает вперёд» (ряд игрока получает эпоху из будущего, исправный плагин остаётся `stale` до перезапуска или до сброса). Лечится экстренным сбросом рядов сервера (дизайн этапа 04, 4.5; здесь только дизайн, реализации нет). Порядок, ПОРЯДОК ВАЖЕН: (1) заблокировать сервер или отозвать ключ: статус `REVOKED` в `bridge_servers` и ротация ключа владельцем (2.4); пока шаг не выполнен, чистить нельзя, иначе атакующий тут же запишет эпоху снова; (2) дождаться барьера: транзакций применения и захватов в полёте нет (пауза не меньше TTL захвата 30 с плюс максимальная длительность применения, затем проверка, что для `{serverId}` нет живых ключей `lock` и счётчик активных применений равен нулю; запросы, принятые до блокировки, уже завершены или отклонены); (3) очистить ряды инвентаря сервера в БД, буфер и служебные ключи `bridge:inv:{serverId}:*` и `maxSeenEpoch`; (4) разблокировать (новое поколение ключа). Каждый шаг пишется в аудит. Право, свежая 2FA и причина сброса — открытый пункт к реализации среза 1 (раздел 13). Вариант «без административного сброса» отвергнут в допущении: ожидание новых снимков не лечит отравленный ряд (вопрос владельцу Q62).
- Правило плагина после отклонённой эпохи (`rejected epoch_out_of_range`) и при повторных `stale` на текущей эпохе. Плагин: (а) НЕ повторяет часть вслепую и не пытается «перебить» эпоху: поднять `epoch` выше сохранённого он вправе только при перезапуске (формула выше), никогда по ответу сайта; (б) переходит в безопасный режим инвентаря: снимки и дельты этого сервера не отправляются, `punishment.*`, `player.*` и `bridge.hello` работают как обычно; (в) шлёт alert администратору (консоль и лог, с расхождением часов по `serverTime` и `Date`, без значения ключа) и один раз в час напоминает; (г) повторная синхронизация инвентаря только после подтверждения оператора: консольная команда подтверждения после исправления часов или после экстренного сброса на сайте (она же удаляет локальный сохранённый `epoch`, чтобы следующая эпоха стала временем старта), затем отправляется ОДИН пробный снимок; при повторном отказе плагин возвращается в безопасный режим без автоматических повторов; (д) при `stale` на текущей эпохе три раза подряд для одной группы действует то же правило (б)-(г): признак отравленного ряда, а не повод слать быстрее. Ответы `401` во время блокировки сервера обрабатываются по 5.1 (3 попытки, пауза 5 минут), после разблокировки и смены ключа плагин продолжает работать, но инвентарь возобновляется только по (г).

**Правила сборки на сайте (приёмник).**

1. Применяется ТОЛЬКО полный комплект: присутствуют все номера `1..parts`, набор `slotGroup` равен набору раскладки для `group` (таблица выше), все заголовки совпадают, слоты не пересекаются и лежат в диапазонах своих групп (всего не больше 41 для `main` или 27 для `ender`), собранный снимок проходит ту же строгую схему и санитизацию, что одиночный снимок. До полноты часть ничего не меняет в хранимом состоянии игрока.
2. Идемпотентность двойная: по `(serverId, eventId)` (раздел 5.2) и по `(serverId, snapshotId, part)`. Повтор части с тем же содержимым (по хэшу), пока сборка собирается, — `duplicate`, буфер не меняется. Та же пара `(snapshotId, part)` с другим содержимым — `rejected conflict`, и вся сборка сбрасывается (снимок ненадёжен). Дедупликация по `eventId` для части, которая НЕ завершает комплект, записывается в той же атомарной операции, что и помещение части в буфер (потерянная при сбое часть не превращается в ложный `duplicate`). Для части, которая завершает комплект, запись дедупликации по `eventId` делается ТОЛЬКО после успешного применения (вариант «б»), а повтор завершающей части обрабатывается правилом 7 (вариант «а»): одной дедупликации недостаточно, потому что плагин вправе повторить часть с новым `eventId`.
3. Порядок прихода любой: части могут идти в обратном порядке, перемешиваться с частями других снимков и приходить разными пачками и экземплярами API. Часть не обязана приходить первой, чтобы начать сборку.
4. Несовпадение `parts` или любого общего заголовка между частями одного `snapshotId` — ошибка снимка: `rejected snapshot_mismatch`; сборка сбрасывается, `snapshotId` помечается «отравленным» (метка живёт 300 с, как все метки снимков, см. 5.2; последующие части получают тот же код). Повтор бесполезен: плагин обязан найти ошибку у себя и в следующем цикле построить новый снимок с новым `snapshotId`.
5. Таймаут и отсечка просрочки. Таймаут неполного комплекта: 120 секунд от прихода ПЕРВОЙ части по часам приёмника (`firstSeenAt`, TTL сборки в Redis; абсолютный, не скользящий, чтобы поток частей не удерживал буфер вечно). Значение настраиваемое (допустимо 30–600 с), выбрано как несколько повторов с backoff при `429` и `503` (раздел 5.1) плюс запас, при этом короче периода обычных снимков (по умолчанию 5 минут, но не реже раза в 30 с на игрока и группу). Просроченный комплект отбрасывается целиком без изменения хранимого состояния. Отсечка по `capturedAt` (120 с плюс 30 с на расхождение часов = 150 с) действует ТОЛЬКО для части, которая создала бы НОВУЮ сборку (живой сборки с таким `snapshotId` и меток по нему нет): такая часть с `capturedAt` старше 150 с получает `rejected resync_required` и сборку не создаёт. Части ЖИВОЙ сборки по `capturedAt` не отсекаются: их срок определяет только её таймаут 120 с, поэтому комплект, начатый вовремя, но доставленный с задержками, не теряется из-за расхождения часов. Часть новой сборки с `capturedAt` младше 150 с создаёт сборку, даже если остальные части уже истекли (возобновление: сборка останется неполной и истечёт сама, потеряв только место в квоте). Плагин строит новый снимок с новым `snapshotId`, не чаще раза в 30 с на игрока и группу.
6. Применение и свежесть (единый порядок: `epoch`, затем `rev`). (а) На ПЕРВОЙ части новой сборки приёмник сравнивает `(epoch, rev)` с применённым состоянием `(serverId, игрок, group)` (кэш в Redis, решающая проверка — в транзакции БД): если снимок не свежее, часть получает `stale` и сборка не создаётся. (б) Когда комплект с более свежими `(epoch, rev)` стал полным и применён, он сбрасывает все НЕПОЛНЫЕ сборки той же `(serverId, игрок, group)` с меньшей свежестью (им ставится метка «вытеснен свежим», 300 с); сборка свежее применённой не трогается. (в) Полный комплект, оказавшийся не свежее применённого состояния, не применяется: ответ `stale` на завершающую часть, сборка удаляется, ставится метка `stale` (300 с). Части сброшенных сборок, пришедшие позже, получают `stale`; метка `done` (300 с, правило 7) проверяется первой и даёт `duplicate`, а не `stale`.
7. Атомарность и повтор завершающей части (выбран вариант «а»). Проверка полноты и «захват» применения выполняются одной атомарной операцией в общем хранилище буфера (скрипт Lua или транзакция Redis), чтобы при двух экземплярах API и одновременном приходе последних частей снимок применился ровно один раз. У сборки три состояния: «собирается», «полна, не применена», «применена» (метка `done`, `TTLsvc` (по умолчанию 300 с) вместо 24 часов: единый TTL снимков, 5.2). Захват — ключ с токеном владельца и TTL 30 с. Применение идёт обычной транзакцией БД (дизайн этапа 04, 4.2), которая сама идемпотентна: она хранит `snapshotId`, `epoch`, `rev` применённого состояния, и повторное применение того же `snapshotId` ничего не меняет и возвращает `snapshot_applied`. Алгоритм для любой части (повтор тоже):
   - метка `done` есть — `duplicate`, захват не берётся;
   - сборка «полна, не применена» (в том числе повтор завершающей части под тем же или новым `eventId` с совпадающим хэшем): если захват свободен — взять его и запустить применение; если захват удерживает другой запрос — эта часть получает построчный `rejected inventory_unavailable` (пачка в целом остаётся `200`, остальные события обрабатываются, см. «Построчный отказ по инвентарю»);
   - успех: одной операцией удалить буфер, снять захват, записать метку `done` и дедупликацию `eventId`; ответ `accepted snapshot_applied`;
   - финиш при чужом захвате: если к моменту финиша токен захвата не совпадает (захват истёк за 30 с и его взял другой запрос или ключ исчез), финиш НЕ пишет `done` и `evt`, ничего не удаляет и не сбрасывает чужие сборки; часть получает построчный `rejected inventory_unavailable`; повтор этой части (если он случится) либо увидит `done` (`duplicate`), либо идемпотентно применит тот же `snapshotId` ещё раз и поставит метку. Двойное применение безопасно, потому что транзакция БД идемпотентна по `snapshotId`;
   - финиш при истёкшей сборке: если применение длилось дольше TTL сборки (120 с) и буфер уже исчез, а токен захвата совпал, финиш всё равно пишет `done` и `evt` завершающей части (БД уже содержит результат), удалять нечего; ответ `accepted snapshot_applied`. Сброс «вытесненных свежим» сборок выполняется по индексу игрока, которого уже может не быть: это допустимо, такие сборки истекают сами;
   - сбой БД: часть получает построчный `rejected inventory_unavailable` (не `503` на пачку, иначе задерживаются `punishment.*`), метки `done` и `evt` НЕ пишутся, буфер СОХРАНЯЕТСЯ, захват снимается сразу (проверкой токена), TTL 30 с остаётся страховкой при падении экземпляра; повтор завершающей части (та же пачка) снова берёт захват и запускает применение, а не получает `duplicate`. Если БД записала результат, а метка `done` не записалась, повтор применяет тот же `snapshotId` повторно (идемпотентно) и ставит метку.

   Сбой не бесконечен: сборка истекает по правилу 5 (120 с), и плагин по правилу (в) сам отбрасывает комплект и строит новый снимок.

8. Буфер — общее хранилище с TTL, а не память процесса: Redis (тот же, что для дедупликации `player.*`). Все ключи сервера содержат хэш-тег `{serverId}` (например `bridge:inv:{serverId}:...`), чтобы скрипты Lua с несколькими ключами работали и в Redis Cluster (все ключи сервера в одном слоте); без хэш-тегов контракт предполагает Redis без кластера. Ключи индекса игрока строятся не из открытого UUID, а из внутреннего идентификатора пользователя, который становится известен после проверки привязки (правило 9); UUID в ключах и метриках не хранится. Префикс `serverId` не даёт серверу ни дополнить, ни испортить сборку другого сервера. Недоступен Redis на уровне запроса (проверка нонса) — `503` (раздел 5.1); отказ только операций буфера уже после успешной подписи — построчный `inventory_unavailable`. Потеря буфера при перезапуске Redis равна таймауту: данные не портятся, плагин присылает новый снимок. Политика памяти Redis (M4): при старте приёмника, при КАЖДОМ переподключении к Redis (включая переключение на реплику при failover) и далее периодически читаются `CONFIG GET maxmemory-policy` и `CONFIG GET maxmemory`. Любая политика, кроме `noeviction`, означает, что Redis может молча удалить ключи сборки, `done`, `mark`, `lock` (все они с TTL, поэтому подпадают и под `volatile-*`). Тогда сборка снимков инвентаря fail-closed: каждая часть получает `rejected resync_required` БЕЗ обращения к буферу, срабатывает тревога (метрика и статус сервера); остальные функции Bridge (наказания, `player.*`, подпись и нонсы) работают. Если `CONFIG GET` недоступен (managed Redis, ACL запрещает команду), допущение до Q61: политика и предел считаются непроверенными, буфер fail-closed и тревога «политика не проверена»; владелец может явно подтвердить `noeviction` и ненулевой предел конфигурацией приёмника (имя переменной уточняется при реализации). `maxmemory = 0` (без предела) — ТО ЖЕ поведение, что и вытесняющая политика: буфер fail-closed (`rejected resync_required` без обращения к буферу), тревога «предел памяти не задан»; единственное поведение для обоих случаев, без «предупреждения без отказа»: при `noeviction` без предела общий Redis растёт без границы, и сборки снимков могут довести его до исчерпания памяти хоста, оставив без Redis вход, лимиты и 2FA. Состояние проверяется заново при каждом переподключении, поэтому смена политики или предела на реплике после failover не остаётся незамеченной; окно между проверками — открытый пункт к реализации среза 1 (раздел 13). Нонсы (раздел 2.3) при вытесняющей политике тоже могут исчезнуть раньше срока: это отдельный риск окна повтора (раздел 13), он остаётся в тревоге.
9. Проверка привязки игрока (`unknown_player`, дизайн этапа 04, 4.2) выполняется на ПЕРВОЙ части новой сборки до помещения в буфер: непривязанный UUID не занимает буфер. Устаревшая привязка (L): привязка проверяется на создании сборки, а сборка живёт до 120 с, за это время UUID могут отвязать или привязать к другому пользователю. Поэтому при применении (шаг П5) привязка перечитывается в той же транзакции БД: если `userId` из `meta` сборки больше не соответствует привязке UUID, снимок не применяется, сборка удаляется; ответ `unknown_player` (привязки нет) или `resync_required` (привязан другой пользователь).

**Единый порядок проверок части (один список; нумерация общая с дизайном этапа 04, 4.4).**

- П0, до Redis и БД (чистые проверки): схема и размер части; границы `epoch` и `rev` (6.1, формат `epoch`); `snapshotId`; `parts`; `slotGroup` и его допустимость для `group`; диапазоны слотов. Ошибка — `rejected invalid_data`.
- П1, состояние политики Redis (в памяти, без обращения к Redis): политика не `noeviction`, `maxmemory = 0` или состояние не проверено — `rejected resync_required`, тревога (правило 8).
- П2, зондирование (только чтение): метка `done` — `duplicate`; `evt` — `duplicate`; метки «отравлен» — `snapshot_mismatch`, «вытеснен» — `resync_required`, «сброшен свежим» и `stale` — `stale`. Живая сборка с этим `snapshotId` — переход к П4 (привязка, отсечка и лимиты создания не повторяются).
- П3, только для части, создающей новую сборку: (а) отсечка 150 с по `capturedAt`; (б) привязка UUID; (в) свежесть по правилу 6а.
- П4, атомарный скрипт Redis: ленивая очистка и учёт, повтор проверок П2, при создании — лимит снимков в минуту, лимиты сервера (256 сборок, 8 МБ, служебная память), доля сервера и глобальный потолок, затем сравнение заголовков, запись части, полнота, захват.
- П5, применение вне Redis: транзакция БД с перепроверкой привязки, свежести и идемпотентности по `snapshotId`.
- П6, скрипт финиша: проверка токена захвата, `done`, `evt`, сброс вытесненных (правило 7).

**Лимиты сборки (защита от переполнения буфера).** На сервер: не более 256 одновременно собираемых снимков и не более 8 МБ буфера (Допущение до подтверждения владельцем (Q61)); на `(игрок, group)`: не более 2 одновременных сборок: при создании третьей вытесняется САМАЯ СТАРАЯ по `firstSeenAt` (по часам приёмника, не по `capturedAt`, чтобы плагин не управлял вытеснением), ей ставится метка «вытеснен» (300 с), её поздние части получают `rejected resync_required`. Каждая часть не больше 16 КБ, снимок целиком не больше 32 КБ (Допущение до подтверждения владельцем (Q61); см. дизайн этапа 04, 4.3, 7.3). Помимо потолков сервера действует глобальный потолок буфера с учётом по серверам и справедливой долей на сервер (дизайн этапа 04, 4.4): учёт простаивающего сервера истекает и освобождается, лимит сервера не больше его доли глобального потолка; одному серверу не гарантируется доступ к памяти, уже занятой другими, до её истечения (не более `TTLsvc`, по умолчанию 300 с). При превышении лимита на сервер новая сборка не создаётся: `rejected resync_required` (плагин повторяет снимок позже, не раньше чем через 60 с), существующие сборки не вытесняются. Лимит снимков: не более 6 в минуту на игрока (Допущение до подтверждения владельцем (Q61); дизайн этапа 04) считается ПРИ СОЗДАНИИ сборки, то есть по новому `snapshotId`; части уже существующей сборки этим лимитом не отклоняются и счётчик не увеличивают. Превышение при создании — `rejected resync_required` (повтор не раньше чем через 60 с). Дельты (`inventory.delta`) считаются отдельным счётчиком по событиям (лимит из дизайна этапа 04) и не делят счётчик со снимками. Общие лимиты на сервер (3000 событий в минуту, раздел 5.4) действуют на каждое событие, включая части.

**Построчный отказ по инвентарю (M5).** Сбои, связанные только с инвентарём, не должны останавливать всю пачку: иначе `503` на пачку, где рядом с частью снимка лежит `punishment.created`, задержал бы наказание на время сбоя инвентаря.

- Формат: пачка остаётся `200`, в `results` для затронутого события `{ "eventId": "...", "status": "rejected", "code": "inventory_unavailable" }`; остальные события пачки обрабатываются обычным порядком и получают свои статусы.
- Когда: сбой БД при применении снимка; ошибка, лимит времени (по умолчанию 500 мс на операцию буфера) или недоступность скриптов буфера, если сам запрос уже прошёл подпись и нонс; захват применения удерживает другой запрос; приёмник перегружен именно сборкой инвентаря. `503` на пачку остаётся ТОЛЬКО для ошибок уровня запроса (Redis недоступен для проверки нонса, приёмник выключен, раздел 5.1).
- Код политики и пределов Redis (`resync_required`, правило 8) уже построчный и остаётся таким же; границы `epoch` и `rev`, схема — построчные по определению.
- Порядок обработки внутри пачки: сначала все события, не связанные с инвентарём (`punishment.*`, `player.*`, `queue.overflow`), затем `inventory.*`; задержка или отказ инвентаря не растёт в `429` на пачку (медленное применение инвентаря не считается для порога задержки пачки 5.4).
- Побочные эффекты: отказ `inventory_unavailable` НЕ пишет `evt`, `done` и метки, не сбрасывает сборку и не расходует лимит снимков; буфер сохраняется до своего таймаута, повтор той же части (например, при потерянном ответе) обрабатывается по правилу 7.
- Плагин: часть удаляется из очереди (повторять часть той же пачкой не нужно); комплект считается неотправленным, новый снимок с новым `snapshotId` строится с паузой не менее 60 с, экспоненциальной до 5 минут, с джиттером; пауза действует ТОЛЬКО на снимки и дельты инвентаря, очередь `punishment.*` и `player.*` не замедляется и не ждёт. Рост `inventory_unavailable` выше порога даёт предупреждение в статусе сервера и метрику `bridge_inventory_parts_total{result=unavailable}`.
- Что НЕ блокируется: `punishment.*` никогда не ждут из-за инвентаря: ни ответом `503`, ни `429`, ни паузой плагина; их порядок и идемпотентность (5.2, 5.3) не меняются.

**Метрики (счётчики без содержимого и без UUID игроков).** `bridge_inventory_parts_total{result=buffered|duplicate|stale|conflict|mismatch|resync|invalid|unavailable|epoch}`, `bridge_inventory_snapshots_total{result=applied|expired|superseded|evicted|stale|poisoned|apply_retry|ceiling|policy_blocked|lock_lost}`, `bridge_inventory_assemblies` (gauge, по серверу), `bridge_inventory_buffer_bytes` (gauge), `bridge_inventory_assembly_seconds` (гистограмма времени от первой части до применения). Рост `expired`, `resync` и `apply_retry` выше порога даёт предупреждение в статусе сервера (потеря частей, перегрузка, сбои БД, неверный размер части).

**Правила плагина для частей.** (а) Один `snapshotId` на комплект, все части берутся из ОДНОГО состояния инвентаря на `capturedAt` (иначе предметы могут «раздвоиться» между частями). (б) Повтор части (после `429`, `503`, сетевой ошибки) — с тем же `eventId`, `snapshotId`, `part` и тем же содержимым; часть удаляется из очереди только после `accepted`, `duplicate`, `stale` или `rejected`, но не после `503` уровня запроса; построчный `inventory_unavailable` — отказ (часть удаляется, новый снимок строится с паузой), он не блокирует `punishment.*`. (в) Если с первой отправки части прошло больше таймаута (120 с) или очередь переполнилась и часть отброшена, плагин отбрасывает комплект целиком и строит новый снимок. (г) Неотправленные части снимков НЕ сохраняются в дисковой очереди через перезапуск (раздел 5.3.1): после старта строится свежий снимок с новой `epoch`. (д) Не слать `delta` из эпохи, пока снимок эпохи не подтверждён `snapshot_applied`.

**Тест-векторы для разработчика плагина (текстом).** Игрок `TestPlayer001`, группа `main`, комплект `snapshotId = S1`, `parts = 4` (`hotbar`, `storage_a`, `storage_b`, `equipment`), все заголовки одинаковы.

1. Потеря части: приходят части 1, 2, 4, часть 3 потеряна. Все три получают `accepted` с `part_buffered`; хранимое состояние игрока НЕ меняется; через 120 с сборка отбрасывается; часть 3, пришедшая позже 150 с после `capturedAt` (живой сборки уже нет), получает `rejected resync_required`; плагин сам отбрасывает комплект и строит новый снимок `S2`.
2. Повтор части: часть 2 отправлена дважды (тот же `eventId`), затем ещё раз под новым `eventId` с тем же содержимым. Оба повтора `duplicate`; после прихода остальных частей снимок применяется ровно один раз (в хранимом состоянии нет дублей слотов); повторная отправка части 2 после применения — `duplicate` (метка `done`).
3. Обратный порядок: приходят 4, 3, 2, 1 (в одной пачке или разных). Статусы: `part_buffered` ×3, затем `snapshot_applied` на часть 1; результат тот же, что при порядке 1, 2, 3, 4.
4. Разное `parts`: части 1 и 2 с `parts = 4`, часть 3 с допустимым, но другим `parts = 1` и `slotGroup = all`. Часть 3 — `rejected snapshot_mismatch`; сборка сброшена, ранее принятые части без эффекта; часть 4 того же `snapshotId` тоже `snapshot_mismatch`; состояние игрока не менялось. (Значение `parts` вне закрытого перечня, например 5, отклоняется как `invalid_data` ещё до Redis, см. вектор 12.)
5. Дополнительно: (а) та же часть 2 с другим содержимым — `conflict`, сборка сброшена; (б) неполный `S1` (части 1–2), затем полный `S2` с большими `(epoch, rev)` — `S2` применён, `S1` сброшен, поздняя часть 3 из `S1` получает `stale`; (в) полный `S0` с меньшими `(epoch, rev)`, чем у применённого состояния, — `stale` на завершающую часть, состояние не менялось, повтор той же части — снова `stale`; (г) слот вне диапазона своей `slotGroup`, слот в двух частях или повтор `slotGroup` — `invalid_data`; (д) два экземпляра API получают последние части одновременно — применение одно; (е) 257-я одновременная сборка сервера — `resync_required`, существующие сборки целы.
6. Сбой БД, затем повтор (вариант «а», обязательный тест). Части 1–3 `S1` получили `part_buffered`. Часть 4 завершает комплект, захват взят, транзакция БД падает: часть 4 получает построчный `rejected inventory_unavailable` (пачка `200`, соседние `punishment.*` приняты), состояние игрока не менялось, буфер цел, `evt` и `done` не записаны, захват снят. Плагин по правилу M5 строит новый снимок; а если ответ потерян и ту же часть повторили (тот же `eventId`): часть 4 совпадает по хэшу с буферизованной, метки `done` нет — захват берётся, снимок применяется, ответ `accepted snapshot_applied` (НЕ `duplicate`); состояние изменено ровно один раз. Те же шаги с повтором под НОВЫМ `eventId` дают тот же результат. Вариант: БД записала результат, но метка `done` не записалась — повтор даёт `snapshot_applied` без второго изменения. Вариант: захват удерживает другой запрос — часть получает построчный `rejected inventory_unavailable`, повтор позже применяет снимок или видит `duplicate`, если применение уже завершилось.
7. Возобновление после истечения сборки. `S1`: части 1–2 пришли в момент 0 (`capturedAt` = 0), сборка истекла в 120 с. Часть 3 приходит в 130 с (возраст по `capturedAt` меньше 150 с): создаётся НОВАЯ сборка из одной части, `accepted part_buffered`, состояние игрока не меняется; часть 4 в 135 с — `part_buffered`, комплект неполон (части 1–2 потеряны), через 120 с сборка истекает. Часть, пришедшая в 160 с (возраст больше 150 с, живой сборки нет), — `rejected resync_required`. Отдельно: часть живой сборки, у которой `capturedAt` уже старше 150 с из-за ушедших вперёд часов хоста плагина, НЕ отсекается; её срок определяет только таймаут 120 с.

(б) Полный комплект `S3` с меньшими `(epoch, rev)`, чем применённое состояние: завершающая часть `stale`, повтор любой части `S3` в течение 300 с — снова `stale`, буфер не создаётся.
9. Новая эпоха. Применено состояние `(epoch 5, rev 90)`. Плагин перезапущен: полный комплект `(epoch 6, rev 1)` с `capturedAt` МЕНЬШИМ, чем у применённого (часы хоста ушли назад), применяется (`snapshot_applied`), а не `stale`. Затем запоздавший комплект `(epoch 5, rev 91)` с большим `capturedAt` получает `stale` уже на первой части, сборка не создаётся. Неполный комплект эпохи 5 в буфере при применении эпохи 6 сбрасывается.
10. Счёт лимита снимков. 6 новых `snapshotId` игрока за минуту принимаются со всеми частями (24 части для `main`), 7-й новый `snapshotId` — `rejected resync_required` на первой части; части шести уже созданных сборок не отклоняются лимитом, даже если приходят после 7-го. 6 дельт игрока в той же минуте не расходуют счётчик снимков и наоборот.
11. Вытеснение. У игрока две живые сборки группы `main` (`firstSeenAt` 0 с и 20 с); создаётся третья в 30 с: вытеснена сборка с `firstSeenAt` 0 с, её поздняя часть — `rejected resync_required`; сборка 20 с цела.
12. Проверки до Redis. `snapshotId` из 25 символов или с символом вне `[0-9A-Za-z-]` — `invalid_data`; `slotGroup = ender_a` при `group = main`, `parts = 3` или 5 для `main`, `parts = 4` для `ender` — `invalid_data`; в Redis при этом ничего не создаётся.
13. Границы `epoch` и `rev` (H1, M1). `epoch` = 9007199254740991 или «сейчас + 11 минут» — `rejected epoch_out_of_range`, в Redis и БД ничего не пишется, `maxSeenEpoch` не растёт, прежнее состояние игрока не меняется, а следующий нормальный снимок той же эпохи применяется (не `stale`); `epoch` = «сейчас + 9 минут» проходит проверку границ и принимается С ТРЕВОГОЙ (опережение больше 120 с); `epoch` = «сейчас + 90 с» принимается без отказа, тревога по порогу 120 с не поднимается (допуск расхождения часов); `rev` = 2147483648 — `invalid_data`, `rev` = 2147483647 проходит.
14. Политика Redis (M4). При `maxmemory-policy = allkeys-lru` (или любой, кроме `noeviction`) каждая часть — `rejected resync_required`, обращений к буферу нет, тревога поднята; `player.*`, `punishment.*` в той же пачке принимаются. Тот же результат, если `CONFIG GET` недоступен и владелец не подтвердил `noeviction`. После смены политики на `noeviction` и повторной проверки сборка возобновляется. Тот же результат (fail-closed, тревога «предел памяти не задан») при `noeviction` и `maxmemory = 0`; ненулевой предел на реплике после failover обнаруживается при переподключении, а не только при следующей периодической проверке.
15. Производный TTL (M3). При таймауте 120 с `done`, `evt` и `mark` истекают через `TTLsvc` = 300 с (а не 24 часа); повтор части применённого снимка через 301 с с `capturedAt` старше 150 с — `resync_required`, с более молодым — `stale` на первой части; применение второй раз не происходит. При таймауте 600 с `TTLsvc` = 970 с: повтор части применённого снимка через 301 с и через 900 с по-прежнему `duplicate` (окно повтора не возвращается); конфигурация с `TTLsvc < T + 90` отклоняется при запуске.
16. Финиш (L). Завершающая часть взяла захват, применение длится дольше 30 с, захват перехвачен другим запросом: финиш первого запроса не пишет `done`, часть получает построчный `rejected inventory_unavailable`; повтор даёт `duplicate` или идемпотентное повторное применение. Сборка истекла за время применения при совпавшем токене: `done` записан, ответ `snapshot_applied`. Между созданием сборки и применением UUID отвязан: снимок не применён, `unknown_player`.

17. Построчный отказ (M5). Пачка из `punishment.created` и последней части снимка при падении БД на применении: ответ `200`, `punishment.created` — `accepted`, часть снимка — `rejected inventory_unavailable`, `evt` и `done` не записаны; очередь `punishment.*` плагина не замедляется; новый снимок строится с паузой не менее 60 с. Тот же результат, если захват применения удерживает другой запрос или операция буфера превысила лимит времени. Недоступность Redis до проверки нонса — по-прежнему `503` на запрос.
18. Экстренный сброс и безопасный режим (H1). Ряд игрока отравлен эпохой «сейчас + 8 минут» (принята с тревогой), исправный плагин получает `stale` три раза подряд для группы: плагин переходит в безопасный режим инвентаря, `punishment.*` и `player.*` продолжают идти, alert администратору; эпоху сам не поднимает. Порядок сброса: сервер заблокирован (`REVOKED`, запросы `401`) → барьер (нет живых `lock` и применений) → очистка рядов, буфера и `maxSeenEpoch` → разблокировка с новым ключом; пробный снимок после подтверждения оператора применяется (`snapshot_applied`). Попытка очистки до блокировки или до барьера отклоняется.

## 7. Серверная часть сайта (приёмник)

Новый модуль `bridge` в `apps/api` (реализация после решений владельца, раздел 12):

- `BridgeSignatureGuard`: разделы 2.3–2.4; нужен `rawBody` (через `APP_CREATE_OPTIONS`, как в ADR-0157).
- `BridgeController`: `GET /bridge/v1/handshake`, `POST /bridge/v1/events`, `POST /bridge/v1/punishments/snapshot`. Свой `@Throttle` по `key-id`.
- `BridgeIngestService`: валидация по схемам, дедупликация, диспетчер обработчиков по `type`.
- Обработчики: `punishment.*` в реализацию `PunishmentSource` с `subscribe` (дизайн этапа 02, раздел 10), то есть тот же синхронизатор, зеркало и WebSocket; `player.*` в сервис присутствия (Redis, TTL), в БД на первом шаге ничего не пишет; будущие типы — `unsupported_type`.
- Статус серверов (`lastSeenAt`, версия плагина, расхождение часов, потери `seq`) в админке, доступ по существующим правам.
- Fail-closed: без `BRIDGE_ENABLED=true` и `BRIDGE_MASTER_SECRET` все пути отвечают `503`; никакого тестового режима, обходящего подпись, в продуктовом коде нет.
- Логи: только `key-id`, `eventId`, тип, код результата. Тело, подписи, ключи, нонсы и IP игроков в логи не попадают.

Переменные окружения (только имена): `BRIDGE_ENABLED`, `BRIDGE_MASTER_SECRET` (секрет, не менее 32 байт), `BRIDGE_TIMESTAMP_WINDOW_S` (60), `BRIDGE_MAX_BODY_BYTES` (262144), `BRIDGE_KEY_OVERLAP_DAYS` (7), `BRIDGE_APPLY_LATENCY_LIMIT_MS` (2000), `BRIDGE_BODY_READ_TIMEOUT_MS` (10000, 1000-30000).

Очистка журнала (обязательна, в срезе 1). Механизм - внутрипроцессный планировщик по образцу существующих в `apps/api` (`StorageRetentionScheduler`: `OnModuleInit`/`OnModuleDestroy`, `setTimeout` со следующим запуском, `unref()`, в `NODE_ENV=test` выключен; `punishments.scheduler.ts`, `news.scheduler.ts`). Раз в сутки (например в 04:00, после существующей очистки) выполняется `deleteMany({ where: { receivedAt: { lt: now - RETENTION } } })` пачками (например по 5000 строк, чтобы не держать долгую транзакцию) до исчерпания. Порог хранения RETENTION строго не меньше 7 суток: значение ниже 7 суток недопустимо ни в коде, ни в конфиге (константа с нижней границей, валидация при старте); очередь плагина отбрасывает события старше 6 суток (5.2), поэтому повтор не переживёт журнал. Сбой очистки логируется предупреждением без данных и не валит процесс; метрика/поле возраста самой старой записи (`now - min(receivedAt)`) публикуется, превышение 8 суток - сигнал о неработающей очистке (R119). Индекс `receivedAt` уже есть.

## 8. Симулятор плагина (тестовый инструмент, не боевой код)

Явно: симулятор — ТЕСТОВЫЙ инструмент для разработки и e2e. В продуктовом коде приёмника нет ни моков, ни веток вида «если это симулятор»; приёмник не отличает симулятор от настоящего плагина и проверяет подпись одинаково.

Дизайн (по образцу существующего `apps/api/scripts/minecraft-plugin-sim.ts`):

- Расположение: `apps/api/scripts/bridge-plugin-sim.ts` и сценарии `apps/api/test/fixtures/bridge/*.json`. Не входит в сборку production.
- Запуск только при `NODE_ENV` in {development, test}; иначе завершается с ошибкой. Секрет и адрес берёт из переменных окружения, значения в вывод не печатает.
- Подпись считает общей функцией подписи из модуля `bridge` (тот же код, что у приёмника, без копии логики), а контрактные тесты дополнительно проверяют независимую реализацию на эталонном векторе (2.2).
- Команды: `hello`; `punishment create|update|remove|delete`; `player join|quit`; `scenario <файл>`; `flood <N>`; `snapshot <kind> <файл>`.
- Режимы отказов (для тестов приёмника): неверная подпись; просроченное и «из будущего» время; повтор нонса; повтор пачки с теми же `eventId`; обратный порядок событий; пропуск `seq`; пачка 101 событие; тело больше лимита; чужой `serverId` в событии; будущие типы (`inventory.snapshot`); для частей снимка инвентаря (6.1, Q35): потеря части, повтор части (тот же и новый `eventId`), обратный порядок, разное `parts`, истечение таймаута, переполнение буфера.

## 9. Записка для разработчика плагина

1. Что делает плагин v1: слушает наказания (рекомендуется через LiteBans API, `Events.Listener.entryAdded` и `entryRemoved`, мягкая зависимость; плагин обязан работать и без LiteBans, `punishmentSource: none`), входы и выходы игроков, отправляет пачки на сайт. Ничего не принимает от сайта.
2. Не блокировать главный поток: сеть, диск и запросы к БД LiteBans (в его API запрещены на главном потоке) только в фоне.
3. Подпись: раздел 2.2, сверить свою реализацию с эталонным вектором. Нонс — криптостойкий случайный, на каждый запрос. Время — системное, сервер должен быть синхронизирован по NTP.
4. Очередь на диске (5.3.1), повтор той же пачки с теми же `eventId` с экспоненциальной паузой 1 с до 5 мин с джиттером; уважать `Retry-After`; отправлять следующую пачку только после ответа.
5. `eventId`: UUIDv7 или ULID, создаётся один раз при возникновении события и сохраняется в очереди.
6. Состояние наказания отправлять целиком. `occurredAt` для `punishment.*` — время изменения состояния. Консоль — `executor.console = true`.
7. Данные: ник и UUID в формате с дефисами в нижнем регистре; из причин удалять цветовые коды (`§x`, `&x`, hex-цвета); IP игроков не отправлять; не отправлять ничего сверх контракта.
8. Секрет: только в конфиге с правами 600, не логировать ни ключ, ни подпись, ни нонс, ни тело. При `401` не долбить сайт: 3 попытки, затем пауза 5 минут и сообщение в консоль.
9. При старте: `bridge.hello`, затем полный `snapshot` наказаний (6); далее каждые 6 часов.
10. Версия: слать `x-twomc-protocol: 1`, на `426` останавливаться и сообщать о необходимости обновления.
11. Платформа: UniverseSpigot 1.21.4 (форк Spigot), сборка против стандартного Spigot API `1.21.4-R0.1-SNAPSHOT`, Java не ниже 21 (Q32). Только стандартный Spigot API, без зависимости от внутренностей форка (NMS, расширения форка); поведение на реальном сервере владельца проверять до выпуска, отдельно потоки (асинхронные задачи Bukkit scheduler) и события входа и выхода. Плагин пишется после ответов владельца на открытые вопросы раздела 12.
12. Снимок инвентаря (тип будущий, Q33) передаётся частями с `snapshotId`, `part` (с 1), `parts` и группой слотов; каждая часть не больше 16 КБ, неполный комплект сайт отбрасывает через 120 с (6.1, Q35; значение — допущение до Q61); частей не больше 4, свежесть снимков определяется по `epoch`, затем `rev`; `epoch` не дальше «сейчас + 10 минут» (иначе `epoch_out_of_range`: безопасный режим инвентаря, без повторов вслепую, alert, возобновление только после подтверждения оператора, 6.1); отказ `inventory_unavailable` — построчный, часть удалить и строить новый снимок с паузой, не замедляя `punishment.*`.

## 11. Тест-план приёмника (после решений владельца)

1. Контрактные: эталонный вектор подписи; схемы на валидных и невалидных примерах.
2. Безопасность: неверная подпись, просроченное время, повтор нонса, чужой `serverId`, отозванный сервер, отсутствие секрета (все `401` или `503` без деталей).
3. Идемпотентность: повтор пачки, параллельная отправка одной пачки (одно применение), порядок и `stale`.
4. Лимиты: 413, 422 (101 событие), 429 с `Retry-After`.
5. Сверка: snapshot с потерянным событием, удалением и правкой.
6. Интеграция с этапом 02: те же сценарии синхронизации, что для LiteBans, но через Bridge-источник; приватность публичных событий.
7. Нагрузка: 1000 событий в минуту, задержка применения, память Redis.
8. Части снимка инвентаря (Q35, 6.1; обязательны): потеря части (не применён, по таймауту отброшен), повтор части (без дублей), обратный и перемешанный порядок, разное `parts`, конфликт содержимого, более свежий полный комплект вместо неполного, параллельные последние части на двух экземплярах, переполнение буфера, сбой БД и повтор завершающей части (снимок применён), возобновление после истечения сборки, метка `done` после `stale`, новая эпоха с меньшим `capturedAt`, счёт лимита снимков и дельт, вытеснение самой старой сборки, проверки `snapshotId`/`slotGroup` до Redis (векторы 6.1, 6–12); `epoch` и `rev` вне границ (вектор 13); политика Redis не `noeviction`, `maxmemory = 0` и недоступный `CONFIG GET`, повторная проверка при переподключении (вектор 14); производный TTL `done`, `evt`, `mark` при таймаутах 120 и 600 с (вектор 15); построчный отказ без задержки `punishment.*` (вектор 17); экстренный сброс и безопасный режим плагина (вектор 18); финиш при чужом захвате, истёкшей сборке и отвязке UUID (вектор 16); простаивающий сервер освобождает долю глобального потолка (дизайн этапа 04, раздел 11).

## 12. Решения владельца и открытые вопросы

Решено (Q32, 2026-11-17):

1. Платформа: ядро UniverseSpigot 1.21.4 (Spigot API `1.21.4-R0.1-SNAPSHOT`, Minecraft 1.21.4), Java не ниже 21 (точную версию на хосте владелец уточнит). Плагин под стандартный Spigot API; это форк, поведение проверять на реальном сервере.

3. Мастер-секрет и ключи серверов создаёт владелец; вывод HKDF от мастер-секрета, ротация (раздел 2.4). Агент ключи не создаёт и не видит. Рекомендуемая ротация: раз в 6 месяцев или при подозрении.
4. Миграции `bridge_servers` и `bridge_event_log` (7.1) создаются по Q28 (одноразовая локальная БД, ревью expand/contract, production применяет владелец).
5. Данные игроков: вход и выход передаются, IP не передаётся (никогда); чат вынесен в отдельное решение позже.

Решено (Q35, 2026-11-17): снимок инвентаря делится на части по группам слотов (`snapshotId`, `part` с 1, `parts`); сайт применяет только полный комплект и отбрасывает неполный по таймауту 120 с (допущение до Q61); лимит события 16 КБ не повышается; тесты на потерю и повтор частей обязательны (раздел 6.1). Ревизия 2 (находки ревью): единый TTL `done`, `evt`, `mark`, верхние границы `epoch` и `rev` (2^31 - 1), проверка политики памяти Redis (fail-closed для буфера), единый порядок проверок П0–П6. Ревизия 3 (раунд исправлений 3, допущения до ответов владельца на Q61 и Q62): граница `epoch` сужена с 7 суток до now + 10 минут, `maxSeenEpoch` и тревога при опережении больше 120 с, порядок экстренного сброса и правило плагина после отклонённой эпохи; `maxmemory = 0` — fail-closed, как и вытесняющая политика, проверка при каждом переподключении; TTL служебных ключей `TTLsvc` выводится из таймаута сборки; отказы по инвентарю построчные (`inventory_unavailable`), `punishment.*` не блокируются.

## 13. Независимое security-ревью дизайна (2026-11-17)

Ревью выполнил отдельный read-only security-специалист до коммита. Учтено в тексте: лимит по `key-id` только после подписи и защита от выбивания чужого лимита (2.3, 5.4); границы `occurredAt` и порядок приёма вместо сравнения `eventId` (5.3); защита snapshot от массового «удаления» зеркала (6); канонизация подписи с `key-id`, проверка форматов и длины подписи до `timingSafeEqual`, запрет query и `Content-Encoding` (2.2, 2.3); однозначный `info` HKDF, формат мастер-секрета, экстренная ротация (2.4); дедупликация `player.*` в Redis и журнал только для `punishment.*` (5.2); `subjectName` до 32 символов и игнорирование `status` из `data` (4); `player.*` были выключены по умолчанию в первоначальном дизайне, затем разрешены владельцем без IP (3.2, Q32); `queue.overflow` (3.2, 5.3); угроза компрометации ключа сервера (10).

Остаётся открытым (решение при реализации или владельца):

- Redis с AOF или явное принятие окна повтора до 60 с после его сброса. Дополнение: при политике памяти, отличной от `noeviction`, нонсы тоже могут быть вытеснены раньше срока (окно повтора шире 60 с); проверка политики при старте (правило 8 раздела 6.1) даёт тревогу, но для нонсов защитой остаются окно времени и идемпотентность `eventId`.
- Ограничение возможностей сервера (`capabilities`) и оповещение о всплесках `punishment.created` и `punishment.deleted`: пороги задаст владелец.
- Для событий источника не LiteBans: пометка проверки или задержка публичного показа.
- Приватность `player.*`: вход и выход разрешены (Q32), IP нет; публичный показ статуса «онлайн» по uuid запрещён без отдельного решения. Юридическая оценка 152-ФЗ ведётся владельцем отдельно (Q31) и реализацию не блокирует.
- Ключ зеркала наказаний с учётом нескольких источников: `(source, sourceScope, kind, sourceId)` (см. дизайн этапа 02, раздел 7).

### 13.1 Открытые пункты ревью Q35 (к реализации среза 1 этапа 04)

Отмечены как «к реализации среза 1»: до начала среза не блокируют дизайн, решаются при реализации или ответом владельца (Q61, Q62).

- M2, окно проверки политики Redis при failover. Политика и предел читаются при старте, при каждом переподключении и периодически (правило 8, 6.1); между проверками после переключения на реплику с другой настройкой буфер может работать на вытесняющей политике. Решить в срезе 1: период проверки (кандидат 30 с), дополнительные триггеры (ошибки `READONLY`/`MOVED`, события failover клиента), допустимое окно и тревога при его превышении. К реализации среза 1.
- M6, детали админ-сброса. Допущение Q62: право `inventory.reset_server` только у старшего персонала, СВЕЖАЯ 2FA непосредственно перед действием, причина — выбор из списка плюс комментарий, запись в аудит каждого шага (блокировка, барьер, очистка, разблокировка), защита от повторного запуска. Точное имя права, срок «свежести» 2FA, список причин и поведение при обрыве посреди сброса — к реализации среза 1.
- LOW: порядок П3 и П4 (6.1). Проверки создания (отсечка, привязка, свежесть) стоят до атомарного скрипта, а лимиты и повтор проверок П2 внутри него; гонка между ними безопасна (скрипт повторяет П2), но порядок отказов при одновременном нарушении нескольких условий (например, `stale` и лимит) надо зафиксировать тестом. К реализации среза 1.
- LOW: флуд аудита. Построчные отказы, тревоги скачка эпохи и шаги сброса пишут события в аудит и метрики; нужны дедупликация и лимит записей на сервер в минуту, иначе скомпрометированный ключ заполнит аудит. К реализации среза 1.
- LOW: Redis Cluster. Хэш-тег `{serverId}` (правило 8) делает скрипты одного сервера однослотовыми, но служебные ключи глобального потолка и учёта по серверам лежат в других слотах; в кластере глобальный потолок либо выносится в отдельный экземпляр, либо считается приближённо. К реализации среза 1; пока контракт предполагает Redis без кластера.
- LOW: расхождение ссылок между ветками. Контракт ссылается на разделы дизайна этапа 04 (3.2, 3.4, 4.2–4.5, 7.3, 11), которые живут в другой ветке и могут быть перенумерованы; перед слиянием сверить номера и заменить на ссылки по заголовкам. К реализации среза 1 (до слияния веток).
- Хранение `maxSeenEpoch` (Redis с персистентностью или поле `bridge_servers`): влияет на миграцию, решается в срезе 1 вместе с Q33. Миграции не создаются этим документом.
