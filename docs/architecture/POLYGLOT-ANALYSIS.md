# Полиглот-анализ: где TypeScript достаточно, а где нужен другой язык

Статус: фаза A (анализ, только чтение кода). Дата: 2026-11-23. Источник: промпт владельца 22.
Метод: статический разбор `apps/api/src/modules/*`, `giveaway/`, `infrastructure/`. Замеров нет — все оценки выигрыша экспертные и помечены как гипотезы до фазы B.
Ограничения среды: VDS 6 vCPU / 15 ГБ ОЗУ, лимиты контейнеров (`infrastructure/docker-compose.prod.yml`): postgres 1 ГБ, redis 256 МБ, api 768 МБ, web 768 МБ. Сопровождение: один владелец + агенты.

## 1. Главный вывод

1. Почти весь backend — CRUD над PostgreSQL через Prisma. Узкое место там — БД, индексы и сеть, а не язык. Переписывание CRUD-модулей даст менее 5 % к задержке запроса и добавит второй стек в эксплуатацию. Решение: оставить TypeScript.
2. Реальных CPU-bound участков мало: bcrypt (пул libuv), обработка изображений sharp (уже нативный libvips), HMAC/HKDF (нативный OpenSSL). Нативные части Node уже работают на уровне C/C++, поэтому перенос этих операций на Rust почти ничего не даёт.
3. Единственные кандидаты на отдельный сервис: (а) приём событий Bridge/Giveaway при росте до сотен игровых серверов или сотен событий в секунду, (б) расчёт цен корзины как эксперимент (уже запланирован, промпт 19), (в) аналитика, рейтинги, античит-эвристики на Python как офлайн-задания, а не онлайн-сервис. Сейчас (4–6 серверов, ключ на сервер) нагрузка Bridge — единицы RPS, порог не достигнут.
4. Java уже оправдана там, где нет альтернативы: Minecraft-плагины (`giveaway/plugin`, плагин Bridge) — платформа диктует язык.
5. Порядок: ничего не мигрировать без бенчмарка фазы B и без реальной боли (p95 выше порога или CPU более 60 % устойчиво).

## 3. Кандидаты и оценка выигрыша против цены

Честные оговорки: (1) для запросов «БД, затем JSON» язык определяет единицы процентов задержки; (2) Node держит порядка тысяч RPS простого JSON на ядро, проектная нагрузка — десятки RPS; (3) выигрыш Rust/Java заметен только на CPU-bound чистых функциях и при очень большом числе одновременных соединений.

### 3.1 Расчёт корзины (store/pricing)
- Профиль: чистая арифметика (Decimal) и 3–6 запросов к БД (скидки, промокод, число заказов). Время запроса доминирует БД.
- Rust: выигрыш на CPU-части в разы-десятки, на сквозной задержке малый. Java 21 (виртуальные потоки): ближе к TS по сквозной, выигрыш в стабильности p99.
- Контроль: перед сравнением языков надо проверить вариант «TS с исправленным N+1» (батч скидок вместо `getBulkDiscount` на позицию, `pricing.service.ts:164`): если он даёт почти весь выигрыш, переписывать нечего.
- Цена: новый сервис, дублирование правил скидок (риск расхождения денег), второй образ (оценка: Rust около 10–30 МБ, Java около 150–250 МБ), второй пайплайн сборки, совпадение копейка в копейку.
- Риск: высокий (деньги, два источника правды).
- Решение: оставить TS; эксперимент фазы B даст числа.

### 3.2 Приём событий Bridge/Giveaway
- Профиль: подпись HMAC/HKDF, разбор JSON, запись в Redis/БД. Верхняя граница: 100 событий по 16 КБ на пакет, 256 КБ на тело.
- Rust (axum): меньше памяти на соединение, нет пауз GC; но узкое место — запись в PostgreSQL/Redis.
- Цена: общий секрет и HKDF-вывод ключей в двух стеках, дублирование схемы валидации (`bridge-schema.ts`).
- Решение: оставить TS; быстрые улучшения без смены языка: кэш выведенных ключей, батчевые вставки. Триггер выделения: более 500 событий/с устойчиво или p99 приёма более 500 мс.

### 3.3 WebSocket (chat, DM, notifications)
- Профиль: много долгоживущих соединений, мало CPU. socket.io на одной ноде тянет тысячи соединений в 768 МБ.
- Кандидаты: Go (простая эксплуатация) или Rust (tokio-tungstenite), но теряется экосистема socket.io и протокол клиента.
- Решение: оставить TS; при росте — Redis-адаптер и вторая реплика, а не смена языка.

### 3.4 Обработка изображений (files)
- Профиль: CPU и память (AVIF). sharp уже вызывает libvips (C), Rust-переписывание не ускорит кодирование.
- Улучшение: отдельный процесс/воркер с очередью и лимитом конкуренции (`sharp.concurrency`), сохранить `limitInputPixels`.
- Решение: оставить sharp; вынести в воркер при появлении медиатеки (промпт 19).

### 3.5 Криптография (bcrypt, HMAC, HKDF, TOTP)
- bcrypt — нативный модуль, выполняется в пуле libuv (по умолчанию 4 потока). Является ли это узким местом, не установлено: утверждение «очередь при пике логинов» — гипотеза. Метрика B3: задержка `bcrypt.compare` и пропускная способность логина при 1/50/500 параллельных запросов и `UV_THREADPOOL_SIZE` = 4 / 8 / 16 (одинаковые раунды как в `auth.service.ts`, `bcryptRounds`); смотреть также влияние на event loop (задержка прочих запросов во время логинов). Решение о настройке `UV_THREADPOOL_SIZE` — только по этим числам. Rate-limit на логин уже есть. Rust/argon2 требует миграции формата хэшей, цена выше пользы без замера.
- HMAC/HKDF/TOTP занимают микросекунды (ожидание, измерить в B3). Оставить TS.

### 3.6 Аналитика, статистика, рейтинги, античит-эвристики (Python)
- Это офлайн-задания по расписанию над данными PostgreSQL: сводки, рейтинги, обнаружение аномалий (быстрое повторение действий, подозрительные паттерны входа и выдачи).
- Python (pandas/SQL) уместен как отдельное задание, читающее реплику или копию и пишущее результат в таблицу; не онлайн-путь API.
- Цена: интерпретатор и зависимости на VDS, расписание, доступ к БД только на чтение, ревью приватности (данные игроков, IP).
- Решение: пока SQL-материализации и Redis ZSET; Python — когда появится реальная потребность (например, античит по данным Bridge) и после решения владельца по хранению данных.

### 3.7 LiteBans и игровые серверы
- Синхронизация уже сделана на стороне API с лидер-локом и пакетами. Java оправдана только для кода внутри игрового сервера.
- Решение: оставить; Java — лишь если нужно читать данные плагином на сервере.

### 3.8 Прочие технологии
- SQL-материализации и частичные индексы — самый дешёвый выигрыш для рейтингов и ленты наказаний.
- Redis-структуры: ZSET для рейтингов, HyperLogLog для онлайна, Streams вместо опроса (delivery опрашивает раз в 15 с).
- Go: только как лёгкий WS-/прокси-сервис; задачи, где он явно лучше Rust/TS, в проекте нет, а цена — третий язык.
- Kotlin избыточен рядом с Java-плагинами.
- Составные модули (Rust + Python/PyO3): сценария, где польза перекрывает сложность сборки и отладки, нет. Не рекомендуется.

## 4. Цена полиглота для VDS и команды

- Образы: сейчас node:20-alpine (api/web). Rust-сервис добавляет порядка 10–30 МБ (статическая сборка musl), Java — 150–250 МБ образа и 128–256 МБ ОЗУ JVM минимум. Для VDS 15 ГБ терпимо, но каждый сервис — +1 контейнер в `docker-compose.prod.yml`, health-check, логи, бэкап конфигурации.
- Сборка: Rust и JDK тяжёлые — только на VDS вне часов нагрузки или в CI (правило промпта 19); локально не собирать.
- Безопасность: у каждого стека свой набор зависимостей и CVE-мониторинг; общие секреты (мастер Bridge, HMAC платёжных вебхуков) нельзя тиражировать за пределы доверенной границы.
- Поддержка: один владелец и агенты. Каждый новый язык увеличивает контекст ревью; нужны отдельные лиды и тестовые контракты.
- Контракты: любой вынесенный сервис обязан иметь golden-фикстуры и контрактные тесты, общие с TS-реализацией.
- Порядок миграции для любого кандидата: (1) метрика боли и порог; (2) прототип в `experiments/`; (3) бенчмарк; (4) параллельный запуск (shadow, сравнение ответов); (5) переключение за флагом; (6) TS-код остаётся до команды владельца («ничего не удалять»).

### Методика (общая)
1. Среда: VDS, отдельные контейнеры, одинаковые лимиты CPU (например, 2 vCPU) и памяти (например, 512 МБ); запуск по очереди; стенд не под нагрузкой; `nice`; нагрузчик (k6, oha или wrk) на отдельных ядрах.
2. Данные: одинаковые golden-фикстуры, одинаковая одноразовая копия БД; БД-заглушка для чистого CPU-замера и реальная БД для сквозного.
3. Прогрев 30 с, затем замер не менее 60 с на каждый уровень параллелизма 1 / 50 / 500; 3 повтора, медиана.
4. Метрики: RPS, p50/p95/p99, доля ошибок, CPU %, RSS (пик и средний), холодный старт (до первого 200), размер образа, время сборки.
5. Эквивалентность: ответы совпадают с эталоном копейка в копейку (Decimal); расхождение останавливает замер.
6. Отчёт: `docs/reports/lang-bench-report.md` (общий с промптом 19) с оговорками про БД и сеть.

### Критерий «выигрыш оправдан ценой»
Миграция допустима, только если выполнены все условия:
- сквозной p95 лучше текущего минимум в 2 раза при реальной БД, либо память на тот же RPS меньше минимум в 3 раза;
- прирост нужен реальной нагрузке (текущей или прогнозу на 12 месяцев), а не синтетической;
- добавочная эксплуатация укладывается в бюджет VDS: не более +1 контейнер и +256 МБ ОЗУ на сервис;
- есть общие контрактные тесты, переключение обратимо флагом;
- владелец явно одобрил расходы и сопровождение.

Если сквозной выигрыш менее 30 % — решение «оставить TypeScript».

### Правило решения по приросту (допущение: исходный текст порогов для «средней зоны» не задаёт)
Прирост считается относительно лучшего варианта TS, а не относительно худшего: сравниваем с «TS с исправленным N+1» (контроль), иначе выигрыш от устранения N+1 ошибочно припишется языку.
- Прирост сквозного p95 менее 30 %: решение «оставить TypeScript»; при необходимости внедрить только исправление N+1 в TS.
- От 30 % до 2x: «серая зона». Само по себе переписывание не оправдано. Решаем по остальным условиям критерия: нужна ли прибавка реальной нагрузке (текущей или прогноз на 12 месяцев), укладываемся ли в бюджет VDS (+1 контейнер, +256 МБ), есть ли выигрыш по памяти в 3 раза и более. Если реальная нагрузка далека от порога (проектные десятки RPS) — оставить TypeScript; в отчёт записывается «возможный запас роста». Владельцу выносится вопрос только при наличии реальной боли (p95 выше порога или CPU более 60 % устойчиво).
- 2x и более (и выполнены остальные условия критерия): кандидат на фазу C (сервис рядом, контракт, shadow, флаг, откат на TS).
- Любое решение требует нулевых расхождений на эквивалентности (см. ниже).

### B1 — подробный критерий (числа)
Варианты: (a) текущий TS, (b) TS с исправленным N+1 (контроль: одна выборка скидок на всю корзину вместо вызова `getBulkDiscount` на позицию, `store/pricing.service.ts:164`), (c) Rust, (d) Java 21.
1. Базовая линия — вариант (a): p50/p95/p99 и загрузка CPU контейнера при 1, 50 и 500 одновременных запросах (профили корзины: 3, 10, 50 позиций), 3 повтора, медиана. Все остальные варианты сравниваются с (a) и с (b).
2. Эквивалентность: ноль расхождений на N не менее 1000 сгенерированных корзин (детерминированный seed) и на всех golden-фикстурах, сравнение денег строками Decimal. Любое расхождение останавливает замер.
3. Сквозной замер: одинаковый пул соединений с источником данных (одинаковое число соединений и одинаковая задержка/БД у всех вариантов) и одинаковый объём данных (одна и та же выгрузка правил скидок). Замер «чистой логики» (без источника данных) и сквозной обязательно разделяются в отчёте.
4. Java: прогрев JIT не менее 60 с под нагрузкой до начала замера; фиксированный лимит heap (`-Xmx`, одинаковый в повторах); холодный старт и «горячий» режим отчитываются раздельно.
5. Размер образов — только как оценка (Rust около 10–30 МБ, Java 150–250 МБ, Node 150–200 МБ) до фактической сборки на VDS; в отчёт идёт измеренное значение, помеченное как таковое.
6. Лимиты контейнеров одинаковые (`--cpus`, `--memory`); нагрузчик на отдельных ядрах; запуск по очереди.

### Требования безопасности к прототипам и аналитике
Прототипы (`experiments/lang-bench/`, B1–B6):
- Мастер-секрет Bridge, боевые ключи, токены, пароли и содержимое `.env*` не попадают в образы, переменные окружения контейнеров, фикстуры и логи `experiments/`. Для бенчмарков используются синтетические ключи, сгенерированные на раннере на один запуск и удаляемые вместе с контейнером.
- В B2/B3 Rust-приём обязан совпадать с TS: HKDF-вывод ключа, подпись, окно nonce и защита от повторов эквивалентны (общие тестовые векторы, расхождение = блокирующий дефект); сравнение подписей — константное по времени; ошибка проверки не раскрывает причину.
- Персональные данные (IP-адреса, ники, контакты) не попадают в фикстуры, генераторы, отчёты и скриншоты; только синтетические идентификаторы.
- Образы без шелла и лишних утилит там, где это возможно; запуск не от root; без публикации портов наружу на раннере (своя docker-сеть).

Python-аналитика (если появится, фаза C):
- Только псевдонимизация: вместо ников и IP — устойчивые хэши с солью, которая хранится вне репозитория; соль у владельца.
- Срок хранения производных данных ограничен и записан (допущение: не более 90 дней для сырых выборок, дольше только агрегаты); выгрузки удаляются по расписанию.
- Доступ к БД только на чтение (отдельная роль без права записи), предпочтительно к реплике или копии; результаты пишутся в отдельную таблицу.
- Решение Q31: IP-адреса и контактные данные никогда не публикуются; в публичных рейтингах и статистике — только агрегаты и публичные ники в рамках приватности профиля.
- Античит-выводы — подсказка для модератора, а не автоматическое наказание.
