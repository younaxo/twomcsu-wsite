Статус: проект (ADR-0168, Proposed). Дата: 2026-11-17. Только документ: код, миграции, Prisma-схема, ключи, зависимости и Docker не затрагивались. Реализация заблокирована решениями владельца (раздел 13).

Связанные документы: `docs/stage-03/BRIDGE-CONTRACT.md` (ADR-0167), `docs/stage-02/LITEBANS-INTEGRATION-DESIGN.md` (ADR-0166), `docs/donations/REQUIREMENTS.md` (hard gate), `docs/decisions/OWNER-ECONOMY-AND-CONTESTS.md` (hard gate, ветка `docs/owner-decisions-2026-11`).

## 1. Цель, границы, статус

Цель: игрок видит на сайте свой инвентарь Minecraft (основной, броня, вторая рука, Ender Chest) с предметами, количеством, зачарованиями и временем обновления; решает, показывать ли его другим; персонал смотрит чужой только по отдельному праву с аудитом.

В границах документа: схема данных Bridge для инвентаря (предложение к контракту v1.x), хранение, API сайта, приватность и права, безопасность, изображения предметов, UI-состояния, тест-план, срезы и вопросы владельцу.

Вне границ (hard gate, только упоминание): правила и уровни Donation Privileges, экономика, платежи, рубины, магазин, мини-игры, розыгрыши. Раздел 10 описывает Site Cosmetics Inventory только как границы.

Не делается: выдача и изъятие предметов с сайта (команды сайт→сервер запрещены в v1), показ вложенного содержимого контейнеров, история изменений инвентаря по умолчанию, карта и координаты.

## 3. Данные из Bridge

Предложение к контракту v1.x: два новых типа события, оформляются отдельной ревизией `BRIDGE-CONTRACT.md` после решения Q32 и Q33. Сам контракт этим документом не меняется. Общие правила (подпись, `eventId`, `serverId`, `streamId`, `seq`, лимиты 100 событий, 256 КБ тело, 16 КБ событие) — из Bridge 3, 5. Возможность сервера `inventory-sync` объявляется в `bridge.hello` (`capabilities`, Bridge 7.1); без неё получатель отвечает `unsupported_type`.

### 3.1 Что и когда отправляет плагин

| Событие              | Когда                                                                                                 | Содержимое                                                     |
| -------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `inventory.snapshot` | вход игрока; выход; раз в N минут для онлайн-игрока при изменении (по умолчанию 5); по запросу сверки | полное состояние ОДНОГО контейнера-группы (`main` или `ender`) |
| `inventory.delta`    | изменение между снимками, не чаще раза в 5 с на игрока (слияние изменений)                            | изменённые слоты относительно `rev`                            |

Группы: `main` — основной инвентарь (слоты 0–35), броня (4), вторая рука (1), итого 41 слот; `ender` — Ender Chest (27 слотов). Отдельные события нужны, чтобы каждое укладывалось в 16 КБ и чтобы Ender Chest можно было не отправлять вовсе (его включает владелец сервера настройкой плагина).

Допущение: версии игры ниже 1.20.5 и разные форматы компонентов предметов — забота плагина; сайт видит только нормализованный JSON из 3.2. Размер стека и названия зачарований приходят как есть, сайт их не пересчитывает.

### 3.2 Схема `inventory.snapshot` (поле `data`)

```json
{
  "uuid": "069a79f4-44e9-4726-a5be-fca90e38aaf5",
  "group": "main",
  "epoch": "01JC...",
  "rev": 1,
  "capturedAt": "2026-11-17T12:00:00.000Z",
  "playerOnline": true,
  "schemaVersion": 1,
  "slots": [
    {
      "area": "hotbar",
      "slot": 0,
      "item": {
        "id": "minecraft:diamond_sword",
        "count": 1,
        "damage": 12,
        "maxDamage": 1561,
        "enchants": [{ "id": "minecraft:sharpness", "level": 5 }],
        "storedEnchants": [],
        "name": [{ "text": "Меч", "color": "#F26A1B", "italic": false }],
        "lore": [[{ "text": "Строка лора" }]],
        "customModelData": null,
        "itemsAdderId": null,
        "unbreakable": false,
        "dyeColor": null,
        "potion": null,
        "containerItemCount": null
      }
    }
  ]
}
```

| Поле                  | Тип и ограничения                                                                                                                                       |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `uuid`                | UUID игрока; сайт принимает только UUID, привязанные в `MinecraftAccount` (раздел 7.5)                                                                  |
| `group`               | `main` или `ender`                                                                                                                                      |
| `epoch`               | строка 26–64, идентификатор «эпохи» снимка; `delta` применима только к своей эпохе                                                                      |
| `rev`                 | целое >= 1, растёт на 1 с каждой дельтой внутри эпохи; у снимка — начальное значение                                                                    |
| `capturedAt`          | ISO 8601 UTC; границы как у `occurredAt` (Bridge 5.3): не старше 7 суток и не позже сейчас + 60 с                                                       |
| `playerOnline`        | игрок в сети в момент снимка; для снимка при выходе — `false`. Признак «offline» на сайте берётся отсюда (события `player.*` выключены, Bridge 3.2)     |
| `schemaVersion`       | `1`                                                                                                                                                     |
| `slots`               | массив, до 41 (`main`) или 27 (`ender`); пустые слоты не передаются; `area`: `hotbar`, `main`, `armor`, `offhand`, `ender`; `slot` — индекс внутри area |
| `item.id`             | `^[a-z0-9_.-]+:[a-z0-9_./-]+$`, до 64 символов                                                                                                          |
| `item.count`          | целое 1–99                                                                                                                                              |
| `damage`, `maxDamage` | целые >= 0, до 100000, либо `null`                                                                                                                      |
| `enchants`            | до 32 пар `{id, level}`, `level` 1–255; `storedEnchants` — то же для книг                                                                               |
| `name`, `lore`        | массивы «прогонов» текста (3.3); `name` до 16 прогонов, `lore` до 20 строк по 16 прогонов, суммарно до 2000 символов на предмет                         |
| `customModelData`     | целое 0–2147483647 или `null`                                                                                                                           |
| `itemsAdderId`        | `^[a-z0-9_.-]+:[a-z0-9_./-]+$`, до 96 символов, или `null`; если задан, сайт показывает иконку по нему, а `id` — запасной вариант (раздел 8)            |
| `dyeColor`            | целое 0–16777215 или `null`; `potion` — строка id или `null`                                                                                            |
| `containerItemCount`  | для шалкеров, мешков и подобных: число непустых вложенных предметов (0–64) или `null`. Вложенное содержимое НЕ передаётся (v1)                          |

Не передаются и не принимаются: сырой NBT и компоненты целиком, текст книг, владелец головы и любые UUID/ники внутри предмета, координаты, ссылки `clickEvent`/`hoverEvent`, `selector`, `nbt`, `translate`/`keybind` с подстановкой. Неизвестное поле — `rejected invalid_data` (строгая схема, `additionalProperties: false`).

### 3.3 Текст предметов («прогоны»)

Плагин сам превращает text component в плоский массив прогонов `{ "text", "color"?, "bold"?, "italic"?, "underlined"?, "strikethrough"?, "obfuscated"? }`. `color` — `#RRGGBB` или одно из 16 имён. Сайт повторно проверяет: длина `text` до 256, управляющие символы и символы направления письма (U+202A–U+202E, U+2066–U+2069) вырезаются, цвет только по шаблону, остальное отбрасывается. Классические коды `§` плагин убирает до отправки; сайт тоже.

### 3.4 Схема `inventory.delta`

```json
{
  "uuid": "069a79f4-44e9-4726-a5be-fca90e38aaf5",
  "group": "main",
  "epoch": "01JC...",
  "baseRev": 1,
  "rev": 2,
  "capturedAt": "2026-11-17T12:00:07.000Z",
  "playerOnline": true,
  "changes": [{ "area": "hotbar", "slot": 0, "item": null }]
}
```

`changes` — до 41 записей; `item: null` — слот опустел; иначе предмет по схеме 3.2. Применение: только если `epoch` и `baseRev` совпадают с сохранёнными (раздел 4.2). Иначе получатель отвечает `rejected` с кодом `resync_required` (новый код, Bridge 5.1 перечисляет только существующие) и плагин присылает полный снимок. Если плагин не поддерживает дельты, достаточно снимков; дельты — оптимизация трафика (раздел 12, срез 4), а не обязательное требование.

### 3.5 Идемпотентность, порядок, размер

- Ключ дедупликации — `(serverId, eventId)` из Bridge 5.2. Для `inventory.*` журнал в БД НЕ ведётся (как для `player.*`): дедупликация в Redis с TTL 24 часа. Повтор того же `eventId` безвреден: снимок — полное состояние, дельта защищена `baseRev`.
- Порядок: снимок побеждает, если его `capturedAt` больше сохранённого (при равенстве — принятый позже); старее — `stale`. Дельта применяется строго по `baseRev`; пропуск ревизии — `resync_required`. Порядок задаёт приёмник, часы плагина ограничены окном 5.3. [уточнено ADR-0179 п.10: порядок по epoch, затем rev; capturedAt не участвует]
- Размер: событие до 16 КБ (Bridge 5.4); верхняя оценка `main` — 41 предмет; предмет с полным лором и зачарованиями может быть около 1 КБ, поэтому плагин при превышении делит `main` на несколько снимков с одинаковой `epoch` и полем `part`. Это усложнение отнесено к вопросу Q35 (рекомендация: лимит 600 байт на предмет и обрезка лора на стороне плагина без `part`).
- Части снимка (уточнено ADR-0179, пп. 9-10; риск R101; поля определены по коду: сравнение заголовка в `redis-inventory-assembly.store.ts`, сборка в `inventory-assembler.service.ts`): все части одного `snapshotId` несут одинаковые `parts`, `group`, `epoch`, `rev`, `capturedAt`, `playerOnline` и `uuid` игрока (сервер сравнивает его хэш). Различаются только `part` и `slotGroup`; `slotGroup` в заголовок не входит, он проверяется отдельно (пустая часть с иным `slotGroup` даёт `slot_group_differs`). Расхождение любого поля заголовка отклоняет весь снимок: `snapshot_mismatch`, причина `header`, `snapshotId` помечается испорченным.
- Частота: не более 1 снимка на игрока и группу за 30 с (плагин) и 6 событий в минуту на игрока (приёмник, ответ `429` по Bridge 5.4); суммарно действуют лимиты на сервер (3000 событий в минуту).

## 4. Хранение

Только текст; миграции агентам запрещены (Q28 (б)), реализация после решения владельца.

### 4.1 Модели (эскиз Prisma)

```prisma
model PlayerInventory {
  id           String   @id @default(cuid())
  userId       String
  serverSlug   String   @db.VarChar(32)
  /// main | ender
  grp          String   @db.VarChar(8)
  epoch        String   @db.VarChar(64)
  rev          Int
  /// Нормализованный JSON слотов (раздел 3.2), без сырого NBT; до 24 КБ.
  slots        Json
  slotCount    Int
  /// SHA-256 от канонического JSON слотов (дедупликация, ETag).
  contentHash  String   @db.VarChar(64)
  capturedAt   DateTime
  /// Последнее подтверждение (в том числе без изменений).
  lastSeenAt   DateTime
  playerOnline Boolean  @default(false)
  schemaVersion Int     @default(1)
  updatedAt    DateTime @updatedAt

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([userId, serverSlug, grp])
  @@index([lastSeenAt])
  @@map("player_inventories")
}

model InventoryPrivacy {
  userId          String   @id
  /// Основной инвентарь, броня и вторая рука видны другим игрокам.
  inventoryPublic Boolean  @default(false)
  /// Ender Chest виден другим; имеет смысл только при inventoryPublic.
  enderPublic     Boolean  @default(false)
  updatedAt       DateTime @updatedAt

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@map("inventory_privacy")
}
```

Решения:

- Один ряд на `(пользователь, сервер, группа)`: хранится только последнее состояние. Каскадное удаление с пользователем (`onDelete: Cascade`, как у `MinecraftAccount`, `schema.prisma:542`) покрывает удаление аккаунта (152-ФЗ).
- UUID в таблице не хранится: связь через `userId` и `MinecraftAccount`. При отвязке Minecraft-аккаунта строки `PlayerInventory` пользователя удаляются в той же транзакции (риск: путь отвязки требует сверки).
- `InventoryPrivacy` вынесена из `User`, чтобы не расширять большую модель и чтобы точка расширения доната (раздел 6.4) не затрагивала `User`. Отсутствие строки = «приватно».
- Нормализованный JSON, а не таблица по слотам: чтение всегда целиком, предметов до 68, запросов по предметам («у кого есть алмазный меч») не требуется и не планируется (это поисковая слежка за игроками).

### 4.2 Применение события (транзакция)

1. Проверка подписи и лимитов (Bridge 2.3) уже выполнена guard-ом.
2. Схема по 3.2/3.4, строгая; затем санитизация текста (3.3).
3. `uuid` → `MinecraftAccount` → `userId`; нет привязки — `rejected` с кодом `unknown_player` (неисправимо, плагин не повторяет; метрика счётчика, без записи в БД).
4. `serverSlug` берётся из `key-id`, не из тела (Bridge 2.3). Сервер без возможности `inventory-sync` — `unsupported_type`.
5. Транзакция `SERIALIZABLE` либо `SELECT ... FOR UPDATE` по ряду `(userId, serverSlug, grp)`: снимок — сравнить `capturedAt`; дельта — сверить `epoch` и `baseRev`; применить; пересчитать `contentHash`.
6. Если `contentHash` не изменился, обновляются только `lastSeenAt`, `playerOnline` и `capturedAt` (одно маленькое UPDATE; содержимое JSON не перезаписывается).

SQL-эскиз (только текст) проверки и применения снимка:

```sql
-- в транзакции, $1 userId, $2 serverSlug, $3 grp
SELECT epoch, rev, "contentHash", "capturedAt"
  FROM player_inventories
 WHERE "userId" = $1 AND "serverSlug" = $2 AND grp = $3
 FOR UPDATE;

INSERT INTO player_inventories
  ("userId", "serverSlug", grp, epoch, rev, slots, "slotCount", "contentHash",
   "capturedAt", "lastSeenAt", "playerOnline", "schemaVersion")
VALUES ($1, $2, $3, $4, $5, $6, $7, $8, $9, now(), $10, 1)
ON CONFLICT ("userId", "serverSlug", grp) DO UPDATE
   SET epoch = EXCLUDED.epoch, rev = EXCLUDED.rev, slots = EXCLUDED.slots,
       "slotCount" = EXCLUDED."slotCount", "contentHash" = EXCLUDED."contentHash",
       "capturedAt" = EXCLUDED."capturedAt", "lastSeenAt" = now(),
       "playerOnline" = EXCLUDED."playerOnline"
 WHERE player_inventories."capturedAt" < EXCLUDED."capturedAt";
```

(`id` и `updatedAt` заполняет Prisma; в реальной реализации вместо сырого SQL предпочтителен `prisma.$transaction` с тем же условием.)

### 4.3 Срок хранения и объём

- Последнее состояние хранится, пока привязан аккаунт; очистка строк, не обновлявшихся более 90 дней (`lastSeenAt`), задание планировщика (значение предлагается, подтверждает владелец, Q36).
- История изменений по умолчанию НЕ хранится: объём (до 68 предметов × частота снимков) и приватность. Если история нужна (расследования краж персоналом), отдельный вопрос Q36: рекомендация — не вводить в первом релизе.
- Оценка объёма: ряд до ~24 КБ JSON, два ряда на игрока и сервер; при 5 000 привязанных игроков и 2 серверах — порядка сотен МБ в худшем случае, фактически ниже в разы (разреженные слоты); оценка требует сверки на реальных данных.
- Сопоставление `serverSlug` Bridge (`bridge_servers.slug`, `BRIDGE-CONTRACT.md:285`) и `Server.slug` (`schema.prisma:1608`): отдельное поле связи не вводится на первом шаге; в API отдаётся `displayName` из `bridge_servers`. Требует сверки (Q32).

## 5. API сайта

Все пути под существующим префиксом API сайта, точный префикс и версия требуют сверки. Ответы строятся из явного белого списка полей (DTO), а не из строки БД.

| Метод и путь                           | Кто                                  | Назначение                                                           |
| -------------------------------------- | ------------------------------------ | -------------------------------------------------------------------- |
| `GET /inventory/me`                    | владелец (вошёл)                     | свой основной инвентарь по серверам: `?server=slug`                  |
| `GET /inventory/me/ender`              | владелец                             | свой Ender Chest                                                     |
| `GET /inventory/me/privacy`            | владелец                             | настройки `inventoryPublic`, `enderPublic`                           |
| `PATCH /inventory/me/privacy`          | владелец                             | изменить настройки                                                   |
| `GET /users/:username/inventory`       | любой, по правилам 6.2               | чужой основной инвентарь (по нику)                                   |
| `GET /users/:username/inventory/ender` | любой, по правилам 6.2               | чужой Ender Chest                                                    |
| `GET /admin/inventory/:userId`         | персонал: `inventory.view_any` + 2FA | основной инвентарь любого пользователя (`?group=main`)               |
| `GET /admin/inventory/:userId/ender`   | персонал: `inventory.view_any` + 2FA | Ender Chest; отдельное право `inventory.view_ender_any` (раздел 6.3) |

Решения:

- Основной инвентарь и Ender Chest — разные маршруты и разные фильтры на сервере. Ender Chest никогда не попадает в ответ основного, даже скрытым полем: «скрыто в интерфейсе» не считается защитой.
- Администраторский доступ — отдельные маршруты по `userId`, а не флаг в публичных: публичный маршрут не содержит «обходов», его нельзя заставить отдать больше параметрами запроса.
- Параметры: `server` — только `^[a-z0-9-]{1,32}$` и только из известных серверов с возможностью `inventory-sync`, иначе `422`; других параметров нет (ни `fields`, ни `include`).
- В ответе для не-владельца нет `userId`, UUID, `lastSeenAt`, `epoch`, `rev`, `contentHash`. Владельцу и персоналу UUID не нужен тоже: аватар строится по нику (`skins.controller.ts:17`).

Форма ответа (для всех групп):

```json
{
  "server": { "slug": "survival", "name": "Выживание" },
  "group": "main",
  "state": "ok",
  "capturedAt": "2026-11-17T12:00:00.000Z",
  "playerOnline": false,
  "isFresh": true,
  "slots": [{ "area": "hotbar", "slot": 0, "item": { "id": "minecraft:diamond_sword" } }],
  "viewer": { "relation": "owner" }
}
```

`state`: `ok` или `no_data` (привязка есть, снимка нет). `isFresh` = (сейчас − `capturedAt`) < порога (по умолчанию 15 минут для `playerOnline=true`; для offline — всегда `true`, время показывается как есть). Состояния «нет привязки» и «приватно» — коды ответа ниже.

### 5.1 Коды ответов

| Код   | Когда                                                                                                         | Тело `code`                                      |
| ----- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `200` | данные или `no_data`                                                                                          | —                                                |
| `304` | `If-None-Match` совпал (раздел 5.3)                                                                           | —                                                |
| `401` | `/me` и `/admin` без сессии                                                                                   | `unauthenticated`                                |
| `403` | профиль виден, привязка есть, но инвентарь приватен; нет права `inventory.view_any`; админ без 2FA (ADR-0156) | `inventory_private`, `forbidden`, `2fa_required` |
| `404` | пользователь не найден, профиль не виден зрителю (`NOBODY`, блокировка), нет привязки Minecraft               | `not_found` (одинаковое тело)                    |
| `422` | неверный `server` или `userId`                                                                                | `invalid_param`                                  |
| `429` | лимит (5.2)                                                                                                   | `rate_limited`, заголовок `Retry-After`          |
| `503` | Bridge выключен (`BRIDGE_ENABLED` не задан, Bridge 7), для функции нет возможностей ни у одного сервера       | `inventory_unavailable`                          |

`404` для «не виден профиль» и «нет привязки» одинаков по телу и времени ответа, чтобы по нему нельзя было перебирать, у кого есть привязка. `403 inventory_private` отдаётся только когда зритель вправе увидеть сам профиль и ник (иначе факт привязки не раскрывается больше, чем уже раскрывает профиль, `profiles.service.ts:221`).

### 5.2 Защита от IDOR, прямых запросов и перебора

- Идентификатор субъекта берётся только из сессии (`/me`), из ника в пути, разрешаемого к `userId` на сервере, или из `userId` админ-маршрута под правом. Нигде нет параметра «чей» вместе с «доверием клиенту».
- Решение о доступе принимает ОДНА функция `canViewInventory(viewer, target, group)` (раздел 6.2), вызываемая в каждом обработчике ДО чтения `PlayerInventory`; покрыта тестами на каждую комбинацию (раздел 11). Прямой запрос к Ender Chest или к чужому `userId` без права получает те же `403/404`, что и из интерфейса, потому что интерфейс ничего не решает.
- Нет эндпоинтов списка, поиска по предметам и «кто онлайн с предметом»; нет массовых выдач (`GET /inventory?user=a,b,c`).
- Лимиты (шаблон `@Throttle`, `minecraft-link.controller.ts:26`): `/me*` — 60 запросов в минуту на пользователя; чужой инвентарь — 30 в минуту на зрителя и 10 различных целей в минуту (перебор ников); без входа чужой инвентарь доступен только если профиль `EVERYONE` и инвентарь публичен, лимит — по IP (учитывая `TRUST_PROXY` (`apps/api/src/config/env.validation.ts`) и подсеть /64 для IPv6 (ADR-0163); точное применение требует сверки), 20 в минуту; админ — 30 в минуту. Лимит повторной смены приватности — 10 в минуту.
- `Cache-Control: private, no-cache` и `ETag`, `Vary: Cookie`; публичного (CDN или общего) кэша нет: приватность меняется мгновенно и не должна отдаваться из чужого кэша.

### 5.3 Кэш и ETag

`ETag = hash(contentHash, capturedAt, playerOnline, версия настроек приватности зрителя)`. Проверка доступа выполняется ДО сравнения `If-None-Match` (иначе `304` стал бы оракулом приватности). Кэша на стороне сервера (Redis) не вводится на первом шаге: чтение по уникальному ключу `(userId, serverSlug, grp)` дёшево. Фронтенд: опрос раз в 30 с, пока вкладка видима и `playerOnline=true`; после скрытия вкладки опрос остановлен. Push по WebSocket — отдельное решение (у Socket.IO сайта нет Redis-адаптера, `BRIDGE-CONTRACT.md:20`).

## 6. Приватность и права

### 6.1 Базовая модель (допущение)

- Владелец всегда видит свой инвентарь и Ender Chest.
- Выбор «публично» или «приватно» для основного инвентаря; по умолчанию приватно. Ender Chest скрыт по умолчанию и может стать публичным только при публичном основном инвентаре.
- Зритель видит публичный инвентарь только если он вправе видеть профиль владельца: `canViewProfile` (`visibility.ts:9`): `NOBODY`, `FRIENDS_ONLY` без дружбы и блокировка в любую сторону скрывают инвентарь, даже если он «публичный».
- Новых уровней вроде «только друзья» нет; при необходимости расширяется отдельным решением (вопрос Q34).

### 6.2 Единая функция доступа

```text
canViewInventory(viewer, target, group):
  если viewer.id == target.id                         -> разрешить
  если target нет Minecraft-привязки                   -> 404
  если !canViewProfile(target, viewer.id)             -> 404
  если !entitlementHook.allows(viewer, target, group) -> по хуку (6.4)
  если !privacy.inventoryPublic                       -> 403 inventory_private
  если group == ender и !privacy.enderPublic          -> 403 inventory_private
  иначе                                               -> разрешить
```

Администраторские маршруты (6.3) эту функцию не вызывают: у них свой guard и свои проверки.

### 6.3 Право персонала

Предлагаются новые ключи каталога (`packages/shared/src/permissions.ts`, модуль `inventory`): `inventory.view_any` (основной инвентарь любого пользователя) и `inventory.view_ender_any` (Ender Chest любого). Раздельные, чтобы выдавать минимально необходимое. Названия — предложение, окончательные выбирает владелец (Q34). Условия доступа:

- `@RequirePermissions('inventory.view_any')` на админ-маршрутах + admin-2FA (`permissions.guard.ts:43`, fail-closed, ADR-0156 и ADR-0164).
- Каждый успешный просмотр пишет `AuditService.log` (`audit.service.ts:40`): `actorId`, `action: 'inventory.view_any'`, `targetType: 'user'`, `targetId`, `severity: 'warning'`; содержимое инвентаря в журнал не попадает. Неуспех (нет права, нет 2FA) тоже фиксируется с `severity: 'warning'`.
- Иерархия персонала (проверка равного приоритета при mute/ban, ветка Q11, ADR-0164 в CHANGELOG; не смержено) НЕ распространяется на просмотр инвентаря сама: просмотр цели с равным или более высоким приоритетом — вопрос Q34 (рекомендация: разрешить, но всегда писать аудит).
- Лимит 30 запросов в минуту, оповещение при более чем 50 разных целей за час (порог задаёт владелец).
- Право не даёт ни изменять предметы, ни скрыто выдавать их: изменяющих маршрутов нет.

### 6.4 Точка расширения для доната (без правил)

Интерфейс `InventoryEntitlementPolicy` с одним методом `evaluate(viewer, target, group): 'default' | 'deny' | 'allow'`. Реализация по умолчанию возвращает `'default'` (остаётся базовая модель 6.2), правил и уровней в ней нет. Модуль Donation Entitlements (этап 05, hard gate) в будущем подставит свою реализацию. Что именно разрешено Apollo+, Ares+, Poseidon+, Zeus (`docs/donations/REQUIREMENTS.md`, строки 98–108, 167–168) — решает владелец на этапе 05; этот документ их не проектирует. Расхождение с требованиями: по ТЗ скрыть свой инвентарь могут «Poseidon+», а в базовой модели скрытие доступно всем (и это по умолчанию); см. Q34.

### 6.5 Персональные данные (152-ФЗ)

Данные инвентаря сами по себе не идентифицируют человека, но связаны с аккаунтом, ником и UUID. Меры: минимизация (только привязанные аккаунты; без IP, координат, текста книг и ников внутри предметов; без истории), приватность по умолчанию, каскадное удаление с аккаунтом и при отвязке, отсутствие публичных списков и поиска по предметам, UUID не отдаётся клиенту. Публикация ника уже есть в профиле (`profiles.service.ts:221`). Юридическая оценка — решение владельца (Q39); агенты заключений не дают.

## 7. Безопасность

### 7.1 Санитизация и XSS

- Текст предметов — только данные: приёмник вырезает всё, кроме полей схемы 3.3; на фронтенде он выводится React-текстом, никогда через `dangerouslySetInnerHTML`, `innerHTML` или построение HTML-строк. Ссылки в именах и лоре не превращаются в кликабельные.
- Цвет из данных переносится только как значение `style.color` после проверки по шаблону `#RRGGBB`/из списка имён; контраст проверяется (раздел 9: слишком тёмный цвет на тёмной теме поднимается до читаемого).
- Строки проходят нормализацию Unicode (NFC), вырезание управляющих символов и символов направления письма, лимиты длины (3.2). Имена предметов — пользовательский контент (переименование на наковальне): потенциально оскорбительный; жалоба на предмет не планируется на первом шаге (Q38).
- Нормализованный JSON хранится как есть; повторная санитизация выполняется и при выдаче (двойной контур), чтобы изменение правил действовало на старые данные.

### 7.2 Сырой NBT клиенту не отдаётся

Приёмник не принимает NBT (3.2); клиент получает только поля DTO. Сопоставление `enchants[].id` с русскими названиями делает фронтенд по справочнику; неизвестный id показывается как есть (в безопасном виде) без падений.

### 7.3 Лимиты и отказ в обслуживании

Лимиты Bridge (размер тела, пачка, событие) + лимиты раздела 3.5, 5.2; `slots` не более 41/27, строки не более 256, суммарный JSON ряда до 24 КБ, иначе `rejected invalid_data`. Рост БД ограничен одним рядом на `(user, server, group)`. Всплеск дельт одного игрока гасится слиянием в плагине и лимитом 6 событий в минуту.

### 7.4 Принадлежность UUID серверу и компрометация ключа сервера

Ключ сервера (Bridge 2.4) подписывает данные от его имени. Скомпрометированный ключ позволил бы подменить инвентарь ЛЮБОГО привязанного игрока. Меры: запись в `PlayerInventory` содержит `serverSlug` из `key-id`; данные разных серверов не пересекаются и не перезаписывают друг друга; в интерфейсе всегда виден сервер; ограничение возможностей сервера (`capabilities.inventory-sync`) выключено по умолчанию и включается админом для конкретного сервера; метрика «число различных UUID на сервер за час» с оповещением (порог задаёт владелец). Проверка «игрок действительно был на этом сервере» невозможна без `player.join` (выключены по Bridge 3.2): остаточный риск, принимается владельцем (Q37).

### 7.5 Принимаются только привязанные UUID

Данные принимаются только для UUID из `MinecraftAccount` (раздел 4.2, шаг 3). Это ограничивает: объём хранения, перебор чужих UUID через скомпрометированный сервер (нет «пустых» рядов под непривязанных) и объём персональных данных. Игрок, привязавшийся позже, получит данные при следующем входе (плагин шлёт снимок при входе).

### 7.6 Прочее

- Права и приватность проверяются на backend; фронтенд только отображает состояние (требование этапа 04).
- Логи: `userId`, `serverSlug`, `eventId`, тип, код результата. Содержимое предметов, тексты и UUID в логи не попадают.
- Без `BRIDGE_ENABLED=true` весь функционал отвечает `503` (fail-closed, Bridge 7). Тестового режима в продуктовом коде нет.

## 8. Изображения предметов

### 8.1 Задача и источники

Нужна картинка на каждый `item.id` ванили и на каждый `itemsAdderId`.

| Источник                 | Что это                                                                                                                    | Статус                                                                                                                   |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Ванильные иконки         | текстуры предметов клиента Minecraft                                                                                       | ЛИЦЕНЗИЯ НЕ ВЫЯСНЕНА: правила использования ресурсов Mojang запрещают распространять игровые ассеты; нужно решение (Q40) |
| Ресурс-пак сервера TwoMC | собственные иконки владельца (путь `minecraft/resourspack/...` на CDN уже используется для валют, `currency-assets.ts:15`) | предпочтительный источник для кастомных предметов                                                                        |
| Предметы ItemsAdder      | текстуры и модели из пакета ресурсов сервера                                                                               | формат и состав пакета требуют сверки; 3D-модели плоской иконкой не являются                                             |
| Сторонние наборы иконок  | открытые наборы с разрешающей лицензией                                                                                    | выбор и проверка лицензии — владелец; агент ничего не скачивает                                                          |

Агент не создаёт, не скачивает и не загружает ассеты; сборка атласа и загрузка на CDN — внешнее действие владельца.

### 8.2 CDN, реестр и атлас

- Хост: `cdn-files.twomc.su` (разрешён в `next.config.mjs:56`). Пути относительные, абсолютный URL собирает frontend; URL в JSX не пишутся — только через реестр (как у `currency-assets.ts`), новый реестр `item-assets` в `packages/shared/src` по тому же шаблону.
- Атлас: один PNG-лист иконок 16×16 (или 32×32) по версии игры + JSON-манифест `id → {x, y}`; файлы с версией и хэшем в имени (`atlas-<версия>.<хэш>.png`), `Cache-Control: public, max-age=31536000, immutable`. Манифест ItemsAdder — отдельный JSON `itemsadder-manifest.<хэш>.json` (`namespace:id → путь/координаты`), собирается из пакета ресурсов сервера скриптом владельца.
- Отрисовка: `background-position` по манифесту, масштаб только целочисленный, `image-rendering: pixelated` (как для валют: PNG без AVIF/WebP). Не `next/image` с оптимизацией для спрайтов.
- Порядок поиска иконки: `itemsAdderId` в манифесте → `item.id` в ванильном атласе → запасная иконка (Lucide `Package`) с текстовым названием. Неизвестный id никогда не ломает сетку.
- Загрузка: манифест и атлас — по одному запросу на страницу, предзагрузка; весь инвентарь рендерится без запросов на каждый предмет (оптимизация против 68 отдельных картинок).
- Безопасность: пути из данных НЕ подставляются в URL; фронтенд берёт путь только из манифеста по ключу. Ключ, которого нет в манифесте — запасная иконка.
- CSP `img-src` и хост-лист — сверить перед срезом 3 (требует сверки).

### 8.3 Оптимизация снимков (суммарно)

Хэш содержимого (4.2) не даёт перезаписывать неизменённое; дельты (3.4) уменьшают трафик; слияние событий в плагине; один ряд на игрока и группу; чтение без кэша по PK; иконки из атласа, а не по одной.

## 9. UI-состояния и вид («Полдень»)

Тема dark-first, акцент `#F26A1B`, иконки Lucide, сплошные подложки и семантические токены. Glassmorphism, `backdrop-filter`, размытие и liquid-glass не используются; тултипы и оверлеи — сплошной фон с рамкой.

| ------------ | ------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Нет привязки | у пользователя нет `MinecraftAccount` | карточка с пояснением и кнопкой «Привязать аккаунт» (путь `/site-connect`, ADR-0072)                 |
| Нет данных   | `state: no_data`                      | «Данных пока нет. Зайдите на сервер: инвентарь обновится при входе»; сетка пустых слотов не рисуется |
| Загрузка     | запрос идёт                           | скелетон сетки слотов (41/27), без анимации при `prefers-reduced-motion`                             |
| Offline      | `playerOnline=false`                  | плашка «Игрок не в сети. Данные на {время}», время и относительное («2 ч назад»)                     |
| Устарело     | `playerOnline=true` и `isFresh=false` | плашка «Данные могли устареть (последнее обновление {время})»                                        |
| Приватно     | `403 inventory_private`               | иконка замка Lucide (`Lock`), «Владелец скрыл инвентарь»; владельцу — ссылка на настройки            |
| Ошибка       | `5xx`, сеть, `503`                    | «Не удалось загрузить» + «Повторить»; `503` — «Раздел временно недоступен»                           |
| Rate limit   | `429`                                 | «Слишком часто. Повторите через N с», без автоповтора раньше `Retry-After`                           |

### 9.1 Раскладка

Две области: «Основной инвентарь» — сетка 9×3 (слоты 9–35) и хотбар 9×1 (0–8) под ней; «Экипировка» — 4 слота брони вертикально (шлем, нагрудник, поножи, ботинки) и вторая рука; «Ender Chest» — вкладка, сетка 9×3, показывается владельцу и тем, кто вправе (раздел 6). Слот — кнопка размера не менее 40×40 CSS px (цель касания), внутри иконка и число количества справа внизу (контрастная обводка текста, не тень-размытие).

### 9.2 Тултипы и доступность

- Тултип предмета: название (прогоны с цветом), `id` в моно-шрифте, зачарования («Острота V»), прочность («1549 / 1561»), лор, «ItemsAdder: namespace:id», для контейнера — «Внутри предметов: N». Сплошной фон, граница, текст не меньше 14 px.
- Открывается по наведению, фокусу с клавиатуры и долгому нажатию; закрывается Esc; не перехватывает фокус; не требует наведения для доступа к информации.
- Клавиатура: сетка — единый tab-stop, стрелки перемещают по слотам (roving tabindex), `Home`/`End` — начало и конец ряда; активный слот открывает панель деталей (на узком экране — нижний лист со сплошным фоном).
- ARIA: контейнер `role="grid"` либо `role="list"`; у слота `aria-label` вида «Слот 1: Алмазный меч, 1 шт., зачарован»; пустой слот — «Слот 2: пусто»; обновление данных объявляется вежливой `aria-live` областью (только смена плашки состояния, не каждого слота).
- Контраст: текст и границы не ниже WCAG AA на обеих темах; цвета из текста предметов корректируются до читаемого; фокус — заметное кольцо акцентом, не только цветом (дополнительная рамка толщиной 2 px).
- Блеск зачарования: статичный маркер (рамка акцента или иконка Lucide `Sparkles` в углу), анимация только вне `prefers-reduced-motion`.
- Адаптив: от 375 px; на узких экранах сетка масштабируется целым множителем иконки, прокрутка контента внутри страницы без горизонтальной.

## 10. Site Cosmetics Inventory — границы

Отдельная сущность от Minecraft Inventory: каталог украшений профиля (рамки, бейджи, баннеры и т. п.), не игровые предметы. В этом документе только границы.

Зависит от hard gate (НЕ проектируется и не реализуется без команды владельца): покупка украшений, цены и валюты (рубины, монеты), магазин, Donation Entitlements и их уровни, привилегии по уровням, передача, мини-игры и розыгрыши как источник украшений, реальные платежи.

Возможно без hard gate (эскиз модели, реализация по отдельному решению):

- Ручная выдача и отзыв украшения администратором (по праву, с аудитом); история выдачи.
- Экипировка (одно украшение на слот профиля), витрина профиля, предпросмотр на аватаре.
- Эскиз: `Cosmetic` (id, slug, тип, название, ссылка на реестр ассета), `UserCosmetic` (userId, cosmeticId, источник `ADMIN_GRANT`, выдал, выдано, отозвано), `UserCosmeticEquip` (userId, слот, cosmeticId). Поле «источник» остаётся расширяемым значением, чтобы будущие источники (магазин, донат) добавлялись без переделки, но в этом документе они не вводятся.
- Существующие аналоги, требующие сверки перед проектированием: `UserBadge` (`schema.prisma:706`), `BannerPreset` (`schema.prisma:781`), `Award` и `UserAward` (`schema.prisma:864`, `882`): возможно, уже покрывают часть задач; дублировать нельзя.

Вопрос Q41 (после решений по экономике): нужно ли вообще отдельное хранилище украшений.

## 11. Тест-план

Реализация после решений владельца. Данные симулятора Bridge — ЯВНО тестовые (ники вида `TestPlayer001`, UUID из диапазона тестовых), в продуктовом коде моков нет.

Unit (без БД):

- Схема `inventory.snapshot` и `inventory.delta`: валидные, лишние поля, `count` 0 и 100, слоты за границами, `id` с недопустимыми символами, строки длиннее лимита, 42 слота `main`.
- Санитизация прогонов текста: `§`-коды, управляющие символы, символы направления письма, `clickEvent`-подобные поля, некорректный цвет, длинные строки.
- `canViewInventory`: таблица всех комбинаций (владелец, чужой, друг, блокировка, `NOBODY`, `FRIENDS_ONLY`, нет привязки, `inventoryPublic`, `enderPublic`, хук доната `deny`/`allow`/`default`).
- Применение дельты: верная `baseRev`, неверная, чужая `epoch`, повтор, пропуск.
- Хэш содержимого: перестановка полей даёт тот же хэш (канонизация).

e2e на ОДНОРАЗОВОЙ БД (не рабочей, не production; миграции только в одноразовой):

- Приём через подписанные запросы симулятора: принятый снимок, повтор `eventId` (`duplicate`), устаревший (`stale`), дельта по неверной ревизии (`resync_required`), `unknown_player`, `unsupported_type` без возможности, чужой `serverId` (`server_mismatch`).
- Чтение: владелец; чужой при приватном (`403 inventory_private`); чужой при публичном; публичный, но профиль `NOBODY` (`404`); блокировка (`404`); Ender Chest при публичном основном и скрытом Ender (`403`); прямой запрос Ender Chest по `/admin/...` без права (`403`) и с правом без 2FA (`403 2fa_required`); `404` одинаково для «нет пользователя» и «нет привязки» (сравнение тела и кода).
- Аудит: запись при каждом админ-просмотре, без содержимого.
- Лимиты: `429` и `Retry-After`; перебор различных целей.
- Отвязка и удаление пользователя: каскадное удаление рядов.
- Параллельные снимки и дельты одного игрока: нет потери обновлений (транзакция 4.2).
- Fail-closed: без `BRIDGE_ENABLED` — `503`.

Frontend (jsdom): состояния раздела 9, клавиатурная навигация по сетке, `aria-label` слотов, отсутствие `dangerouslySetInnerHTML` с данными предметов (статическая проверка), запасная иконка для неизвестного `id`; визуальная проверка на тёмной и светлой теме, ширины 375/768/1440 — вручную владельцем или в браузерных тестах (если они есть).

Безопасность: тест «ответ не содержит `userId`, UUID, `epoch`, `contentHash` для не-владельца»; тест «ответ основного инвентаря не содержит Ender Chest»; fuzz текстовых полей.
