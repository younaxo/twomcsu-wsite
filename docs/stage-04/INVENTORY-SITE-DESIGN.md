## 1. Цель, границы, статус

Цель: игрок видит на сайте свой инвентарь Minecraft (основной, броня, вторая рука, Ender Chest) с предметами, количеством, зачарованиями и временем обновления; решает, показывать ли его другим; персонал смотрит чужой только по отдельному праву с аудитом.

В границах документа: схема данных Bridge для инвентаря (предложение к контракту v1.x), хранение, API сайта, приватность и права, безопасность, изображения предметов, UI-состояния, тест-план, срезы и вопросы владельцу.

Вне границ (hard gate, только упоминание): правила и уровни Donation Privileges, экономика, платежи, рубины, магазин, мини-игры, розыгрыши. Раздел 10 описывает Site Cosmetics Inventory только как границы.

Не делается: выдача и изъятие предметов с сайта (команды сайт→сервер запрещены в v1), показ вложенного содержимого контейнеров, история изменений инвентаря по умолчанию, карта и координаты.

## 3. Данные из Bridge

Предложение к контракту v1.x: два новых типа события, оформляются отдельной ревизией `BRIDGE-CONTRACT.md` после решения Q32 и Q33. Сам контракт этим документом не меняется. Общие правила (подпись, `eventId`, `serverId`, `streamId`, `seq`, лимиты 100 событий, 256 КБ тело, 16 КБ событие) — из Bridge 3, 5. Возможность сервера `inventory-sync` объявляется в `bridge.hello` (`capabilities`, Bridge 7.1); без неё получатель отвечает `unsupported_type`.

### 3.1 Что и когда отправляет плагин

| Событие              | Когда                                                                                                 | Содержимое                                                                                 |
| -------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `inventory.snapshot` | вход игрока; выход; раз в N минут для онлайн-игрока при изменении (по умолчанию 5); по запросу сверки | полное состояние ОДНОГО контейнера-группы (`main` или `ender`), комплектом из частей (3.6) |
| `inventory.delta`    | изменение между снимками, не чаще раза в 5 с на игрока (слияние изменений)                            | изменённые слоты относительно `rev`                                                        |

Группы: `main` — основной инвентарь (слоты 0–35), броня (4), вторая рука (1), итого 41 слот; `ender` — Ender Chest (27 слотов). Отдельные комплекты нужны, чтобы Ender Chest можно было не отправлять вовсе (его включает владелец сервера настройкой плагина). Каждый снимок группы делится на части по группам слотов, чтобы каждое событие укладывалось в 16 КБ (ответ владельца на Q35, раздел 3.6 и `BRIDGE-CONTRACT.md`, 6.1).

Допущение: версии игры ниже 1.20.5 и разные форматы компонентов предметов — забота плагина; сайт видит только нормализованный JSON из 3.2. Размер стека и названия зачарований приходят как есть, сайт их не пересчитывает.

### 3.2 Схема `inventory.snapshot` (поле `data`)

```json
{
  "uuid": "069a79f4-44e9-4726-a5be-fca90e38aaf5",
  "group": "main",
  "epoch": 1763380800000,
  "snapshotId": "01JC8Z3K5T9Q4V7X2M6N8P0R1S",
  "part": 1,
  "parts": 4,
  "slotGroup": "hotbar",
  "rev": 1,
  "capturedAt": "2026-11-17T12:00:00.000Z",
  "playerOnline": true,
  "schemaVersion": 1,
  "slots": [
    {
      "area": "hotbar",
      "slot": 0,
      "item": {
        "id": "minecraft:diamond_sword",
        "count": 1,
        "damage": 12,
        "maxDamage": 1561,
        "enchants": [{ "id": "minecraft:sharpness", "level": 5 }],
        "storedEnchants": [],
        "name": [{ "text": "Меч", "color": "#F26A1B", "italic": false }],
        "lore": [[{ "text": "Строка лора" }]],
        "customModelData": null,
        "itemsAdderId": null,
        "unbreakable": false,
        "dyeColor": null,
        "potion": null,
        "containerItemCount": null
      }
    }
  ]
}
```

| Поле                  | Тип и ограничения                                                                                                                                                                                                                                                   |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `uuid`                | UUID игрока; сайт принимает только UUID, привязанные в `MinecraftAccount` (раздел 7.5)                                                                                                                                                                              |
| `group`               | `main` или `ender`                                                                                                                                                                                                                                                  |
| `epoch`               | целое 1–9007199254740991 (JSON number, целое, не строка; согласовано с `BRIDGE-CONTRACT.md`, 6.1), строго растёт при каждом перезапуске плагина; `delta` применима только к своей эпохе; хранится как `BigInt` (4.1)                                                |
| `rev`                 | целое >= 1; растёт на 1 с каждым снимком и каждой дельтой внутри эпохи, поэтому снимок всегда имеет `rev` больше любого ранее отправленного в этой эпохе; после перезапуска (новая `epoch`) начинается заново                                                       |
| `snapshotId`          | только `inventory.snapshot`; строка, `^[0-9A-Za-z-]{26,64}$` (UUIDv7 или ULID); проверяется ДО обращения к Redis (иначе `rejected invalid_data`); один на комплект, новый для каждого нового снимка, повтор частей использует тот же. Обязателен                    |
| `part`                | только `inventory.snapshot`; целое 1..`parts`, нумерация с 1; обязателен                                                                                                                                                                                            |
| `parts`               | только `inventory.snapshot`; целое, только значение из закрытого перечня раскладок (3.6): `main` — 4 или 1, `ender` — 2 или 1 (всегда не больше 4); одинаково во всех частях; обязателен                                                                            |
| `slotGroup`           | только `inventory.snapshot`; `hotbar`, `storage_a`, `storage_b`, `equipment`, `ender_a`, `ender_b`, `all`; допустимость для `group` и `parts` проверяется ДО Redis (3.6); уникальна в комплекте; обязательна                                                        |
| `capturedAt`          | ISO 8601 UTC; границы как у `occurredAt` (Bridge 5.3): не старше 7 суток и не позже сейчас + 60 с. Служит ТОЛЬКО для отсечки просрочки (4.4) и показа времени; в порядке свежести не участвует (4.2)                                                                |
| `playerOnline`        | игрок в сети в момент снимка; для снимка при выходе — `false`. Признак «offline» на сайте берётся отсюда (события `player.*` выключены, Bridge 3.2)                                                                                                                 |
| `schemaVersion`       | `1`                                                                                                                                                                                                                                                                 |
| `slots`               | слоты ЭТОЙ части: только слоты своей `slotGroup` (диапазоны в 3.6); в собранном снимке до 41 (`main`) или 27 (`ender`); пустая группа — `slots: []`; пустые слоты не передаются; `area`: `hotbar`, `main`, `armor`, `offhand`, `ender`; `slot` — индекс внутри area |
| `item.id`             | `^[a-z0-9_.-]+:[a-z0-9_./-]+$`, до 64 символов                                                                                                                                                                                                                      |
| `item.count`          | целое 1–99                                                                                                                                                                                                                                                          |
| `damage`, `maxDamage` | целые >= 0, до 100000, либо `null`                                                                                                                                                                                                                                  |
| `enchants`            | до 32 пар `{id, level}`, `level` 1–255; `storedEnchants` — то же для книг                                                                                                                                                                                           |
| `name`, `lore`        | массивы «прогонов» текста (3.3); `name` до 16 прогонов, `lore` до 20 строк по 16 прогонов, суммарно до 2000 символов на предмет                                                                                                                                     |
| `customModelData`     | целое 0–2147483647 или `null`                                                                                                                                                                                                                                       |
| `itemsAdderId`        | `^[a-z0-9_.-]+:[a-z0-9_./-]+$`, до 96 символов, или `null`; если задан, сайт показывает иконку по нему, а `id` — запасной вариант (раздел 8)                                                                                                                        |
| `dyeColor`            | целое 0–16777215 или `null`; `potion` — строка id или `null`                                                                                                                                                                                                        |
| `containerItemCount`  | для шалкеров, мешков и подобных: число непустых вложенных предметов (0–64) или `null`. Вложенное содержимое НЕ передаётся (v1)                                                                                                                                      |

В примере выше показана ПЕРВАЯ часть из четырёх (`slotGroup: "hotbar"`); поля `snapshotId`, `part`, `parts`, `slotGroup` есть только у `inventory.snapshot` (у `inventory.delta` их нет, 3.4); остальные части комплекта повторяют заголовки (`uuid`, `group`, `epoch`, `rev`, `capturedAt`, `playerOnline`, `schemaVersion`, `snapshotId`, `parts`), меняя `part`, `slotGroup` и `slots` (3.6).

Не передаются и не принимаются: сырой NBT и компоненты целиком, текст книг, владелец головы и любые UUID/ники внутри предмета, координаты, ссылки `clickEvent`/`hoverEvent`, `selector`, `nbt`, `translate`/`keybind` с подстановкой. Неизвестное поле — `rejected invalid_data` (строгая схема, `additionalProperties: false`).

### 3.3 Текст предметов («прогоны»)

Плагин сам превращает text component в плоский массив прогонов `{ "text", "color"?, "bold"?, "italic"?, "underlined"?, "strikethrough"?, "obfuscated"? }`. `color` — `#RRGGBB` или одно из 16 имён. Сайт повторно проверяет: длина `text` до 256, управляющие символы и символы направления письма (U+202A–U+202E, U+2066–U+2069) вырезаются, цвет только по шаблону, остальное отбрасывается. Классические коды `§` плагин убирает до отправки; сайт тоже.

### 3.4 Схема `inventory.delta`

```json
{
  "uuid": "069a79f4-44e9-4726-a5be-fca90e38aaf5",
  "group": "main",
  "epoch": 1763380800000,
  "baseRev": 1,
  "rev": 2,
  "capturedAt": "2026-11-17T12:00:07.000Z",
  "playerOnline": true,
  "changes": [{ "area": "hotbar", "slot": 0, "item": null }]
}
```

`changes` — до 41 записей; `item: null` — слот опустел; иначе предмет по схеме 3.2. Применение: только если `epoch` и `baseRev` совпадают с сохранёнными (раздел 4.2). Дельта той же `epoch` с `rev` не больше сохранённого (повтор уже применённой или более старая) получает `duplicate` без записи: ключей дедупликации `eventId` для дельт в Redis нет (экономия памяти, 4.4), защита — состояние ряда в БД. Иначе получатель отвечает `rejected` с кодом `resync_required` (новый код, Bridge 5.1 перечисляет только существующие) и плагин присылает полный снимок. Если плагин не поддерживает дельты, достаточно снимков; дельты — оптимизация трафика (раздел 12, срез 4), а не обязательное требование.

### 3.5 Идемпотентность, порядок, размер

- Ключ дедупликации — `(serverId, eventId)` из Bridge 5.2. Для `inventory.*` журнал в БД НЕ ведётся (как для `player.*`): дедупликация частей снимка в Redis с коротким TTL 300 с (допущение до подтверждения владельцем (Q61); вместо 24 часов общего правила Bridge 5.2: срок хватает на повторы плагина в пределах таймаута 120 с и отсечки 150 с, а 24 часа держали бы миллионы ключей вне лимитов памяти, 4.4). Для дельт ключей `eventId` нет: повтор отсекается состоянием ряда (3.4). Повтор того же `eventId` безвреден: снимок — полное состояние (идемпотентно по `snapshotId`), дельта защищена `epoch` и `baseRev`.
- Порядок свежести (один везде: 3.6, 4.2, 4.4): СНАЧАЛА `epoch`, затем `rev`. Снимок A свежее сохранённого B, если `A.epoch > B.epoch` либо эпохи равны и `A.rev > B.rev`; не свежее — `stale`; тот же `snapshotId` — повтор применённого (`snapshot_applied` без изменений). `capturedAt` в сравнении НЕ участвует: он берётся с часов хоста плагина, которые могут уйти назад, и сравнение по нему отбросило бы как `stale` снимок после перезапуска плагина (новая `epoch`, `rev` с начала), то есть актуальное состояние. `epoch` растёт при каждом перезапуске, поэтому снимок новой эпохи всегда новее. `capturedAt` нужен только для отсечки просрочки первой части (4.4) и для показа времени. Дельта применяется строго по `epoch` и `baseRev`; пропуск ревизии — `resync_required`. Порядок задаёт приёмник; часы плагина ограничены окном 5.3.
- Размер: событие до 16 КБ (Bridge 5.4), лимит НЕ повышается (допустимые раскладки частей — 3.6). Верхняя оценка `main` — 41 предмет по 600 байт (около 24,6 КБ) не помещается в одно событие, поэтому по решению владельца (Q35) снимок делится на части по группам слотов с общим `snapshotId`, номером части и числом частей (3.6); сайт применяет только полный комплект и отбрасывает неполный через 120 с (4.4).
- Частота: не более 1 снимка на игрока и группу за 30 с (плагин) и не более 6 СНИМКОВ в минуту на игрока (приёмник; Допущение до подтверждения владельцем (Q61)). Счёт ведётся ПРИ СОЗДАНИИ сборки, то есть по новому `snapshotId`: один снимок из 4 частей = 1, шесть таких снимков (24 события) укладываются в лимит; части уже существующей сборки лимитом не отклоняются и счётчик не увеличивают; повтор части не увеличивает. Превышение при создании — `rejected resync_required` (повтор не раньше чем через 60 с, как в контракте 6.1; не `429` на весь запрос, чтобы не задерживать остальные события пачки). Дельты считаются ОТДЕЛЬНЫМ счётчиком по событиям: не более 30 в минуту на игрока (плагин шлёт не чаще раза в 5 с, то есть до 12 в минуту; Допущение до подтверждения владельцем (Q61)), превышение — `rejected resync_required`; счётчики снимков и дельт не делятся. Суммарно действуют лимиты на сервер (3000 событий в минуту, включая каждую часть).

### 3.6 Части снимка (ответ владельца на Q35)

Решение владельца (Q35, 2026-11-17): снимок инвентаря делится на части (чанки) по группам слотов с общим идентификатором снимка, номером части и числом частей; сайт собирает снимок из частей, применяет только полный комплект и по таймауту отбрасывает неполный; лимит одного события Bridge не поднимается; контракт Bridge и этот дизайн обновляются; тесты на потерю и повтор частей обязательны. Транспортные правила (поля, нумерация, таймаут, ответы, метрики, тест-векторы для плагина) — `docs/stage-03/BRIDGE-CONTRACT.md`, раздел 6.1 (ADR-0167); здесь они не дублируются, только следствия для сайта.

- Снимок группы (`main` или `ender`) всегда приходит комплектом из `parts` событий `inventory.snapshot` с общим `snapshotId`; `part` нумеруется с 1; у каждой части своя метка `slotGroup` и свой массив `slots`. Допустимы ТОЛЬКО раскладки закрытого перечня (как в контракте 6.1; `parts` не больше 4); любое другое сочетание `(group, parts, slotGroup)` — `rejected invalid_data` до обращения к Redis:

  | `group` | `parts` | Набор `slotGroup` (по одному на часть)                                                                                                            |
  | ------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `main`  | 4       | `hotbar` (area `hotbar`, 9 слотов), `storage_a` (area `main`, слоты 0–13), `storage_b` (area `main`, 14–26), `equipment` (`armor` 4, `offhand` 1) |
  | `main`  | 1       | `all` (все 41 слот; только если событие помещается в 16 КБ)                                                                                       |
  | `ender` | 2       | `ender_a` (area `ender`, 0–13), `ender_b` (14–26)                                                                                                 |
  | `ender` | 1       | `all` (все 27 слотов; только если событие помещается в 16 КБ)                                                                                     |

  Общие заголовки (`uuid`, `group`, `epoch`, `rev`, `capturedAt`, `playerOnline`, `schemaVersion`, `snapshotId`, `parts`) повторяются в каждой части и обязаны совпадать. Слот обязан лежать в диапазоне своей `slotGroup` и встречаться ровно в одной части.

- Каждая часть не больше 16 КБ (лимит Bridge 5.4 не повышен); ориентир предмета — до 600 байт, группа части — до 14 слотов. Это заменяет прежнее допущение 3.5 («лимит 600 байт и обрезка лора без `part`»): `part` введён по решению владельца, а ограничение предмета остаётся защитой размера.
- Сайт применяет снимок только после сборки полного комплекта (раздел 4.4); неполный комплект не меняет хранимое состояние и отбрасывается через 120 секунд. Для `inventory.delta` ничего не меняется, кроме правила: дельта эпохи, чей снимок ещё не применён, получает `resync_required`.
- Собранный снимок проверяется как одиночный снимок схемы 3.2 (до 41 или 27 слотов, строгая схема, санитизация) плюс проверки комплекта: слоты не пересекаются между частями, `slotGroup` уникальны, площадь (`area`) и индекс слота допустимы для его `slotGroup`. Полнота комплекта определяется НАБОРОМ `slotGroup`, а не числом частей: комплект полон, только когда набор принятых `slotGroup` равен набору раскладки для `group` (две части `hotbar` вместо `hotbar` и `equipment` при `parts = 4` не дают полноты и отвергаются как дубль или `conflict`).
- Порядок свежести един с 3.5: `epoch`, затем `rev`; `capturedAt` — только для отсечки просрочки первой части (4.4).

### 4.1 Модели (эскиз Prisma)

```prisma
model PlayerInventory {
  id           String   @id @default(cuid())
  userId       String
  serverSlug   String   @db.VarChar(32)
  /// main | ender
  grp          String   @db.VarChar(8)
  /// Порядок свежести: сначала epoch, затем rev (3.5); capturedAt в порядке не участвует.
  epoch        BigInt
  /// snapshotId применённого комплекта: повтор того же снимка идемпотентен (4.4).
  snapshotId   String   @db.VarChar(64)
  rev          Int
  /// Нормализованный JSON слотов (раздел 3.2), без сырого NBT; до 32 КБ (4.3).
  slots        Json
  slotCount    Int
  /// SHA-256 от канонического JSON слотов (дедупликация, ETag).
  contentHash  String   @db.VarChar(64)
  capturedAt   DateTime
  /// Последнее подтверждение (в том числе без изменений).
  lastSeenAt   DateTime
  playerOnline Boolean  @default(false)
  schemaVersion Int     @default(1)
  updatedAt    DateTime @updatedAt

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([userId, serverSlug, grp])
  @@index([lastSeenAt])
  @@map("player_inventories")
}

model InventoryPrivacy {
  userId          String   @id
  /// Основной инвентарь, броня и вторая рука видны другим игрокам.
  inventoryPublic Boolean  @default(false)
  /// Ender Chest виден другим; имеет смысл только при inventoryPublic.
  enderPublic     Boolean  @default(false)
  updatedAt       DateTime @updatedAt

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@map("inventory_privacy")
}
```

Решения:

- Один ряд на `(пользователь, сервер, группа)`: хранится только последнее состояние. Каскадное удаление с пользователем (`onDelete: Cascade`, как у `MinecraftAccount`, `schema.prisma:542`) покрывает удаление аккаунта (152-ФЗ).
- UUID в таблице не хранится: связь через `userId` и `MinecraftAccount`. При отвязке Minecraft-аккаунта строки `PlayerInventory` пользователя удаляются в той же транзакции (риск: путь отвязки требует сверки).
- `InventoryPrivacy` вынесена из `User`, чтобы не расширять большую модель и чтобы точка расширения доната (раздел 6.4) не затрагивала `User`. Отсутствие строки = «приватно».
- Нормализованный JSON, а не таблица по слотам: чтение всегда целиком, предметов до 68, запросов по предметам («у кого есть алмазный меч») не требуется и не планируется (это поисковая слежка за игроками).

### 4.2 Применение события (транзакция)

1. Проверка подписи и лимитов (Bridge 2.3) уже выполнена guard-ом.
2. Схема по 3.2/3.4, строгая; затем санитизация текста (3.3).
3. `uuid` → `MinecraftAccount` → `userId`; нет привязки — `rejected` с кодом `unknown_player` (неисправимо, плагин не повторяет; метрика счётчика, без записи в БД).
4. `serverSlug` берётся из `key-id`, не из тела (Bridge 2.3). Сервер без возможности `inventory-sync` — `unsupported_type`.
5. Транзакция `SERIALIZABLE` либо `SELECT ... FOR UPDATE` по ряду `(userId, serverSlug, grp)`: снимок — сравнить свежесть: СНАЧАЛА `epoch`, затем `rev` (3.5; `capturedAt` не сравнивается: часы хоста плагина после перезапуска могут уйти назад, и снимок новой эпохи не должен отбрасываться как `stale`); тот же `snapshotId` — повтор, без изменений (`snapshot_applied`); дельта — сверить `epoch` и `baseRev`; применить; пересчитать `contentHash`.
6. Если `contentHash` не изменился, обновляются только `lastSeenAt`, `playerOnline` и `capturedAt` (одно маленькое UPDATE; содержимое JSON не перезаписывается).

SQL-эскиз (только текст) проверки и применения снимка:

```sql
-- в транзакции, $1 userId, $2 serverSlug, $3 grp
SELECT epoch, rev, "snapshotId", "contentHash"
  FROM player_inventories
 WHERE "userId" = $1 AND "serverSlug" = $2 AND grp = $3
 FOR UPDATE;
-- приложение: тот же snapshotId -> ничего не менять, ответ snapshot_applied;
-- (epoch, rev) не свежее сохранённого -> stale; иначе INSERT ... ON CONFLICT ниже.

INSERT INTO player_inventories
  ("userId", "serverSlug", grp, epoch, rev, "snapshotId", slots, "slotCount",
   "contentHash", "capturedAt", "lastSeenAt", "playerOnline", "schemaVersion")
VALUES ($1, $2, $3, $4, $5, $11, $6, $7, $8, $9, now(), $10, 1)
ON CONFLICT ("userId", "serverSlug", grp) DO UPDATE
   SET epoch = EXCLUDED.epoch, rev = EXCLUDED.rev, "snapshotId" = EXCLUDED."snapshotId",
       slots = EXCLUDED.slots,
       "slotCount" = EXCLUDED."slotCount", "contentHash" = EXCLUDED."contentHash",
       "capturedAt" = EXCLUDED."capturedAt", "lastSeenAt" = now(),
       "playerOnline" = EXCLUDED."playerOnline"
 WHERE (player_inventories.epoch, player_inventories.rev) < (EXCLUDED.epoch, EXCLUDED.rev);
```

(`id` и `updatedAt` заполняет Prisma; в реальной реализации вместо сырого SQL предпочтителен `prisma.$transaction` с тем же условием.)

### 4.3 Срок хранения и объём

- Последнее состояние хранится, пока привязан аккаунт; очистка строк, не обновлявшихся более 90 дней (`lastSeenAt`), задание планировщика (значение предлагается, подтверждает владелец, Q36).
- История изменений по умолчанию НЕ хранится: объём (до 68 предметов × частота снимков) и приватность. Если история нужна (расследования краж персоналом), отдельный вопрос Q36: рекомендация — не вводить в первом релизе.
- Лимит хранимого ряда (Q35, следствие деления на части): 32 КБ JSON слотов (32 768 байт). Прежний лимит 24 КБ меньше полной группы: 41 слот × 600 байт = 24 600 байт плюс служебные поля слотов (`area`, `slot`, обёртка) около 1,5 КБ, что в сумме более 24 КБ и потеряло бы полный `main`. 32 КБ — допущение с запасом около 25% (подтверждает владелец вместе с Q35; не меньше полной группы, но и не безразмерно). Ряд сверх лимита после сборки — `invalid_data`, снимок отбрасывается, прежнее состояние сохраняется.
- Оценка объёма: ряд `main` до 32 КБ JSON, `ender` фактически до ~17 КБ, два ряда на игрока и сервер; при 5 000 привязанных игроков и 2 серверах — до ~0,5 ГБ в худшем случае (фактически в разы ниже: разреженные слоты), фактически ниже в разы (разреженные слоты); оценка требует сверки на реальных данных.
- Сопоставление `serverSlug` Bridge (`bridge_servers.slug`, `BRIDGE-CONTRACT.md:285`) и `Server.slug` (`schema.prisma:1608`): отдельное поле связи не вводится на первом шаге; в API отдаётся `displayName` из `bridge_servers`. Требует сверки (Q32).

### 4.4 Сборщик частей снимка (Q35)

Только текст; код и миграций нет. Сборщик — часть обработчика `inventory.*` приёмника Bridge (контракт, раздел 7), вызывается ПОСЛЕ проверки схемы части и ДО транзакции применения. Транспортные правила и порядок свежести — `BRIDGE-CONTRACT.md`, 6.1; ниже их реализация на стороне сайта. Числовые значения этого раздела (таймаут 120 с, отсечка 150 с, снимок 32 КБ, 256 сборок и 8 МБ на сервер, 6 снимков в минуту, захват 30 с, TTL `done` и `evt` 300 с, потолки памяти 20 МБ и 64 МБ) — Допущение до подтверждения владельцем (Q61).

**Где хранится буфер: Redis с TTL, не БД.** Причины: (1) у API может быть несколько экземпляров, части одного комплекта приходят на разные, поэтому память процесса не подходит; (2) буфер временный (до 120 с), его потеря безопасна (плагин присылает новый снимок), поэтому БД, миграции (Q28) и очистка не нужны; (3) TTL удаляет просроченное без задания планировщика; (4) Redis уже используется приёмником Bridge (дедупликация, лимиты). Redis недоступен или вернул OOM — `503` по Bridge 5.1, а не тихая потеря частей. Приёмник не должен зависеть от того, что Redis сохранит буфер при перезапуске (AOF не обязателен): потеря равна таймауту. Память Redis ограничена потолками (ниже, «Память Redis»), поэтому штатное заполнение буфера не доводит Redis до OOM.

**Три состояния сборки.** (1) «собирается»: есть `asm`, не все части; (2) «полна, не применена»: набор `slotGroup` равен набору раскладки (3.6), метки `done` нет; в этом состоянии повтор любой части (в том числе завершающей, под тем же или новым `eventId`) берёт захват и запускает применение; (3) «применена»: метка `done`, повтор части — `duplicate`. Состояние (2) возникает при сбое БД и при гонке за захват.

**Раскладка ключей.** Все ключи сервера содержат хэш-тег `{serverId}` (значение — `serverSlug` из `key-id`, не из тела), так что скрипты Lua с несколькими ключами работают и в Redis Cluster (один слот на сервер). Ключи игрока строятся от ВНУТРЕННЕГО `userId` (известен после проверки привязки), а не от UUID: UUID в ключах, метриках и логах нет. Глобальный ключ `bridge:inv:g` (последняя строка таблицы) требует Redis без кластера (как допущение контракта); в кластере глобальный потолок заменяется суммой серверных (число серверов с `inventory-sync` умножается на 20 МБ).

| Ключ (после `bridge:inv:`)        | Тип и TTL                                                                                    | Содержимое                                                                                                                                                    |
| --------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `{serverId}:asm:{snapshotId}`     | HASH, 120 с от первой части (EXPIRE ставится один раз, не продлевается)                      | `meta` (заголовки, `parts`, `userId`, `firstSeenAt`, `bytes`), `p:{n}` (слоты части, JSON), `h:{n}` (хэш части), `g:{n}` (`slotGroup`)                        |
| `{serverId}:idx`                  | ZSET, балл `firstSeenAt`; TTL ключа 300 с (обновляется)                                      | `snapshotId` живых сборок сервера (счёт 256); просроченные (старше 125 с) удаляются лениво в начале каждого скрипта                                           |
| `{serverId}:idxb`                 | HASH, TTL как у `idx`                                                                        | `snapshotId` -> байты сборки (полезная нагрузка + 1 КБ служебных полей); сумма значений даёт учёт 8 МБ без дрейфа счётчика                                    |
| `{serverId}:svc`                  | ZSET, балл — момент истечения самого долгого служебного ключа снимка (`firstSeenAt` + 300 с) | `snapshotId`, у которых ещё живы `done`, `evt`, `mark`; `ZCARD` × 2 КБ — учёт служебной памяти (12 МБ); просроченные удаляются лениво                         |
| `{serverId}:own:{userId}:{group}` | ZSET, 120 с                                                                                  | `snapshotId` живых сборок игрока и группы, балл `firstSeenAt` (по нему вытесняется самая старая, не по `capturedAt`); `(epoch, rev)` берутся из `meta` сборки |
| `{serverId}:done:{snapshotId}`    | STRING, 300 с                                                                                | метка «применён»: повтор части — `duplicate`                                                                                                                  |
| `{serverId}:mark:{snapshotId}`    | STRING, 150 с                                                                                | метка с видом: `poison` (`snapshot_mismatch`, `conflict`), `evicted` (вытеснен лимитом игрока), `superseded` (сброшен более свежим), `stale`                  |
| `{serverId}:lock:{snapshotId}`    | STRING NX, 30 с                                                                              | захват применения: токен владельца; снятие только при совпадении токена                                                                                       |
| `{serverId}:evt:{eventId}`        | STRING, 300 с                                                                                | дедупликация `eventId` частей снимка (3.5); для дельт ключей нет                                                                                              |
| `{serverId}:rl:{userId}`          | счётчик, 60 с                                                                                | снимков, созданных за минуту (INCR только при создании сборки); отдельный `rld:{userId}` — счётчик дельт                                                      |
| `g` (без `{serverId}`)            | HASH, TTL 600 с (обновляется)                                                                | `serverId` -> байты сборок + служебная память сервера; сумма значений — глобальный потолок                                                                    |

Почему `done` и `evt` живут 300 с, а не 24 часа. Метка нужна, только чтобы поздняя часть уже применённого комплекта не превратилась в новую сборку. Плагин повторяет часть не дольше таймаута (120 с); часть, которая создала бы новую сборку, всё равно отсекается по `capturedAt` старше 150 с (шаг 2), а запоздавший комплект не свежее применённого получает `stale` (шаг 2в). Значит, метка нужна минимум 150 с плюс окно расхождения часов (`capturedAt` может опережать приёмник до 60 с, Bridge 5.3), то есть не меньше 210 с; взято 300 с (запас около 40%). Метки `mark` — 150 с, как в контракте. Прежние 24 часа держали бы до 3000 событий в минуту × 1440 минут = около 4,3 млн ключей по 200 байт, то есть около 860 МБ на сервер в худшем случае (при реалистичных 200 снимках в минуту — около 170 МБ) вне всяких лимитов.

**Порядок проверок части (согласован с контрактом 6.1, правило 9).**

0. До Redis: схема; `snapshotId` по `^[0-9A-Za-z-]{26,64}$`; `parts` и `slotGroup` по закрытому перечню раскладок и допустимость `slotGroup` для `group` (3.6); диапазоны слотов; размер части. Ошибка — `rejected invalid_data`, Redis не вызывается (злоумышленник не создаёт ключи мусорными `snapshotId`).
1. Зондирование (только чтение): `done` — `duplicate`; `evt` — `duplicate` (часть, не завершавшая комплект); `mark`: `poison` — `rejected snapshot_mismatch`, `evicted` — `rejected resync_required`, `superseded` и `stale` — `stale`. `done` проверяется первым: поздняя часть применённого комплекта — `duplicate`, а не `stale`. Если живая сборка с этим `snapshotId` есть, идти к шагу 3: привязка, отсечка 150 с и лимиты создания не проверяются повторно (`userId` берётся из `meta`).
2. Только если живой сборки нет (часть создаёт новую), вне Lua: (а) отсечка по `capturedAt`: старше 150 с (таймаут 120 с + 30 с на расхождение часов) — `rejected resync_required`; сборка не создаётся. Это единственный способ «ответить за просрочку» без хранения следов истёкших сборок. Отсечка действует ТОЛЬКО на эту часть: части ЖИВОЙ сборки по `capturedAt` не отсекаются, их срок определяет таймаут 120 с, поэтому комплект, начатый вовремя, но доставленный с задержками, не теряется из-за расхождения часов. (б) привязка UUID к `userId` (`unknown_player`, 4.2 шаг 3): непривязанный UUID не занимает буфер. (в) свежесть: `(epoch, rev)` не свежее применённого ряда `(userId, serverSlug, grp)` (чтение из БД по PK; решающая проверка всё равно в транзакции 4.2) — `stale`, сборка не создаётся. Для `userId`, найденного здесь, скрипт вызывается с признаком «проверки создания пройдены».
3. Скрипт Lua (атомарно, ключи одного хэш-тега):
   1. Лениво удалить просроченное из `idx`, `idxb`, `svc` (старше 125 с / по баллу).
   2. Повторить проверки `done`, `evt`, `mark` (между зондом и скриптом они могли появиться).
   3. Сборки нет: если зонд видел её живой, а теперь её нет (истекла между зондом и скриптом), вернуть `reprobe` (обработчик повторяет шаги 1–2 один раз). Иначе проверить по порядку: счётчик `rl:{userId}` (не более 6) → 256 сборок и 8 МБ (`idxb`) → служебная память (`svc`) → потолок сервера и глобальный потолок. Любое нарушение — `rejected resync_required` (повтор не раньше чем через 60 с), существующие сборки не вытесняются, `rl` не увеличивается. Лимиты `(userId, group)`: если живых сборок уже 2, вытесняется самая старая по `firstSeenAt` (метка `evicted`, метрика `evicted`), и только после прохождения всех проверок выше. Затем создать `asm` (`meta`, EXPIRE 120 с один раз), добавить в `idx`, `idxb`, `own`, `svc`, увеличить `rl`.
   4. Сравнить заголовки и `parts` с `meta`: несовпадение — метка `poison`, удалить сборку, `rejected snapshot_mismatch`.
   5. Если `p:{n}` уже есть: сборка в состоянии «собирается» и тот же хэш — `duplicate`; другой хэш — метка `poison`, удалить сборку, `rejected conflict`. Если сборка уже «полна, не применена» и хэш тот же — не `duplicate`, а переход к шагу 7 (вариант «а» контракта: повтор завершающей части берёт захват и запускает применение). Иначе записать `p:{n}`, `h:{n}`, `g:{n}` (`slotGroup` уникален в комплекте; повтор `slotGroup` в другой части — `conflict`), обновить `bytes` и `idxb` (сборка не более 32 КБ, иначе `invalid_data` и сброс).
   6. Если комплект не полон — записать `evt:{eventId}` (в этом же скрипте, после записи части; потерянная при сбое часть не превращается в ложный `duplicate`) и ответить `accepted part_buffered`. Полнота — набор `slotGroup` равен набору раскладки для `group`, а не только число частей.
   7. Комплект полон, `done` нет: взять `lock` (SET NX, токен, 30 с). Захват получен — вернуть вызывающему все части для применения (`evt:{eventId}` ЕЩЁ НЕ пишется). Захват занят другим запросом — вся пачка получает `503` с `Retry-After` (отдельного «повторного» статуса для события нет), плагин повторяет ту же пачку.

**Применение полного комплекта (вне Lua).** Объединить части, отсортировать слоты по `(area, slot)`, проверить схему 3.2 целиком, санитизировать текст (3.3), вычислить `contentHash`; выполнить транзакцию 4.2 (`SELECT ... FOR UPDATE` по `(userId, serverSlug, grp)`; тот же `snapshotId` — без изменений; иначе свежесть `(epoch, rev)`). Результат:

- Применён: скриптом финиша, одной атомарной операцией (при совпадении токена `lock`): записать `done` (300 с) и `evt:{eventId}` завершающей части, удалить `asm`, `lock`, записи `idx`, `idxb`, `own`, оставить в `svc` служебный учёт до истечения `done`; сбросить из `own` все НЕПОЛНЫЕ сборки игрока и группы с меньшей свежестью `(epoch, rev)` (метка `superseded`, их поздние части получат `stale`; более свежие сборки остаются). Ответ `accepted snapshot_applied`.
- Не свежее применённого (`stale`): сборка удаляется, ставится метка `stale` (150 с), `evt` пишется, ответ `stale`.
- Сбой БД (вариант «а», выбор для п. 1 ревью): ответ `503`, сборка и части СОХРАНЯЮТСЯ, `lock` снимается сразу по токену (TTL 30 с остаётся страховкой при падении экземпляра), метки `done` и `evt:{eventId}` завершающей части НЕ пишутся. Повтор завершающей части (та же пачка, под тем же или новым `eventId`) попадает на шаги 3.5 и 3.7: сборка «полна, не применена» — берётся захват и применение запускается заново, а не `duplicate`. Если БД записала результат, а `done` не записалась (сбой между ними), повтор применяет тот же `snapshotId` повторно (транзакция идемпотентна) и ставит метку. Сбой не бесконечен: сборка истекает по таймауту 120 с, плагин отбрасывает комплект и строит новый снимок (метрика `apply_retry`, предупреждение при росте).

**Дедупликация `eventId`.** Для частей, не завершающих комплект, `evt:{eventId}` пишется в том же скрипте, что и помещение части в буфер (шаг 3.6). Для части, завершающей комплект, — ТОЛЬКО после успешного применения (скрипт финиша); одной дедупликации недостаточно, потому что плагин вправе повторить часть с новым `eventId`, поэтому повтор обрабатывается состоянием сборки (три состояния выше), а не только `evt`.

**Таймаут.** 120 секунд абсолютных от первой части, как в контракте 6.1; настраивается серверной настройкой приёмника (30–600 с) и должен быть равен значению у плагина (отсечка и TTL `done` пересчитываются: отсечка = таймаут + 30 с, `done` не меньше отсечки + 60 с). Значение — допущение (Q61): оно покрывает несколько повторов с backoff при `429` и `503`, но короче периода обычных снимков.

**Возобновление после истечения.** Сборка истекла (120 с), но часть пришла при возрасте `capturedAt` от 120 до 150 с: живой сборки нет, отсечка не сработала — создаётся НОВАЯ сборка с одной частью; она останется неполной и истечёт сама (потеря только места в квоте и одного учёта `rl`). Если за ней успеют прийти все остальные части, комплект полон и применяется как обычный.

**Лимиты и защита от переполнения.**

| Лимит                          | Значение                                                                 | Поведение при превышении                                     |
| ------------------------------ | ------------------------------------------------------------------------ | ------------------------------------------------------------ |
| Одновременных сборок на сервер | 256                                                                      | новая сборка не создаётся, `rejected resync_required`        |
| Буфер сборок на сервер         | 8 МБ (`idxb`)                                                            | то же                                                        |
| Служебная память на сервер     | 12 МБ (`svc`: не более 6144 снимков за окно 300 с по 2 КБ)               | то же                                                        |
| Потолок сервера всего          | 20 МБ (8 + 12)                                                           | то же                                                        |
| Глобальный потолок             | 64 МБ (сумма по серверам, ключ `g`)                                      | то же                                                        |
| Сборок на `(userId, group)`    | 2                                                                        | вытесняется самая старая по `firstSeenAt`                    |
| Частей в комплекте             | 1, 2 или 4 по закрытому перечню                                          | `invalid_data` (до Redis)                                    |
| Размер части                   | 16 КБ (лимит события Bridge)                                             | `invalid_data`                                               |
| Размер собранного снимка (ряд) | 32 КБ (4.1, 4.3)                                                         | `invalid_data`, сборка сбрасывается                          |
| Снимков в минуту на игрока     | 6; счёт при создании сборки (по новому `snapshotId`), части не считаются | `rejected resync_required` (повтор не раньше чем через 60 с) |
| Дельт в минуту на игрока       | 30; отдельный счётчик по событиям                                        | `rejected resync_required`                                   |

**Память Redis.** Прежняя оценка учитывала только сборки; ключи `done`, `mark`, `lock`, `own`, `idx`, `evt` и счётчики жили вне лимитов, а при политике `noeviction` заполнение Redis дало бы `503` ВСЕМ потребителям Redis (сессии, лимиты, дедупликация `player.*`). Теперь буфер и все служебные ключи ограничены общим потолком, который приложение проверяет САМО, не дожидаясь OOM Redis.

- Допущение развёртывания: общий Redis с жёстко заданным `maxmemory` и `noeviction`; `maxmemory` не меньше нагрузки остальных потребителей плюс 64 МБ (глобальный потолок) плюс запас 25%. Рекомендация: отдельный экземпляр Redis для Bridge (логическая БД разделяет только имена ключей; `maxmemory` и политика на экземпляр общие, то есть память логическая БД не изолирует). Отдельный экземпляр — расход и инфраструктура, решение владельца (Q61).
- Потолки: сервер 20 МБ (сборки 8 МБ + служебные 12 МБ), глобально 64 МБ. Достижение потолка — `rejected resync_required` по событию снимка (не `503` на весь запрос: иначе повтор пачки задерживал бы события других типов); остальные типы событий и остальные потребители Redis не затронуты. `503` остаётся для недоступного Redis и для OOM самого Redis.
- Оценка объёма (допущение, сверить на реальных данных). Ключ Redis вместе с именем и накладными расходами — около 200 байт. Служебный след одного снимка: `done` (около 0,2 КБ) + `mark` (до 0,2) + `evt` до 4 частей (до 0,8) + `lock` (0,2, временный) + доля `rl` и учёта `idx`, `svc` (около 0,3) = около 1,7 КБ, учёт 2 КБ. Худший случай на сервер: сборки 256 × 33 КБ ≈ 8 МБ + служебные 6144 × 2 КБ ≈ 12 МБ = 20 МБ; при 2 серверах 40 МБ (под глобальным потолком 64 МБ, запас на третий сервер и рост). Реалистичный случай (500 игроков в сети, снимок каждые 5 минут по 2 группам, около 200 снимков в минуту): живых сборок единицы (менее 1 МБ), служебные 200 × 5 мин × 2 КБ ≈ 2 МБ, итого около 3 МБ на сервер.
- Сервер с компрометированным ключом (7.4) может занять только свои 20 МБ; чужой буфер недоступен; глобальный потолок не даёт одному серверу вытеснить остальные (его доля ограничена 20 МБ), существующее состояние не затирается до полного валидного комплекта с большей свежестью.
- Метрики памяти: `bridge_inventory_buffer_bytes`, `bridge_inventory_service_bytes` (оценка `svc`), число отказов по потолку (`bridge_inventory_snapshots_total{result=ceiling}`); предупреждение в статусе сервера при 80% потолка.

**Метрики и логи.** Как в контракте 6.1: счётчики `bridge_inventory_parts_total{result}` и `bridge_inventory_snapshots_total{result}` (дополнительно `ceiling`, `reprobe`), gauge сборок и байтов буфера, гистограмма времени сборки. Логи: `key-id`, тип, код, `snapshotId`, `part`, `parts`; UUID игрока, слоты и текст предметов в логи не пишутся.

## 5. API сайта

Все пути под существующим префиксом API сайта, точный префикс и версия требуют сверки. Ответы строятся из явного белого списка полей (DTO), а не из строки БД.

| Метод и путь                           | Кто                                  | Назначение                                                           |
| -------------------------------------- | ------------------------------------ | -------------------------------------------------------------------- |
| `GET /inventory/me`                    | владелец (вошёл)                     | свой основной инвентарь по серверам: `?server=slug`                  |
| `GET /inventory/me/ender`              | владелец                             | свой Ender Chest                                                     |
| `GET /inventory/me/privacy`            | владелец                             | настройки `inventoryPublic`, `enderPublic`                           |
| `PATCH /inventory/me/privacy`          | владелец                             | изменить настройки                                                   |
| `GET /users/:username/inventory`       | любой, по правилам 6.2               | чужой основной инвентарь (по нику)                                   |
| `GET /users/:username/inventory/ender` | любой, по правилам 6.2               | чужой Ender Chest                                                    |
| `GET /admin/inventory/:userId`         | персонал: `inventory.view_any` + 2FA | основной инвентарь любого пользователя (`?group=main`)               |
| `GET /admin/inventory/:userId/ender`   | персонал: `inventory.view_any` + 2FA | Ender Chest; отдельное право `inventory.view_ender_any` (раздел 6.3) |

Решения:

- Основной инвентарь и Ender Chest — разные маршруты и разные фильтры на сервере. Ender Chest никогда не попадает в ответ основного, даже скрытым полем: «скрыто в интерфейсе» не считается защитой.
- Администраторский доступ — отдельные маршруты по `userId`, а не флаг в публичных: публичный маршрут не содержит «обходов», его нельзя заставить отдать больше параметрами запроса.
- Параметры: `server` — только `^[a-z0-9-]{1,32}$` и только из известных серверов с возможностью `inventory-sync`, иначе `422`; других параметров нет (ни `fields`, ни `include`).
- В ответе для не-владельца нет `userId`, UUID, `lastSeenAt`, `epoch`, `rev`, `contentHash`. Владельцу и персоналу UUID не нужен тоже: аватар строится по нику (`skins.controller.ts:17`).

Форма ответа (для всех групп):

```json
{
  "server": { "slug": "survival", "name": "Выживание" },
  "group": "main",
  "state": "ok",
  "capturedAt": "2026-11-17T12:00:00.000Z",
  "playerOnline": false,
  "isFresh": true,
  "slots": [{ "area": "hotbar", "slot": 0, "item": { "id": "minecraft:diamond_sword" } }],
  "viewer": { "relation": "owner" }
}
```

`state`: `ok` или `no_data` (привязка есть, снимка нет). `isFresh` = (сейчас − `capturedAt`) < порога (по умолчанию 15 минут для `playerOnline=true`; для offline — всегда `true`, время показывается как есть). Состояния «нет привязки» и «приватно» — коды ответа ниже.

### 5.1 Коды ответов

| Код   | Когда                                                                                                         | Тело `code`                                      |
| ----- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `200` | данные или `no_data`                                                                                          | —                                                |
| `304` | `If-None-Match` совпал (раздел 5.3)                                                                           | —                                                |
| `401` | `/me` и `/admin` без сессии                                                                                   | `unauthenticated`                                |
| `403` | профиль виден, привязка есть, но инвентарь приватен; нет права `inventory.view_any`; админ без 2FA (ADR-0156) | `inventory_private`, `forbidden`, `2fa_required` |
| `404` | пользователь не найден, профиль не виден зрителю (`NOBODY`, блокировка), нет привязки Minecraft               | `not_found` (одинаковое тело)                    |
| `422` | неверный `server` или `userId`                                                                                | `invalid_param`                                  |
| `429` | лимит (5.2)                                                                                                   | `rate_limited`, заголовок `Retry-After`          |
| `503` | Bridge выключен (`BRIDGE_ENABLED` не задан, Bridge 7), для функции нет возможностей ни у одного сервера       | `inventory_unavailable`                          |

`404` для «не виден профиль» и «нет привязки» одинаков по телу и времени ответа, чтобы по нему нельзя было перебирать, у кого есть привязка. `403 inventory_private` отдаётся только когда зритель вправе увидеть сам профиль и ник (иначе факт привязки не раскрывается больше, чем уже раскрывает профиль, `profiles.service.ts:221`).

### 5.2 Защита от IDOR, прямых запросов и перебора

- Идентификатор субъекта берётся только из сессии (`/me`), из ника в пути, разрешаемого к `userId` на сервере, или из `userId` админ-маршрута под правом. Нигде нет параметра «чей» вместе с «доверием клиенту».
- Решение о доступе принимает ОДНА функция `canViewInventory(viewer, target, group)` (раздел 6.2), вызываемая в каждом обработчике ДО чтения `PlayerInventory`; покрыта тестами на каждую комбинацию (раздел 11). Прямой запрос к Ender Chest или к чужому `userId` без права получает те же `403/404`, что и из интерфейса, потому что интерфейс ничего не решает.
- Нет эндпоинтов списка, поиска по предметам и «кто онлайн с предметом»; нет массовых выдач (`GET /inventory?user=a,b,c`).
- Лимиты (шаблон `@Throttle`, `minecraft-link.controller.ts:26`): `/me*` — 60 запросов в минуту на пользователя; чужой инвентарь — 30 в минуту на зрителя и 10 различных целей в минуту (перебор ников); без входа чужой инвентарь доступен только если профиль `EVERYONE` и инвентарь публичен, лимит — по IP (учитывая `TRUST_PROXY` (`apps/api/src/config/env.validation.ts`) и подсеть /64 для IPv6 (ADR-0163); точное применение требует сверки), 20 в минуту; админ — 30 в минуту. Лимит повторной смены приватности — 10 в минуту.
- `Cache-Control: private, no-cache` и `ETag`, `Vary: Cookie`; публичного (CDN или общего) кэша нет: приватность меняется мгновенно и не должна отдаваться из чужого кэша.

### 5.3 Кэш и ETag

`ETag = hash(contentHash, capturedAt, playerOnline, версия настроек приватности зрителя)`. Проверка доступа выполняется ДО сравнения `If-None-Match` (иначе `304` стал бы оракулом приватности). Кэша на стороне сервера (Redis) не вводится на первом шаге: чтение по уникальному ключу `(userId, serverSlug, grp)` дёшево. Фронтенд: опрос раз в 30 с, пока вкладка видима и `playerOnline=true`; после скрытия вкладки опрос остановлен. Push по WebSocket — отдельное решение (у Socket.IO сайта нет Redis-адаптера, `BRIDGE-CONTRACT.md:20`).

## 6. Приватность и права

### 6.1 Базовая модель (допущение)

- Владелец всегда видит свой инвентарь и Ender Chest.
- Выбор «публично» или «приватно» для основного инвентаря; по умолчанию приватно. Ender Chest скрыт по умолчанию и может стать публичным только при публичном основном инвентаре.
- Зритель видит публичный инвентарь только если он вправе видеть профиль владельца: `canViewProfile` (`visibility.ts:9`): `NOBODY`, `FRIENDS_ONLY` без дружбы и блокировка в любую сторону скрывают инвентарь, даже если он «публичный».
- Новых уровней вроде «только друзья» нет; при необходимости расширяется отдельным решением (вопрос Q34).

### 6.2 Единая функция доступа

```text
canViewInventory(viewer, target, group):
  если viewer.id == target.id                         -> разрешить
  если target нет Minecraft-привязки                   -> 404
  если !canViewProfile(target, viewer.id)             -> 404
  если !entitlementHook.allows(viewer, target, group) -> по хуку (6.4)
  если !privacy.inventoryPublic                       -> 403 inventory_private
  если group == ender и !privacy.enderPublic          -> 403 inventory_private
  иначе                                               -> разрешить
```

Администраторские маршруты (6.3) эту функцию не вызывают: у них свой guard и свои проверки.

### 6.3 Право персонала

Предлагаются новые ключи каталога (`packages/shared/src/permissions.ts`, модуль `inventory`): `inventory.view_any` (основной инвентарь любого пользователя) и `inventory.view_ender_any` (Ender Chest любого). Раздельные, чтобы выдавать минимально необходимое. Названия — предложение, окончательные выбирает владелец (Q34). Условия доступа:

- `@RequirePermissions('inventory.view_any')` на админ-маршрутах + admin-2FA (`permissions.guard.ts:43`, fail-closed, ADR-0156 и ADR-0164).
- Каждый успешный просмотр пишет `AuditService.log` (`audit.service.ts:40`): `actorId`, `action: 'inventory.view_any'`, `targetType: 'user'`, `targetId`, `severity: 'warning'`; содержимое инвентаря в журнал не попадает. Неуспех (нет права, нет 2FA) тоже фиксируется с `severity: 'warning'`.
- Иерархия персонала (проверка равного приоритета при mute/ban, ветка Q11, ADR-0164 в CHANGELOG; не смержено) НЕ распространяется на просмотр инвентаря сама: просмотр цели с равным или более высоким приоритетом — вопрос Q34 (рекомендация: разрешить, но всегда писать аудит).
- Лимит 30 запросов в минуту, оповещение при более чем 50 разных целей за час (порог задаёт владелец).
- Право не даёт ни изменять предметы, ни скрыто выдавать их: изменяющих маршрутов нет.

### 6.4 Точка расширения для доната (без правил)

Интерфейс `InventoryEntitlementPolicy` с одним методом `evaluate(viewer, target, group): 'default' | 'deny' | 'allow'`. Реализация по умолчанию возвращает `'default'` (остаётся базовая модель 6.2), правил и уровней в ней нет. Модуль Donation Entitlements (этап 05, hard gate) в будущем подставит свою реализацию. Что именно разрешено Apollo+, Ares+, Poseidon+, Zeus (`docs/donations/REQUIREMENTS.md`, строки 98–108, 167–168) — решает владелец на этапе 05; этот документ их не проектирует. Расхождение с требованиями: по ТЗ скрыть свой инвентарь могут «Poseidon+», а в базовой модели скрытие доступно всем (и это по умолчанию); см. Q34.

### 6.5 Персональные данные (152-ФЗ)

Данные инвентаря сами по себе не идентифицируют человека, но связаны с аккаунтом, ником и UUID. Меры: минимизация (только привязанные аккаунты; без IP, координат, текста книг и ников внутри предметов; без истории), приватность по умолчанию, каскадное удаление с аккаунтом и при отвязке, отсутствие публичных списков и поиска по предметам, UUID не отдаётся клиенту. Публикация ника уже есть в профиле (`profiles.service.ts:221`). Юридическая оценка — решение владельца (Q39); агенты заключений не дают.

## 7. Безопасность

### 7.1 Санитизация и XSS

- Текст предметов — только данные: приёмник вырезает всё, кроме полей схемы 3.3; на фронтенде он выводится React-текстом, никогда через `dangerouslySetInnerHTML`, `innerHTML` или построение HTML-строк. Ссылки в именах и лоре не превращаются в кликабельные.
- Цвет из данных переносится только как значение `style.color` после проверки по шаблону `#RRGGBB`/из списка имён; контраст проверяется (раздел 9: слишком тёмный цвет на тёмной теме поднимается до читаемого).
- Строки проходят нормализацию Unicode (NFC), вырезание управляющих символов и символов направления письма, лимиты длины (3.2). Имена предметов — пользовательский контент (переименование на наковальне): потенциально оскорбительный; жалоба на предмет не планируется на первом шаге (Q38).
- Нормализованный JSON хранится как есть; повторная санитизация выполняется и при выдаче (двойной контур), чтобы изменение правил действовало на старые данные.

### 7.2 Сырой NBT клиенту не отдаётся

Приёмник не принимает NBT (3.2); клиент получает только поля DTO. Сопоставление `enchants[].id` с русскими названиями делает фронтенд по справочнику; неизвестный id показывается как есть (в безопасном виде) без падений.

### 7.3 Лимиты и отказ в обслуживании

Лимиты Bridge (размер тела, пачка, событие) + лимиты раздела 3.5, 5.2; `slots` не более 41/27, строки не более 256, суммарный JSON ряда до 32 КБ (после сборки частей, 4.4), иначе `rejected invalid_data`. Рост памяти Redis ограничен ОБЩИМ потолком буфера и всех служебных ключей (4.4, «Память Redis»: сборки 8 МБ и служебные 12 МБ, итого 20 МБ на сервер, 64 МБ глобально; 256 сборок, 2 сборки на игрока и группу, таймаут 120 с, TTL `done` и `evt` 300 с; допущения до подтверждения владельцем (Q61)). Рост БД ограничен одним рядом на `(user, server, group)`. Всплеск дельт одного игрока гасится слиянием в плагине и отдельным лимитом дельт 30 в минуту на игрока (3.5); лимит снимков (6 в минуту) считается по снимкам, а не по частям.

### 7.4 Принадлежность UUID серверу и компрометация ключа сервера

Ключ сервера (Bridge 2.4) подписывает данные от его имени. Скомпрометированный ключ позволил бы подменить инвентарь ЛЮБОГО привязанного игрока. Меры: запись в `PlayerInventory` содержит `serverSlug` из `key-id`; данные разных серверов не пересекаются и не перезаписывают друг друга; в интерфейсе всегда виден сервер; ограничение возможностей сервера (`capabilities.inventory-sync`) выключено по умолчанию и включается админом для конкретного сервера; метрика «число различных UUID на сервер за час» с оповещением (порог задаёт владелец). Проверка «игрок действительно был на этом сервере» невозможна без `player.join` (выключены по Bridge 3.2): остаточный риск, принимается владельцем (Q37).

### 7.5 Принимаются только привязанные UUID

Данные принимаются только для UUID из `MinecraftAccount` (раздел 4.2, шаг 3). Это ограничивает: объём хранения, перебор чужих UUID через скомпрометированный сервер (нет «пустых» рядов под непривязанных) и объём персональных данных. Игрок, привязавшийся позже, получит данные при следующем входе (плагин шлёт снимок при входе).

### 7.6 Прочее

- Права и приватность проверяются на backend; фронтенд только отображает состояние (требование этапа 04).
- Логи: `userId`, `serverSlug`, `eventId`, тип, код результата. Содержимое предметов, тексты и UUID в логи не попадают.
- Без `BRIDGE_ENABLED=true` весь функционал отвечает `503` (fail-closed, Bridge 7). Тестового режима в продуктовом коде нет.

### 8.2 CDN, реестр и атлас

- Хост: `cdn-files.twomc.su` (разрешён в `next.config.mjs:56`). Пути относительные, абсолютный URL собирает frontend; URL в JSX не пишутся — только через реестр (как у `currency-assets.ts`), новый реестр `item-assets` в `packages/shared/src` по тому же шаблону.
- Атлас: один PNG-лист иконок 16×16 (или 32×32) по версии игры + JSON-манифест `id → {x, y}`; файлы с версией и хэшем в имени (`atlas-<версия>.<хэш>.png`), `Cache-Control: public, max-age=31536000, immutable`. Манифест ItemsAdder — отдельный JSON `itemsadder-manifest.<хэш>.json` (`namespace:id → путь/координаты`), собирается из пакета ресурсов сервера скриптом владельца.
- Отрисовка: `background-position` по манифесту, масштаб только целочисленный, `image-rendering: pixelated` (как для валют: PNG без AVIF/WebP). Не `next/image` с оптимизацией для спрайтов.
- Порядок поиска иконки: `itemsAdderId` в манифесте → `item.id` в ванильном атласе → запасная иконка (Lucide `Package`) с текстовым названием. Неизвестный id никогда не ломает сетку.
- Загрузка: манифест и атлас — по одному запросу на страницу, предзагрузка; весь инвентарь рендерится без запросов на каждый предмет (оптимизация против 68 отдельных картинок).
- Безопасность: пути из данных НЕ подставляются в URL; фронтенд берёт путь только из манифеста по ключу. Ключ, которого нет в манифесте — запасная иконка.
- CSP `img-src` и хост-лист — сверить перед срезом 3 (требует сверки).

### 8.3 Оптимизация снимков (суммарно)

Хэш содержимого (4.2) не даёт перезаписывать неизменённое; дельты (3.4) уменьшают трафик; слияние событий в плагине; один ряд на игрока и группу; чтение без кэша по PK; иконки из атласа, а не по одной.

## 11. Тест-план

Реализация после решений владельца. Данные симулятора Bridge — ЯВНО тестовые (ники вида `TestPlayer001`, UUID из диапазона тестовых), в продуктовом коде моков нет.

Unit (без БД):

- Схема `inventory.snapshot` и `inventory.delta`: валидные, лишние поля, `count` 0 и 100, слоты за границами, `id` с недопустимыми символами, строки длиннее лимита, 42 слота `main`.
- Санитизация прогонов текста: `§`-коды, управляющие символы, символы направления письма, `clickEvent`-подобные поля, некорректный цвет, длинные строки.
- `canViewInventory`: таблица всех комбинаций (владелец, чужой, друг, блокировка, `NOBODY`, `FRIENDS_ONLY`, нет привязки, `inventoryPublic`, `enderPublic`, хук доната `deny`/`allow`/`default`).
- Применение дельты: верная `baseRev`, неверная, чужая `epoch`, повтор, пропуск.
- Хэш содержимого: перестановка полей даёт тот же хэш (канонизация).

Сборка частей снимка (Q35; тесты на потерю и повтор частей ОБЯЗАТЕЛЬНЫ, блокируют закрытие среза 2). Unit (чистая логика сборщика) и e2e (локальные Redis и одноразовая БД, подписанные запросы симулятора Bridge):

- Потеря части: из 4 частей приходят 3, состояние игрока не меняется; после таймаута сборка отсутствует в Redis (проверка по TTL, время можно ускорить настройкой таймаута); поздняя часть с `capturedAt` старше 150 с — `resync_required`; потерянная первая, средняя и последняя части по отдельности.
- Повтор части: тот же `eventId` — `duplicate`; новый `eventId` с тем же `(snapshotId, part)` и содержимым — `duplicate`; повтор после применения — `duplicate` (метка `done`); в БД нет дублей слотов, снимок применён один раз; та же часть с другим содержимым — `conflict`, сборка сброшена, дальнейшие части — `snapshot_mismatch`.
- Порядок: прямой, обратный, перемешанный, по разным пачкам; результат одинаков (`contentHash` совпадает).
- Несогласованность: разное `parts`; разные `epoch`, `rev`, `capturedAt`, `group`, `uuid` между частями; `part` вне 1..`parts`; `parts` вне закрытого перечня (больше 4, `(main, 2)`, `(ender, 4)`); пересекающиеся слоты; дубли `slotGroup`; суммарно 42 слота `main`; части с пустым `slots`.
- Свежесть: порядок `epoch`, затем `rev`. Более свежий полный комплект вытесняет неполный; полный комплект не свежее применённого — `stale`; свежая неполная сборка не сбрасывается применением более старой; снимок новой эпохи (`epoch 6, rev 1`) с МЕНЬШИМ `capturedAt`, чем у применённого `(epoch 5, rev 90)`, применяется, а не `stale`; снимок той же эпохи с меньшим `rev` и БОЛЬШИМ `capturedAt` — `stale`; тот же `snapshotId` повторно — `snapshot_applied` без изменений; `done` после более свежего: `S1` применён (`done`), затем применён более свежий `S2`; повтор части `S1` — `duplicate`, а не `stale` (метка `done` проверяется первой); полный `S3` не свежее применённого — `stale` на завершающую часть, повтор любой его части в течение 150 с — снова `stale`, буфер не создаётся.
- Отсечка 150 с только для первой части: часть живой сборки с `capturedAt` старше 150 с (но сборка моложе 120 с) ПРИНИМАЕТСЯ; первая часть новой сборки старше 150 с — `resync_required`, сборка не создаётся.
- Возобновление после истечения: сборка истекла (120 с), часть пришла при возрасте `capturedAt` между 120 и 150 с — создаётся новая неполная сборка и истекает сама; если пришли все части — применяется.
- Конкурентность: две параллельные последние части на двух экземплярах (или двух процессах) — одно применение (`lock`), у проигравшего `503` с `Retry-After`; параллельные дельта и снимок одного игрока.
- Сбой БД -> 503 -> повтор -> снимок применён (п. 1 ревью, вариант «а»): последняя часть при сбое БД (внедрённая ошибка транзакции) — `503`; сборка и части в Redis целы, `lock` снят, `done` и `evt` завершающей части НЕ записаны; повтор завершающей части под тем же `eventId` и под НОВЫМ `eventId` — `accepted snapshot_applied`, снимок в БД один раз; повторная отправка после этого — `duplicate`; сбой дольше 120 с — сборка истекла, плагин строит новый снимок; сбой между записью в БД и меткой `done` — повторное применение того же `snapshotId` идемпотентно и ставит метку; падение экземпляра с удерживаемым `lock` — через 30 с применение берёт другой экземпляр.
- Лимиты: 257-я сборка сервера — `resync_required` без вытеснения; третья сборка игрока вытесняет самую старую по `firstSeenAt` (а не по `capturedAt`); буфер 8 МБ; снимок сверх 32 КБ — `invalid_data`; непривязанный UUID не создаёт сборку; изоляция серверов (одинаковый `snapshotId` на двух `serverId` не пересекается).
- Счёт лимита снимков и дельт: шесть снимков по 4 части (24 события) за минуту проходят, седьмой снимок — `resync_required`; при исчерпанном лимите части уже существующей сборки принимаются и счётчик не растёт; повтор части счётчик не растёт; 12 дельт в минуту не затрагивают счётчик снимков, 31-я дельта за минуту — `resync_required`; отказ по лимиту не вытесняет сборки игрока и не увеличивает счётчик.
- Проверки до Redis: `snapshotId` вне `^[0-9A-Za-z-]{26,64}$`, `parts` вне перечня, `slotGroup` недопустимый для `group` (например, `ender_a` для `main`), слот вне диапазона своей `slotGroup` — `invalid_data` при НУЛЕ обращений к Redis (счётчик вызовов в тесте).
- Полнота по набору `slotGroup`: при `parts = 4` два раза `hotbar` и без `equipment` комплект не полон и не применяется; полный набор из четырёх разных `slotGroup` в любом порядке применяется.
- Ключи Redis: все ключи сервера содержат `{serverId}` (статическая проверка аргументов скриптов: один хэш-тег); ключи игрока содержат внутренний `userId` и не содержат UUID; `done` и `evt` истекают через 300 с, `mark` через 150 с; после истечения `done` повтор части комплекта — `resync_required` по отсечке 150 с (а не повторное применение).
- Память Redis (п. 2 ревью): заполнение до лимита (256 сборок, 8 МБ, 12 МБ служебных, потолок сервера и глобальный) -> отказ только для снимков инвентаря (`resync_required`), а не `503` всего запроса; другие типы событий в той же пачке принимаются; остальные функции Redis (сессии, лимиты, дедупликация `player.*`) работают; Redis не получает OOM; после истечения TTL приём возобновляется; `ZCARD(svc)` и `idxb` возвращаются к нулю; ленивая очистка `idx` убирает просроченное; сервер A на потолке не мешает серверу B в пределах глобального потолка; OOM самого Redis — `503`.
- Redis: недоступен — `503` без изменения состояния; ложный `duplicate` не возникает (дедупликация `eventId` не завершающей части пишется после буферизации, завершающей — после применения); перезапуск Redis без AOF равен таймауту.
- Метрики: счётчики `bridge_inventory_*` растут по результатам; в логах нет UUID, слотов и текста предметов.

e2e на ОДНОРАЗОВОЙ БД (не рабочей, не production; миграции только в одноразовой):

- Приём через подписанные запросы симулятора: принятый снимок, повтор `eventId` (`duplicate`), устаревший (`stale`), дельта по неверной ревизии (`resync_required`), `unknown_player`, `unsupported_type` без возможности, чужой `serverId` (`server_mismatch`).
- Чтение: владелец; чужой при приватном (`403 inventory_private`); чужой при публичном; публичный, но профиль `NOBODY` (`404`); блокировка (`404`); Ender Chest при публичном основном и скрытом Ender (`403`); прямой запрос Ender Chest по `/admin/...` без права (`403`) и с правом без 2FA (`403 2fa_required`); `404` одинаково для «нет пользователя» и «нет привязки» (сравнение тела и кода).
- Аудит: запись при каждом админ-просмотре, без содержимого.
- Лимиты: `429` и `Retry-After`; перебор различных целей.
- Отвязка и удаление пользователя: каскадное удаление рядов.
- Параллельные снимки и дельты одного игрока: нет потери обновлений (транзакция 4.2).
- Fail-closed: без `BRIDGE_ENABLED` — `503`.

Frontend (jsdom): состояния раздела 9, клавиатурная навигация по сетке, `aria-label` слотов, отсутствие `dangerouslySetInnerHTML` с данными предметов (статическая проверка), запасная иконка для неизвестного `id`; визуальная проверка на тёмной и светлой теме, ширины 375/768/1440 — вручную владельцем или в браузерных тестах (если они есть).

Безопасность: тест «ответ не содержит `userId`, UUID, `epoch`, `contentHash` для не-владельца»; тест «ответ основного инвентаря не содержит Ender Chest»; fuzz текстовых полей.
