# Runbook: production-деплой и откат

Скрипт: `infrastructure/deploy.sh` (запускается на сервере из корня checkout). Решение по порядку шагов — ADR-0158.
Деплой, откат и восстановление выполняет только владелец или назначенный им человек; агенты их не запускают.

## Предусловия

- `.env` заполнен по `.env.example` (в git не попадает), на сервере чистый `main`.
- Свободное место: снимок БД + образы нового релиза. Проверить `df -h` до запуска.
- Каталог снимков вне репозитория: `PREDEPLOY_BACKUP_DIR` (по умолчанию `$HOME/twomc-backups/predeploy`). Каталог и файлы создаются с `umask 077`. Снимок содержит персональные данные: не копировать в репозиторий, не отправлять в чаты и тикеты.
- Допущение по размеру сервера: от 4 ГБ RAM. Лимиты памяти (`POSTGRES_MEM_LIMIT` 1g, `REDIS_MEM_LIMIT` 256m, `API_MEM_LIMIT` 768m, `WEB_MEM_LIMIT` 768m) переопределяются в `.env`. Ротация логов: `LOG_MAX_SIZE` (10m), `LOG_MAX_FILE` (5).

## Порядок деплоя

`infrastructure/deploy.sh`:

1. Проверки: есть `.env`, дерево чистое (маркеры `.release*` в `.gitignore`), ветка `main`, `git pull --ff-only`.
2. `build` образов `twomc-api:<sha>`, `twomc-web:<sha>`.
3. `up -d postgres redis`.
4. Снимок БД (`pg_dump -Fc` внутри контейнера postgres, проверка `pg_restore --list`). Любая ошибка (в том числе пустой файл) останавливает деплой до миграций.
5. `prisma migrate deploy` (только expand-миграции, см. ниже). Ошибка останавливает деплой, приложения не переключаются.
6. Запись `.release.prev` (если был `.release`) и `.release`, `up -d api web`.
7. Health check api (`/health`) и web (`/`). Успех: очистка старых тегов образов. Провал: автооткат образов.
8. Ненулевой код выхода при любом провале; сообщение «Откат образов выполнен» печатается только если откат реально прошёл health check.

Настройки: `KEEP_RELEASES` (по умолчанию 3, минимум 2) — сколько последних тегов `twomc-api` и `twomc-web` хранить; текущий и предыдущий релиз никогда не удаляются. `PREDEPLOY_BACKUP_KEEP` (7) — число снимков. `docker image prune -f` не используется; висячие (`<none>`) слои и build-кэш чистить вручную при нехватке диска (`docker builder prune` — осознанно, не по cron).

## Откат образов

- Автоматически при провале health check, либо вручную: `infrastructure/deploy.sh rollback` (нужен `.release.prev`).
- Откат меняет только образы api и web. Схема БД не откатывается.
- Первый деплой (нет `.release.prev`): автооткат невозможен, скрипт честно сообщает об этом и завершается с кодом 1. Плохой релиз остаётся запущенным: остановить `docker compose ... stop api web` вручную или быстро исправить и повторить деплой. Заранее убедитесь в работоспособности на staging либо с `API_PORT`/`WEB_PORT` вне публичного nginx.
- Если откат не прошёл health check, скрипт печатает «Откат НЕ выполнен» и завершается с кодом 1: нужно ручное вмешательство (логи `docker compose ... logs --tail=200 api web`).

## Откат схемы из снимка

Выполнять только если миграция повредила данные или предыдущий релиз несовместим со схемой. Приводит к потере записей, сделанных после снимка (заказы, регистрации): оценить с владельцем.

1. Остановить приложения: `docker compose --env-file .env -f infrastructure/docker-compose.prod.yml stop api web`.
2. Выбрать снимок: `ls -lt "$PREDEPLOY_BACKUP_DIR"`; имя содержит sha релиза и время.
3. Сохранить текущее состояние перед восстановлением (ещё один `pg_dump -Fc` тем же способом).
4. Восстановить в чистую БД: `pg_restore --clean --if-exists --no-owner -d "$POSTGRES_DB"` внутри контейнера postgres, подав файл на stdin (`exec -T postgres ... < снимок`), либо в пересозданную пустую БД.
5. Запустить предыдущий релиз: `infrastructure/deploy.sh rollback` (образы) и проверить health.
6. Репетиция restore-drill на синтетических данных и бэкапы по расписанию — задача P3-03b; до её завершения восстановление не отрепетировано (риск R3/R8).

## Правило expand/contract для миграций

Скрипт применяет миграцию до переключения приложений, поэтому действующий (старый) релиз какое-то время работает на новой схеме, а при автооткате старый релиз возвращается на неё же. Следовательно, каждая миграция должна быть обратно совместима с предыдущим релизом:

- Expand (в релизе N): добавлять таблицы, колонки (nullable или с default), индексы; не удалять и не переименовывать то, что читает релиз N-1.
- Migrate: код релиза N пишет в новое и старое, backfill отдельным шагом.
- Contract (в релизе N+1 или позже, после того как N-1 больше не нужен для отката): удалять старые колонки, ужесточать `NOT NULL`, переименовывать.
- Необратимая миграция (drop, смена типа, `NOT NULL` без default) в одном релизе с кодом, который её требует, запрещена без явного одобрения владельца и проверенного снимка.
- Откат такого релиза возможен только из снимка (см. выше).

## Проверки скрипта без деплоя

`bash -n infrastructure/deploy.sh`; shellcheck (временное окружение `pip install shellcheck-py` в venv); `git check-ignore .release .release.prev`; `docker compose --env-file <dummy.env> -f infrastructure/docker-compose.prod.yml config -q` с dummy-значениями; стаб-тесты со стабами docker/curl/git (сценарии из отчёта `docs/reports/2026-11-16-00-p3-03a.md`).
