# Runbook: production-деплой и откат

Скрипт: `infrastructure/deploy.sh` (запускается на сервере из корня checkout). Решение по порядку шагов и правилу expand/contract принято владельцем (Q18), Redis `noeviction` (Q20) — ADR-0158.
Деплой, откат и восстановление выполняет только владелец или назначенный им человек; агенты их не запускают.

## Предусловия

- `.env` заполнен по `.env.example` (в git не попадает), на сервере чистый `main`.
- Свободное место: снимок БД + образы нового релиза. Проверить `df -h` до запуска.
- Каталог снимков вне репозитория: `PREDEPLOY_BACKUP_DIR` (по умолчанию `$HOME/twomc-backups/predeploy`). Каталог и файлы создаются с `umask 077`. `chmod 700` ставится только после проверок: каталог не символическая ссылка, не общий каталог (`$HOME`, `/`, `/tmp`) и не внутри репозитория; иначе деплой останавливается до снимка. Нужен выделенный подкаталог. Снимок содержит персональные данные: не копировать в репозиторий, не отправлять в чаты и тикеты.
- Допущение по размеру сервера: от 4 ГБ RAM. Лимиты памяти (`POSTGRES_MEM_LIMIT` 1g, `REDIS_MEM_LIMIT` 256m, `API_MEM_LIMIT` 768m, `WEB_MEM_LIMIT` 768m) переопределяются в `.env`. Ротация логов: `LOG_MAX_SIZE` (10m), `LOG_MAX_FILE` (5).

## Порядок деплоя

`infrastructure/deploy.sh`:

1. Проверки: есть `.env`, дерево чистое (маркеры `.release*` в `.gitignore`), ветка `main`, `git pull --ff-only`.
2. `PREDEPLOY_BACKUP_KEEP` должен быть целым числом не меньше 1, иначе выход с кодом 1 до любых действий над БД.
3. Pre-flight: если есть `.release`, проверяется health текущего релиза (`PREFLIGHT_TRIES`, по умолчанию 3 попытки). Провал: код 1, снимок и миграции не запускались. Обход для hotfix, когда текущий релиз уже сломан: `SKIP_PREFLIGHT=1` (скрипт печатает предупреждение).
4. Скан миграций: новые `apps/api/prisma/migrations/*/migration.sql` между `.release` и `HEAD` проверяются на `DROP TABLE`, `DROP COLUMN`, `DROP CONSTRAINT`, `DROP INDEX`, `ALTER TABLE ... DROP <имя>` (без слова `COLUMN`, в том числе `DROP IF EXISTS`; безопасные `DROP DEFAULT`, `DROP NOT NULL`, `DROP IDENTITY`, `DROP EXPRESSION` не считаются), `RENAME`, `ALTER COLUMN ... TYPE`, `SET NOT NULL`, `TRUNCATE` (строчные `--`-комментарии игнорируются, блочные `/* */` не разбираются). Найдено, либо коммит из `.release` неизвестен git (например, shallow clone): код 1 до снимка. Обход: `ALLOW_DESTRUCTIVE_MIGRATION=1` только с одобрением владельца и после свежего снимка. Это текстовая эвристика (ложные срабатывания и пропуски возможны), а не доказательство совместимости: ревью миграций обязательно (см. expand/contract ниже). На первом деплое pre-flight и скан пропускаются.
5. `build` образов `twomc-api:<sha>`, `twomc-web:<sha>`.
6. `up -d postgres redis`.
7. Снимок БД (`pg_dump -Fc` внутри контейнера postgres, проверка `pg_restore --list`). Любая ошибка (в том числе пустой файл) останавливает деплой до миграций. Только что созданный снимок ротацией не удаляется.
8. `prisma migrate deploy` (только expand-миграции, см. ниже). Ошибка останавливает деплой, приложения не переключаются.
9. `up -d api web`. Маркеры на этом шаге НЕ пишутся.
10. Health check api (`/health`) и web (`/`). Успех: запись `.release.prev` (прежний `.release`, только если он отличается от нового sha) и `.release`, затем очистка старых тегов образов. Провал: автооткат образов на прежний релиз, `.release` и `.release.prev` не меняются.
11. Ненулевой код выхода при любом провале; сообщение «Откат образов выполнен» печатается только если откат реально прошёл health check. Если запись маркеров или `mv` при ручном откате не удались, скрипт сообщает об этом и завершается с кодом 1.

Порядок «снимок, миграция, переключение, health» отступает от формулировки «миграция после health-check»; владелец принял его вместе с правилом expand/contract (Q18, ADR-0158). Двухфазный деплой не вводится. Health (`/health`) выполняет только `SELECT 1` и не проверяет схему, поэтому успешный health не доказывает совместимость кода со схемой.

Настройки: `KEEP_RELEASES` (по умолчанию 3, минимум 2) — сколько последних тегов `twomc-api` и `twomc-web` хранить; текущий и предыдущий релиз никогда не удаляются. `PREDEPLOY_BACKUP_KEEP` (7, целое не меньше 1) — число снимков, включая свежий. `REDIS_MAXMEMORY` (192mb) — лимит данных Redis с политикой `noeviction` (fail-closed): ключи не вытесняются, при заполнении запись возвращает ошибку, вход и проверка прав отвечают 500, обхода лимитов нет, но возможен DoS. Throttler хранит счётчики в памяти процесса API, не в Redis; в Redis лежат счётчики brute-force, кеш прав, состояния 2FA и чат. Политика `noeviction` принята владельцем (Q20, ADR-0158); альтернативы (`volatile-lru`, без `maxmemory`) отвергнуты. Мониторинг памяти Redis (алерт, рекомендуется порог ~80% от `REDIS_MAXMEMORY`) — задача на момент появления сервера, пока не настроен; держать не выше ~75% от `REDIS_MEM_LIMIT`. `docker image prune -f` не используется; висячие (`<none>`) слои и build-кэш чистить вручную при нехватке диска (`docker builder prune` — осознанно, не по cron).

## Откат образов

- Автоматически при провале health check (цель: прежний `.release`), либо вручную: `infrastructure/deploy.sh rollback` (цель `.release.prev`, после успеха он становится `.release`).
- Откат меняет только образы api и web. Схема БД не откатывается.
- Первый деплой (нет `.release.prev`): автооткат невозможен, скрипт честно сообщает об этом и завершается с кодом 1. Плохой релиз остаётся запущенным: остановить `docker compose ... stop api web` вручную или быстро исправить и повторить деплой. Заранее убедитесь в работоспособности на staging либо с `API_PORT`/`WEB_PORT` вне публичного nginx.
- Если откат не прошёл health check, скрипт печатает «Откат НЕ выполнен» и завершается с кодом 1: нужно ручное вмешательство (логи `docker compose ... logs --tail=200 api web`).

## Откат схемы из снимка

Выполнять только если миграция повредила данные или предыдущий релиз несовместим со схемой. Приводит к потере записей, сделанных после снимка (заказы, регистрации): оценить с владельцем.

1. Остановить приложения: `docker compose --env-file .env -f infrastructure/docker-compose.prod.yml stop api web`.
2. Выбрать снимок: `ls -lt "$PREDEPLOY_BACKUP_DIR"`; имя содержит sha релиза и время.
3. Сохранить текущее состояние перед восстановлением (ещё один `pg_dump -Fc` тем же способом).
4. Восстановить в чистую БД: `pg_restore --clean --if-exists --no-owner -d "$POSTGRES_DB"` внутри контейнера postgres, подав файл на stdin (`exec -T postgres ... < снимок`), либо в пересозданную пустую БД.
5. Запустить предыдущий релиз: `infrastructure/deploy.sh rollback` (образы) и проверить health.
6. Репетиция restore-drill на синтетических данных и бэкапы по расписанию — задача P3-03b; до её завершения восстановление не отрепетировано (риск R3/R8).

## Правило expand/contract для миграций

Скрипт применяет миграцию до переключения приложений, поэтому действующий (старый) релиз какое-то время работает на новой схеме, а при автооткате старый релиз возвращается на неё же. Следовательно, каждая миграция должна быть обратно совместима с предыдущей версией кода (правило принято владельцем, Q18):

- Expand (в релизе N): добавлять таблицы, колонки (nullable или с default), индексы; не удалять и не переименовывать то, что читает релиз N-1.
- Migrate: код релиза N пишет в новое и старое, backfill отдельным шагом.
- Contract (в релизе N+1 или позже, после того как N-1 больше не нужен для отката): удалять старые колонки, ужесточать `NOT NULL`, переименовывать.
- Необратимая миграция (drop, rename, смена типа, truncate, `NOT NULL` без default) в одном релизе с кодом, который её требует, запрещена без явного одобрения владельца и проверенного снимка. Скрипт останавливает деплой при drop (table/column/constraint/index), rename, смене типа, `SET NOT NULL`, truncate; `NOT NULL` в составе `ADD COLUMN` без default не обнаруживается автоматически.
- Откат такого релиза возможен только из снимка (см. выше).

## Проверки скрипта без деплоя

`bash -n infrastructure/deploy.sh`; shellcheck (временное окружение `pip install shellcheck-py` в venv); `git check-ignore .release .release.prev`; `PREDEPLOY_BACKUP_KEEP=0 infrastructure/deploy.sh` (до снимка выходит с кодом 1); `docker compose --env-file <dummy.env> -f infrastructure/docker-compose.prod.yml config -q` с dummy-значениями; стаб-тесты со стабами docker/curl/git (сценарии из отчёта `docs/reports/2026-11-16-00-p3-03a.md`).
