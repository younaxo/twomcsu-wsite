# Runbook: платежи - вебхук, ротация секрета, возвраты, инциденты

Основание: ADR-0157 (подпись вебхука), ADR-0187 (платёжный слой, fail-closed, ротация), ADR-0188 (возвраты и сверка, 0.9), ADR-0184 (выдача). Переменные - `docs/runbooks/production-env-checklist.md`. Приёмка - `docs/runbooks/acceptance-checklist.md`.
Боевые ключи, регистрацию вебхука, включение флагов и деньги выполняет только владелец. В репозиторий, чаты и логи секреты не попадают.

Состояние на 2026-11-23: реальный провайдер не выбран (адаптер 0.8b не начат). В production допустим только `PAYMENT_PROVIDER` пусто: оплаты нет, оформление отвечает 503 `payment_unavailable`. Провайдеры `test` и `mock-http` в production не регистрируются. Разделы о регистрации вебхука у реального провайдера описывают контракт сайта; детали кабинета провайдера дополнить после выбора.

## 1. Вебхук

- Адрес: `POST https://<домен API>/webhooks/payments/<имя провайдера>` (контроллер `payments-webhook.controller.ts`). Путь должен быть доступен снаружи через nginx; другие пути API закрывать не нужно.
- Ответы: неизвестный провайдер - 404; нет или неверная подпись - 401; успех - 200 (повтор того же события идемпотентен). Провайдеры повторяют не-2xx, поэтому лимит вебхука отдельный: 600 запросов в минуту на IP (R29).
- Подпись: HMAC-SHA256 над строкой `timestamp.rawBody` ключом `PAYMENT_WEBHOOK_SECRET`; заголовки `x-twomc-signature` и `x-twomc-timestamp` (общая функция `webhook-signature.ts`; формат реального провайдера определит адаптер 0.8b). Сравнение в постоянное время. Секрет короче 32 символов отвергается при старте; пустой секрет = все вебхуки 401.
- Проверяются: подпись, провайдер, `paymentId`, сумма и валюта заказа (`amount_mismatch`, `currency_mismatch`), идемпотентность по событию.
- Регистрация у провайдера (владелец): указать адрес выше и секрет подписи; тот же секрет записать в `.env` как `PAYMENT_WEBHOOK_SECRET`, перезапустить api. Только HTTPS. Источник IP: см. `docs/runbooks/cloudflare-real-ip.md` (лимит считается по реальному IP клиента).
- Проверка без боевых ключей (dev): `docs/runbooks/payment-webhook-sim.md`. На production симулятор отказывает.

## 2. Ротация секрета вебхука (ADR-0187 п. 7)

Секрет меняется без простоя, пока принимаются подписи обоих значений.

1. Владелец генерирует новый секрет (не короче 32 символов) у себя; в чат и репозиторий не вставлять.
2. В `.env`: новое значение в `PAYMENT_WEBHOOK_SECRET`, прежнее в `PAYMENT_WEBHOOK_SECRET_PREVIOUS`. Перезапустить api.
3. В кабинете провайдера заменить секрет подписи на новый.
4. Убедиться, что вебхуки идут (тестовое событие или первая оплата): в логе api нет всплеска 401.
5. Очистить `PAYMENT_WEBHOOK_SECRET_PREVIOUS`, перезапустить api.
Утечка секрета: сразу шаги 1-3 с немедленной очисткой PREVIOUS (старый секрет считать скомпрометированным), затем разобрать заказы за период (раздел 5).

## 3. Возвраты (0.9, ADR-0188)

Включение: `STORE_REFUNDS_ENABLED=true` (по умолчанию выкл.). При выкл. флаге `admin/store/refunds/*` отвечает 503 `refunds_disabled`, сверка не работает, старый `PATCH /admin/orders/:id/refund` - только учётная отметка (деньги не возвращаются). При вкл. старый путь отвечает 409 `refund_use_refunds_api`.

API (все под JWT и проверкой прав):

| Действие                     | Запрос                                                  | Право                                      | Условия                                                                                  |
| ---------------------------- | ------------------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------- |
| Список                       | `GET /admin/store/refunds`                              | `orders.refund`                            | фильтры `status`, `orderId`                                                              |
| Обычный возврат              | `POST /admin/store/refunds/orders/:orderId`             | `orders.refund`                            | `reason` 1-1000, `twoFactorCode`, `amount?` (без неё весь остаток); только до выдачи     |
| Возврат по ошибке (override) | `POST /admin/store/refunds/orders/:orderId/override`    | `orders.refund` и `store.refund.override`  | только если товар выдан; причина и свежий код 2FA; по умолчанию право только у владельца |
| Ручной выход из ожидания     | `POST /admin/store/refunds/orders/:orderId/mark-failed` | `orders.refund`                            | заказ в `REFUND_PENDING`, причина, 2FA; иначе 409 `refund_not_pending`                   |

- 2FA: только TOTP (резервные коды не принимаются), шаг одноразовый: повтор того же кода отклоняется, ждать следующий.
- До/после выдачи (Q85): после выдачи обычный возврат 409 `refund_after_delivery`; только override. Задания в `IN_PROGRESS` - 409 `delivery_in_progress`.
- Рубины: заказ с `paymentMethod = ruby` возврату не подлежит (422 `refund_rubies_unsupported`).
- Override при полном возврате: сайтовая выдача отзывается автоматически; игровая НЕТ - в `order_refunds.requiresManualRevoke = true` и запись в аудите: администратор отзывает вручную (команда или отметка в админке). Это обязательный ручной шаг.
- Частичный возврат выдачу не отзывает, заказ остаётся `COMPLETED`.
- Статусы заказа: `REFUND_PENDING` (ответа нет, ждёт сверки), `REFUND_FAILED` (отказ или тайм-аут; повтор разрешён и использует тот же ключ идемпотентности, второго возврата у провайдера не будет), `REFUNDED`. Пока заказ в `REFUND_PENDING`/`REFUND_FAILED`, выдача не идёт.
- Аудит: `orders.refund.*` (в том числе `override_requested/_completed`, `marked_failed`, `failed`) - критичный.

Фоновая сверка (только при `STORE_REFUNDS_ENABLED=true`, таймер 5 минут):

- Заказы в статусах оплаты PENDING и «ложный FAILED» с `paymentId`, старше `STORE_REFUNDS_RECONCILE_MIN_AGE_MINUTES` (15) и не старше `STORE_REFUNDS_RECONCILE_WINDOW_HOURS` (72), партия `STORE_REFUNDS_RECONCILE_BATCH` (50): опрос `getPaymentStatus`, затем тот же путь, что у вебхука. Не чаще порога на заказ (`orders.paymentReconciledAt`).
- `REFUND_PENDING` сверяется по `refundedAmount` провайдера; дольше `STORE_REFUNDS_PENDING_TIMEOUT_HOURS` (72) без отражения возврата - `REFUND_FAILED` (`provider_timeout`).
- Если у провайдера возврат есть, а на сайте нет, или частичный мимо сайта, заказ не завершается, пишется предупреждение для ручного разбора. Логи содержат только id заказов и коды.

Миграция `20261122100000_store_refunds` (expand-only) применяет только владелец, после бэкапа БД, ДО деплоя кода и до включения флага; не применялась на момент написания (ADR-0188 п. 10).

## 4. Рекомендуемый порядок включения оплаты (владелец)

1. Миграции применены, restore-drill пройден (`backup-restore.md`).
2. `PAYMENT_PROVIDER`, `PAYMENT_API_KEY`, `PAYMENT_WEBHOOK_SECRET` заданы (после 0.8b); вебхук зарегистрирован.
3. `STORE_DELIVERY_ENABLED` и настройка сайта `store.delivery.enabled` включены только после проверки шаблонов команд (0.11) на тестовом игровом сервере.
4. `STORE_REFUNDS_ENABLED=true` до первой боевой оплаты, чтобы приёмочный возврат прошёл по новому API.
5. `QUICK_BUY_ENABLED=true` - отдельным решением владельца.
6. Приёмочная оплата малой суммы по `acceptance-checklist.md`.

Аварийное выключение (любое из, без деплоя и отката схемы): `PAYMENT_PROVIDER` пусто и перезапуск api - оформление 503; `QUICK_BUY_ENABLED=false`; `STORE_DELIVERY_ENABLED=false` - выдача останавливается; `STORE_REFUNDS_ENABLED=false` - возвраты 503; право `system.modules.protected` выключает модуль магазина.

## 5. Инциденты

Общее: сначала зафиксировать время и номера заказов (`O-...`), ПДн и секреты в тикет не копировать.

### 5.1 Провайдер недоступен

Признаки: оформление падает с кодами `unavailable`/`timeout`, много `REFUND_PENDING`, рост 5xx в логе. Адаптер сам повторяет только `unavailable`/`timeout` (`PAYMENT_HTTP_RETRIES`, по умолчанию 2); 4xx не повторяется.
Действия: проверить страницу статуса провайдера; при затяжном сбое выключить оформление (`PAYMENT_PROVIDER` пусто) или `QUICK_BUY_ENABLED=false`; `REFUND_PENDING` ничего не делать вручную до срока `STORE_REFUNDS_PENDING_TIMEOUT_HOURS`: сверка сама разрешит после восстановления. Не нажимать «повторить возврат» вслепую: ключ идемпотентности защитит, но сначала проверить статус в кабинете провайдера. `mark-failed` - только после подтверждения в кабинете, что деньги НЕ ушли.

### 5.2 Двойной вебхук

Ожидаемо и безопасно: повтор события идемпотентен (заказ не завершается дважды, задания выдачи не дублируются, ответ 200). Если провайдер сообщает о двух РАЗНЫХ платежах по одному заказу - это не дубль вебхука: второй платёж вернуть вручную через кабинет провайдера и записать в аудит; проверить, что заказ завершён один раз.
Поздний `succeeded` по заказу в `FAILED` возвращает заказ в обработку и выдачу (ADR-0187 п. 6); по `CANCELLED` заказ не восстанавливается: уходит уведомление HIGH персоналу с `orders.view` и суперпользователям, решение о возврате принимает человек (раздел 3).

### 5.3 Расхождение сумм или валюты

Вебхук с `amount_mismatch`/`currency_mismatch` заказ НЕ завершает. Действия: сравнить сумму в кабинете провайдера и `total` заказа; если деньги получены в другом размере - вернуть разницу или всё через кабинет провайдера и записать причину; заказ не завершать вручную без решения владельца. Системное расхождение (все заказы) - вероятна ошибка настройки валюты или ключей; выключить оформление и разобраться до включения.

### 5.4 Подпись отклоняется (всплеск 401)

После ротации секрета: проверить порядок шагов раздела 2 и что перезапущен именно api. Иначе возможна подделка вебхуков: оценить, не утёк ли секрет, при подозрении выполнить ротацию. Лимит 600/мин на IP ограничивает флуд.

### 5.5 Деньги вернулись у провайдера мимо сайта

Сверка пишет предупреждение, заказ не завершается. Действия: вручную отметить заказ по правилам владельца (учётная отметка возврата только при выключенном флаге; при включённом использовать API возвратов) и при выданном товаре отозвать выдачу.
