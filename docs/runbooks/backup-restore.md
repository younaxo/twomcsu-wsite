# Runbook: бэкап и восстановление

Скрипты: `infrastructure/backup/backup.sh`, `restore.sh`, `restore-drill.sh`; compose для drill — `infrastructure/docker-compose.restore-drill.yml`. Решение — ADR-0159, риск — R30 (связан с R3 и R8).
Бэкап, восстановление и drill выполняет только владелец или назначенный им человек; агенты их не запускают. Сервера пока нет (R8): расписание не включено, drill не выполнялся («drill отложен: диск»).

## Допущения (решение владельца D9 не принято)

- RPO 24 часа (плановый бэкап раз в сутки) плюс снимок перед каждым деплоем с миграциями. RTO 4 часа.
- Шифрование `age` публичным ключом; приватный ключ хранится офлайн у владельца и на сервере не лежит. Альтернатива — gpg (ниже).
- Хранение: RU-S3 (провайдер не выбран) через rclone или aws cli; без S3 — локальный fallback с ротацией. Срок хранения: 14 локальных копий, срок в S3 задаётся lifecycle-правилом бакета (предложение: 30 дней).
- Подтверждение restore в production (допущение, решение владельца не принято): интерактивно — ввод имени БД; без TTY — только при `RESTORE_CONFIRM=OVERWRITE-PRODUCTION` вместе с `--non-interactive`; api должен быть остановлен; перед `pg_restore --clean` скрипт сам снимает дамп текущей БД и при неудаче останавливается.
- Ключи и учётные данные S3 не создаются и в репозиторий не попадают; ниже только имена переменных.

## Что копируется

| Объект           | Способ                                                                                                 | Примечание                                                                                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PostgreSQL       | `pg_dump -Fc` через `docker compose exec -T postgres`                                                  | проверка `pg_restore --list`                                                                                                                                                 |
| Роли и пароли БД | `pg_dumpall --globals-only`                                                                            | содержит хеши паролей; хранится только зашифрованным                                                                                                                         |
| `uploads`        | `tar` из временного контейнера, том смонтирован `:ro`, `--network none`, `--read-only`, `--pull=never` | при переходе на S3-драйвер хранилища — бэкап бакета, а не тома                                                                                                               |
| Redis            | не копируется                                                                                          | кеш и временные счётчики (brute-force, presence); refresh-сессии лежат в Postgres. После восстановления пользователи могут разово войти заново. Подтверждение владельца — D9 |
| `.env` и секреты | вне этих скриптов                                                                                      | хранить в менеджере секретов                                                                                                                                                 |

Каждый бэкап — каталог `twomc-<UTC-время>-<метка>/`: `postgres.dump(.age|.gpg)`, `globals.sql(...)`, `uploads.tar.gz(...)`, `MANIFEST.txt` (формат, время, шифрование, число записей `pg_restore --list`), `PLAIN.sha256` (хеши открытых файлов), `SHA256SUMS` (хеши хранимых файлов и манифеста). Каталог создаётся как `.partial` и переименовывается только после успеха; права `umask 077`.

## Переменные окружения

`backup.sh`: `BACKUP_DIR` (`$HOME/twomc-backups/scheduled`, вне репозитория), `BACKUP_KEEP` (14 последних на каждую метку отдельно), `BACKUP_MIN_FREE_MB` (2048), `BACKUP_TAG` (`scheduled`; перед деплоем — `predeploy`), `BACKUP_ENCRYPT` (`age` | `gpg` | `none` только с `BACKUP_ALLOW_UNENCRYPTED=1`), `AGE_RECIPIENT`, `GPG_RECIPIENT`, `BACKUP_S3_RCLONE_REMOTE` (вид `remote:bucket/prefix`; учётные данные в конфиге rclone) либо `BACKUP_S3_URI` и `BACKUP_S3_ENDPOINT` (aws cli; учётные данные в окружении aws), `UPLOADS_VOLUME`, `BACKUP_SKIP_UPLOADS`.
`restore.sh`: `RESTORE_SINGLE_TRANSACTION` (1 по умолчанию, 0 отключает), `AGE_IDENTITY` (путь к файлу приватного ключа), `RESTORE_TMP_DIR`, `RESTORE_MIN_FREE_MB`, `RESTORE_CONFIRM` (только с `--non-interactive`), `RESTORE_SNAPSHOT_DIR` (снимки перед prod-восстановлением, по умолчанию `$HOME/twomc-backups/pre-restore`; внутри репозитория отказ), `RESTORE_SNAPSHOT_KEEP` (3 последних снимка), `AGE_RECIPIENT` (шифрование снимка), `RESTORE_SNAPSHOT_PLAIN_DAYS` (7, срок в предупреждении). Параметры: `--target drill|prod`, `--non-interactive`.
Коды выхода `backup.sh`: 0 успех; 1 ошибка; 3 нет места (до начала); 4 бэкап создан локально, но выгрузка в S3 не удалась; 5 бэкап сохранён, но ротация не удалила старую копию (4 приоритетнее 5; причина в stderr; cron должен уведомлять о любом ненулевом коде). `restore.sh`: 2 — нарушена целостность (sha256, дешифровка, `pg_restore --list`), восстановление не начато; 3 — нет места.

## Бэкап

1. Предусловия: `df -h` (нужно места больше размера БД и uploads, плюс временный открытый дамп до шифрования), `AGE_RECIPIENT` задан, каталог `BACKUP_DIR` вне репозитория.
2. Плановый: `infrastructure/backup/backup.sh`. Снимок перед деплоем: `BACKUP_TAG=predeploy infrastructure/backup/backup.sh`. Встроенный снимок `deploy.sh` (ADR-0158) остаётся; подключение `backup.sh` вместо него — отдельный шаг после появления сервера.
3. Без S3 скрипт печатает «S3 не настроен — локальный fallback» и хранит `BACKUP_KEEP` последних копий каждой метки: ротация идёт отдельно по тегу, свежие `scheduled` не вытесняют `predeploy`. Ошибка удаления при ротации печатает «ОШИБКА РОТАЦИИ» в stderr, бэкап остаётся сохранённым, а выход будет 5 (при провале S3 остаётся 4, как более важный). При нехватке места выход 3 и бэкап не начат; нехватка посреди бэкапа даёт ненулевой выход, `.partial` удаляется.
4. Расписание (cron или systemd timer) настраивается на сервере после его появления, не в репозитории. Ненулевой код должен приводить к уведомлению.
5. Копию без S3 нужно регулярно вывозить с сервера: бэкап на том же диске не защищает от потери сервера.

## Восстановление

Выполняет владелец. Приводит к потере записей, сделанных после бэкапа (оценить с владельцем).

1. Остановить api и web: `docker compose --env-file .env -f infrastructure/docker-compose.prod.yml stop api web`.
2. Сохранить текущее состояние полным бэкапом (с uploads): `BACKUP_TAG=prerestore infrastructure/backup/backup.sh`. Отдельно `restore.sh --target prod` сам делает снимок БД (только БД) в `RESTORE_SNAPSHOT_DIR` (вне репозитория, иначе отказ). С `AGE_RECIPIENT` снимок шифруется (`.dump.age`); без него остаётся открытый дамп с ПДн, скрипт громко предупреждает, и его нужно зашифровать или удалить не позднее чем через 7 дней после проверки. Хранится `RESTORE_SNAPSHOT_KEEP` (3) последних снимков, ротация отдельная от плановых бэкапов; сбой удаления даёт предупреждение.
3. Если копия в S3 — скачать каталог бэкапа целиком (`rclone copy`) во временный каталог вне репозитория.
4. `AGE_IDENTITY=<файл ключа> infrastructure/backup/restore.sh --target prod <каталог>` из терминала: после проверок скрипт просит ввести имя БД production; иное значение отменяет восстановление. Без TTY (автоматизация) требуются оба условия: `RESTORE_CONFIRM=OVERWRITE-PRODUCTION` и `--non-interactive`, иначе отказ. Если api запущен, перезапускается (restarting) или на паузе, отказ (проверяются состояния running, restarting, paused); если снимок текущей БД не удался, стоп до `pg_restore --clean`. Скрипт сначала проверяет sha256 хранимых файлов; при несовпадении печатает «ОТКАЗ», выходит с кодом 2 и ничего не меняет. Затем расшифровка, сверка sha256 открытого дампа, `pg_restore --list`, `pg_restore --clean --if-exists --single-transaction --no-owner --no-acl`. Открытый дамп живёт во временном каталоге и удаляется при выходе.
5. Роли: `globals.sql` скрипт не применяет. Нужен только при пересоздании кластера: расшифровать и выполнить `psql` вручную.
6. uploads: расшифровать `uploads.tar.gz`, проверить `tar -tzf`, распаковать во временный контейнер с монтированием тома на запись (`docker run --rm -v <том>:/data ... tar -C /data -xzf -`).
7. Запустить api и web, проверить `/health`, вход, загрузку изображения. При необходимости откат образов — `docs/runbooks/deploy.md`.

Режим `--single-transaction` (по умолчанию): `pg_restore --clean --if-exists` выполняется одной транзакцией, поэтому при любой ошибке всё откатывается и БД остаётся в прежнем состоянии, а не наполовину очищенной. Он совместим с `--clean --if-exists`; несовместим с `-j` (параллельное восстановление), но `restore.sh` читает дамп со stdin и `-j` не использует. Глобальные объекты (роли, `globals.sql`) pg_restore не затрагивает, они остаются ручным шагом. Цена: любая ошибка, даже та, что обычный режим пропустил бы, откатывает восстановление целиком; тогда `restore.sh` выходит с кодом 1, а причину нужно искать в stderr `pg_restore`. Если известно, что ошибки безобидны (например, конфликт расширений), можно запустить с `RESTORE_SINGLE_TRANSACTION=0` (печатается предупреждение; при сбое БД может остаться частично восстановленной, откат возможен только из снимка перед восстановлением). Реальным PostgreSQL режим пока не проверен: его проверит restore-drill при первом запуске (Docker недоступен в среде исправления).

Целостность и подмена: `SHA256SUMS`, `PLAIN.sha256` и манифест защищают от повреждения при хранении и передаче, но не от подмены: тот, кто может изменить каталог бэкапа, может пересчитать хеши. Подпись (например, `age`/`minisign`/gpg-подпись `SHA256SUMS` ключом владельца с проверкой при восстановлении) — будущее улучшение, сейчас не реализовано.

Расшифровка вручную: `age -d -i <ключ> -o postgres.dump postgres.dump.age`; проверка: `sha256sum -c SHA256SUMS` в каталоге бэкапа.

## gpg вместо age

`BACKUP_ENCRYPT=gpg GPG_RECIPIENT=<идентификатор открытого ключа>`; расшифровка при восстановлении использует локальный gpg-агент владельца. Открытый ключ импортируется на сервер, секретный на сервере не хранится.

## Restore-drill

Назначение: доказать цикл «дамп, (шифрование), восстановление» на синтетике и измерить время против RTO. Настоящие дампы (ПДн) и миграции production-схемы в drill не используются; это только по отдельному разрешению владельца и после появления сервера (R8).

```
DRILL_POSTGRES_PASSWORD=<одноразовое значение, не из production> infrastructure/backup/restore-drill.sh
```

Поднимает проект `twomc-restore-drill` (контейнер `twomc-restore-drill-postgres`, порт `127.0.0.1:55432`, том `drill-pgdata`, без production `env_file`), создаёт таблицу из `DRILL_ROWS` (10000) строк через `psql`, делает `backup.sh`, удаляет таблицу, выполняет `restore.sh --target drill`, сверяет число строк и md5, печатает размер дампа и время, затем `down -v` (только свой проект). Для цикла с шифрованием: `BACKUP_ENCRYPT=age AGE_RECIPIENT=... AGE_IDENTITY=<файл>`.
Нужен Docker и свободное место (образ `postgres:16-alpine`, дамп, том). Образы заранее не скачиваются скриптами.

Журнал drill (заполнить после выполнения):
