# Чек-лист приёмки владельцем (подэтап 0.10)

Цель: владелец выкладывает сайт с оплатой и принимает первую боевую оплату. Все пункты выполняет и отмечает владелец (или назначенный им человек); агенты сервер, деньги, ключи и DNS не трогают. Связанные документы: `deploy.md`, `production-env-checklist.md`, `backup-restore.md`, `payments.md`, `monitoring.md`, `smoke-test.md`, `cloudflare-real-ip.md`, `owner-emergency-access.md`.
Отмечать так: `[x]` с датой. Любой невыполненный пункт блокирует боевую оплату.

## A. Сервер и домен (D7)

- [ ] Сервер от 4 ГБ RAM, один сервер на территории РФ для ПДн граждан РФ (юридическая проверка владельцем), бюджет согласован.
- [ ] Docker и compose установлены, SSH только по ключам, файрвол: наружу только 80/443 (и порт игры, см. раздел B), порты api/web слушают `127.0.0.1`.
- [ ] Чистый checkout `main`, `.env` создан на сервере (не в git).
- [ ] nginx по `infrastructure/nginx.twomc.su.conf.example`, HTTPS-сертификат выпущен, автопродление проверено.

## B. DNS и Cloudflare (Q4, Q14, Q56)

- [ ] Схема прокси (Q4): по умолчанию `клиент -> nginx -> api` (DNS в Beget, без Cloudflare — как в infrastructure/nginx.twomc.su.conf.example); `TRUST_PROXY=1`. Вариант `Cloudflare -> nginx -> api` — только по отдельному решению владельца.
- [ ] Только если владелец выбрал Cloudflare: real_ip и закрытие origin по `cloudflare-real-ip.md` (диапазоны актуальны, файрвол origin, Authenticated Origin Pulls по желанию).
- [ ] Игровой трафик Minecraft НЕ проксируется через Cloudflare (Q14); для игрового хоста отдельное имя и адрес без проксирования (Q56, вариант а).
- [ ] Путь `/webhooks/payments/` достижим снаружи по HTTPS (проверка: запрос без подписи даёт 401 или 404, не 502 и не таймаут).

## C. Секреты и переменные

## I. Приёмочная оплата малой суммы

Только после A-H. Выполняет владелец реальной картой на минимальной сумме.

- [ ] Включены `STORE_REFUNDS_ENABLED=true` и (если проверяется) `STORE_DELIVERY_ENABLED`/настройка `store.delivery.enabled`; api перезапущен.
- [ ] Оформление заказа на недорогой товар; оплата проходит у провайдера.
- [ ] Заказ в админке перешёл в `COMPLETED` (вебхук принят, сумма и валюта совпали).
- [ ] Выдача: для игрового товара задание выполнено и привилегия/команда видна в игре; для сайтового - видна в профиле. Статус задания в админке корректен.
- [ ] Проверка quick-buy по нику (если владелец включает `QUICK_BUY_ENABLED`): оформление без входа, лимит 10/мин, выдача в игре.
- [ ] Возврат этой суммы через `POST /admin/store/refunds/orders/:orderId` (если товар уже выдан - через override с причиной, и ручной отзыв игровой выдачи): свежий TOTP, `REFUNDED`, деньги пришли обратно, аудит записан.
- [ ] Заказ, возврат и задание выдачи видны в админке; чек (если подключён) сформирован.
- [ ] После приёмки: решено, какие флаги остаются включёнными (`payments.md`, раздел 4); аварийное выключение понятно.

## K. Напоминание: девять вопросов «Вернуться в конце слоя 0»

Chief напоминает владельцу вместе с приёмкой; ответы не запрашиваются заранее. Полный текст: `docs/plan/PRIORITY-PLAN-DRAFT.md`, раздел 7.4, и `docs/reports/QUESTIONS-FOR-OWNER.md`, раздел «Вернуться в конце слоя 0». Кратко:

1. Что даёт каждая привилегия, что значит «от» в цене, доплата при апгрейде.
2. Список нарушений, за которые бан и мут за деньги не снимаются; лимиты платного снятия.
3. Где тратятся рубины и боевой пропуск.
4. Политика возвратов (до и после выдачи).
5. Хостинг и месячный бюджет.
6. Проверка бухгалтером: самозанятый и виртуальные товары, лимит дохода.
7. Иностранные карты и евро.
8. Регистрация тестовых аккаунтов провайдера.
9. Оферта и политика ПДн перед запуском.

Безопасные допущения до ответов: возврат до выдачи на исходный способ, после выдачи только override; бан и мут за деньги снимаются только по правилам владельца; описываются только реально работающие перки.

## L. Повторная проверка ADR-0183 нагрузкой

После 0.10 перепроверить значения `connection_limit=15`, `pool_timeout=10`, `PRISMA_TX_MAX_WAIT_MS`/`PRISMA_TX_TIMEOUT_MS` 10000/10000 нагрузкой, близкой к боевой (вебхуки оплаты, голосование и формы под advisory-lock, приёмник Bridge):

- [ ] Нагрузочный прогон выполнен на staging или в окно владельца (не на боевых данных без согласования; e2e и нагрузка - только при свободных ресурсах).
- [ ] Нет роста 503 `busy` (P2024/P2028), `pg_stat_activity` не упирается в `connection_limit` + служебные.
- [ ] Значения оставлены или пересмотрены (запись в ADR-0183 и `production-env-checklist.md`).
