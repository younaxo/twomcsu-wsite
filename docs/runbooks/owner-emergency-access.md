# Runbook: аварийный доступ владельца при обязательной 2FA

Решение: ADR-0169 (Accepted, решение владельца Q22/Q24), уточняет ADR-0109 и ADR-0156. Окружение: `docs/runbooks/production-env-checklist.md`.
Статус документа на 2026-11-17: процедура составлена по коду, на реальной БД и сервере не проверялась.
В документе нет паролей, токенов, значений ключей, адресов и хостов. Реальные значения в репозиторий, чаты и тикеты не попадают.
Выполняет владелец (или человек, которого он назначил лично). Агенты ничего из этого не запускают (см. последний раздел).

## Что нужно знать заранее

- 2FA персонала обязательна всегда. Если на сервере задан `TWO_FACTOR_ENCRYPTION_KEY` (не короче 32 символов), любое действие по праву у пользователя без включённой 2FA даёт 403 с кодом `admin_2fa_required` (`apps/api/src/modules/roles/guards/permissions.guard.ts:33-44`, `:118`).
- Вход при этом не блокируется: пользователь без 2FA входит и может настроить её сам. Контроллер `auth/2fa` закрыт только `JwtAuthGuard`, без проверки прав, поэтому настройка, включение и отключение 2FA доступны и пользователю, которому действия по праву отклоняются (`apps/api/src/modules/auth/two-factor/two-factor.controller.ts:19-20`, `:31`, `:38`, `:48`).
- В production без ключа длиной не менее 32 символов API не стартует (`apps/api/src/config/env.validation.ts:224-237`), а если стартовал, guard отклоняет всех (fail-closed, `permissions.guard.ts:40-42`).

## (а) Резервные коды

- При включении 2FA создаётся 10 одноразовых кодов вида `xxxx-xxxx` (`apps/api/src/modules/auth/two-factor/backup-codes.ts:7`, `:10-18`).
- Коды возвращаются в ответе `enable` один раз (`apps/api/src/modules/auth/two-factor/two-factor.service.ts:114-157`, возврат на `:156`); повторно сервер их показать не может.
- На сервере хранится только HMAC-SHA256 хеш нормализованного кода с секретным pepper, производным от `TWO_FACTOR_ENCRYPTION_KEY` (`apps/api/src/modules/auth/two-factor/secret-box.ts:25-27`, `:61-63`; запись хешей `two-factor.service.ts:149-154`).
- Хранение владельцем: только офлайн. Бумага или офлайн-носитель в надёжном месте; не облако, не чат, не заметки на синхронизируемых устройствах, не скриншот.
- Регистр, пробелы и дефис при вводе не важны (`backup-codes.ts:21-24`). Всё же вводите код с дефисом: ввод из одних цифр без дефиса (алфавит содержит цифры 2-9, такой код возможен, но редок) распознаётся как код TOTP и не подойдёт (`two-factor.service.ts:226`).
- Каждый код действует один раз: после использования он помечается `usedAt` (`two-factor.service.ts:250-254`). Остаток кодов видно в статусе 2FA (`two-factor.service.ts:73-89`).

## (б) Потерял устройство с приложением, резервные коды есть

Вход по резервному коду работает. Проверено по коду:

1. `POST /auth/login` с верным паролем при включённой 2FA возвращает `twoFactorRequired` и одноразовый челлендж вместо сессии (`apps/api/src/modules/auth/auth.service.ts:301-307`).
2. `POST /auth/login/2fa` (`apps/api/src/modules/auth/auth.controller.ts:186-209`) вызывает `completeTwoFactorLogin` (`auth.service.ts:320-346`), затем `completeChallenge` (`two-factor.service.ts:277-313`), затем `verify` с разрешёнными резервными кодами по умолчанию (`two-factor.service.ts:214-255`, резервная ветка `:247-254`).
3. Ограничения: челлендж живёт 5 минут и сгорает после 5 неверных кодов (`two-factor.service.ts:28-29`, `:295-302`); неверные коды считаются неудачей входа для IP (`auth.service.ts:338-343`).

После входа по резервному коду. Ключевое ограничение, следующее из кода:

- Перевыпуск резервных кодов (`POST /auth/2fa/backup-codes`) принимает только код из приложения. Резервный код там отклоняется (`two-factor.service.ts:191-197`, `allowBackup: false`). Без устройства этот путь недоступен.
- Остаётся путь через отключение 2FA: `POST /auth/2fa/disable` требует пароль и действующий код, причём резервный код подходит (`two-factor.service.ts:160-187`; проверка пароля `:168`, проверка кода `:171` вызывает `verify` с резервными кодами по умолчанию). Для этого нужен второй, ещё не использованный резервный код: первый уже израсходован при входе.
- Отключение удаляет все резервные коды и секрет (`two-factor.service.ts:174-186`). Затем сразу настройте 2FA заново на новом устройстве: `POST /auth/2fa/setup`, затем `POST /auth/2fa/enable` с кодом из приложения (`two-factor.service.ts:93-157`). Будет выдан новый набор из 10 кодов; запишите его офлайн, старый набор уничтожьте.
- Пока 2FA отключена, действия персонала по праву отклоняются с `admin_2fa_required` (при заданном ключе). Это ожидаемо; окно закрывается включением 2FA.
- Если после входа неиспользованных резервных кодов не осталось, `disable` выполнить нельзя (нужен код, а пароль без кода не принимается): тогда действуйте по разделу (в).

## (в) Нет ни устройства, ни резервных кодов: сброс 2FA в БД (только владелец)

ВНИМАНИЕ. Это обход защиты. Выполняет только владелец на сервере, лично. Агентам запрещено выполнять и тем более запускать этот SQL. Шаблон приведён как текст.

Предварительно:

1. Сделайте бэкап базы (по `docs/runbooks/deploy.md` и бэкап-скриптам, ADR-0158/ADR-0159), убедитесь, что бэкап читается.
2. Определите `<USER_ID>` и сверьте его по двум признакам: например, `username` и `email` (или дата создания). Ошибка в id отключит 2FA чужому пользователю.
3. Убедитесь, что запрос идёт именно в нужную БД, а не в тестовую.

Имена таблиц и колонок сверены по `apps/api/prisma/schema.prisma`: таблица `users` (`@@map("users")`, `:475`), колонки поля `twoFactorEnabled`, `twoFactorSecret`, `twoFactorPendingSecret`, `twoFactorEnabledAt`, `twoFactorLastStep` без `@map`, то есть в БД это camelCase и в SQL нужны двойные кавычки (`:279-284`); таблица `two_factor_backup_codes` (`:3312`), колонка `"userId"` без `@map` (`:3304`). Набор колонок повторяет `disable()` (`two-factor.service.ts:174-186`).

```sql
-- Сверка перед сбросом: должна вернуться ровно одна строка, ожидаемый пользователь.
SELECT id, username, email, "twoFactorEnabled"
FROM users
WHERE id = '<USER_ID>';

BEGIN;

UPDATE users
SET "twoFactorEnabled" = false,
    "twoFactorSecret" = NULL,
    "twoFactorPendingSecret" = NULL,
    "twoFactorEnabledAt" = NULL,
    "twoFactorLastStep" = NULL
WHERE id = '<USER_ID>';
-- Ожидается: UPDATE 1. Иначе ROLLBACK;

DELETE FROM two_factor_backup_codes
WHERE "userId" = '<USER_ID>';

COMMIT;
```

Если `UPDATE` затронул не 1 строку, выполните `ROLLBACK;` вместо `COMMIT;`.

После сброса:

1. Немедленно войдите этим пользователем (пароль) и настройте 2FA заново: `/auth/2fa/setup`, `/auth/2fa/enable`; запишите новые резервные коды офлайн.
2. ВАЖНО: пока 2FA выключена, при заданном ключе действия по праву дают 403 `admin_2fa_required`. Человек сможет войти, но не работать. Это ожидаемое поведение.
3. Сессии. Если есть подозрение на компрометацию, пользователь после входа может отозвать все свои сессии: `DELETE /auth/sessions` (`auth.controller.ts:247-250`, `auth.service.ts:511-515`; помечает `revokedAt` у `refresh_tokens`, `schema.prisma:629-643`). Отзыв чужих сессий через SQL здесь не описан: срок жизни уже выданных access-токенов по коду не проверялся (не проверено).
4. Запись события. Прямой SQL обходит приложение, и автоматической записи в аудит не будет: `AuditService.log` вызывается кодом приложения (`apps/api/src/modules/audit/audit.service.ts:40-64`), а `AuditInterceptor` покрывает HTTP-мутации персонала. Таблица `audit_logs` (`schema.prisma:1657-1679`) требует `actorId` существующего пользователя. Готового механизма «ручная запись из консоли» в коде не найдено. Поэтому: запишите событие (дата и время, кто выполнил, причина, `<USER_ID>`, ссылка на бэкап) в офлайн-журнал владельца. Хранение audit по умолчанию 90 дней (`audit.service.ts:37`, `:135-143`), поэтому журнал владельца нужен и как долговременная запись. Ручной `INSERT` в `audit_logs` не рекомендуется: механизм не проверялся (не проверено).

## (г) Смена или потеря `TWO_FACTOR_ENCRYPTION_KEY`

Что зависит от ключа:

- Секреты TOTP шифруются AES-256-GCM, ключ шифрования выводится из `TWO_FACTOR_ENCRYPTION_KEY` через SHA-256 (`secret-box.ts:24`, `:30-40`).
- Хеши резервных кодов считаются HMAC с pepper, тоже производным от этого ключа (`secret-box.ts:25-27`, `:61-63`).

Что происходит при другом (но допустимом, не короче 32) ключе. По коду:

- Вход кодом из приложения: расшифровка секрета бросает ошибку (`secret-box.ts:42-57`, проверка тега GCM), она вызывается из `verify` (`two-factor.service.ts:228`) и не является `UnauthorizedException`, поэтому проходит через `completeTwoFactorLogin` без изменений (`auth.service.ts:338-345`). В `apps/api/src` собственного глобального фильтра исключений не найдено (поиск `APP_FILTER`, `@Catch`), значит по умолчанию Nest вернёт 500. Точный ответ не проверялся запуском (не проверено).
- Вход резервным кодом: хеш не совпадёт, `verify` вернёт `null`, пользователь получит 401 `two_factor_invalid` (`two-factor.service.ts:250-254`, `:308-312`).
- Итог: все существующие 2FA непригодны, персонал со включённой 2FA не может войти; `disable` и `regenerate` тоже не работают (они вызывают `verify`). Единственный выход: сброс по разделу (в) для каждого пользователя.
- Ожидающие секреты (`twoFactorPendingSecret`) тоже не расшифруются при `enable` (`two-factor.service.ts:129`).

Если ключ не задан или короче 32 символов:

- В production API не стартует (`env.validation.ts:224-237`). Если всё же запущен без ключа (обход схемы), guard отклоняет все действия персонала (fail-closed, `permissions.guard.ts:40-42`, `isProductionLike` в `apps/api/src/config/node-env.ts:6-9`).
- `TwoFactorService` без ключа не создаёт шифратор: операции 2FA отвечают 503 `two_factor_unavailable` (`two-factor.service.ts:50-56`, `:63-71`), в том числе второй шаг входа пользователя со включённой 2FA.
- Только при явном `NODE_ENV=development` или `test` требование не применяется (`permissions.guard.ts:30-31`).

Плановая ротация ключа. Допущение: безопасного пути смены ключа без потери 2FA в коде нет (ключа версий и перешифровки не найдено). Рекомендация: заранее сбросить 2FA всем пользователям (контрактная операция по решению владельца), затем сменить ключ, затем каждый заново включает 2FA. Окно, когда у персонала нет 2FA, означает 403 `admin_2fa_required` на их действиях; планируйте его. Предыдущий ключ хранится в менеджере владельца до завершения ротации (`production-env-checklist.md`). Ключ никогда не попадает в чат и репозиторий.

## (д) Аварийная учётная запись владельца (break-glass)

Допущение (рекомендация, не реализовано и не требуется кодом): завести отдельную учётную запись владельца с полным доступом и включённой 2FA, с собственным набором резервных кодов, хранимым офлайн отдельно от кодов основной учётной записи. В повседневной работе её не использовать; вход под ней записывать в журнал владельца. Это снижает вероятность ситуации (в), но не отменяет её: при потере ключа сервера (раздел (г)) 2FA нужно сбрасывать у всех, включая эту запись.

## Что делать агентам

Ничего из этого не выполнять. Агентам запрещено:

- запускать SQL из раздела (в) или любой другой запрос к боевой БД;
- читать, печатать, менять или генерировать `TWO_FACTOR_ENCRYPTION_KEY`, `.env*` и хранилище секретов;
- вызывать `/auth/2fa/*` и `/auth/login*` на боевом сервере, отзывать сессии, менять учётные записи владельца;
- создавать break-glass-учётку или резервные коды.

Агент, получивший запрос на аварийный доступ, останавливается и сообщает владельцу ссылку на этот runbook.

## Не проверено

- Реальный HTTP-ответ при расшифровке с другим ключом (ожидается 500, см. (г)).
- Срок действия уже выданных access-токенов после сброса 2FA и отзыв сессий через SQL.
- Допустимость ручной записи в `audit_logs` и существование отдельной админ-процедуры для неё.
- Весь SQL и вся процедура не выполнялись ни на одной БД.
- Расхождение пробелов в ключе: guard и схема обрезают пробелы (`trim`, `permissions.guard.ts:37-39`), `TwoFactorService` длину проверяет без `trim` (`two-factor.service.ts:50-51`). Ключ без пробелов по краям это не затрагивает; при ключе с краевыми пробелами поведение не проверялось.
