# Доступ сайта к БД LiteBans: пользователь только для чтения, сеть и TLS (этап 02)

Статус: инструкция владельцу, НЕ выполнена. Основание: ответ владельца Q31 (2026-11-17), движок MySQL, драйвер `mysql2` (Q29). Сервер и БД при подготовке не затрагивались, агент к ним не подключается.

Связанные документы: `docs/stage-02/LITEBANS-INTEGRATION-DESIGN.md` (разделы 2.1-2.4, ADR-0166), `docs/runbooks/production-env-checklist.md`.

Правила этого документа:

- Все значения в угловых скобках (`<...>`) — плейсхолдеры. Реальные хосты, IP, пароли и пути к сертификатам в репозиторий, чат и отчёты не попадают.
- Пароль пользователя БД создаёт и хранит только владелец (хранилище секретов). Агент его не видит и не принимает.
- Сайт получает от LiteBans только чтение: нет `INSERT`, `UPDATE`, `DELETE`, DDL и прав на другие базы.
- Столбец `ip` недоступен пользователю ни в одной таблице (IP и контактные данные на сайте не показываются никогда, Q31).

## 1. Что понадобится

| Что                              | Значение                                          |
| -------------------------------- | ------------------------------------------------- |
| Имя БД LiteBans                  | `<ИМЯ_БД_LITEBANS>` (по умолчанию `litebans`)     |
| Префикс таблиц                   | `<ПРЕФИКС>` (по умолчанию `litebans_`)            |
| Адрес сервера БД                 | `<ХОСТ_БД>`, порт `<ПОРТ_БД>` (по умолчанию 3306) |
| Адрес сайта (исходящий IP)       | `<IP_САЙТА>` (статический)                        |
| Имя пользователя                 | `twomc_ro`                                        |
| Пароль                           | `<ПАРОЛЬ_ЗАДАЁТ_ВЛАДЕЛЕЦ>`                        |
| Каталог сертификатов (сервер БД) | `<КАТАЛОГ_TLS_СЕРВЕРА>`                           |
| Файл CA (сайт)                   | `<ПУТЬ_К_CA_НА_САЙТЕ>`                            |

Перед началом выполните сверку схемы (раздел 1.4 дизайна: `SELECT VERSION();`, `SHOW TABLES LIKE 'litebans%';`, `SHOW CREATE TABLE ...`) и пришлите вывод текстом без реальных ников и IP: права ниже строятся по реальным столбцам.

## 2. Пользователь MySQL только с SELECT на litebans\_\*

Выполняется администратором БД. Имя хоста в учётке — это адрес сайта, с которого он подключается (`<IP_САЙТА>`), а не `%`.

```sql
CREATE USER 'twomc_ro'@'<IP_САЙТА>'
  IDENTIFIED BY '<ПАРОЛЬ_ЗАДАЁТ_ВЛАДЕЛЕЦ>'
  REQUIRE SSL
  WITH MAX_USER_CONNECTIONS 3
       MAX_QUERIES_PER_HOUR 0;

-- Только SELECT, только на столбцы без ip.
GRANT SELECT (id, uuid, reason, banned_by_uuid, banned_by_name, removed_by_uuid, removed_by_name,
              removed_by_reason, removed_by_date, `time`, `until`, template, server_scope,
              server_origin, silent, ipban, ipban_wildcard, active)
  ON `<ИМЯ_БД_LITEBANS>`.`<ПРЕФИКС>bans`  TO 'twomc_ro'@'<IP_САЙТА>';
GRANT SELECT (id, uuid, reason, banned_by_uuid, banned_by_name, removed_by_uuid, removed_by_name,
              removed_by_reason, removed_by_date, `time`, `until`, template, server_scope,
              server_origin, silent, ipban, ipban_wildcard, active)
  ON `<ИМЯ_БД_LITEBANS>`.`<ПРЕФИКС>mutes` TO 'twomc_ro'@'<IP_САЙТА>';
-- warnings: тот же список плюс столбец warned
GRANT SELECT (id, uuid, reason, banned_by_uuid, banned_by_name, removed_by_uuid, removed_by_name,
              removed_by_reason, removed_by_date, `time`, `until`, template, server_scope,
              server_origin, silent, ipban, ipban_wildcard, active, warned)
  ON `<ИМЯ_БД_LITEBANS>`.`<ПРЕФИКС>warnings` TO 'twomc_ro'@'<IP_САЙТА>';
GRANT SELECT (id, uuid, reason, banned_by_uuid, banned_by_name, `time`, `until`, template,
              server_scope, server_origin, silent, ipban, ipban_wildcard, active)
  ON `<ИМЯ_БД_LITEBANS>`.`<ПРЕФИКС>kicks` TO 'twomc_ro'@'<IP_САЙТА>';
GRANT SELECT (id, uuid, name, date)
  ON `<ИМЯ_БД_LITEBANS>`.`<ПРЕФИКС>history` TO 'twomc_ro'@'<IP_САЙТА>';
GRANT SELECT (id, name, uuid, date)
  ON `<ИМЯ_БД_LITEBANS>`.`<ПРЕФИКС>servers` TO 'twomc_ro'@'<IP_САЙТА>';

-- Проверка: должны быть только перечисленные GRANT SELECT (...), и ни одного другого права.
SHOW GRANTS FOR 'twomc_ro'@'<IP_САЙТА>';
```

Заметки:

- Таблицу `<ПРЕФИКС>allow` сайт не читает: права на неё не выдавать.
- Если в реальной БД столбцы отличаются от документации (сверка в разделе 1), список в `GRANT` приведите к фактическим, без `ip`.
- Пользователь не получает `SHOW VIEW`, `PROCESS`, `FILE`, `SUPER`, `GRANT OPTION` и никаких прав на другие базы.
- Пароль: длинный случайный (не менее 32 символов), не используется нигде больше. Хранится только в хранилище секретов сайта.

## 3. Сетевой доступ: без публичного порта

Цель: порт MySQL доступен только с адреса сайта.

1. Привязка. Если сайт и БД на одной машине, слушать только `127.0.0.1` (`bind-address = 127.0.0.1`) и порт наружу не открывать вообще. Если на разных, `bind-address` — внутренний или конкретный интерфейс, не `0.0.0.0` без файрвола.
2. Файрвол/allowlist. На сервере БД и в панели хостера: разрешить входящий TCP `<ПОРТ_БД>` только с `<IP_САЙТА>`, остальным DROP. Порт по умолчанию 3306 не должен быть виден из интернета.
3. Пример для `ufw` (адаптируйте под свой файрвол):

```sh
ufw deny  <ПОРТ_БД>/tcp
ufw allow from <IP_САЙТА> to any port <ПОРТ_БД> proto tcp
```

4. Игровой сервер LiteBans подключается к той же БД своим пользователем; его правила не меняйте и не расширяйте.
5. Если адрес сайта нестатический или нужен закрытый канал, используйте VPN (WireGuard) либо SSH-туннель вместо открытия порта; тогда в `<IP_САЙТА>` подставляется адрес внутри VPN.
6. Проверка снаружи (с машины, не входящей в allowlist): подключение к `<ХОСТ_БД>:<ПОРТ_БД>` должно завершаться тайм-аутом или отказом.

## 4. TLS для MySQL

Задача: шифрование канала и проверка подлинности сервера клиентом (защита от подслушивания и подмены).

1. Серверу БД нужен сертификат, выпущенный CA, которому доверяет сайт, с именем, совпадающим с `<ХОСТ_БД>` (SAN). Допустим собственный CA; самоподписанный сертификат без проверки клиентом недопустим.
2. В конфигурации MySQL (раздел `[mysqld]`) указать пути серверных файлов и минимальную версию протокола:

```ini
[mysqld]
ssl_ca   = <КАТАЛОГ_TLS_СЕРВЕРА>/ca.pem
ssl_cert = <КАТАЛОГ_TLS_СЕРВЕРА>/server-cert.pem
ssl_key  = <КАТАЛОГ_TLS_СЕРВЕРА>/server-key.pem
tls_version = TLSv1.2,TLSv1.3
require_secure_transport = ON
```

Права на файл ключа: чтение только для пользователя службы БД. Закрытые ключи не копируются и не пересылаются.

3. Перезапустить MySQL по вашей процедуре обслуживания (окно простоя согласовать: LiteBans на игровом сервере переподключится сам, но проверьте).
4. Пользователь `twomc_ro` уже создан с `REQUIRE SSL` (раздел 2). Усиление по желанию: сертификат клиента.

```sql
ALTER USER 'twomc_ro'@'<IP_САЙТА>' REQUIRE X509;
-- или с проверкой издателя и субъекта
ALTER USER 'twomc_ro'@'<IP_САЙТА>'
  REQUIRE ISSUER '<ИЗДАТЕЛЬ_CA>' AND SUBJECT '<СУБЪЕКТ_КЛИЕНТСКОГО_СЕРТИФИКАТА>';
```

Для `X509` клиентский сертификат и ключ кладутся на сайт с правами 600; значения путей идут только в переменные окружения (раздел 5).

5. Клиент (сайт) обязан проверять сертификат сервера и имя хоста (`verify-full`), это включает `LITEBANS_DB_SSL=required` вместе с `LITEBANS_DB_SSL_CA_FILE`. В production без файла CA запуск отклоняется; режим `disabled` допустим только в разработке.
6. Проверка TLS с машины сайта (интерактивный пароль вводит владелец, в скриптах и истории оболочки пароль не оставлять):

```sh
mysql --host=<ХОСТ_БД> --port=<ПОРТ_БД> --user=twomc_ro --password \
  --ssl-mode=VERIFY_IDENTITY --ssl-ca=<ПУТЬ_К_CA_НА_САЙТЕ> \
  --execute="SHOW SESSION STATUS LIKE 'Ssl_version';"
```

Ожидается `TLSv1.2` или `TLSv1.3`. Тот же запрос без `--ssl-ca` или с неверным CA должен завершаться ошибкой проверки.

## 5. Переменные окружения сайта (только имена)

Значения вносит владелец в хранилище секретов production; в репозиторий, чат и отчёты они не попадают. Описание — раздел 2.3 дизайна.

| Переменная                                                            | Назначение                                      | Секрет              |
| --------------------------------------------------------------------- | ----------------------------------------------- | ------------------- |
| `LITEBANS_ENABLED`                                                    | включатель интеграции (по умолчанию выключено)  | нет                 |
| `LITEBANS_DB_DRIVER`                                                  | значение `mysql`                                | нет                 |
| `LITEBANS_DB_HOST`, `LITEBANS_DB_PORT`, `LITEBANS_DB_NAME`            | адрес и имя БД                                  | хост не публиковать |
| `LITEBANS_DB_USER`, `LITEBANS_DB_PASSWORD`                            | учётка только для чтения                        | пароль: да          |
| `LITEBANS_DB_SSL`                                                     | `required` (проверка сертификата и имени хоста) | нет                 |
| `LITEBANS_DB_SSL_CA_FILE`                                             | путь к файлу CA на сайте                        | нет                 |
| `LITEBANS_TABLE_PREFIX`                                               | префикс таблиц (по умолчанию `litebans_`)       | нет                 |
| `LITEBANS_POLL_INTERVAL_MS`, `LITEBANS_BATCH_SIZE`                    | частота и размер пачки опроса                   | нет                 |
| `LITEBANS_ACTIVE_CHECK_INTERVAL_S`, `LITEBANS_RECONCILE_INTERVAL_MIN` | сверка активных и полная сверка                 | нет                 |
| `LITEBANS_DB_CONNECT_TIMEOUT_MS`, `LITEBANS_DB_QUERY_TIMEOUT_MS`      | тайм-ауты                                       | нет                 |

Если понадобятся имена переменных для клиентского сертификата (вариант `REQUIRE X509`), они будут добавлены в дизайн отдельным изменением до реализации.

## 6. Проверка доступа запросом только для чтения

Выполняется с машины сайта (или из процесса сайта после реализации), пользователем `twomc_ro`, через TLS (раздел 4, п. 6). Нужны только агрегаты, без реальных ников и IP в выводе.

```sql
-- должно работать
SELECT COUNT(*), MAX(id) FROM `<ИМЯ_БД_LITEBANS>`.`<ПРЕФИКС>bans`;
SELECT id, `time`, `until`, active FROM `<ИМЯ_БД_LITEBANS>`.`<ПРЕФИКС>bans` ORDER BY id DESC LIMIT 1;

-- должно завершиться отказом (ERROR 1143/1142: SELECT command denied)
SELECT ip FROM `<ИМЯ_БД_LITEBANS>`.`<ПРЕФИКС>bans` LIMIT 1;
SELECT * FROM `<ИМЯ_БД_LITEBANS>`.`<ПРЕФИКС>bans` LIMIT 1;
UPDATE `<ИМЯ_БД_LITEBANS>`.`<ПРЕФИКС>bans` SET reason = reason WHERE id = 0;
DELETE FROM `<ИМЯ_БД_LITEBANS>`.`<ПРЕФИКС>bans` WHERE id = 0;
```

Критерий успеха: первые два запроса выполняются, остальные четыре отклонены БД. Запросы `UPDATE` и `DELETE` с `id = 0` не затрагивают ни одной строки, даже если права выданы ошибочно; DDL (`CREATE`, `ALTER`, `DROP`) для проверки не выполняйте, достаточно `SHOW GRANTS` из раздела 2. `SELECT *` отклоняется, потому что нет права на `ip`: это ожидаемое и нужное поведение, адаптер сайта всегда перечисляет столбцы явно.

Затем сообщите агенту только факт «проверка пройдена» (или текст ошибки без хостов и паролей).

## 7. Сопровождение и отзыв

- Ротация пароля: `ALTER USER 'twomc_ro'@'<IP_САЙТА>' IDENTIFIED BY '<НОВЫЙ_ПАРОЛЬ_ЗАДАЁТ_ВЛАДЕЛЕЦ>';`, затем обновить `LITEBANS_DB_PASSWORD` и перезапустить API. Рекомендуемая периодичность: раз в 6 месяцев или при подозрении на утечку.
- Срочный отзыв: `DROP USER 'twomc_ro'@'<IP_САЙТА>';` и/или закрыть правило файрвола; сайт перейдёт в статус «источник недоступен» и не покажет подложных данных.
- Смена IP сайта: создать пользователя для нового адреса по разделу 2, обновить правило файрвола, затем удалить старого пользователя и старое правило.
- Обновление LiteBans: после обновления плагина повторить сверку схемы (раздел 1) и проверить, что список столбцов в `GRANT` по-прежнему соответствует; новые столбцы без явного решения не выдавать.
