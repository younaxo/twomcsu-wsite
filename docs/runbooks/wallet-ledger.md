# Runbook: журнал кошелька рубинов (0.15, ADR-0191)

Миграции применяет и флаги включает только владелец. Агенты миграции на production и общей БД не применяют. Флаг `WALLET_LEDGER_ENABLED` по умолчанию выключен.

## 1. Миграции (порядок и ревью)

1. `20261124100000_wallet_ledger` - таблица `wallet_ledger_entries`, enum `WalletEntryKind`, триггер запрета UPDATE и DELETE.
2. `20261124110000_wallet_ledger_hardening` - значение `OPENING_BALANCE`, триггер запрета TRUNCATE.

Обе expand-only: без DROP, без изменения существующих данных. Применять `prisma migrate deploy` после резервной копии (`docs/runbooks/backup-restore.md`).

## 2. Права роли приложения на БД (рекомендация, ADR-0191)

Триггеры защищают журнал от обычных запросов, но владелец таблицы может их отключить. Рекомендуется отдельная роль PostgreSQL для приложения: на `wallet_ledger_entries` только `SELECT` и `INSERT` (без `UPDATE`, `DELETE`, `TRUNCATE`, `TRIGGER`), владельцем таблицы остаётся миграционная роль. Миграции выполняются миграционной ролью, не ролью приложения.

## 3. Сведение существующих балансов до включения флага

Если в `wallets` уже есть строки RUBY с ненулевым балансом, а журнала нет, любая запись кошелька отклоняется с `wallet_inconsistent` (сумма журнала не равна балансу). Это намеренно. Порядок:

1. Остановить изменения `wallets.balance` в обход журнала (их нет в коде; ручные правки SQL запрещены).
2. Резервная копия БД.
3. Отчёт (ничего не пишет): `pnpm --filter api exec ts-node prisma/scripts/wallet-opening-balance.ts` (переменные окружения БД - как у остальных служебных скриптов). Скрипт только для владельца.
4. Записать: тот же скрипт с `--apply`. Для каждого расходящегося кошелька создаётся проводка `OPENING_BALANCE` на разницу (баланс минус сумма журнала), ключ `opening-balance:<userId>`: повторный запуск ничего не меняет. Баланс при этом не меняется.
5. Случай «журнал больше баланса» скрипт не правит: строка `РУЧНОЙ РАЗБОР`, нужен разбор владельцем.
6. Повторить отчёт: должно быть `Расходящихся кошельков RUBY: 0`.
7. Только после этого включить `WALLET_LEDGER_ENABLED=true` и перезапустить api. При старте с включённым флагом сервис пишет в лог ошибку, если расхождения остались (запуск не останавливается, записи по этим кошелькам отклоняются).

## 4. Лимиты корректировок

- `WALLET_ADJUST_MAX` - потолок одной корректировки (по умолчанию 100000).
- `WALLET_ADJUST_DAILY_MAX` - сумма модулей корректировок одного администратора за скользящие 24 часа (по умолчанию 500000), ответ 400 `wallet_adjust_daily_limit`.
- Собственный кошелёк корректировать нельзя: 403 `wallet_self_adjust_forbidden`.

## 5. Зачисление покупки и возврат

Исполнитель `wallet` блокирует заказ (`FOR UPDATE`) раньше кошелька, как и возврат; не зачисляет, если заказ не оплачен, в `REFUND_PENDING`, `REFUNDED` или есть активный возврат (задание `failed`: `order_not_paid`, `order_refund_in_progress`). Цена позиции должна быть 1 рубль за штуку: иначе задание `NEEDS_ATTENTION` с причиной `currency_price_mismatch` (ручной разбор, рубины не зачислены).
