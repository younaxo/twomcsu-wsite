# ADR-G002 — коды, сессия браузера и билеты (розыгрыш, фаза 2)

Статус: принято (допущения помечены «Допущение»). Дата: 2026-11-19. Продолжает ADR-G001. Требования: `MASTER-PROMPT-17.1.md`. Отклонение от рекомендаций chief: п. 6.2 (POST вместо GET для progress), обоснование там же.

Базовый URL: `https://giveaway.twomc.su`. Все пути `/api/giveaway/v1/...`. Ошибки: `{"error":"<код>"}` без деталей. Время: UTC (ISO 8601) плюс строки «по МСК».

## 1. Cookie-сессия браузера

1.1. Анонимная, без связи с аккаунтами сайта. Токен: 32 байта CSPRNG (256 бит), в cookie base64url. В БД хранится только `sessionHash = HMAC-SHA256(K_session, токен)` (hex).
1.2. Cookie `gw_session`: `HttpOnly; Secure; SameSite=Lax; Path=/api/giveaway; Max-Age=86400`. Создаётся при первом `POST /codes`, если cookie нет или формат неверный. Токены сессий не логируются.
1.3. Ключи `K_session` и `K_code` выводятся HKDF-SHA256 из `GIVEAWAY_MASTER_SECRET`, `salt = "giveaway-static"`, `info = "twomc-giveaway" 0x00 <метка> 0x00 "v1"`, метки `session` и `code`. Они отличаются от ключей серверов (у тех соль = id сервера, а info содержит u32be версии).
1.4. Сессия живёт ~1 сутки, продления нет. Сайт и API на одном домене (`giveaway.twomc.su`); страница обязана вызывать API с `credentials: "same-origin"`.

## 2. Коды

2.1. Алфавит Crockford без I, L, O, U: `0123456789ABCDEFGHJKMNPQRSTVWXYZ` (32 символа). Длина 16, 80 бит. Генерация: `randomBytes`, из каждого байта берутся младшие 5 бит (256 делится на 32, смещения нет).
2.2. Показ: `XXXX-XXXX-XXXX-XXXX`. Нормализация при вводе: верхний регистр, удалить `-` и пробелы, `O -> 0`, `I, L -> 1` (правила Crockford); затем строго `^[0-9A-HJKMNP-TV-Z]{16}$`. Ввод с `U` и иными символами невалиден.
2.3. Хранение: `codeHash = HMAC-SHA256(K_code, нормализованный код)` (hex, UNIQUE). Сам код в БД и логах не хранится и возвращается один раз в ответе на `POST /codes`.
2.4. TTL 10 минут (`expiresAt`). Один активный код на сессию: новый `POST /codes` в той же транзакции аннулирует (`revokedAt`) все непогашенные прежние коды сессии. Выдача сериализуется Redis-замком на сессию (5 с). Фаза 2b (M2): инвариант держит БД - частичный уникальный индекс `giveaway_codes_one_active_per_session` на `sessionHash` WHERE `redeemedAt IS NULL AND revokedAt IS NULL` (только в SQL миграции `20261119150000_giveaway_phase2b`, Prisma его не выражает); нарушение (`P2002`) сервис трактует как гонку выдачи и отвечает `429 rate_limited` с `Retry-After: 1`. L5: токен сессии ротируется при КАЖДОЙ выдаче (cookie перезаписывается новым значением, прежний хэш теряет коды); лимиты и замок привязаны к прежнему хэшу, чтобы ротация не обнуляла счётчик по сессии.
2.5. Лимиты Redis (в ключах хэш адреса, не сам IP): выдача по адресу (IPv4 полностью, IPv6 по /64 через `rateLimitKey`) 30 в час; по точному адресу 15 в час; по сессии 10 за 10 минут. Превышение: `429 {"error":"rate_limited"}` и `Retry-After`. L3: проверки идут по очереди (адрес/подсеть, точный адрес, сессия); отказ одной не расходует остальные счётчики.
2.6. Допущение: Turnstile. Флаг `GIVEAWAY_CAPTCHA_ENABLED` (по умолчанию false). `CaptchaService` принадлежит `AuthModule` и в режиме `GIVEAWAY_ONLY` недоступен. При включённом флаге и недоступном сервисе `POST /codes` отвечает `503 {"error":"captcha_unavailable"}` (fail closed); при доступном проверяется токен из тела `{"captchaToken":"..."}`. Ограничение: в мини-выкладке капча фактически не работает; защита лимитами 2.5.

## 3. POST /codes (публичный)

Запрос: пустое тело или `{"captchaToken"?: string}`. Ответ `200`, `Cache-Control: no-store`:
```json
{"code":"ABCD-EFGH-JKMN-PQRS","expiresAt":"2026-11-22T10:10:00.000Z","ttlSeconds":600}
```
Ошибки: `429 rate_limited`, `503 unavailable | captcha_unavailable`. Кнопка «Новый код» делает тот же вызов.

## 4. GET /codes/status (по cookie)

Только для владельца сессии (cookie `gw_session`); без cookie или с неизвестной сессией: `{"status":"none"}`. Ответы по последнему коду сессии:
- `{"status":"pending","expiresAt":"..."}`: код выдан, не погашен, не просрочен. Если игрок вводил код при нехватке времени, добавляется `lastAttempt`: `{"result":"not_enough","minutes":N,"remainingMinutes":M,"thresholdMinutes":T}` (без ника и UUID; хранится в колонках `lastAttemptAt/Minutes/Threshold` кода, миграция phase2b);
- `{"status":"redeemed","ticket":"K417","playerName":"Steve"}`: к коду привязан билет (страница запускает анимацию букв и цифр, при `prefers-reduced-motion` без анимации);
- `{"status":"expired"}`: просрочен или аннулирован.
Опрос раз в 2–3 с; лимит 60 запросов в минуту на сессию (`429`). `Cache-Control: no-store`.

## 5. GET /public (публичный, без ПД)

```json
{"status":"running","thresholdMinutes":3000,"thresholdHours":50,
 "startAtUtc":"...","cutoffAtUtc":"...","startAtMsk":"22.11.2026 00:00:00 по МСК","cutoffAtMsk":"30.12.2026 23:59:59 по МСК","ticketsIssued":123}
```
`status`: `before` (до старта) | `running` (идёт) | `finished` (завершён). Лимит 120 запросов в минуту на адрес. `Cache-Control: no-store`.

## 6. Подписанные вызовы плагина

Общее: заголовки, ключ и подпись как в ADR-G001 (тот же guard). Подписываемый `path` всегда публичный: `/api/giveaway/v1/redeem` или `/api/giveaway/v1/progress` (даже если прокси срезает `/api`). Сервер определяется по ключу и должен быть в `allowedServers` («Анархия Новой Эры»), иначе `403`.

### 6.1. POST /redeem: команда `/giveaway <код>` (алиас `/ticket`)

Тело: `{"code":"ABCD-EFGH-JKMN-PQRS","playerUuid":"<uuid>","playerName":"Steve"}` (поля строго, лишние: `422 invalid_envelope`).
Порядок обработки (строго):
1. Лимиты по очереди: по UUID (10 в минуту), затем по серверу; отказ по UUID не расходует лимит сервера (L3); превышение `429`. L4: лимит на сервер поднят с 60 до 600 в минуту: основная защита от перебора кода - лимит по UUID, а при 60 один спамящий игрок или несколько могли заблокировать redeem всем остальным на сервере; 600 лишь страховка от потока (сверх лимита guard подписанных вызовов).
2. Если у UUID уже есть билет: `{"status":"issued","ticket":"K417","repeat":true}`; если переданный код при этом валиден и не погашен, он привязывается к этому билету (страница покажет билет); невалидный код на ответ не влияет.
3. Окно: до `startAt` `{"status":"not_started"}`, после `cutoffAt` `{"status":"closed"}`.
4. Если минут меньше порога: `{"status":"not_enough","minutes":N,"remainingMinutes":M,"thresholdMinutes":T}`; ответ не зависит от кода (не раскрывает его валидность). Код НЕ гасится; если код валиден и активен, на нём сохраняется последняя попытка (`lastAttempt` в п. 4). Заметка про индекс по `codeHash`: этот поиск идёт по UNIQUE-хэшу HMAC с секретным ключом, ответ плагину одинаков для любого кода, а время ответа определяется одним индексным `UPDATE` независимо от результата - временного оракула валидности кода нет.
5. Проверка кода: неверный формат, неизвестный, просроченный, аннулированный, погашенный: единый ответ `{"status":"invalid_code"}`, различий нет. HMAC и поиск в БД выполняются всегда (для неверного формата над фиксированной строкой), сравнение хэшей за постоянное время.
6. Одна транзакция: условный `UPDATE ... WHERE codeHash=? AND redeemedAt IS NULL AND revokedAt IS NULL AND expiresAt>now` (0 строк: `invalid_code`; это одноразовость при конкуренции), создание билета, привязка `ticketId`, ник и UUID. Ответ `{"status":"issued","ticket":"K417"}`.
Все перечисленные статусы приходят с HTTP 200; `401/403/422/429/503` ошибки. Тексты игроку формирует плагин.

### 6.2. POST /progress: пакетный прогресс

Отклонение от рекомендации chief (GET с query): подпись ADR-G001 не покрывает query и запрещает его (`checkFormat`), а пакет UUID естественно передаётся подписанным телом. Поэтому `POST`. Тело: `{"uuids":["<uuid>", ... до 100]}`. Ответ:
```json
{"thresholdMinutes":3000,"startAt":"2026-11-21T21:00:00.000Z","cutoffAt":"2026-12-30T20:59:59.000Z","startText":"22.11 00:00 по МСК","cutoffText":"30.12 23:59 по МСК","players":[{"playerUuid":"...","minutes":120,"thresholdMinutes":3000,"remainingMinutes":2880,"percent":4,"qualified":false,"ticket":null}]}
```
`percent` целая часть, максимум 100. `startAt`/`cutoffAt` (UTC ISO) и `startText`/`cutoffText` (МСК, без года и секунд) берутся из настроек розыгрыша (как на сайте); поля добавлены 2b, старые не изменены. Данные для плейсхолдеров PlaceholderAPI и уведомления о пороге (плагин опрашивает по своему расписанию). Ответ `POST /events` не изменён (совместимость с плагином фазы 1).

### 6.3. Учёт только с разрешённого сервера

Приём событий уже отклоняет не разрешённые серверы (`403`, ADR-G001 п. 7). Фаза 2 дополнительно считает минуты только по `serverSlug IN allowedServers` (раньше счёт шёл по всем сохранённым корзинам): исправление отмечено.

## 7. Билет

7.1. Формат: буква `ABCDEFGHJKLMNPQRSTUVWXYZ` (24, без I и O) плюс три цифры `000`-`999` (пример `K417`); `randomInt` (CSPRNG, без смещения). Пространство 24 000 значений.
7.2. UNIQUE на `ticket` и на `playerUuid`. При коллизии `ticket` повтор в новой транзакции, до 8 попыток, затем `503 unavailable`. Коллизия по `playerUuid` (гонка) возвращает уже существующий билет.
7.3. Билет определяется сервером до анимации и не меняется. Розыгрыш только среди билетов. Выдача только в окне `[startAt, cutoffAt]`.
7.4. Допущение: 24 000 значений достаточно для ожидаемого числа участников; при росте числа билетов повторы возрастают (обрабатываются по 7.2), владелец должен знать предел. Расширение пространства (две буквы) отдельное решение.

## 8. Ограничения и допущения

- Код не привязан к IP: кто знает код, тот может ввести его в игре; защита TTL 10 минут, одноразовость, показ только владельцу сессии.
- L2, принятый риск: игрок с билетом может привязать к своему билету любой валидный непогашенный код (п. 6.1/2); последствие только показ его билета на странице владельца кода (владелец сам передал код); допустимо, поведение сохранено.
- Выдача билета возможна только при `GIVEAWAY_ENABLED=true` и корректном секрете, иначе `503`.
- Логи: только коды причин; коды, токены сессий, IP, подписи не логируются.
- Миграция `<ts>_giveaway_phase2` (expand-only, таблицы `giveaway_tickets`, `giveaway_codes`) создана, не применена; применение по правилу Q28 на одноразовой БД. Отдельной таблицы сессий нет: хэш сессии хранится в `giveaway_codes`.
- L7: очистка просроченных кодов ОТЛОЖЕНА: в модуле нет планировщика, добавлять зависимость `@nestjs/schedule` вне scope; строки малы (один на сессию, индекс по `expiresAt` есть), рост ограничен лимитами выдачи. Вернуться в фазе 3 (задача по расписанию только при `GIVEAWAY_ENABLED`).
- Миграция `20261119150000_giveaway_phase2b` (expand-only: три NULL-колонки и частичный уникальный индекс) создана, не применена; на таблице с уже существующими дубликатами активных кодов индекс не создастся (сначала аннулировать лишние - отдельное решение владельца). e2e `apps/api/test/giveaway-concurrency.e2e-spec.ts` (гонки по коду, UUID, коллизия билета, индекс) не запускался: проверка на VDS после выкладки.
